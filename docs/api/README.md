Здесь живёт **`openapi.yaml`** — единственный источник истины по HTTP-контракту Bad CRM.

> **Файл появился** в [STORY-003-05](../../epics/epic-003-server-skeleton-and-api-contract/stories/story-003-05-openapi-contract-and-codegen.md):
> [`openapi.yaml`](openapi.yaml) описывает первую продуктовую операцию `GET /api/v1/meta`, схему
> ошибки `Problem` и `enum` кодов ошибок. Служебные `/health` и `/ready` в спеку **не входят** —
> они в allow-list контрактного теста. Правила ниже — то, по чему спека живёт дальше.

> раньше маршрута; тройка маркеров

> переносит инвариант №2 из реестра маршрутов в сам договор; и
> [решение по `Idempotency-Key`](#idempotency-key-на-auth-маршрутах) — на каких небезопасных

## Зачем contract-first

Спека **правится руками в pull request и является договором**. Она не генерируется из кода.

Отвергнутая альтернатива — генерировать OpenAPI из аннотаций или Zod-схем (`zod-to-openapi` и
подобное). Причина отказа: сгенерированная спека перестаёт быть договором и начинает описывать
случайное текущее поведение. Ревьюить изменения API становится нечем — в диффе видно, что
поменялся код, но не видно, что поменялся контракт. Ломающее изменение проходит ревью незамеченным
и доезжает до клиента как 400 в проде.

При contract-first порядок обратный: сначала обсуждается и мержится изменение спеки, потом под него
пишется код. Это медленнее на один шаг и дешевле на все последующие.

Что даёт спека как источник истины:

- **Типы клиента генерируются из неё** — несуществующий путь, лишний query-параметр или неверная
  форма тела становятся ошибкой компиляции, а не 400 в рантайме.
- **Изменение API видно в ревью как изменение спеки** — с точной диагностикой «это ломающее».
- **Двусторонний контрактный тест** ловит расхождение раньше, чем оно уедет к клиенту.
- **Документация не устаревает**, потому что она и есть контракт.

## Поток

```
docs/api/openapi.yaml   ←── source of truth, правится руками в PR
        │
        ├── pnpm api:gen ──► openapi-typescript
        │                    → packages/client/src/shared/api/schemas/api-schema.d.ts
        │                    (файл коммитится в git; в CI проверяется `git diff --exit-code`)
        │
        ├── контрактный тест (packages/server) ──► сверяет реальный роутер со спекой
        │
        └── клиент: openapi-fetch + openapi-react-query поверх сгенерированных типов
```

### Генерация типов

```bash
pnpm api:gen     # openapi-typescript docs/api/openapi.yaml → api-schema.d.ts
pnpm api:lint    # валидация спеки (Spectral)
```

Сгенерированный `api-schema.d.ts` **коммитится**. В CI после `pnpm api:gen` выполняется
`git diff --exit-code`: забытая регенерация после правки спеки блокирует pull request. Причина, по
которой файл лежит в git, а не генерируется на лету: он должен быть виден в ревью — изменение
контракта обязано быть заметным, а не спрятанным в шаге сборки.

Сгенерированные типы живут в `packages/client`, **не** в `packages/shared`: это артефакт сборки
клиента. Если бы они лежали в `shared`, от них зависел бы и сервер, и спека перестала бы быть
независимым контрактом.

### Контрактный тест

Живёт в `packages/server/test/contract/openapi.test.ts` и проверяет **обе стороны**:

1. Нет ни одного зарегистрированного Express-роута, которого нет в спеке — кроме явного allow-list:
   `/health`, `/ready`, `/metrics`, `/socket.io`.
2. Нет ни одной операции в спеке, для которой нет роута.

Реализация берёт список роутов из Express, нормализуя `:param` → `{param}`, и множество
`paths × methods` из `openapi.yaml`. Тест обязателен: без него спека и код расходятся за недели.

Отдельно `packages/server/test/contract/error-codes.test.ts` сверяет **каталог кодов ошибок**
`packages/shared/src/errors/error-code.enums.ts` с `enum` `ErrorCode` в спеке, а
`validation-issue.enums.ts` — с `ValidationIssueCode`. Оба множества обязаны совпадать точно.

**Что делать, когда тест упал.** Сообщение называет направление расхождения:

- *«route not described in docs/api/openapi.yaml: …»* — маршрут есть, операции нет. Либо опиши
  операцию в спеке и прогони `pnpm api:gen`, либо убери маршрут. Служебный endpoint — добавь его в
  `test/contract/service-route-allow-list.constant.ts` с обоснованием (это ревьюируемая строка).
- *«operation not implemented: …»* — операция описана, маршрута нет. Добавь запись в
  `presentation/http/route-registry.factory.ts` (с permission или `public` + `publicReason`) —
  либо, если операция сознательно опубликована раньше реализации, пометь её `x-implemented-by`
  (следующий раздел).
- *«ErrorCode matches packages/shared exactly»* — каталог и `enum` разошлись: правь оба, код
  добавляется сначала в каталог, потом в спеку.

### Операция опубликована раньше реализации

Contract-first означает, что спека мержится **до** кода: сначала обсуждается договор, потом под него
пишется реализация. Ровно это на один коммит ставит второе направление контрактного теста —
«нет операции без роута» — в конфликт с тем, как проект устроен.

Выбор был между «ослабить утверждение для всего» и «пометить те несколько операций, для которых оно
пока не выполняется». Выбрано второе:

```yaml
  /auth/login:
    post:
      operationId: login
      x-implemented-by: STORY-006-02   # опубликовано, маршрут появится в этой истории
```

Маркер — не комментарий. Его стережёт `packages/server/test/contract/planned-operations.test.ts`:

1. значение обязано быть идентификатором истории (`STORY-\d{3}-\d{2}`), и **файл истории обязан
   существовать** в `epics/*/stories/` — «потом» маркером не запишешь, у операции всегда есть
   владелец;
2. помеченная операция обязана быть **не** реализована: как только роутер начинает её отвечать,
   тест падает с «implemented while still marked» — то есть маркер удаляется тем же коммитом,
   который добавляет маршрут, а не когда-нибудь;
3. операция без маршрута и без маркера падает как «published, unimplemented and unexplained».

Что маркер **не** делает: не ограничивает исключение сроком и не ограничивает их число. Дата в тесте
— это дата, которую двигают; ссылка на живую историю проверяется по борду.

Первое направление теста (роут → спека) маркер не трогает вовсе: недокументированный маршрут
по-прежнему падает.

### Кто может звать операцию

Инвариант №2 (`CLAUDE.md`) требует, чтобы каждый endpoint объявлял permission или причину быть
публичным. Реестр маршрутов это обеспечивает — но срабатывает он в момент написания **кода**, то
есть уже после того, как API спроектировано и договор смержен. К этому моменту «кому это можно»
решил тот, кто придумал путь, и никто его об этом не спросил.

Поэтому на вопрос отвечает и сам документ. У каждой операции ровно один из трёх маркеров:

| Маркер | Смысл | Что проверяется |
|---|---|---|
| `x-permission` | право из закрытого каталога `packages/shared/src/permissions/permissions.catalog.ts` | ключ обязан быть в каталоге — опечатка это упавший тест, а не право, которого ни у кого нет |
| `x-public-reason` | достижима без учётных данных, и почему | обязана стоять вместе с `security: []`, и наоборот; текст не короче осмысленного предложения |
| `x-self-service-reason` | аутентифицирована, но capability неприменима: субъект и объект — один и тот же человек | текст обязателен; форма умышленно узкая, см. ниже |

Проверяет `packages/server/test/contract/route-authorization.test.ts`. Он же следит, что
document-level `security` остаётся `bearerAuth` — «публичный по умолчанию» не должен появиться
незаметно.

**Про третью форму.** Она не выдумана здесь: `permission-model.md` §3.20 уже описывает ровно эту
логику для операций человека над собственной ключевой парой — «проверяется владением паролем, а не
полномочием; отобрать право не помешает, выдать не поможет». EPIC-006 — второе такое семейство:
завершить свою сессию, посмотреть свой список сессий, сменить свой пароль. Право `user:read_sessions`
из каталога — это чтение **чужих** сессий администратором, другая операция.

Форма при этом самая опасная из трёх: это очевидное место, куда можно спрятать endpoint, которому
полагалась permission. Отсюда обязательный письменный текст причины и отдельный пункт в работе
агента `permission-matrix-auditor`.

### `Idempotency-Key` на auth-маршрутах

Клиентская обёртка (`shared/api/idempotency-middleware.util.ts`) ставит заголовок на **любой**
небезопасный запрос — ни один call site не может его забыть. Значит, вопрос не «слать ли», а
«какая операция его хранит и воспроизводит». Решение по группе `auth`:

| Операция | `Idempotency-Key` | Почему |
|---|---|---|
| `POST /auth/register` | **обязателен** | повтор после обрыва иначе создаёт вторую организацию (acceptance STORY-006-01) |
| `POST /auth/forgot-password` | **обязателен** | повтор иначе отправляет второе письмо |
| `POST /auth/reset-password` | **обязателен** | токен одноразовый: повтор потерянного ответа иначе получает 400 на уже потраченном токене |
| `POST /auth/change-password` | **обязателен** | отправляет письмо; и повтор иначе падает с `invalid_credentials`, потому что «текущий» пароль уже сменён |
| `POST /auth/login` | **игнорируется** | сохранённый ответ — это сохранённые **учётные данные**: воспроизведение вернуло бы access-токен и refresh-cookie, которые с тех пор ротированы или отозваны. Плюс повтор одного ключа проскочил бы мимо счётчика неудачных попыток, на котором держится lockout |
| `POST /auth/refresh` | **игнорируется** | воспроизведение сохранённого ответа — это ровно то, что ловит reuse detection; хранить этот ответ значит хранить учётные данные |
| `POST /auth/logout`, `DELETE /auth/sessions/{id}`, `POST /auth/sessions/revoke-others` | **игнорируется** | идемпотентны по построению: повтор отдаёт тот же 204 / `revokedCount: 0`, хранить нечего |

Операция «принимает» ключ ровно тогда, когда объявляет параметр `IdempotencyKey` — по спеке это
видно без чтения кода.

Отдельная деталь для реализации: таблица `idempotency_key` по `stack.md` ключуется кортежем
`(organization_id, key, endpoint, request_hash)`, а `register`, `forgot-password` и
`reset-password` выполняются **до** того, как организация известна (в случае регистрации — она и
создаётся). Эти записи живут в pre-tenant области; чем именно (nullable `organization_id` или
отдельная таблица) — решает история, которая идемпотентность реализует.

### Ничего чувствительного в URL

В этом договоре нет ни одного параметра пути или query, который мог бы нести секрет, и это
проверяется: `route-authorization.test.ts` падает на параметре с именем, похожим на
`token`/`password`/`secret`/`key`. Токен сброса пароля — **поле тела** `POST /auth/reset-password`.

Причина не в эстетике. Query-строка попадает в access-log каждого прокси перед инсталляцией,
уезжает в `Referer` при переходе на другой origin и копируется вместе со ссылкой в тикет
поддержки — а логи и тикеты живут дольше, чем часовой TTL токена. Это то же соображение, по
которому в `Problem` нет поля `instance` (см. комментарий в схеме) и по которому HTTP-логгер пишет
**шаблон** маршрута, а не URL (`CLAUDE.md` → «Чувствительность данных»).

Ссылка в письме ведёт на клиентский маршрут `/reset-password/$token`
(`../architecture/ux-architecture.md`) — путь, не query; браузер превращает его в тело запроса, и
API токен в URL не видит никогда.

### Три вопроса, которые контракт поставил, и чем они закончились

Раздел сохранён как запись решений: все три были заведены как открытые и закрыты в том же эпике,
после разбора судьёй. Оставлен, чтобы следующий читатель видел не только исход, но и почему исход
именно такой.

1. **Адрес сессии: `ipHash` **и** `ipMasked`, оба обязательны.** STORY-006-04 требует показывать IP,
   а модель хранила только хеш — расхешировать его нельзя, значит одно из двух должно было
   измениться. Отказ от показа отвергнут: экран активных сессий существует ради распознавания «это
   не я», а устройство и время такого сигнала не дают — сменившийся город виден только по адресу.
   Решение: **маскировать на входе** (IPv4 → /24, IPv6 → /48) и хранить уже маскированное; полного
   адреса нет нигде, что по `CLAUDE.md` → «Персональные данные» строже прежнего замысла, а не
   слабее. `ipHash` остался для сопоставления сессий между собой. Сделано до релиза намеренно:
   колонка `NOT NULL` и поле обязательное; после первой поставки это было бы навсегда nullable.
2. **Форма записи «действие над собой» — заведена здесь, а не в EPIC-011.** Реестр знал две формы:
   `permission` из каталога и `public` + `publicReason`. Ни одна не подходит операции над
   собственной сессией: нужного ключа в каталоге нет, а `public: true` — прямая ложь, снимающая
   аутентификацию с маршрута, который её требует, и она прошла бы все тесты. EPIC-011 наполняет
   **каталог прав**; форма записи маршрута — не его предмет, и отложить её было нельзя: первый же
   контроллер эпика упёрся бы в выбор между «соврать в реестре» и «изобрести право по месту».
   `SelfServiceRoute` требует письменного обоснования и **обязательного** указания, где проверяется
   владение (в отличие от опционального `aclCheckedIn`) — именно потому, что это очевидное место,
   куда можно спрятать endpoint. Спека и реестр сверяются по форме в обе стороны.
3. **`mail_not_configured` (503) и `feature_disabled` (501) — два кода.** Различие не в тексте, а в
   семантике HTTP: 501 — «сервер такого не умеет», ретрай бессмыслен; 503 — временно, ретрай
   осмыслен. Оператору они говорят разное: «подсистему выключили» против «развёртывание не
   закончено, чинится конфигом». SMTP убран из перечня при `feature_disabled` — до этого каталог
   утверждал в одном файле обе взаимоисключающие вещи. Следствие, которое важнее самого кода:
   **решение об отсутствии SMTP принимается до резолва адреса**, иначе 503 на
   `POST /auth/forgot-password` отличает существующий адрес от несуществующего и ломает
   постоянство ответа, ради которого вся операция и устроена.

## Правила изменения контракта

### Что можно внутри `/api/v1`

Только **совместимые** изменения:

- новый endpoint;
- новое **опциональное** поле в теле ответа или запроса;
- новое опциональное значение query-параметра;
- расширение описаний, примеров, тегов.

### Что считается ломающим изменением

- удаление или переименование endpoint'а, поля, параметра;
- превращение опционального поля в обязательное;
- сужение типа или набора допустимых значений;
- изменение семантики поля при том же имени (самое коварное — компилятор молчит);
- изменение кода ошибки или HTTP-статуса для существующей ситуации;
- изменение формы пагинации у существующего списка.

Ломающее изменение делается только новым префиксом `/api/v2` с параллельной поддержкой `v1` не
менее одного минорного релиза; о снятии `v1` объявляется в [`../../CHANGELOG.md`](../../CHANGELOG.md).
Отдельно от версии API в ответах живёт `X-App-Version` — клиент по несовпадению предлагает
перезагрузить SPA.

### Обязательное для каждой новой операции

- [ ] Путь под `/api/v1`, имя ресурса — из [`../product/glossary.md`](../product/glossary.md).
- [ ] В спеке — ровно один маркер авторизации: `x-permission` (ключ каталога), `x-public-reason`
      (вместе с `security: []`) или `x-self-service-reason`
      ([раздел выше](#кто-может-звать-операцию)).
- [ ] Если маршрута ещё нет — `x-implemented-by: STORY-XXX-YY`, и маркер снимается тем же коммитом,
      который добавляет маршрут ([раздел выше](#операция-опубликована-раньше-реализации)).
- [ ] Запись в реестре маршрутов `packages/server/src/presentation/http/route-registry.factory.ts`
      с **permission из каталога** `packages/shared/src/permissions/permissions.catalog.ts` — либо
      `public: true` с непустым `publicReason`. Маршруты монтируются только из реестра, поэтому
      маршрута без объявления не существует; проверка самой permission живёт **в use-case**, а не
      только в middleware (инвариант №2, см. [`../../CLAUDE.md`](../../CLAUDE.md) и
      [`../security/permission-model.md`](../security/permission-model.md)).
- [ ] Все ответы об ошибках — `application/problem+json` (RFC 9457) со **стабильным `code`** из общего
      каталога; `title`/`detail` пользователю не показываются и могут меняться.
- [ ] Отсутствие доступа к сущности другой организации — **404**, а не 403. 403 только внутри своей
      организации. Иначе API становится оракулом существования чужих сущностей.
- [ ] Схема пагинации выбрана по типу данных: cursor для лент (activity, комментарии, чат,
      уведомления, аудит), offset для таблиц (задачи, проекты, сотрудники, документы, файлы,
      инвойсы), cursor + fractional indexing для канбан-колонок.
- [ ] Небезопасные методы, которые создают сущности, шлют почту или тратят деньги и токены,
      принимают `Idempotency-Key`. Операция, которая выдаёт учётные данные, — **не** принимает:
      сохранённый ответ там сам является учётными данными
      ([раздел выше](#idempotency-key-на-auth-маршрутах)).
- [ ] Ничего чувствительного в пути и query — секрет идёт телом
      ([раздел выше](#ничего-чувствительного-в-url)).
- [ ] Пример запроса и ответа в спеке — они читаются чаще, чем схемы.
- [ ] `pnpm api:gen` прогнан, `api-schema.d.ts` закоммичен.
- [ ] Контрактный тест зелёный.

### Правило клиента

**Никакого raw `fetch` и никакого `axios` в клиентском коде.** Все вызовы идут через
`openapi-fetch`-клиент, типизированный сгенерированной схемой; ESLint запрещает `fetch(` и `axios`
вне `packages/client/src/shared/api`.

## Формат ошибок

Один формат на все ошибки, включая валидацию — `application/problem+json`:

```json
{
  "type": "https://bad-crm.dev/problems/validation-failed",
  "title": "Request validation failed",
  "status": 422,
  "code": "validation_failed",
  "detail": "2 fields are invalid",
  "requestId": "01J8Z2F5Q3K9V6N0R4T7YB3XQD",
  "errors": [
    { "path": "title", "code": "too_small", "message": "String must contain at least 1 character" }
  ]
}
```

Поля `instance` здесь нет, и это не сокращение примера: RFC разрешает его опустить, а единственное
честное значение — URL запроса, который этот продукт печатать не может (есть маршруты, где сегмент
пути **сам является** учётными данными). Occurrence идентифицируется `requestId`. Схема `Problem` в
спеке фиксирует это отсутствие, и `error-codes.test.ts` его проверяет.

`code` — машинный идентификатор, по которому клиент выбирает локализованное сообщение. Полное
соответствие «ситуация → HTTP → code» — в [`../architecture/stack.md`](../architecture/stack.md),
раздел «Формат ошибок».

**Коды, добавленные EPIC-006** (полные обоснования — в `error-code.enums.ts` рядом с каждым):

| Ситуация | HTTP | `code` |
|---|---|---|
| логин: неверный пароль **или** несуществующий email; смена пароля с неверным `currentPassword` | 401 | `invalid_credentials` |
| пароль верен, аккаунт `SUSPENDED` | 403 | `account_suspended` |
| открытая регистрация выключена в инсталляции | 403 | `registration_disabled` |
| токен сброса неизвестен, использован или просрочен | 400 | `password_reset_token_invalid` |
| операции нужна почта, `SMTP_URL` не настроен | 503 | `mail_not_configured` |
| чужая или несуществующая сессия | 404 | `session_not_found` |

Первая строка — **одна** запись на две ситуации, и это acceptance-критерий эпика: два ответа
превращают форму входа в справочник сотрудников компании. Неразличимость требуется по коду, по телу
и по времени ответа, поэтому use-case проверяет пароль о заглушку, когда пользователя нет.
`invalid_credentials` при этом отделён от `unauthenticated` (нет токена / истёк), потому что для
клиента это противоположные вещи: первое — «скажи человеку, что пароль неверный», второе —
«обнови сессию».
