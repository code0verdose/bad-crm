# ADR-0001 — Монорепо на pnpm workspaces и turborepo

## Контекст

Bad CRM — self-hosted multi-tenant open-source CRM/workspace для команд разработки. Продукт состоит
из четырёх artefacts, которые физически не могут развиваться независимо:

- **клиент** — React 19 + Vite SPA;
- **сервер** — Express 5 + Prisma + BullMQ;
- **общий изоморфный код** — каталог permissions, коды ошибок, Zod-схемы value-objects (деньги,
  длительности, идентификаторы), типы событий outbox;
- **e2e-набор** — Playwright поверх поднятого стека.

Между клиентом и сервером есть жёсткий контракт, который существует в двух формах: OpenAPI-спека
(см. [ADR-0003](0003-openapi-as-source-of-truth.md)) и разделяемый TypeScript-код. Каталог
permissions — самый показательный случай: если клиент и сервер получат его из разных источников,
рассинхронизация проявится как «кнопка есть, а сервер отвечает 403» — то есть как продуктовый баг,
который никакой тест на одной стороне не поймает.

Отдельное ограничение задаёт модель поставки. Проект под AGPL-3.0 и рассчитан на то, что случайный
контрибьютор клонирует репозиторий и получает рабочее окружение одной командой. Всё, что требует
координации нескольких репозиториев, публикации промежуточных пакетов в реестр или ручной сборки
зависимостей, этот сценарий ломает.

Третье ограничение — CI на бесплатных раннерах GitHub Actions при одном-двух мейнтейнерах. Полный
прогон (lint + typecheck + unit + integration с Testcontainers + e2e) на каждый PR должен
укладываться в разумное время, иначе гейт перед коммитом (тесты, security, production-readiness)
станет формальностью, которую начнут пропускать.

## Решение

Один репозиторий, **pnpm workspaces** для разрешения зависимостей и **turborepo** для оркестрации и
кеширования задач.

Раскладка — четыре пакета в `packages/`:

```
packages/
  shared/   # изоморфный код: permissions.catalog, коды ошибок, Zod value-objects, типы событий
  server/   # Express 5 + Prisma + BullMQ
  client/   # React 19 + Vite
  e2e/      # Playwright
```

Направление зависимостей однонаправленное и является инвариантом:

```
client ──► shared
server ──► shared
e2e    ──► (ничего из исходников; только HTTP/UI поднятого приложения)
shared ──► (ничего из packages)
```

Три следствия, которые важнее самой раскладки:

1. **`shared` не зависит ни от Node-only, ни от браузерных API.** Отдельный `tsconfig` с
   `lib: ["ES2023"]`, без `DOM` и без `@types/node`. Пакет, который «случайно» импортировал
   `node:crypto`, не соберётся, а не сломается в рантайме браузера.
2. **`e2e` намеренно не зависит от `server`.** Тест, знающий внутренности, перестаёт быть
   end-to-end. Данные готовятся через публичный API и seed-скрипт.
3. **Сгенерированные из OpenAPI типы живут в `client`, а не в `shared`.** Это артефакт сборки
   клиента; если бы `server` от них зависел, спека перестала бы быть независимым контрактом и
   превратилась бы в отражение кода.

Turborepo описывает pipeline с явными зависимостями и кеш-выходами:

```jsonc
{
  "tasks": {
    "build":     { "dependsOn": ["^build"], "outputs": ["dist/**"] },
    "typecheck": { "dependsOn": ["^build"], "outputs": [] },
    "lint":      { "outputs": [] },
    "test":      { "dependsOn": ["^build"], "outputs": ["coverage/**"] },
    "test:e2e":  { "dependsOn": ["^build"], "cache": false },
    "db:migrate":{ "cache": false },
    "dev":       { "cache": false, "persistent": true }
  }
}
```

Всё, что зависит от внешнего состояния (БД, поднятый стек), помечено `cache: false` — иначе
turborepo отдаст «зелёный» результат для задачи, которая на самом деле не выполнялась в текущем
окружении. Remote cache **не включаем**: в публичном репозитории это завязка на вендорский сервис и
дополнительный секрет в CI.

Версии фиксируются: `packageManager: "pnpm@9.x.x"` (Corepack), `engines` с Node `>=22.11 <23`,
`.nvmrc`. `pnpm-lock.yaml` коммитится всегда, в CI — `pnpm install --frozen-lockfile`.

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **Polyrepo** (client / server / shared в отдельных репозиториях) | Полная независимость релизных циклов; понятные права доступа на репозиторий; меньше шума в истории каждого репозитория | Изменение контракта требует согласованных PR в 2–3 репозиториях; `shared` приходится публиковать в npm или тянуть git-ссылкой; локальная разработка требует `pnpm link` и ломается у контрибьютора; атомарный коммит «поменял API + поменял клиент» невозможен | Убивает главный сценарий: «клонировал и запустил». Контракт между клиентом и сервером меняется постоянно, а любое изменение, которое нельзя сделать одним PR, гарантированно расползётся |
| **npm workspaces** | Встроено в npm, нулевая установка инструментов; знакомо большинству | Плоский `node_modules` с hoisting — пакет может импортировать то, что не объявил в своих зависимостях (фантомные зависимости), и это вскроется только у контрибьютора с другим порядком установки; заметно медленнее на холодной установке | Фантомные зависимости особенно опасны для `shared`: изоморфность пакета перестаёт быть проверяемой, если он может дотянуться до чужих зависимостей. pnpm со строгим symlink-деревом делает объявленные зависимости единственно доступными |
| **yarn workspaces (Berry, PnP)** | Быстрая установка, zero-install, строгое разрешение зависимостей | PnP до сих пор требует патчей для части инструментария (Prisma-generate, некоторые Vite-плагины, IDE-интеграции); `nodeLinker: node-modules` сводит преимущество к нулю; лишняя когнитивная нагрузка на случайного контрибьютора | Строгость мы получаем от pnpm без экосистемных рисков. Барьер входа для контрибьютора — самостоятельная ценность проекта |
| **Nx** | Мощный граф задач, генераторы, distributed task execution, отличная визуализация зависимостей | Существенно больше конфигурации и собственных абстракций; генераторы навязывают свою раскладку, конфликтующую с гексагональной структурой сервера и FSD-структурой клиента; распределённое выполнение полезно при десятках пакетов | Четыре пакета не окупают модель Nx. Turborepo решает единственную реальную задачу — «не пересобирать то, что не менялось» — конфигом на 20 строк |
| **Bazel / Pants** | Герметичные, воспроизводимые сборки; лучшая инкрементальность в индустрии | Крайне высокая стоимость входа для TypeScript-стека; правила для Prisma/Vite пишутся руками; отпугивает контрибьюторов | Несоразмерно масштабу и аудитории |
| **Монорепо без кеша задач** (только pnpm workspaces, скрипты через `pnpm -r`) | Минимум инструментов | Каждый PR пересобирает и перепроверяет всё; при четырёх пакетах и Testcontainers это единицы минут впустую на каждый прогон | Кеш turborepo — единственное, что делает строгий commit-гейт (несколько проверок на каждый PR) практически применимым при бесплатных раннерах |

## Последствия

### Положительные

- **Контракт меняется атомарно.** Правка `permissions.catalog.ts`, серверного use-case и клиентского
  хука — один коммит, один ревью, один откат.
- **`shared` не публикуется в реестр.** Нет версионирования внутреннего пакета, нет окна, в котором
  клиент собран против старой версии каталога прав.
- **Один набор конфигов.** `tsconfig.base.json`, `eslint.config.js`, настройки Vitest и Prettier
  живут в корне; расхождение стиля между пакетами физически невозможно.
- **Барьер входа — одна команда.** `pnpm install && docker compose up -d && pnpm dev` даёт рабочее
  окружение. Для AGPL-проекта, живущего за счёт внешних контрибьюторов, это функциональное
  требование, а не удобство.
- **CI дешевеет.** Изменение только в `client` не перезапускает интеграционные тесты сервера.
- **Направление зависимостей проверяемо.** Правило линтера превращает архитектурный инвариант в
  ошибку сборки, а не в договорённость.

### Отрицательные / цена

- **Общая история и общий CI.** Правка README формально касается всего репозитория; фильтрация
  сборок ложится на turborepo и `paths` в workflow, и её нужно поддерживать.
- **Нет независимых версий пакетов.** Выпустить `shared` отдельно для внешнего потребителя нельзя
  без дополнительной работы. Осознанно: внешнего потребителя не планируется.
- **Соблазн размыть границы.** Импорт из `server` в `client` физически возможен и запрещается
  только линтером. Правило `import/no-restricted-paths` — обязательная часть решения, а не опция.
- **Turborepo — ещё одна зависимость** в цепочке сборки, с собственными мажорными апгрейдами.
  Версия пинуется точно (не `^`), потому что минорка меняет поведение кеша.
- **Ложно-зелёный кеш** при неверно объявленных `inputs`/`outputs`. Диагностируется тяжело: задача
  «прошла», хотя не выполнялась. Отсюда правило: всё с внешним состоянием — `cache: false`.

### Что становится трудно изменить позже

- **Разделить репозиторий обратно** технически возможно (`git filter-repo`), но к моменту, когда это
  понадобится, `shared` будет содержать десятки модулей, а каждый импорт из него станет
  межрепозиторным контрактом с версионированием. Практически это переписывание границ, а не
  переезд.
- **Сменить пакетный менеджер.** Уход с pnpm ломает предположение о строгом дереве зависимостей:
  код, годами писавшийся при отсутствии hoisting, может неявно опираться на него (например,
  `shared` действительно не имеет доступа к `@types/node`). Переход на npm/yarn с hoisting эти
  гарантии снимает молча.
- **Ввести пятый пакет с другим языком/рантаймом** (Go-воркер, Python-сервис для ML). Pipeline
  turborepo и общие конфиги заточены под TypeScript; такой пакет придётся выводить из общего
  pipeline, что немедленно ставит вопрос о polyrepo.
- **Раскладка `client/server/shared/e2e` зашита в документацию, эпики и правила проекта.**
  Переименование пакетов — сквозная правка по десяткам файлов и всем эпикам.

## Проверяемость

- **ESLint `import/no-restricted-paths`** — направление зависимостей между пакетами. Нарушение
  (`client` → `server`, `shared` → что угодно из `packages`) ломает `pnpm lint`.
- **Отдельный `tsconfig` для `shared`** с `lib: ["ES2023"]`, без `DOM` и `@types/node`. Шаг
  `typecheck` в CI падает при попытке использовать API конкретного рантайма.
- **`depcheck` в CI** — необъявленные и неиспользуемые зависимости пакета.
- **`pnpm install --frozen-lockfile`** — расхождение `package.json` и лок-файла блокирует PR.
- **Шаг CI «turbo кеш не маскирует БД-задачи»**: `test:e2e` и `db:migrate` объявлены `cache: false`;
  проверяется тестом конфигурации `turbo.json` (парсинг + утверждение о списке некешируемых задач).
- **Проверка версий среды**: `engines` + Corepack + `.nvmrc`; несовпадение версии Node в CI и в
  `.nvmrc` ломает workflow.
- Гейт-агенты `commit-hygiene` и `production-readiness` (см. правила проекта) проверяют, что в
  коммит не попали временные скрипты и что структура пакетов не расползлась.
