# ADR-0002 — Гексагональный backend на Express 5 и Prisma поверх PostgreSQL 16

## Контекст

Серверная часть Bad CRM обслуживает четырнадцать доменных контекстов (проекты, задачи, документы,
база знаний, файлы, vault, тайм-трекинг, чат, интеграции, AI, биллинг, онбординг, аудит, IAM) в
рамках одного развёртываемого образа. Три требования формируют выбор архитектуры сильнее, чем
предпочтения по фреймворкам.

**Первое: правила доступа должны тестироваться без базы.** Модель прав — конъюнкция capability и
resource ACL с наследованием по цепочке предков (см.
[ADR-0008](0008-permission-model-rbac-plus-acl.md)). Это десятки краевых случаев: истёкший override,
явный `NONE` на промежуточном узле, owner в обход ACL, guest, приватный проект → 404 вместо 403.
Если решение о доступе принимает репозиторий или SQL-запрос, каждый такой случай стоит поднятого
Postgres и подготовленных фикстур. Тогда их либо не покроют, либо покроют частично — а незакрытая
ветка в модели прав это не «пробел в тестах», а потенциальная утечка данных между сотрудниками.

**Второе: половина инфраструктуры опциональна.** Профиль `minimal` не поднимает Meilisearch и не
имеет AI-ключей (см. [ADR-0020](0020-self-host-packaging-docker.md)). Поиск должен деградировать на
Postgres FTS, AI-эндпоинты — возвращать «функция отключена». Это требует, чтобы выбор реализации
был свойством конфигурации, а не разбросанных по коду `if (meilisearchEnabled)`.

**Третье: контрибьютор должен понимать код за вечер.** AGPL-проект живёт внешними правками. Любая
«магия» — декораторы, автоматическое связывание по типам, скрытые контейнеры — это то, что придётся
объяснять в каждом ревью.

Отдельный вопрос — ветка Express. Express 4.x находится в конце жизненного цикла (получает только
критические исправления), а 5.x с 2024 года — рекомендованная ветка. Ключевое техническое отличие
не в производительности: в 4.x отклонённый промис в async-обработчике **не доходит** до
error-handler, запрос виснет до таймаута, и лечится это обёрткой `asyncHandler` вокруг каждого
маршрута — то есть дисциплиной, которую забывают. В 5.x это встроенное поведение.

## Решение

**Гексагональная архитектура (ports & adapters)** в `packages/server`, транспорт — **Express 5.x**,
доступ к данным — **Prisma 5.x/6.x**, хранилище — **PostgreSQL 16 + pgvector**.

Четыре слоя с жёстко заданным направлением зависимостей `presentation → application → domain`,
`infrastructure → application` (реализует порты):

```
packages/server/src/
  domain/                     # правила предметной области, ноль I/O
    <context>/
      *.entity.ts             # сущность с инвариантами
      *.value.ts              # value-object
      *.errors.ts             # доменные ошибки
      access/*.policy.ts      # чистые функции решения о доступе
    shared/{errors,ids,money,result}/
  application/                # сценарии
    <context>/
      ports/                  # интерфейсы, нужные use-case'ам
      use-cases/              # команды (меняют состояние)
      *.query.ts              # чтения (не меняют состояние)
  infrastructure/             # реализации портов
    persistence/prisma/  storage/  queue/  redis/  crypto/
    ai/  search/  realtime/  logging/  mail/  integrations/  bootstrap/
  presentation/http/          # тонкий транспорт
    controllers/ middleware/ validators/ serializers/ error-handler.ts
  main.ts                     # composition root
```

Правила слоёв, которые делают решение проверяемым:

- **`domain` не импортирует ничего инфраструктурного.** Ни Prisma, ни Express, ни Redis, ни
  `process.env`, ни `Date.now()`. Время приходит через `ClockPort`, идентификаторы — через
  `IdGeneratorPort`. Следствие: доменный тест — обычный синхронный юнит-тест.
- **Решение о доступе принимает policy в `domain`, а не репозиторий.** Use-case загружает контекст
  (membership, ACL-цепочку, роли) через порт и передаёт его чистой функции. Это прямое следствие
  первого требования из контекста.
- **Контроллер тонкий**: `parse (Zod) → use-case → serialize (DTO из OpenAPI)`. Бизнес-ветвлений в
  контроллере нет.
- **Composition root — единственное место, где известны конкретные адаптеры.** `main.ts` читает
  провалидированный env, собирает адаптеры, внедряет их в use-cases, поднимает HTTP или воркер в
  зависимости от `ROLE`. Никакого DI-контейнера с автоматическим разрешением: зависимости
  передаются конструктором явно.
- **Express 5.x**, а не 4.x. Отклонённый промис сам доходит до error-handler; `asyncHandler`-обёртка
  не нужна и запрещена (её наличие означает, что кто-то писал по памяти под 4.x). Дополнительно 5.x
  чинит класс уязвимостей парсинга путей (`path-to-regexp`) и снимает ряд устаревших API.
- **Prisma** — типобезопасные запросы и миграции. Расширение `$extends` реализует `withTenant`:
  открывает транзакцию и выставляет `SET LOCAL app.organization_id` (см.
  [ADR-0004](0004-multi-tenancy-postgres-rls.md)). Prisma-модели **не** являются доменными
  сущностями: между ними есть явный маппинг в `infrastructure/persistence/prisma`.
- **PostgreSQL 16 + pgvector** — одна база на всё: реляционные данные, JSONB (контент документов),
  полнотекстовый поиск (профиль `minimal`), векторы (RAG), RLS (изоляция арендаторов).

Формат ошибок API — `application/problem+json` (RFC 9457); доменная ошибка транслируется в
проблему единственным `error-handler.ts`.

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **NestJS** | Готовая модульность, DI из коробки, интерцепторы/guards/pipes, огромная экосистема, единый стиль для больших команд, отличная документация | Декораторы и `reflect-metadata` — неявное связывание, которое трудно проследить глазами; собственная модель модулей поверх и без того явных границ контекстов; заметный объём фреймворк-специфичного кода, который не переносится; более крутая кривая входа для случайного контрибьютора | Nest даёт DI-контейнер, а у нас уже есть явный composition root, который делает то же самое читаемым кодом. Мы платили бы фреймворк-специфичностью и «магией» за то, что уже решено 60 строками в `main.ts` |
| **Fastify** | Заметно выше RPS, встроенная валидация схемами, первоклассная типизация, активная разработка | Экосистема middleware беднее (часть решений — через `@fastify/express`); собственная модель плагинов и энкапсуляции; выигрыш в RPS не является узким местом при self-host нагрузке до ~100 пользователей, где доминируют БД и сеть | Оптимизация не того, что болит. Профиль нагрузки — десятки одновременных пользователей на VPS; бутылочное горлышко — Postgres и Meilisearch, а не парсер HTTP |
| **Hono / Elysia** | Очень лёгкие, отличная типизация, edge-совместимость | Молодая экосистема; edge-совместимость нам не нужна (нужен долгоживущий процесс с сокетами, воркерами и пулом БД); меньше готовых решений для helmet/rate-limit/сессий | Преимущества направлены на сценарий, которого у нас нет |
| **Слоистая архитектура (MVC: controller → service → repository)** | Знакома всем, меньше файлов, быстрее пишется на старте | Сервис почти всегда получает ORM напрямую → правила доступа и бизнес-логика перемешиваются с запросами; «протестировать без БД» становится невозможно; смена реализации (поиск, storage, AI) требует правок в сервисах | Прямой конфликт с требованием №1 и №2. При 14 контекстах и опциональной инфраструктуре слоистая схема через год превращается в сервисы по 800 строк, знающие про Prisma, Redis и Meilisearch одновременно |
| **Drizzle ORM** | SQL-first, лёгкий, отличные типы, прозрачные запросы, мгновенный старт | Миграции и introspection менее зрелые для схемы из 40+ таблиц с партиционированием, RLS-политиками и `EXCLUDE`-ограничениями; меньше готовых рецептов для tenant-контекста | Отвергнут по зрелости миграционного тракта, а не по качеству API. Для схемы этого размера цена ошибки в миграции на чужой self-host инсталляции выше, чем удобство SQL-first |
| **Kysely** | Чистый типобезопасный query-builder, полный контроль над SQL, нулевая «магия» | Не даёт миграций и генерации схемы — их пришлось бы вести отдельно; больше ручного кода для CRUD, которого в CRM много | Хороший инструмент для сложных запросов; но как основной слой доступа требует собственного миграционного тракта, который мы бы всё равно строили на чём-то ещё |
| **TypeORM** | Зрелый, поддерживает Active Record и Data Mapper, декораторы-сущности | Исторически нестабильное поведение миграций и связей; декораторы-сущности провоцируют смешение доменной модели с персистентной; медленное развитие | Ровно то смешение слоёв, которого архитектура должна избегать |
| **Express 4.x вместо 5.x** | Максимум готовых рецептов в интернете, все middleware гарантированно совместимы | Ветка в конце жизни (только критические фиксы); async-ошибки не доходят до error-handler без обёртки на каждом маршруте; известные проблемы парсинга путей | Забытая обёртка `asyncHandler` — это зависший запрос и утечка соединения, то есть отказ, а не косметика. Полагаться на дисциплину там, где фреймворк уже умеет правильно, — плохой обмен |
| **MongoDB вместо PostgreSQL** | Гибкая схема, простое горизонтальное шардирование | Нет RLS (изоляция арендаторов ушла бы целиком в код); транзакции есть, но модель консистентности сложнее; отчёты по времени и биллингу — реляционные по своей природе | Multi-tenancy с RLS и финансовые агрегаты — два требования, прямо противоречащих выбору |

## Последствия

### Положительные

- **Правила доступа покрываются табличными юнит-тестами без БД.** Policy — чистая функция; 100 %
  покрытие ветвей достижимо и дёшево.
- **Инфраструктура заменяема без правки сценариев.** `SearchPort` резолвится в Meilisearch или
  Postgres FTS, `AIProviderPort` — в четыре вида провайдера, `FileStoragePort` — в S3 или MinIO.
  Профиль `minimal` — это другой composition root, а не другой код.
- **Границы контекстов физически видны** в дереве каталогов; нарушение ловится линтером.
- **Express 5 снимает целый класс отказов**: незаобёрнутый async-обработчик больше не вешает запрос.
- **Prisma даёт единый миграционный тракт** (`expand → migrate → contract`), что критично для
  self-host: обновление инсталляции — это `migrate deploy` в одноразовом контейнере.
- **Один Postgres закрывает пять задач** (реляционка, JSONB, FTS, векторы, RLS) — минус четыре
  контейнера в compose.

### Отрицательные / цена

- **Больше файлов и больше церемонии.** Простой CRUD-эндпоинт — это порт, репозиторий, use-case,
  контроллер, валидатор, сериализатор. Для тривиальных случаев это избыточно, и соблазн «срезать»
  постоянен.
- **Маппинг entity ↔ row пишется руками.** Prisma-модель и доменная сущность расходятся, и это
  дублирование нужно поддерживать.
- **Prisma абстрагирует SQL** — сложные аналитические запросы (rollup, отчёты) всё равно уходят в
  `$queryRaw`, и там типобезопасность держится на дисциплине.
- **Express не даёт схемной валидации из коробки** — она делается Zod в `validators/`, и связь
  «маршрут ↔ схема ↔ OpenAPI» поддерживается контрактным тестом, а не фреймворком.
- **Composition root растёт.** При 14 контекстах `main.ts`/`bootstrap` — это несколько сотен строк
  явной сборки. Читаемо, но объёмно.

### Что становится трудно изменить позже

- **Гексагональная структура — это форма всего серверного кода.** Переход на слоистую схему или на
  Nest означает переписывание всех use-cases и портов. Практически необратимо после первых
  нескольких контекстов.
- **Правило «policy в domain, не в SQL» становится необратимым вместе с моделью прав.** Как только
  policy-функции покрыты сотнями табличных тестов, перенос авторизации в БД потребует переписать и
  логику, и весь корпус тестов (см. [ADR-0008](0008-permission-model-rbac-plus-acl.md)).
- **Prisma как источник схемы.** `schema.prisma` — это и модель данных, и миграции, и генератор
  клиента. Уход с Prisma требует переноса истории миграций и переписывания всех репозиториев;
  RLS-политики, партиционирование и `EXCLUDE`-ограничения при этом живут в ручных SQL-миграциях,
  которые придётся переносить отдельно.
- **PostgreSQL 16 как единственная база.** Решения «pgvector для эмбеддингов» и «JSONB для контента
  документов» намертво привязывают продукт к Postgres. Смена СУБД — это переписывание RLS,
  партиционирования, `EXCLUDE USING gist`, векторного поиска и FTS одновременно.
- **Express 5 в сигнатурах middleware.** Возврат на 4.x после накопления middleware, полагающихся на
  автоматическую обработку async-ошибок, дал бы тихую регрессию: код продолжит компилироваться, а
  запросы начнут виснуть.

## Проверяемость

- **ESLint `import/no-restricted-paths`** — запрет импортов `prisma`, `express`, `ioredis`,
  `process.env` внутри `domain/`; запрет импорта `infrastructure` из `application`.
- **Архитектурный тест** (`dependency-cruiser` или собственный тест на AST): `domain` не имеет ни
  одного импорта за пределы `domain/` и `packages/shared`.
- **Тест «ни один use-case не вызывает `Date.now()` / `crypto.randomUUID()` напрямую»** — время и id
  только через порты; проверяется грепом по AST в CI.
- **Табличные тесты policy** в `domain/**/access/*.policy.spec.ts` — покрытие ветвей 100 %,
  проверяется порогом Vitest coverage.
- **Интеграционные тесты репозиториев на Testcontainers** с реальным Postgres 16 — единственный
  способ проверить RLS, `EXCLUDE`-ограничения и партиционирование.
- **Тест «нет `asyncHandler`»**: грep по `packages/server/src/presentation` — обёртка отсутствует,
  подтверждая опору на поведение Express 5.
- **Проверка версии Express в CI**: `pnpm why express` — мажор ровно `5.x`; даунгрейд ломает шаг.
- Гейт-агенты `db-reviewer` (миграции и запросы) и `security-auditor` (транспорт, middleware) —
  обязательные проверки перед коммитом, см. правила проекта.
