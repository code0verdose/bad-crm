# ADR-0003 — OpenAPI-спецификация как источник истины контракта API

## Контекст

Между `packages/client` и `packages/server` проходит единственная граница, через которую ходят все
данные продукта: HTTP API. У этой границы три особенности, определяющие решение.

**Первая: границу пересекают не только наши клиенты.** Продукт self-hosted и open-source. Владелец
инсталляции пишет скрипты, интеграции, экспортеры; кто-то захочет мобильное приложение или CLI. Для
них API — это публичный контракт, а не деталь реализации. Контракт, существующий только в виде
TypeScript-типов внутри монорепо, для них не существует вовсе.

**Вторая: незаметное изменение контракта — самый дорогой класс багов.** Переименованное поле в
ответе, ставшее обязательным поле в запросе, изменившийся формат ошибки — всё это компилируется,
проходит юнит-тесты сервера и ломается у клиента (своего или чужого) в рантайме. Нужен механизм,
который делает изменение контракта **видимым событием в диффе**, а не побочным эффектом рефакторинга.

**Третья: типы на клиенте не должны писаться руками.** Ручные интерфейсы ответов расходятся с
реальностью со скоростью примерно одного релиза: поле добавили на сервере, на клиенте не отразили;
поле сделали nullable, клиент об этом не узнал. Такие расхождения ловятся не типами, а падением
в проде.

Дополнительный контекст: формат ошибок уже зафиксирован как `application/problem+json`
(RFC 9457), пагинация и идемпотентность описаны в [`../stack.md`](../stack.md) — всё это части
контракта, а не соглашения «по договорённости».

## Решение

**`docs/api/openapi.yaml` (OpenAPI 3.1) — единственный источник истины контракта API.** Спека
пишется руками, ревьюится как код и лежит в репозитории рядом с архитектурной документацией.

Поток работы (contract-first):

1. **Правка спеки первой.** Новый эндпоинт или изменение существующего начинается с `openapi.yaml`.
   Дифф спеки — предмет отдельного внимания на ревью.
2. **Кодогенерация типов клиента.** `openapi-typescript` (7.x) генерирует `paths`/`components` из
   спеки; клиент ходит через `openapi-fetch` + `openapi-react-query`, поэтому URL, параметры и тип
   ответа проверяются компилятором. Сгенерированный файл коммитится.
3. **Сервер спеку не генерирует и от сгенерированных типов не зависит.** Он её *реализует*:
   `validators/` — Zod-схемы запросов, `serializers/` — приведение доменной сущности к DTO,
   описанному в спеке.
4. **Двусторонний контрактный тест** в CI — центральный элемент решения:
   - *спека → маршруты*: каждая операция из `openapi.yaml` имеет зарегистрированный маршрут
     Express с тем же методом и путём; отсутствующая реализация — падение теста;
   - *маршруты → спека*: каждый зарегистрированный маршрут (кроме явного allow-list служебных:
     `/health`, `/metrics`, `/socket.io`) описан в спеке; недокументированный эндпоинт — падение;
   - *ответы → схемы*: интеграционные тесты прогоняют реальные ответы через валидатор JSON Schema,
     собранный из спеки. Ответ, не соответствующий заявленной схеме, — падение.
5. **Регенерация обязательна.** `pnpm api:gen` в CI с `git diff --exit-code`: забытая перегенерация
   типов после правки спеки блокирует PR.

Сгенерированные типы живут в `packages/client`, а не в `packages/shared` — намеренно. Если бы
`server` зависел от них, спека перестала бы быть независимым контрактом и стала бы отражением кода
(см. [ADR-0001](0001-monorepo-pnpm-turborepo.md)).

Версионирование — префикс `/api/v1`; ломающие изменения требуют новой версии, аддитивные (новое
необязательное поле, новый эндпоинт) — нет.

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **tRPC** | Полная типобезопасность без кодогенерации и без спеки; изменение сервера мгновенно отражается в типах клиента; минимум церемонии; отличный DX внутри монорепо | Контракт существует только как TypeScript — для внешнего потребителя (скрипт на Python, curl, мобильное приложение) его нет; процедуры не являются HTTP-ресурсами, поэтому кеширование, идемпотентность и стандартные коды ответов приходится изобретать; жёсткая связка клиента и сервера по версии типов | Прямо противоречит первой особенности контекста: self-hosted продукт обязан иметь документированный HTTP API, которым можно пользоваться извне. tRPC — правильный выбор для приложения с единственным собственным клиентом; у нас не тот случай |
| **GraphQL** | Клиент запрашивает ровно нужные поля; схема самодокументируема и интроспектируема; сильная экосистема; удобно для дашбордов с разнородными данными | N+1 по умолчанию (лечится dataloader'ами, то есть дополнительным слоем); авторизация на уровне полей резко усложняет модель прав, где решение принимает policy по ресурсу; кеширование и rate-limit сложнее (один URL, произвольная стоимость запроса); загрузка на self-host предсказуема хуже | Модель прав (capability ∧ resource ACL) естественно ложится на «операция над ресурсом» и плохо — на «произвольный граф полей». Плюс запрос произвольной стоимости на VPS с 2 vCPU — это готовый вектор отказа |
| **Ручные TypeScript-типы на клиенте** | Ноль инструментов, полный контроль, никакой генерации | Расхождение с реальным ответом — вопрос времени, а не вероятности; ошибка проявляется в рантайме у пользователя; двойная работа при каждом изменении | Это ровно тот класс багов, ради которого решение и принимается |
| **Генерация OpenAPI из кода** (декораторы, `zod-to-openapi`, `tsoa`) | Спека не может «отстать» от кода — она из него и получена; меньше ручной работы; один источник правды в исходниках | Контракт перестаёт быть предметом обсуждения: он становится следствием реализации, и ломающее изменение так же незаметно проходит ревью, как переименование поля; сгенерированные схемы отражают внутренние типы, а не продуманный внешний интерфейс; спека меняется «сама» при рефакторинге | Теряется главное свойство — **дифф контракта как отдельное событие в PR**. Когда спека выводится из кода, ревьюер видит переименование поля как рефакторинг, а не как ломающее изменение API |
| **Спека, но без контрактного теста** | Дешевле в поддержке | Спека немедленно превращается в устаревшую документацию: код уезжает, файл остаётся | Спека без принуждения — это README, а не контракт. Двусторонний тест — не опция решения, а его половина |
| **gRPC / Protobuf** | Строгий контракт, кодогенерация под любой язык, эффективный бинарный формат, стриминг | В браузере требует grpc-web и прокси; отладка курлом невозможна; лишний слой инфраструктуры в compose | Противоречит цели «поднимается одной командой» и усложняет жизнь тому, кто хочет дёрнуть API скриптом |

## Последствия

### Положительные

- **Контракт нельзя изменить незаметно.** Любое изменение — это дифф в `openapi.yaml`, видимый
  ревьюеру отдельно от кода.
- **Клиент типизирован генерацией.** `openapi-fetch` даёт ошибку компиляции при неверном пути,
  параметре или разборе ответа.
- **API документирован по факту существования.** Swagger UI / Redoc поднимается из той же спеки;
  внешние интеграторы получают полноценную документацию без отдельной работы.
- **Расхождение «код ↔ спека» ловится в CI, а не в проде.** Двусторонний тест закрывает оба
  направления дрейфа.
- **Спека — точка проектирования.** Обсуждать форму ресурса на YAML дешевле, чем на реализованном
  контроллере.
- **Сервер не зависит от артефактов клиента** — независимость контракта сохраняется структурно.

### Отрицательные / цена

- **Спека пишется руками.** Это реальная работа на каждый эндпоинт, и её нельзя «сделать потом».
- **Три места на одно поле:** спека, Zod-валидатор запроса, сериализатор ответа. Дублирование
  контролируется контрактным тестом, но не устраняется.
- **Соблазн «сначала код».** Разработчику быстрее написать контроллер и дописать спеку задним
  числом; тогда спека начинает описывать то, что получилось, а не то, что задумано. Держится
  дисциплиной и ревью.
- **Сгенерированный файл в репозитории** создаёт шум в диффах и конфликты при слиянии.
- **OpenAPI 3.1 не выражает всё**: сложные условные схемы, зависимости между полями,
  дискриминированные union'ы описываются громоздко.

### Что становится трудно изменить позже

- **Перейти на tRPC или GraphQL** после того, как внешние пользователи начали ходить в
  `/api/v1`, — значит либо ломать их интеграции, либо вечно держать два API. Для self-hosted
  продукта, где апгрейд делает владелец инсталляции, а не мы, это особенно дорого.
- **Форма ресурсов и имена полей** становятся публичным контрактом с момента первого релиза.
  Переименование поля — ломающее изменение, требующее `/api/v2` или периода двойной поддержки.
- **`application/problem+json` как формат ошибок** проникает в клиентскую обработку ошибок, в
  i18n-словари (`errors.json`, коды → тексты) и в интеграции. Смена формата — сквозная правка через
  весь клиент и все словари (см. [ADR-0019](0019-i18n-en-ru-i18next.md)).
- **Схема пагинации и идемпотентности** зашивается в каждый списочный и каждый мутирующий эндпоинт;
  смена подхода — правка всей спеки разом.
- **Contract-first как процесс** закрепляется в CI и в определении готовности историй; отказ от
  него означает демонтаж контрактного теста, после чего спека деградирует в течение нескольких
  релизов.

## Проверяемость

- **Контрактный тест «спека → маршруты»**: каждая операция `openapi.yaml` имеет зарегистрированный
  маршрут Express. Реализация обходит стек маршрутов и сравнивает множества.
- **Контрактный тест «маршруты → спека»**: каждый маршрут описан в спеке; исключения — явный
  allow-list в самом тесте (не в конфиге), чтобы добавление исключения было видно в диффе.
- **Валидация ответов по схеме**: интеграционные тесты (supertest + Testcontainers) прогоняют тела
  ответов через JSON-Schema-валидатор, собранный из спеки.
- **Шаг CI `pnpm api:gen` + `git diff --exit-code`** — забытая регенерация типов блокирует PR.
- **Линт спеки**: `redocly lint` / `spectral` — обязательные `operationId`, описания, примеры,
  консистентные имена; падение ломает сборку.
- **Diff-гейт на ломающие изменения**: `oasdiff` (или аналог) сравнивает спеку с версией в основной
  ветке; обнаруженное breaking change требует явной метки на PR и новой версии API.
- **ESLint-правило на клиенте**: запрет прямых `fetch`/`axios` к `/api/**` мимо сгенерированного
  клиента — иначе типизация обходится.
- Гейт-агент `production-readiness` проверяет обратную совместимость изменений контракта перед
  коммитом (см. правила проекта).
