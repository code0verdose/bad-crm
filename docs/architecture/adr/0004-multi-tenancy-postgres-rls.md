# ADR-0004 — Мульти-тенантность с первого дня: `organizationId` и Postgres Row Level Security

## Контекст

Bad CRM — multi-tenant продукт: одна инсталляция обслуживает одну или несколько организаций
(арендаторов). Типичный self-host — это агентство с одной организацией; но продукт также
рассчитан на сценарии «студия и её дочерние команды» и на публичный демо-стенд, где организации
принадлежат разным людям.

Ключевой факт, определяющий решение: **утечка данных между арендаторами — катастрофический,
необратимый и почти невыявляемый класс отказа.** Он отличается от обычного бага тремя свойствами:

1. Он возникает от *отсутствия* кода (забытый `WHERE organization_id = ...`), а не от наличия
   неправильного. Ревьюер видит корректно выглядящий запрос и не видит того, чего нет.
2. Он не проявляется в разработке и в тестах, где обычно одна организация. Он проявляется у
   пользователя, у которого их две.
3. Обнаружив утечку, откатить её нельзя: данные уже показаны.

Источники такой ошибки в живом проекте предсказуемы и неустранимы дисциплиной: новый эндпоинт,
написанный контрибьютором; сырой SQL для отчёта или аналитики; динамически собранный фильтр;
фоновый воркер, обрабатывающий события нескольких организаций подряд; выгрузка для дашборда.

Второй фактор — модель поставки. Обновление self-host инсталляции выполняет её владелец командой
`docker compose pull && up`. Всё, что делает миграции сложнее одного `migrate deploy`, ложится на
человека, который не читал наш код.

Третий фактор — размер: одна инсталляция обычно обслуживает 1–5 организаций и десятки-сотни
пользователей. Инфраструктурные схемы изоляции, окупающиеся на тысячах арендаторов, здесь дают
только издержки.

Явно фиксируем: **вопрос «делать multi-tenancy позже» не стоит.** Добавление `organizationId` в
40+ таблиц, во все индексы, во все запросы и во все тесты постфактум — это переписывание модели
данных, а не миграция. Решение принимается до первой таблицы.

## Решение

**Одна база, одна схема, `organizationId` на каждой доменной таблице, Postgres Row Level Security
как последний рубеж.**

Оборона двухуровневая, и второй уровень существует именно потому, что первый рано или поздно даст
сбой:

1. **Приложение фильтрует по арендатору** — Prisma-расширение подмешивает `organizationId`.
2. **RLS отсекает то, что приложение пропустило.** Без RLS ошибка — утечка; с RLS — пустой
   результат и запись в логе.

**Шаблон политики** для каждой tenant-таблицы:

```sql
ALTER TABLE tasks ENABLE ROW LEVEL SECURITY;
ALTER TABLE tasks FORCE  ROW LEVEL SECURITY;   -- иначе владелец таблицы обходит политику

CREATE POLICY tenant_isolation ON tasks
  USING      (organization_id = current_setting('app.organization_id')::uuid)
  WITH CHECK (organization_id = current_setting('app.organization_id')::uuid);
```

Обе части обязательны. Политика только с `USING` даёт классическую дыру: чужие строки не видны, но
**вставить** строку с чужим `organization_id` можно свободно — достаточно, чтобы значение пришло из
тела запроса. `FORCE ROW LEVEL SECURITY` обязателен: без него роль-владелец таблицы игнорирует
политику молча.

Мы **не** используем «мягкий» `current_setting('app.organization_id', true)` в политиках:
отсутствие контекста должно быть громкой ошибкой, а не тихим `NULL → строк нет`.

**Выставление контекста — `SET LOCAL` внутри транзакции**, через расширение Prisma:

```ts
prisma.$extends({
  client: {
    async withTenant<T>(organizationId: string, fn: (tx: TxClient) => Promise<T>) {
      return prisma.$transaction(async (tx) => {
        await tx.$executeRaw`SELECT set_config('app.organization_id', ${organizationId}, true)`;
        return fn(tx);
      });
    },
  },
});
```

Правила, без которых механизм не работает:

- **Любой запрос к tenant-таблицам идёт внутри `withTenant`.** Одиночный `prisma.task.findMany()`
  вне транзакции — ошибка, а не сокращение.
- **Никогда `SET` без `LOCAL`.** Обычный `SET` живёт до конца *соединения*, а соединение
  возвращается в пул и достаётся следующему запросу — уже другого арендатора. Это худший из
  возможных багов: утечка, проявляющаяся под нагрузкой и невоспроизводимая в тестах.
- **PgBouncer только в режиме `transaction` или `session`**, никогда `statement`.
- **Воркер, читающий outbox, выставляет контекст на каждое событие отдельно** — пачка событий
  принадлежит разным организациям.

**Источник истины об арендаторе — сессия** (claim `org` в access-токене), и только она. Поддомен
(`acme.example.com`) — клиентская навигационная подсказка: он выбирает, какую сессию открыть, но
сервер никогда не берёт `organizationId` из заголовка `Host`. Несовпадение приводит к редиректу на
логин, а не к смене контекста.

**Три роли БД** с разными полномочиями:

| Роль | Назначение | RLS | Права |
|---|---|---|---|
| `app_user` | обычные запросы приложения | **подчиняется** | CRUD на доменных таблицах; на `audit_logs` только INSERT/SELECT; не владелец объектов |
| `app_migrator` | миграции, DDL, партиции | владелец (обходит RLS → все таблицы с `FORCE`) | CREATE/ALTER/DROP; не используется приложением |
| `app_auth` | логин до определения организации | ограниченный `BYPASSRLS` | EXECUTE на нескольких `SECURITY DEFINER`-функциях; прямого SELECT на таблицы нет |

Единственная роль с `BYPASSRLS` не имеет доступа ни к одной доменной таблице; роль, ходящая в
доменные таблицы, не может обойти RLS ни при каких условиях. Приложение подключается строго как
`app_user`; health-check при старте отказывает в запуске, если `current_user = app_migrator`.

**RLS — это изоляция арендаторов, и только.** Она отвечает на вопрос «принадлежит ли строка моей
организации», но не на вопрос «имеет ли этот сотрудник право на этот ресурс». Второе — policy-слой
в `domain` (см. [ADR-0008](0008-permission-model-rbac-plus-acl.md)). Разделение формулируется так:
**RLS — стена между организациями, policy-слой — двери внутри организации.**

Без RLS остаются только глобальные справочники: `Permission` (каталог прав, задаётся кодом),
`Activity` (виды трудозатрат; кастомизация арендатора — в `ActivityOverride` под RLS) и служебная
`_prisma_migrations`. Всё остальное — под RLS без исключений; «таблица маленькая / служебная» не
аргумент, потому что из неё выводятся существование и объёмы чужих данных.

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **Single-tenant** (одна инсталляция = одна организация) | Простейшая модель данных: нет `organizationId`, нет RLS, нет tenant-контекста; невозможно «утечь» между арендаторами по построению; проще запросы и индексы | Сценарий «студия + дочерние команды» и демо-стенд закрываются только N инсталляциями с N базами и N обновлениями; переход к multi-tenant позже — переписывание схемы, всех запросов и всех тестов | Требование продукта — несколько организаций в одной инсталляции. И, главное, добавить мульти-тенантность потом невозможно эволюционно: `organizationId` — часть первичного пути каждого индекса |
| **Схема на арендатора** (`tenant_acme.tasks`) | Сильная изоляция средствами БД; легко выгрузить или удалить одного арендатора; ошибка в `WHERE` не даёт межарендаторную утечку | Prisma работает с одной схемой — поддержка N схем требует своего миграционного тракта; миграция должна примениться ко всем схемам атомарно, иначе инсталляция окажется в смешанном состоянии; пул соединений на схему; кросс-арендаторная аналитика невозможна без `UNION` по схемам | Миграции — центральный риск self-host обновления. «Одна схема — одна миграция» стоит больше, чем дополнительная изоляция, которую RLS даёт и так |
| **База на арендатора** | Максимальная изоляция, включая ресурсную; независимые бэкапы и восстановление; естественный путь к шардированию | То же умножение миграций плюс умножение соединений, бэкапов, мониторинга; создание организации становится инфраструктурной операцией; для типового self-host с одной организацией — чистые издержки | Несоразмерно масштабу. Путь оставлен открытым для крупных инсталляций в «Открытых вопросах» `data-model.md`, но как основной сценарий не подходит |
| **Изоляция только в коде** (везде `where: { organizationId }`, без RLS) | Ноль накладных расходов в БД; никаких транзакционных ограничений; проще отлаживать; нет риска «пустого результата из-за невыставленного контекста» | Единственная забытая проверка — утечка; сырой SQL для отчётов обходит любую ORM-обёртку; фоновые воркеры особенно уязвимы; проверить полноту невозможно (нельзя протестировать отсутствие кода) | Ровно тот класс ошибок, ради которого решение принимается. RLS превращает «утечку» в «пустой результат» — то есть в баг, который заметят и починят, а не в инцидент |
| **RLS, расширенная до полной авторизации** (политики с подзапросами по ACL) | Одно место для всех правил доступа; невозможно обойти из приложения | Политика с подзапросом выполняется **для каждой строки** и лишает планировщик индексов — списки задач деградируют на порядки; продуктовое изменение правил доступа становится миграцией БД; отказ невозможно объяснить («пусто» вместо «нет права, потому что…»); юнит-тестами не покрыть | Отвергнуто отдельно и явно (см. `data-model.md`, «RLS — это изоляция арендаторов, и только»). RLS остаётся узкой и быстрой; тонкая авторизация — в `domain` |
| **Дискриминатор без RLS, но с обязательным репозиторным слоем** | Дешевле RLS, компилятор может помочь через типы | Не покрывает сырой SQL и миграционные скрипты; «обязательность» держится на ревью | Половинчатая мера: даёт ощущение защиты без гарантии |

## Последствия

### Положительные

- **Забытый `WHERE` перестаёт быть утечкой.** Он становится пустым результатом — заметным багом.
- **Одна схема — одна миграция.** Обновление self-host инсталляции остаётся одной командой.
- **Компрометация приложения не даёт доступа к чужим данным**: роль `app_user` физически не может
  обойти RLS, а роль с `BYPASSRLS` не видит доменных таблиц.
- **Сырой SQL безопасен по умолчанию** — отчётные запросы внутри `withTenant` подчиняются политике.
- **Кросс-арендаторная аналитика для владельца инсталляции возможна** (одна база), не требуя
  расшивания изоляции.
- **Демо-стенд и мультиорганизационные инсталляции работают из коробки**, без развёртывания
  отдельной копии на каждого.

### Отрицательные / цена

- **Каждый запрос обязан быть в транзакции.** Это не привычный стиль Prisma и требует
  дисциплины плюс линтера. Одиночный вызов вне `withTenant` — ошибка.
- **`SET LOCAL` и пул соединений — главная ловушка подсистемы.** Ошибка «`SET` вместо `SET LOCAL`»
  даёт межарендаторную утечку под нагрузкой, невоспроизводимую в тестах.
- **Ограничение на PgBouncer**: только `transaction`/`session`. Это ограничивает варианты
  масштабирования соединений.
- **`organizationId` — первая колонка почти каждого индекса.** Индексы шире, планы запросов
  зависят от селективности по организации.
- **Накладные расходы RLS** — дополнительное условие в каждом плане. Мало при простой политике по
  индексированной колонке, но не ноль.
- **Отладка усложняется**: «данных нет» может означать и отсутствие данных, и невыставленный
  контекст. Отсюда выбор «жёсткого» `current_setting` без второго аргумента — чтобы это была
  ошибка, а не пустота.
- **Три роли БД** нужно создать и поддерживать в docker-compose, в миграциях и в документации по
  развёртыванию.

### Что становится трудно изменить позже

Это самый необратимый раздел всего набора ADR.

- **Убрать `organizationId`** нельзя: он входит в первичные пути индексов, в составные уникальные
  ограничения (`uq_timesheets (user_id, period_start)` и десятки подобных на самом деле
  организационно-скоупированы), в партиционирование аудита, в ключи объектов S3
  (`org/{organizationId}/...`), в имена комнат Socket.IO (`org:{id}:{resource}:{id}`), в фильтры
  Meilisearch и в tenant tokens. Мульти-тенантность пронизывает все подсистемы, а не только схему.
- **Уйти от RLS к «изоляции только в коде»** технически просто (`DROP POLICY`), но это означает,
  что весь корпус кода, писавшийся в предположении «второй рубеж есть», внезапно остаётся без него.
  Ни один из существующих запросов не будет перепроверен на полноту фильтрации.
- **Перейти на схему-на-арендатора или базу-на-арендатора** требует нового миграционного тракта,
  переписывания `withTenant`, переработки пула соединений и переезда данных. Это отдельный проект,
  а не рефакторинг. Путь оставлен открытым сознательно, но с полным пониманием цены.
- **Требование «запрос внутри транзакции»** становится свойством всего слоя доступа к данным.
  Отказ от него (например, ради read-replica без транзакций) потребует пересмотра модели изоляции
  целиком.
- **Три роли БД** попадают в инструкции по развёртыванию, которые уже выполнены на чужих серверах.
  Изменение схемы ролей — это миграция, требующая ручных действий владельца инсталляции.
- **`SET LOCAL` в транзакции ограничивает варианты пулинга** на всё время жизни продукта: любой
  будущий пулер, не сохраняющий границы транзакций, несовместим.

## Проверяемость

- **Тест изоляции на каждую tenant-таблицу** (Testcontainers, реальный Postgres 16): открыть
  транзакцию арендатора A, попытаться прочитать и **вставить** строку арендатора B — оба действия
  обязаны провалиться. Проверяются обе половины политики (`USING` и `WITH CHECK`).
- **Тест полноты покрытия политиками**: запрос к `pg_class`/`pg_policies` — каждая таблица, кроме
  явного allow-list (`permissions`, `activities`, `_prisma_migrations`), имеет `relrowsecurity` и
  `relforcerowsecurity` = true и ровно одну политику `tenant_isolation`. Новая таблица без политики
  ломает CI автоматически, без правки теста.
- **Тест «нет запроса вне `withTenant`»**: ESLint-правило, запрещающее прямые вызовы
  `prisma.<model>.*` вне слоя репозиториев, плюс архитектурный тест, что репозитории принимают
  транзакционный клиент, а не корневой `PrismaClient`.
- **Grep-гейт в CI на `SET ` без `LOCAL`** и на `current_setting('app.organization_id', true)` в
  файлах миграций — оба паттерна запрещены.
- **Health-check при старте**: приложение отказывается стартовать, если `current_user` —
  `app_migrator` или если роль имеет `rolbypassrls`.
- **Тест воркера outbox**: пачка событий разных организаций обрабатывается с выставлением контекста
  на каждое; событие организации B не должно видеть данные организации A.
- **Ревью миграций** — гейт-агент `db-reviewer` (правила проекта) обязателен для любого диффа,
  трогающего схему.
- **Проектный агент `tenancy-rls-auditor`** (`.claude/agents/tenancy-rls-auditor.md`) — сквозная
  проверка: новая таблица под RLS, новый запрос внутри транзакции, новый воркер выставляет контекст.
  Запускается на PR, трогающих `schema.prisma`, миграции или репозитории.
- **Чек-лист «добавляется новая таблица»** в [`../data-model.md`](../data-model.md) — часть
  определения готовности истории.
