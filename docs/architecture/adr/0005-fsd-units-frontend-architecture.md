# ADR-0005 — Архитектура клиента: Feature-Sliced Design в варианте «units»

## Контекст

`packages/client` — SPA на React 19 + Vite, покрывающая четырнадцать доменных областей: проекты,
канбан, документы, база знаний, чат, файлы, E2EE-хранилище, тайм-трекинг, табели, дашборды, отчёты,
delivery (клиенты, контракты, счета), онбординг, администрирование. Это не «сайт с несколькими
экранами», а рабочее место, где один экран (карточка задачи) может одновременно использовать
задачи, комментарии, файлы, тайм-трекинг и права.

Три обстоятельства формируют требование к структуре.

**Первое: доменная логика на клиенте реальна и её много.** Это не тонкий слой над API. Фильтры,
живущие в URL и валидируемые схемой; оптимистичные обновления с откатом; композиция query и
mutation; форматирование денег и длительностей; вычисление того, что пользователю можно показать по
правам. Если этому негде жить кроме компонентов, компоненты вырастают до 500 строк и перестают
поддаваться ревью.

**Второе: направление зависимостей должно быть проверяемым.** В проекте с внешними
контрибьюторами договорённость «не импортируй из страницы в фичу» не работает: её не знают. Работает
только правило линтера.

**Третье: E2EE-хранилище задаёт жёсткое ограничение изоляции.** Крипто-модуль обязан быть отдельным
лениво загружаемым чанком, который не импортирует ничего, кроме `libsodium-wrappers-sumo`, не имеет
доступа к HTTP-клиенту и физически не может отправить данные наружу (см.
[ADR-0009](0009-e2ee-vault-key-hierarchy.md)). Это требование проверяется архитектурным тестом,
а значит архитектура должна иметь явные границы, по которым такой тест можно написать.

Дополнительный контекст: выбранный стек — Mantine 9 + CSS Modules
([ADR-0006](0006-mantine-css-modules-no-tailwind.md)), TanStack Router + Query
([ADR-0007](0007-tanstack-router-and-query.md)). Обе библиотеки нейтральны к раскладке файлов, но
обе предполагают, что «где живёт запрос» и «где живёт схема search-параметров» решено заранее.

## Решение

**Feature-Sliced Design в варианте «units»** — пять слоёв со строго нисходящим направлением
зависимостей:

```
app → pages → widgets → units → shared
```

| Слой | Содержимое |
|---|---|
| `app` | провайдеры, роутер, тема, глобальные стили, `main.tsx`, `routes/**` |
| `pages` | `page.tsx` + `ui/` + локальные `hooks/`; только композиция |
| `widgets` | `*.widget.tsx` — составные блоки, переиспользуемые между страницами |
| `units` | доменные слайсы, имя — kebab-case в **единственном** числе и совпадает с термином глоссария: `task`, `vault`, `time`, `chat`, `doc`, `kb`, `sprint`, … (см. `rules/naming-and-structure.mdc`, п. 11) |
| `shared` | `ui/`, `lib/`, `hooks/`, `api/` — ничего доменного |

**Сегменты юнита** (создаются по мере надобности, не пустыми):

```
units/<unit>/
  api/          <unit>.api.ts        # чистые fetch-функции поверх сгенерированного клиента
  service/
    queries/    *.query.ts           # queryOptions-фабрики
    mutations/  *.mutation.ts        # мутации с оптимистикой
    hooks/      use-*.hook.ts        # публичное API юнита для ui
    stores/     *.store.ts           # zustand — см. ADR-0026
  model/
    enums/ constants/ validation/    # union+label-map, константы, Zod-схемы
  lib/          utils/ …             # доменные чистые функции
  types/        <unit>.types.ts
  ui/           *.component.tsx
  index.ts                           # namespace-barrel
```

**Call-chain фиксирован:** `ui → service/hooks → service/{queries,mutations} → api → SharedApi`.
Хук уровня `service/hooks` — публичное API юнита для UI: он композирует query, mutation, состояние
и форматирование. Компонент вызывает `const { data, onSubmit } = useX()` и рендерит.

**Импорты — только `@`-алиасы, потребление — через namespace.** Каждый слой и каждый юнит
реэкспортирует свои сегменты как namespace:

```ts
// units/task/index.ts
export * as TaskService from './service';
export * as TaskUi from './ui';
export * as TaskModel from './model';
export * as TaskTypes from './types';

// потребление
import { TaskService } from '@units/task';
const { data } = TaskService.useTaskList(filters);
```

Алиасы (`@app/*`, `@pages`, `@widgets/*`, `@units/*`, `@shared`, `@shared/*`) настраиваются
одновременно в `tsconfig.paths` и в `vite.resolve.alias`. Глубокие относительные пути (`../../../`)
запрещены, импорт внутрь юнита мимо barrel — тоже: внутренности сегментов приватны.

**Правила размещения логики** (это и есть суть решения, а не раскладка папок):

- переиспользуемое и не доменное (форматтер даты, дебаунс, generic-UI) → `shared`;
- завязанное на сущность (хук по entity, доменный расчёт, доменный тип) → `units/<unit>`, никогда в
  `shared` и никогда inline в компоненте;
- специфичное для одной страницы → `pages/<page>/{ui,hooks}`;
- **компонент = JSX + хендлеры + вызовы хуков.** Никаких helper-функций, объявленных в файле
  компонента; чистая функция уезжает в `*.util.ts`;
- **один файл — одна ответственность, один компонент на файл.**

Именование — kebab-case + role-suffix: `task-card.component.tsx`, `use-task-list.hook.ts`,
`tasks.query.ts`, `task-status.enums.ts`. Экспорты — named; компоненты `PascalCase`, хуки
`camelCase`.

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **Классический FSD** (`entities` / `features` / `widgets` / `pages`) | Каноничная методология с документацией и сообществом; более тонкая нарезка ответственности; `entities` явно отделяет данные от действий | Граница `entities` ↔ `features` требует постоянного решения «это сущность или действие»; в CRM почти каждое действие принадлежит своей сущности, и слой `features` вырождается в набор папок с одним хуком; два слоя вместо одного удваивают количество barrel-файлов и импортов | Мы берём ту же идею слоёв и того же направления зависимостей, но склеиваем `entities` + `features` в `units`. Это сокращает споры на ревью и число файлов, сохраняя главное свойство — проверяемое направление зависимостей |
| **Feature-folders без слоёв** (`src/features/tasks/**`, каждая фича самодостаточна) | Минимум церемонии; всё про фичу в одном месте; легко удалить фичу целиком | Нет запрета на импорт между фичами → через полгода граф зависимостей произвольный; «общее» либо дублируется, либо стихийно оседает в `utils/`, который становится свалкой; направление зависимостей непроверяемо | Отсутствие слоёв означает отсутствие правила, которое можно линтовать. Для проекта с внешними контрибьюторами это решающий аргумент |
| **Группировка по типу файла** (`components/`, `hooks/`, `api/`, `utils/`) | Знакомо всем; предельно просто на старте | При 14 доменах `components/` содержит сотни файлов без связи друг с другом; чтобы понять фичу, нужно открыть четыре папки; удаление функциональности требует археологии | Не масштабируется до размера продукта. Это раскладка для приложения на 20 экранов |
| **Атомарный дизайн** (atoms / molecules / organisms / templates / pages) | Хорошо описывает UI-иерархию; полезен для дизайн-системы | Классифицирует **только вёрстку** и ничего не говорит о том, где живут запросы, доменная логика и состояние; споры «это молекула или организм» бесконечны и бесплодны | Решает не ту задачу. Полезная часть (иерархия презентационных компонентов) уже покрыта разделением `shared/ui` ↔ `units/*/ui` |
| **Модули по маршрутам** (структура повторяет дерево роутов) | Прямое соответствие URL и файлов; удобно с file-based роутингом | Домен, используемый на пяти страницах (задачи — на доске, в поиске, в дашборде, в отчётах, в карточке), не имеет своего места; логика дублируется или уезжает в общую свалку | Маршруты и домены — ортогональные разрезы. У нас file-based маршруты (ADR-0007) поверх доменных юнитов, а не вместо них |
| **Монолитный `src/` без правил** | Максимальная скорость на первой неделе | Через три месяца — нечитаемый граф импортов; любой рефакторинг рискован | Неприемлемо для продукта, рассчитанного на годы и внешние правки |

## Последствия

### Положительные

- **Направление зависимостей проверяется линтером**, а не договорённостью. `units` не может
  импортировать `pages`; нарушение ломает сборку.
- **Доменная логика имеет адрес.** Вопрос «куда положить этот хук» имеет один ответ, а не три
  мнения на ревью.
- **Компоненты остаются читаемыми**: правило «JSX + хендлеры + хуки» держит их в десятках строк.
- **Крипто-модуль изолируется естественно** — `units/vault/lib/crypto` с собственным barrel, и
  архитектурный тест может утверждать про его импорты (см. ADR-0009).
- **Code-splitting ложится на слои**: доменный namespace грузится вместе с чанком маршрута,
  i18n-namespace — тоже (см. [ADR-0019](0019-i18n-en-ru-i18next.md)).
- **Namespace-импорты делают источник видимым в месте использования**: `TaskService.useTaskList` —
  сразу понятно, чей это хук, без перехода к определению.
- **Удаление функциональности локально**: юнит удаляется целиком, и линтер показывает всех, кто на
  него ссылался.

### Отрицательные / цена

- **Больше файлов и barrel'ов.** Один хук — это файл хука, запись в `index.ts` сегмента и запись в
  `index.ts` юнита.
- **Порог входа выше**, чем у feature-folders: контрибьютору нужно прочитать правила раскладки
  прежде, чем добавить кнопку.
- **Namespace-барели и tree-shaking.** `export * as X` требует аккуратности: побочные эффекты в
  модуле юнита сведут shaking на нет. Контролируется `sideEffects: false` и анализом бандла.
- **Граница `shared` ↔ `units` требует решения в каждом спорном случае.** Форматтер длительности —
  общий или доменный? Ошибка в обе стороны неприятна: в `shared` уезжает доменное знание либо в
  каждом юните появляется своя копия.
- **Дублирование алиасов** в `tsconfig` и `vite.config` — два места, которые расходятся молча.
- **Циклы между юнитами возможны** (задачи ↔ комментарии ↔ файлы) и требуют отдельного правила
  линтера, а не только слоёв.

### Что становится трудно изменить позже

- **Раскладка слоёв и сегментов пронизывает все импорты приложения.** Смена методологии — это
  массовое перемещение файлов и перезапись каждого импорта; автоматизируется частично, но ломает
  историю git и все открытые ветки.
- **Namespace-барели становятся публичным API юнита.** Переименование юнита или сегмента — сквозная
  правка по всем потребителям. Особенно чувствительно для `shared`, на который ссылается всё.
- **Правило «логика в хуках, не в компонентах»** определяет форму каждого компонента продукта.
  Отказ от него означает не «разрешить исключение», а постепенное расползание логики обратно в JSX
  без возможности откатиться.
- **Границы юнитов = границы доменов** совпадают с ubiquitous language из
  [`../../product/glossary.md`](../../product/glossary.md) и с bounded contexts сервера. Пересмотр
  границы юнита обычно означает пересмотр доменной модели с обеих сторон.
- **`@`-алиасы** зашиты в тысячи импортов; их переименование — единовременная массовая правка,
  выполнимая, но всегда конфликтующая с параллельными ветками.

## Проверяемость

- **ESLint `import/no-restricted-paths`** (или `boundaries`): `units` не импортирует `widgets`/
  `pages`/`app`; `shared` не импортирует ничего выше себя; `pages` не импортирует другие `pages`.
- **ESLint-правило на глубокие относительные импорты** — `../../` запрещены, только `@`-алиасы.
- **Правило «импорт только через barrel»**: `@units/task/service/hooks/use-task-list.hook` —
  ошибка; допустим только `@units/task`.
- **Тест на циклы**: `dependency-cruiser` с `no-circular` по всему `src` — падает сборка.
- **Архитектурный тест изоляции крипто-модуля**: граф импортов `units/vault/lib/crypto` содержит
  только `libsodium-wrappers-sumo`; отсутствуют любые сетевые API (`fetch`, `XMLHttpRequest`,
  `WebSocket`, `navigator.sendBeacon`) — см. ADR-0009.
- **ESLint-правило «один компонент на файл»** (`react/no-multi-comp`) и запрет объявления функций
  верхнего уровня в файлах `*.component.tsx` кроме самого компонента.
- **Тест соответствия имени файла и роли**: `*.hook.ts` экспортирует только `use*`, `*.component.tsx`
  экспортирует ровно один PascalCase-компонент. Реализуется правилом `filename-rules` + тестом на AST.
- **Проверка синхронности алиасов**: тест сравнивает `tsconfig.paths` и `vite.resolve.alias` —
  расхождение ломает сборку.
- **`rollup-plugin-visualizer` + `size-limit`** в CI: рост чанка маршрута сверх порога — падение;
  это косвенно ловит просочившиеся из `units` в `shared` тяжёлые зависимости.
- Гейт-агент `code-reviewer` (правила проекта) — семантическая проверка «логика в хуках, а не в
  компонентах», которую линтер не выражает.
