# ADR-0007 — Маршрутизация на TanStack Router и серверное состояние на TanStack Query v5

## Контекст

Клиент Bad CRM — SPA с большим числом списочных экранов, у каждого из которых есть фильтры,
сортировка и пагинация. Первый принцип интерфейса, зафиксированный в
[`../ux-architecture.md`](../ux-architecture.md), звучит так: **состояние экрана всегда
восстанавливается из URL**. Ссылку на «просроченные задачи проекта X за прошлую неделю» должно быть
можно переслать коллеге, положить в закладки и открыть после перезагрузки. Кнопки «назад» и
«вперёд» обязаны работать как ожидается.

Отсюда следует, что фильтры — это не локальный `useState`, а типизированное состояние URL. И тогда
сразу возникают задачи, которые обычно решают вручную и плохо: парсинг строковых query-параметров в
числа и даты, отбрасывание мусора, whitelist допустимых значений мультиселекта, сброс страницы при
смене фильтра, отмена устаревшего запроса при быстрой смене фильтра.

Второе требование: **guard авторизации должен срабатывать до загрузки данных и до рендера.** Продукт
целиком за логином; часть разделов требует прав. Проверка внутри компонента даёт мигание защищённого
экрана и лишние запросы, которые всё равно вернут 403.

Третье: **серверное состояние доминирует.** Практически все данные экрана приходят с сервера и
разделяются между экранами (список задач нужен на доске, в дашборде, в поиске и в отчётах). Ручное
кеширование в глобальном сторе означает написание собственного слоя инвалидации — того, что уже
решено библиотеками.

Четвёртое: **realtime — транспорт уведомлений, а не источник истины**
([ADR-0010](0010-realtime-socketio-redis-adapter.md)). Клиент на событие инвалидирует
соответствующий query-key; расхождение лечится обычным рефетчем. Это требует, чтобы ключи кеша были
предсказуемыми и типизированными, а не собирались ad-hoc в каждом хуке.

Пятое: **оптимистичные обновления обязательны** там, где ответ предсказуем (перетаскивание карточки
на доске, чекбокс, старт/стоп таймера). Без библиотечной поддержки отката это источник
рассогласований.

## Решение

**TanStack Router** для маршрутизации и **TanStack Query v5** для серверного состояния. Роутер
оркеструет, Query кеширует.

**Маршрутизация.**

- **File-based routes** в `app/routes/**` + `createFileRoute('/path')`. Дерево генерируется в
  `routeTree.gen.ts` плагином Vite; руками не пишется.
- **Route-файл тонкий**: только wiring — `validateSearch`, `beforeLoad`, `loader`, `component`.
  Рендер делегируется композиции из `pages/<page>`; бизнес-логика и запросы — в `units`
  (см. [ADR-0005](0005-fsd-units-frontend-architecture.md)).
- **Глобальная регистрация типов** один раз в `app/router.tsx`:

  ```ts
  declare module '@tanstack/react-router' {
    interface Register { router: typeof router }
  }
  ```

  После этого `Link`, `useNavigate` и `redirect` типобезопасны во всём приложении: несуществующий
  путь или параметр — ошибка компиляции. Данные маршрута берутся только через типизированные хуки
  route (`Route.useSearch()`, `Route.useParams()`, `Route.useLoaderData()`).
- **Search-параметры — типизированное состояние через Zod**:
  `validateSearch: zodValidator(filtersSchema)` (`@tanstack/zod-adapter`). Это **канонический
  механизм фильтров**: схема выполняет парсинг, приведение (`z.coerce`), whitelist и отбрасывание
  мусора; `Route.useSearch()` отдаёт уже валидный типизированный объект. Навигация —
  `navigate({ search: prev => ({ ...prev, page: 1 }) })`; при смене любого фильтра `page`
  сбрасывается. Схемы фильтров живут в `units/<unit>/model/validation`.
- **Авторизация — типизированный context + `beforeLoad`-guard**:

  ```ts
  beforeLoad: ({ context, location }) => {
    if (!context.auth.isAuthed)
      throw redirect({ to: '/login', search: { redirect: location.href } });
  }
  ```

  Защищённые ветки — pathless layout route `_authenticated.tsx`: guard объявляется один раз на
  ветку. Проверка прав (capability) — в `beforeLoad` конкретной ветки через `units/auth`.
  Логин/логаут → обновление auth-состояния + `router.invalidate()` + переход на `search.redirect`.
- **Границы состояний на уровне маршрута**: `pendingComponent` (+ `defaultPendingMs`),
  `errorComponent`, `notFoundComponent`. Глобальные дефолты — в `createRouter`.
- **Loaders поверх Query**: `context: { queryClient }` пробрасывается в роутер, `loader` вызывает
  `queryClient.ensureQueryData(entityQueryOptions(...))`, компонент затем читает те же данные
  `useSuspenseQuery` с тем же ключом — без второго запроса. `defaultPreload: 'intent'` (префетч по
  наведению), `defaultPreloadStaleTime: 0` — свежесть остаётся зоной ответственности Query.

**Серверное состояние.**

- **Типизированный клиент** — `openapi-fetch` + `openapi-react-query` поверх сгенерированных из
  спеки типов ([ADR-0003](0003-openapi-as-source-of-truth.md)). Auth-middleware: Bearer + 401 →
  refresh с дедупликацией.
- **Query keys — центральная типизированная фабрика** в `shared/lib/enums`
  (`QueryKeys.Tasks.list(...)`, `QueryKeys.Tasks.all`), не ad-hoc массивы в хуках. Инвалидация —
  строго по ключам фабрики; это же делает realtime-инвалидацию однозначной.
- **Defaults**: `{ queries: { retry: 1, staleTime: 30_000 } }` + глобальный `MutationCache.onError`
  → красный toast (пропуская `AbortError`); локальный `onError` **переопределяет**, а не добавляет
  (иначе два тоста на один сбой).
- **Списки** — `useInfiniteQuery` или `useQuery` + `placeholderData: keepPreviousData` (экран не
  мигает при смене страницы или фильтра). Query-key включает **все** параметры фильтра из URL.
- **Отмена запроса обязательна**: `signal` пробрасывается из Query в fetch
  (`queryFn: ({ signal }) => api.list(params, { signal })`). Запрос отменяется при размонтировании и
  при смене query-key — новый фильтр отменяет предыдущий, гонок нет.
- **Debounce текстового ввода** (`useDebouncedValue`, ~300 мс): в URL и в ключ уходит уже
  дебаунснутое значение.
- **Мутации**: оптимистичные (toggle, inline-edit, delete, drag-n-drop) — `onMutate` → снапшот +
  `setQueriesData` синхронно, `onError` → откат, `onSettled` → `invalidateQueries`; пессимистичные
  (создание, тяжёлые записи) — только `onSuccess` → инвалидация + уведомление. Хелперы —
  `shared/api/optimistic.util.ts`.
- **Клиентское состояние, не являющееся серверным** (открытость сайдбара, плотность таблиц) — в
  zustand или в URL, но не в Query. Query не используется как глобальный стор. Полная таблица «где
  что живёт» и обоснование выбора zustand — [ADR-0026](0026-client-state-zustand.md); эта строка
  была единственным местом, где выбор был назван, но не принят.

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **react-router (v6/v7) + ручной парсинг query** | Де-факто стандарт, знаком всем; огромная экосистема и материалы; loaders/actions в data-режиме; меньше вопросов у контрибьютора | Search-параметры не типизированы: парсинг, валидация и whitelist пишутся руками в каждом фильтр-хуке и расходятся между экранами; `Link`/`navigate` принимают произвольную строку — опечатка в пути обнаруживается только в рантайме; guard'ы реализуются вручную и легко забываются на новой ветке | Ручной парсинг URL — именно тот код, который мы хотим устранить: он повторяется на каждом списочном экране и ошибается одинаково. Типизированный `validateSearch` со схемой Zod убирает целый класс багов. Эталонные проекты автора на react-router признаны легаси |
| **Next.js (App Router)** | SSR/RSC, SEO, файловый роутинг, встроенная оптимизация, огромная экосистема | Тянет за собой Node-сервер рендеринга в развёртывание, что противоречит модели «один образ + docker compose» ([ADR-0020](0020-self-host-packaging-docker.md)); продукт целиком за логином — SEO не нужен; RSC плохо сочетаются с E2EE-хранилищем, где вся криптография принципиально клиентская; усложняет отладку для контрибьютора | Основная выгода Next (SSR/SEO) для приложения за логином отсутствует, а стоимость развёртывания и сложности — реальна. Если SSR понадобится, TanStack Start добавляется поверх тех же маршрутов, не переписывая их |
| **RTK Query** | Единый стор с остальным Redux-состоянием; кодоген из OpenAPI; хорошие devtools; нормализация | Тянет Redux Toolkit целиком даже там, где глобальный стор не нужен; оптимистичные обновления и инвалидация выражаются многословнее; infinite queries появились позже и менее удобны | Redux в проекте не нужен: серверное состояние закрывает Query, а немногое клиентское — zustand. Платить объёмом Redux за то, что уже решено, нет причин |
| **SWR** | Очень лёгкий, простой API, отличный кеш «stale-while-revalidate» | Заметно скромнее по возможностям: мутации, оптимистика, infinite queries, отмена и devtools проработаны слабее; экосистема меньше | Продукту нужны именно продвинутые сценарии — оптимистичный drag-n-drop, инвалидация по realtime-событиям, бесконечная лента чата |
| **Собственный слой на `fetch` + Context** | Полный контроль, ноль зависимостей | Придётся написать кеш, дедупликацию, инвалидацию, ретраи, отмену, оптимистику — то есть TanStack Query, но без тестов и документации | Классическое изобретение велосипеда в области, где велосипед уже отличный |
| **Состояние фильтров в `useState`, а не в URL** | Проще пишется, меньше кода | Ссылку нельзя переслать; back/forward ломаются; перезагрузка теряет контекст — прямое нарушение принципа №1 из ux-architecture | Противоречит продуктовому требованию |
| **`nuqs` поверх react-router** | Даёт типизацию search-параметров без смены роутера; лёгкая миграция | Решает половину задачи: типизация путей, guard'ы и интеграция loaders с Query остаются ручными | Половинчатое решение при сопоставимой стоимости внедрения полного |

## Последствия

### Положительные

- **Фильтры и пагинация живут в URL и типизированы схемой.** Один механизм на все списочные экраны;
  парсинг и whitelist не пишутся руками.
- **Опечатка в пути или параметре — ошибка компиляции**, а не 404 у пользователя.
- **Guard срабатывает до загрузки данных**: нет мигания защищённого экрана и нет запросов, заранее
  обречённых на 403.
- **Loader и кеш не дублируют запросы**: `ensureQueryData` + `useSuspenseQuery` с одним ключом.
- **Префетч по наведению** делает переходы мгновенными без ручного управления.
- **Realtime-инвалидация однозначна** благодаря центральной фабрике ключей.
- **Отмена запросов из коробки** — нет гонок при быстрой смене фильтра и нет утечек при
  размонтировании.
- **Единая политика ошибок и загрузки**: `errorComponent`/`pendingComponent` на маршруте плюс
  `MutationCache.onError` — один тост на одно действие.

### Отрицательные / цена

- **Меньше материалов и ответов на StackOverflow**, чем у react-router: контрибьютору чаще придётся
  читать официальную документацию.
- **Сгенерированный `routeTree.gen.ts`** в репозитории — шум в диффах и источник конфликтов слияния.
- **Порог входа выше**: типизированный context, `beforeLoad`, `validateSearch` и связка с
  `queryClient` требуют понимания до написания первого маршрута.
- **Тяжёлые типы** увеличивают время `tsc` и нагрузку на IDE в больших деревьях маршрутов.
- **Дисциплина ключей.** Фабрика ключей должна использоваться всегда; один ad-hoc массив ломает
  инвалидацию тихо.
- **Двойной источник свежести.** Loader и `staleTime` взаимодействуют неочевидно; отсюда правило
  `defaultPreloadStaleTime: 0` — свежесть решает только Query.

### Что становится трудно изменить позже

- **`validateSearch` со схемами Zod становится контрактом URL продукта.** Имена и семантика
  search-параметров попадают в сохранённые ссылки, закладки и переписки пользователей.
  Переименование параметра ломает уже отправленные ссылки — это внешняя совместимость, а не
  внутренний рефакторинг.
- **Фабрика query-ключей** используется всем клиентом и всей realtime-инвалидацией; изменение её
  структуры — сквозная правка, при которой ошибка проявляется как «данные не обновляются», а не как
  ошибка компиляции.
- **Смена роутера** означает переписывание всех route-файлов, всех guard'ов, всей работы с
  search-параметрами и всех `Link`. Типобезопасность, ради которой роутер выбран, здесь же делает
  миграцию массовой.
- **Решение «не Next.js»** фиксирует клиент как чистое SPA: добавление SSR позже — это TanStack
  Start (совместимый путь) либо полное переписывание (если выбрать другой фреймворк).
- **Паттерн оптимистичных обновлений** (снапшот → патч → откат → инвалидация) закрепляется в
  `shared/api/optimistic.util.ts` и используется десятками мутаций; смена подхода затрагивает их все.

## Проверяемость

- **Типизация как тест**: `pnpm typecheck` падает при несуществующем пути, параметре или неверном
  типе search-параметра. Это основной механизм проверки, а не дополнение к нему.
- **Тест «нет запроса мимо фабрики ключей»**: ESLint-правило, запрещающее литеральные массивы в
  `queryKey`; допустимы только вызовы `QueryKeys.*`.
- **Тесты схем search-параметров** (обязательны по правилам проекта): мусорные значения
  отбрасываются, `z.coerce` приводит типы, мультиселект фильтруется по whitelist, смена фильтра
  сбрасывает `page`.
- **Тесты guard'ов**: `beforeLoad` без сессии бросает `redirect` на `/login` с корректным
  `search.redirect`; при недостатке прав — на страницу отказа. Покрытие guard'ов обязательно.
- **Тест отмены**: смена фильтра порождает `AbortError` на предыдущем запросе, и он не показывается
  пользователю как ошибка.
- **Тест «один тост на действие»**: локальный `onError` переопределяет глобальный; проверяется
  счётчиком вызовов нотификаций.
- **E2E-сценарии на URL-состояние** (Playwright): применить фильтры → скопировать URL → открыть в
  новой вкладке → тот же экран; back/forward возвращают предыдущее состояние фильтров.
- **Шаг CI на регенерацию дерева маршрутов** с `git diff --exit-code` — забытая генерация
  `routeTree.gen.ts` блокирует PR.
