# ADR-0009 — E2EE-хранилище секретов с zero-knowledge иерархией ключей

## Контекст

Одна из заявленных функций Bad CRM — хранилище паролей и секретов команды: доступы к серверам
клиентов, API-ключи, учётные записи сервисов, приватные ключи. Это самые чувствительные данные во
всём продукте: их компрометация означает компрометацию инфраструктуры клиентов пользователя, а не
только его собственных данных.

Продукт **self-hosted**. Это радикально меняет модель угроз по сравнению с SaaS. У владельца
инсталляции есть root на хосте, дамп PostgreSQL, доступ к бэкапам и к дискам MinIO. Обычный ответ
SaaS-продуктов — «мы шифруем данные и не смотрим в них» — здесь не работает вообще: «мы» и
«владелец инсталляции» это разные люди, и второй имеет физический доступ ко всему.

Отсюда три продуктовых обещания, которые должны держаться на устройстве данных, а не на политике
доступа:

> Сервер не может прочитать секреты.
> Администратор организации не может прочитать личное хранилище сотрудника.
> Владелец инсталляции, имеющий root, дамп БД, бэкапы и диски, не может прочитать ни одно хранилище.

Дополнительные требования, вытекающие из командной работы: секретами нужно **делиться** (с
человеком, с командой, с проектом), доступ нужно **отзывать**, по хранилищу нужно **искать**, а
организация должна иметь способ не потерять общие секреты при увольнении единственного человека,
который их знал.

## Решение

**Сквозное шифрование по модели zero-knowledge: сервер хранит только шифротекст и метаданные,
ключевой материал существует исключительно в памяти вкладки браузера того человека, который ввёл
свой мастер-пароль.**

**Иерархия ключей** (полностью — в [`../../security/e2ee-design.md`](../../security/e2ee-design.md)):

```
мастер-пароль
  ├─ Argon2id(pwd, saltA) ──► MUK (Master Unlock Key, 32 B) — никогда не покидает браузер
  │     └─ XChaCha20-Poly1305 ──► encryptedPrivateKeys ──► privateKeysBundle
  │            └─ X25519 sk (обмен ключами) + Ed25519 seed (подписи)
  └─ Argon2id(pwd, saltB) ──► authVerifier — уходит на сервер, там хранится argon2id(authVerifier)

VaultKey (32 B, один на хранилище, версионируется keyVersion)
  ├─ crypto_box_seal(VaultKey, member.publicKeyX25519) ──► VaultMembership.wrappedVaultKey
  ├─ HKDF-SHA256(VaultKey, salt=vaultId) ──────────────► BlindIndexKey (неэкспортируемый CryptoKey)
  └─ ItemKey (32 B, СВОЙ НА КАЖДУЮ ВЕРСИЮ элемента)
        ├─ XChaCha20-Poly1305(ItemKey, VaultKey) ──────► VaultItem.itemKeyWrapped
        └─ XChaCha20-Poly1305(payload, ItemKey, AAD) ──► dataEnc / nameEnc
```

Ключевые свойства решения:

- **Два независимых прогона Argon2id** (`m = 64 MiB`, `t = 3`, `p = 1`) из одного пароля с разными
  солями. Один даёт MUK, второй — `authVerifier` для сервера. Один прогон с последующим
  HKDF-разделением был бы вдвое дешевле, но тогда ошибка в разделении домена мгновенно превращалась
  бы в утечку MUK.
- **Envelope-шаринг.** Доступ к хранилищу — это `VaultMembership.wrappedVaultKey`: `VaultKey`,
  запечатанный на публичный X25519-ключ участника и подписанный Ed25519-ключом выдающего. Сервер
  раздаёт конверты, но не может их открыть. Приглашение в хранилище выполняет **человек, у которого
  уже есть ключ**, а не сервер.
- **`ItemKey` на каждую версию элемента.** Отозванный участник, знавший старый `VaultKey`, не
  прочитает содержимое, добавленное после ротации.
- **Blind index для поиска.** HMAC-SHA-256 неэкспортируемым `CryptoKey`, выход усечён до 16 B.
  Поиск по точному совпадению нормализованного значения работает; подстрочный поиск — нет.
  Частотный анализ по blind-index'ам возможен и принят как остаточный риск.
- **Защита от downgrade.** Параметры KDF приходят с сервера, но клиент отвергает всё ниже жёстких
  порогов (`m < 64 MiB`, `t < 3`, `p != 1`, длина соли != 16), и те же параметры входят в **AAD**
  блоба приватных ключей. Свойство схемы: **клиента нельзя тихо понизить, его можно только сломать
  явно.**
- **Восстановление — только Recovery Kit** (128 бит энтропии, печатается при онбординге) либо
  **org escrow** для общих хранилищ (Shamir 2-of-3 по владельцам, с записью в `VaultAccessLog` и
  `AuditLog`). Забытый пароль без recovery-кита = безвозвратная потеря личного хранилища.

**Административный доступ явно исключён.** Для `Vault.kind = PERSONAL` не существует и не может быть
создана `VaultMembership` с `wrappedVaultKey` на кого-либо, кроме владельца. Org escrow — это
**дополнительное членство в общем хранилище**, opt-in, только для `SHARED` и `PROJECT`; это не
депонирование личных ключей. Владелец организации обходит ACL везде
([ADR-0008](0008-permission-model-rbac-plus-acl.md)) — **кроме vault**: там доступ определяется
наличием ключа, и никакое право ключ не заменяет.

**Библиотека — `libsodium-wrappers-sumo`** (ISC), единственная зависимость крипто-модуля. Даёт весь
нужный набор примитивов: `crypto_pwhash` (Argon2id), XChaCha20-Poly1305-IETF, `crypto_box_seal`,
Ed25519. **Размер — принятое осознанное исключение:** ~375 KB min+gzip против бюджета ленивого чанка
≤ 150 KB из `ux-architecture.md`. Целостность одной аудированной библиотеки с полным набором нужных
примитивов важнее ~200 KB перевеса. Перевес не влияет на первую загрузку: чанк
`units/vault/lib/crypto` грузится лениво, один раз, после разблокировки. У чанка **отдельная строка
в `size-limit`** с собственным порогом — он сознательно выведен из-под общего бюджета.

**Ограничение web-E2EE фиксируется явно, а не замалчивается.** Всё E2EE в браузере опирается на
допущение, что доставленный сервером JavaScript — тот, который мы написали. Для веб-страницы это
допущение **непроверяемо в общем случае**: сервер может отдать одному пользователю в один день
модифицированный бандл, который отправит мастер-пароль наружу. Мы не решаем эту проблему, мы её
уменьшаем: воспроизводимые сборки с публикацией SHA-256 бандла, Subresource Integrity, отсутствие
внешних CDN (`connect-src 'self'`), изолированный крипто-модуль без сетевых вызовов (проверяется
архитектурным тестом), жёсткий CSP, AGPL как правовой рычаг, desktop-обёртка (Tauri) в backlog как
единственный способ закрыть вектор по-настоящему.

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **Серверное шифрование ключом инсталляции + KMS/Vault** | Восстановление доступа возможно всегда; полнотекстовый поиск по секретам работает; шаринг тривиален (сервер перешифровывает); нет проблемы забытого мастер-пароля; ротация ключей централизована; нет ограничения web-E2EE | Дамп БД плюс доступ к ключу = все секреты открытым текстом; для self-host владелец инсталляции имеет и то, и другое, то есть обещание «владелец не может прочитать» становится ложным; администратор организации технически читает личные хранилища | Прямо противоречит трём продуктовым обещаниям. В self-host модели «доверенный сервер» не существует: сервер и есть потенциальный противник |
| **Гибрид: E2EE для личных, серверное шифрование для общих** | Общие секреты восстановимы администратором; проще онбординг новых участников; меньше поддержки | Два разных режима безопасности в одном UI — пользователь неизбежно перепутает, где какой; фраза «мы шифруем end-to-end» становится наполовину неверной; общие хранилища содержат самое ценное (доступы к инфраструктуре клиентов) | Ровно то место, где компромисс дороже всего: общие хранилища — главная цель атакующего. Задачу «не потерять общие секреты» решает org escrow с порогом хранителей, не отказываясь от E2EE |
| **Хранение под ACL без шифрования** (как обычные данные) | Простейшая реализация; поиск, шаринг, восстановление — тривиальны; ноль криптографической сложности | Дамп БД, бэкап или снапшот диска раскрывают всё; любая SQL-инъекция или ошибка в правах = утечка учётных данных клиентов | Неприемлемо для класса данных. Секреты в открытом виде в БД — это не «слабое место», а отсутствие продукта |
| **Внешний менеджер паролей** (интеграция с 1Password / Bitwarden / Vaultwarden) | Готовая, аудированная реализация; не нужно писать криптографию; пользователи уже доверяют этим продуктам; есть мобильные и desktop-клиенты | Обязательная внешняя зависимость (или второй контейнер) для self-host — противоречит «одной команде»; связь «секрет ↔ проект/задача/клиент» теряется или требует хрупкой синхронизации; проприетарные варианты несовместимы с AGPL по духу продукта; интеграция с Bitwarden-сервером всё равно требует своего слоя ключей | Продуктовая ценность именно в том, что секрет связан с проектом, задачей и клиентом и виден в одном рабочем месте. Внешний менеджер эту связь не даёт |
| **WebCrypto + `@noble/*` + `hash-wasm` вместо libsodium** | Единицы KB вместо 375 KB; библиотеки аудированы (MIT); WebCrypto даёт неэкспортируемые ключи | Набор примитивов другой: нет `crypto_box_seal` (sealed box пришлось бы собирать из X25519 + AEAD вручную), нет единой реализации Argon2id, часть операций пришлось бы комбинировать самостоятельно; каждая самостоятельная композиция примитивов — новая поверхность для ошибки | Отклонено сознательно и зафиксировано, чтобы не возвращаться «заодно»: переход меняет набор примитивов и требует переписывания всей спецификации `e2ee-design.md`. Целостность одной аудированной библиотеки важнее размера чанка, который грузится лениво один раз |
| **Пароль от vault = пароль от аккаунта** | Один пароль, проще UX, нет отдельного unlock-экрана | Сброс пароля аккаунта (обычная операция поддержки) означал бы потерю всего хранилища либо депонирование ключа на сервере, что разрушает модель | Разделение обязательно: сброс пароля аккаунта не должен трогать криптографию хранилища |

## Последствия

### Положительные

- **Дамп БД, бэкап и снапшот диска не раскрывают ни одного секрета.** Это проверяемое свойство
  данных, а не обещание.
- **Администратор организации не читает личные хранилища** — не «не должен», а не может: конверта
  на его ключ не существует.
- **Компрометация сервера не даёт секретов.** Максимум — метаданные и возможность подменить будущий
  фронтенд (что отдельно зафиксировано как оставшийся вектор).
- **Отзыв доступа криптографически осмыслен**: ротация `VaultKey` + новые `ItemKey` делают
  недоступным всё добавленное после отзыва.
- **Подмена или перестановка шифротекста сервером обнаруживается** — все шифротексты
  аутентифицированы (Poly1305) и привязаны к контексту через AAD.
- **Понижение параметров KDF не проходит незаметно** — пороги в бандле плюс параметры в AAD.
- **Org escrow решает проблему «уволился единственный, кто знал»** для общих хранилищ, не открывая
  доступ к личным и требуя порога хранителей плюс запись в аудит.

### Отрицательные / цена

- **Забытый мастер-пароль без Recovery Kit = безвозвратная потеря личного хранилища.** Поддержка
  ничем не поможет. Это цена, а не дефект, и она должна быть проговорена в онбординге.
- **Поиск ограничен blind index'ом**: только точное совпадение нормализованного значения, никакого
  подстрочного поиска и никакой сортировки по содержимому.
- **Шаринг требует участия человека с ключом.** Нельзя «добавить сотрудника в хранилище» из
  админки — конверт должен выпустить тот, у кого есть `VaultKey`.
- **Разблокировка стоит 1–2.5 с** (два прогона Argon2id по 64 MiB) и заметна на слабых устройствах.
- **Метаданные видны серверу**: количество элементов, структура папок, времена изменений, граф «кто
  с кем делится». Принято осознанно.
- **Rollback-атака сервером возможна**: сервер может отдать более старую, но валидную версию
  элемента; независимого якоря актуальности у клиента нет.
- **Успешный XSS на разблокированной вкладке = полная компрометация хранилища этого пользователя.**
  Отсюда жёсткий CSP и изоляция крипто-модуля как обязательные, а не желательные меры.
- **Крипто-код требует особой дисциплины**: ключи только `Uint8Array`, никогда `string`; ключи не
  попадают в zustand, TanStack Query cache, React state, `postMessage`, `localStorage`, IndexedDB;
  `sodium.memzero` в `finally`. Честная оговорка: JS-рантайм может оставить копии после GC —
  гарантии стирания нет, есть добросовестное усилие.
- **375 KB крипто-чанка** — перевес над общим бюджетом, выведенный в отдельный порог `size-limit`.

### Что становится трудно изменить позже

Это самый необратимый ADR набора: он определяет форму данных, которые **невозможно перечитать без
участия пользователя**.

- **Смена алгоритма или параметров KDF требует участия каждого пользователя.** Сервер не может
  перешифровать `encryptedPrivateKeys` — у него нет MUK. Миграция возможна только как «при
  следующей разблокировке клиент перевыводит ключи и перезаписывает блоб», растянутая на месяцы, с
  поддержкой обоих `algoVersion` всё это время.
- **Смена схемы шифротекста** (формат, AAD, порядок полей) требует поддержки старого формата вечно
  либо ленивой перезаписи каждого элемента при следующем открытии его владельцем.
- **Отказ от libsodium** означает переписывание спецификации и повторную миграцию всех блобов —
  дважды через тот же болезненный процесс. Поэтому альтернатива на `@noble/*` зафиксирована как
  отклонённая явно, а не оставлена «на подумать».
- **Обещание «администратор не читает личные хранилища» необратимо в обе стороны.** Добавить
  административный доступ позже нельзя технически (ключей нет) и нельзя продуктово (это отзыв
  публичного обещания в open-source-проекте, который читают по исходникам).
- **Blind index задаёт границы поиска навсегда** для уже созданных элементов: смена схемы
  нормализации требует переиндексации на клиенте у каждого владельца ключа.
- **Иерархия «vault → item → версия»** зашита в модель данных, в шаринг, в отзыв и в аудит.
  Например, отказ от `ItemKey` на версию ради экономии сломал бы гарантию отзыва.
- **Исключение vault из обхода owner'ом** — не настройка, а следствие криптографии; его нельзя
  «включить» без разрушения всей модели.

## Проверяемость

- **Архитектурный тест изоляции крипто-модуля** (обязателен): граф импортов `units/vault/lib/crypto`
  содержит только `libsodium-wrappers-sumo`; в модуле отсутствуют `fetch`, `XMLHttpRequest`,
  `WebSocket`, `navigator.sendBeacon`, импорты HTTP-клиента и любых сторов. Нарушение ломает сборку.
- **Тест «ключи не покидают модуль»**: статическая проверка, что типы ключевого материала не
  экспортируются из barrel'а `crypto`, и запрет `structuredClone`/`postMessage`/`localStorage`/
  `sessionStorage`/`indexedDB` в файлах модуля.
- **Тесты downgrade-защиты**: клиент отвергает `kdfParams` ниже порогов (`m`, `t`, `p`, длина соли,
  неизвестный `algoVersion`); подмена любого параметра ломает расшифровку блоба через AAD.
- **Тест «сервер не хранит запрещённого»**: интеграционный тест проверяет, что в ответах API и в
  таблицах `Vault*` отсутствуют поля с открытым ключевым материалом; отдельный тест на схему БД —
  список колонок хранилища сверяется с allow-list из спецификации.
- **Тест «PERSONAL vault не имеет чужих membership»**: доменный инвариант плюс ограничение БД;
  попытка создать `VaultMembership` на чужого для `kind = PERSONAL` отклоняется.
- **Тест отзыва**: после отзыва и ротации старый `VaultKey` не расшифровывает новые элементы;
  проверяется на уровне крипто-модуля без сервера.
- **Известные векторы (KAT)** для XChaCha20-Poly1305, Argon2id, HKDF, Ed25519 — регрессия при
  обновлении libsodium ловится сразу.
- **`size-limit` с отдельной строкой** для чанка `units/vault/lib/crypto`; рост сверх собственного
  порога ломает сборку.
- **Воспроизводимость сборки**: шаг CI собирает бандл дважды и сравнивает SHA-256; хеши публикуются
  в GitHub Release.
- **Проверка CSP и SRI** в e2e: `index.html` содержит `integrity` на всех скриптах, `connect-src`
  ограничен `'self'`, внешних origin нет.
- Гейт-агент `security-auditor` (правила проекта) обязателен для любого PR, трогающего
  `units/vault/**` или серверные таблицы хранилища.
