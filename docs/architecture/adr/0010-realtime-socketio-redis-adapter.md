# ADR-0010 — Realtime на Socket.IO с Redis Streams adapter

## Контекст

Несколько подсистем Bad CRM требуют доставки событий в браузер без опроса:

- **чат** — сообщения, индикатор набора текста, прочтения, реакции;
- **канбан** — перемещение карточки другим участником видно немедленно;
- **документы и база знаний** — «эту страницу сейчас редактирует N»;
- **нотификации** — счётчик непрочитанного и всплывающие уведомления;
- **тайм-трекинг** — активный таймер, запущенный на другом устройстве;
- **CI-статусы** — результат GitHub Actions;
- **presence** — кто онлайн.

Ограничения задаются моделью развёртывания ([ADR-0020](0020-self-host-packaging-docker.md)):

1. **Типовая инсталляция — один VPS с docker compose.** Всё, что требует отдельного сервиса с
   собственной конфигурацией, кластером и мониторингом, увеличивает порог входа.
2. **Redis уже есть** — он нужен для BullMQ, rate-limit и ревокации сессий. Использовать то, что
   уже в compose, дешевле, чем добавить новое.
3. **Корпоративные прокси** у части пользователей режут WebSocket. Полный отказ от HTTP-fallback
   означает, что для этих людей продукт частично не работает.
4. **Профиль `scaled`** предполагает несколько экземпляров API за reverse-proxy — значит нужен
   fan-out между процессами.

Отдельное архитектурное решение, влияющее на выбор: **realtime — транспорт уведомлений о фактах, а
не источник истины.** Клиент на событие инвалидирует соответствующий query-key TanStack Query
([ADR-0007](0007-tanstack-router-and-query.md)); расхождение лечится обычным рефетчем. Это
означает, что гарантия доставки может быть слабой: потерянное событие приводит к устаревшим данным
на экране до следующего рефетча, а не к потере данных.

Наконец, события порождает не только HTTP-процесс, но и воркер, обрабатывающий outbox
([ADR-0021](0021-transactional-outbox.md)) — а он сокетов не держит.

## Решение

**Socket.IO 4.x + `@socket.io/redis-streams-adapter`. Socket.IO работает в том же процессе, что и
API.**

**Комнаты строго вида `org:{orgId}:{resource}:{resourceId}`.** Имя комнаты формирует сервер из
проверенных данных; клиент не может «сам зайти» в комнату. Запрос на подписку проходит **ту же
policy-проверку**, что и HTTP-чтение ресурса ([ADR-0008](0008-permission-model-rbac-plus-acl.md)).
Префикс с `orgId` делает межарендаторную утечку через realtime невозможной по построению — это
аналог RLS для канала событий.

**Handshake-авторизация.** Токен передаётся в `handshake.auth` и проверяется тем же кодом, что и
HTTP-middleware. Неавторизованное соединение закрывается до `connect`. Токен не передаётся в
query-строке — иначе он оседает в логах reverse-proxy.

**Fan-out между экземплярами — `@socket.io/redis-streams-adapter`.** Воркер публикует события в тот
же Redis-стрим, поэтому не обязан держать сокеты: он пишет в стрим, а любой API-процесс,
подключённый к нужной комнате, доставит событие. Redis Streams выбран вместо классического pub/sub
адаптера сознательно: pub/sub теряет сообщения при разрыве подписки, стрим — переживает
кратковременный рестарт потребителя.

**Presence** — ключи в Redis с TTL и heartbeat от клиента. При обрыве соединения запись истекает
сама; «зависших онлайн» после падения экземпляра не бывает.

**Socket.IO в процессе API, а не отдельным сервисом.** Это осознанный выбор в пользу простоты
развёртывания: один образ, одна роль `ROLE=api`, никакой дополнительной сетевой конфигурации.
Разделение возможно позже без изменения кода — событие всё равно публикуется через Redis.

**Sticky sessions** нужны, пока разрешён HTTP long-polling fallback: рукопожатие и последующие
polling-запросы должны попадать в один экземпляр. Включаются по cookie/ip-hash на `/socket.io` в
reverse-proxy. Альтернатива — форсировать `transports: ['websocket']` и отказаться от fallback; по
умолчанию так не делаем из-за корпоративных прокси.

**Контракт событий**: событие несёт тип, идентификаторы и версию, но **не полезную нагрузку
документа**. Клиент по событию инвалидирует query-key и перезапрашивает данные через обычный API,
где действуют RLS и policy. Следствие: даже ошибочно доставленное событие не раскрывает содержимое.

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **Нативный WebSocket (`ws`)** | Минимум зависимостей и накладных расходов; полный контроль над протоколом; меньше трафика на сообщение; нет проприетарного handshake | Комнаты, переподключение с backoff, ack, heartbeat, мультиплексирование и fan-out между процессами пишутся руками — это и есть Socket.IO, только без тестов; нет fallback для сетей, режущих WebSocket; собственный протокол придётся документировать и версионировать | Мы бы реализовали подмножество Socket.IO хуже и дороже. Экономия трафика несущественна при нашем объёме событий |
| **Server-Sent Events (SSE)** | Предельно просто; работает поверх обычного HTTP и проходит почти любой прокси; автоматическое переподключение в браузере; отличный fit для «сервер → клиент» | Только односторонний канал: индикатор набора текста, подписка на комнату и ack требуют отдельных HTTP-запросов; лимит одновременных соединений на домен в HTTP/1.1 болезненный (несколько вкладок исчерпывают его); нет встроенных комнат | Чат с двусторонним взаимодействием и presence на SSE превращается в гибрид SSE + POST, то есть в собственный протокол. SSE остаётся правильным выбором для AI-стриминга — там он и используется ([ADR-0014](0014-ai-provider-abstraction.md)) |
| **Long-polling** | Работает везде без исключений | Задержка и накладные расходы на каждое сообщение; высокая нагрузка на сервер при десятках соединений | Оставлен как **fallback** внутри Socket.IO, но не как основной транспорт |
| **Centrifugo** | Специализированный сервер realtime; отличная производительность; готовые presence, история каналов, JWT-авторизация; снимает нагрузку с Node | Ещё один контейнер и ещё одна конфигурация в compose; авторизация подписки требует webhook-обращения обратно в приложение либо дублирования логики прав в токенах — а наша модель прав нетривиальна (конъюнкция capability и ACL); отдельная точка отказа и отдельный мониторинг | Противоречит цели «одна команда до рабочего экземпляра». Плюс дублирование модели прав в конфигурации внешнего сервиса — источник расхождения между тем, что разрешает API, и тем, что разрешает канал |
| **Pusher / Ably / другой SaaS** | Ноль эксплуатации; масштабирование и глобальная доставка из коробки; отличные SDK | Внешняя зависимость и передача метаданных третьей стороне — неприемлемо для self-hosted продукта, часть которого посвящена тому, что данные не покидают инсталляцию; платно; продукт перестаёт работать без интернета | Прямое противоречие модели поставки и обещаниям продукта |
| **Socket.IO с классическим Redis pub/sub adapter** | Проще, меньше памяти в Redis, давно используется | Pub/sub не буферизует: события, отправленные в момент разрыва подписки экземпляра (рестарт, сетевой сбой), теряются безвозвратно | Streams-адаптер переживает кратковременный рестарт потребителя. Для событий, часть которых порождает воркер, это заметно надёжнее при сопоставимой сложности |
| **Отдельный realtime-сервис** (свой процесс/контейнер) | Изоляция нагрузки; независимое масштабирование; рестарт API не рвёт сокеты | Дополнительная роль в compose, дополнительная конфигурация, дублирование кода авторизации | Преждевременно для целевого масштаба. Публикация через Redis сохраняет возможность выделить сервис позже без переписывания |
| **Только поллинг из TanStack Query** (`refetchInterval`) | Ноль дополнительной инфраструктуры; предельная простота; никаких проблем с прокси и sticky sessions | Задержка в секунды и постоянная фоновая нагрузка на API и БД; чат на поллинге неприемлем по UX | Годится как аварийная деградация, но не как основной механизм для чата и presence |

## Последствия

### Положительные

- **Комнаты, переподключение, ack и fallback — из коробки**, включая клиентскую библиотеку.
- **Работает у пользователей за прокси, режущими WebSocket** — благодаря polling-fallback.
- **Fan-out между экземплярами без нового сервиса** — используется уже имеющийся Redis.
- **Воркер публикует события, не держа сокетов**: outbox-обработчик пишет в стрим.
- **Изоляция арендаторов по построению** — `orgId` в имени каждой комнаты.
- **Realtime не является источником истины**, поэтому потеря события деградирует до устаревших
  данных, а не до потери данных. Это резко снижает требования к гарантиям доставки.
- **События не содержат полезной нагрузки** — ошибочная доставка не раскрывает содержимое.
- **Presence самоочищается** через TTL, без «призраков» после падения экземпляра.

### Отрицательные / цена

- **Sticky sessions в reverse-proxy** — требование к развёртыванию, о котором владелец инсталляции
  должен знать. Забытая настройка даёт трудноуловимые обрывы при polling-fallback.
- **Socket.IO — не стандартный WebSocket.** Подключиться сторонним клиентом (скрипт, мобильное
  приложение на другом стеке) можно только через SDK Socket.IO.
- **Накладные расходы протокола** (собственный handshake, служебные пакеты) выше, чем у голого `ws`.
- **Соединения занимают память процесса API**: рестарт API рвёт все сокеты, клиенты
  переподключаются одновременно (thundering herd), что требует джиттера в backoff.
- **Redis становится критичнее**: его недоступность рвёт fan-out между экземплярами. Смягчается
  тем, что realtime не источник истины.
- **Redis Streams требуют настройки обрезки** (`MAXLEN`), иначе стрим растёт неограниченно.
- **Двойная проверка прав** — при подписке и при последующем HTTP-запросе. Дублирование по
  построению, но необходимое.

### Что становится трудно изменить позже

- **Схема имён комнат `org:{orgId}:{resource}:{resourceId}`** становится внутренним контрактом между
  API, воркером и клиентом. Её изменение требует одновременного обновления всех трёх — а при
  rolling-обновлении в профиле `scaled` какое-то время сосуществуют старая и новая схемы, и события
  не доходят.
- **Клиентский SDK Socket.IO** попадает в бандл и в код всех подписок; уход на нативный WebSocket
  означает переписывание клиентского realtime-слоя целиком плюс собственный протокол.
- **Sticky sessions** попадают в инструкции по развёртыванию, уже выполненные на чужих серверах.
  Отказ от них (переход на `transports: ['websocket']`) — ломающее изменение требований к
  инсталляции.
- **Контракт событий** (имена типов, набор полей) потребляется клиентом и потенциально внешними
  интеграциями; смена имён требует версионирования.
- **Решение «Socket.IO в процессе API»** влияет на профиль масштабирования: пока сокеты живут в
  API-процессе, число экземпляров API определяется числом соединений, а не нагрузкой на CPU.

## Проверяемость

- **Тест авторизации handshake**: соединение без валидного токена закрывается до `connect`;
  соединение с токеном чужой организации не получает ни одной комнаты.
- **Тест изоляции комнат**: пользователь организации A не может подписаться на комнату
  `org:B:...` — попытка отклоняется той же policy, что и HTTP-чтение; проверяется автотестом на
  каждый тип ресурса.
- **Тест «клиент не выбирает имя комнаты»**: имя формируется сервером; попытка передать
  произвольную строку игнорируется. Проверяется контрактным тестом обработчика подписки.
- **Тест fan-out между экземплярами** (интеграционный, Testcontainers с Redis): событие,
  опубликованное экземпляром A (или воркером), доходит до клиента, подключённого к экземпляру B.
- **Тест «событие не содержит полезной нагрузки»**: схема события валидируется — допустимы только
  идентификаторы, тип и версия; тело документа/сообщения запрещено. Нарушение ломает тест.
- **Тест presence-TTL**: после разрыва соединения запись присутствия исчезает в пределах порога;
  «зависший онлайн» не воспроизводится.
- **E2E-сценарий двух браузеров** (Playwright): действие в одной сессии отражается в другой без
  ручного обновления; проверяется для чата, канбана и счётчика уведомлений.
- **Проверка обрезки стримов**: конфигурация адаптера задаёт `MAXLEN`; тест конфигурации падает при
  его отсутствии.
- Гейт-агент `production-readiness` (правила проекта) проверяет требование sticky sessions в
  документации по развёртыванию при изменениях realtime-слоя.
