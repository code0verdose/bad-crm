# ADR-0012 — Редактор документов BlockNote, контент как один JSONB

## Контекст

Bad CRM содержит два разных продукта работы с текстом, и их намеренно **не** объединяют:

- **Документы (Notion-like)** — структурированный блочный документ, редактируемый в WYSIWYG:
  заголовки, списки, таблицы, callout, вложенные страницы, упоминания, встроенные задачи и файлы.
  Настоящий ADR — про них.
- **База знаний (Obsidian-like)** — markdown-файлы, приезжающие из git или Obsidian-вольта и
  уезжающие обратно байт-в-байт. Про них — [ADR-0013](0013-kb-markdown-source-of-truth.md).

Общая таблица заставила бы одну из сторон жить в чужом формате, поэтому решения приняты раздельно.

Требования к редактору документов:

- **Блочная структура нужна не для красоты**, а функционально: комментарии привязываются к блоку,
  ссылки — к якорю внутри страницы, частичные обновления и версии считаются по блокам.
- **WYSIWYG обязателен.** Аудитория документов — не только разработчики: менеджеры, клиентские
  менеджеры, HR (онбординг). Markdown-разметка в поле ввода для них барьер.
- **Экспорт в Markdown нужен с первого дня.** Продукт под AGPL обещает переносимость данных
  пользователя; «ваши документы можно забрать» — часть этого обещания, а не фича на будущее.
- **Тематизация должна совпадать с остальным UI** — токены Mantine
  ([ADR-0006](0006-mantine-css-modules-no-tailwind.md)), включая тёмную тему.
- **Лицензия каждой подключаемой части проверяется** — политика зависимостей
  ([ADR-0018](0018-license-agpl-3.md)) запрещает несовместимое с AGPL.

Отдельный, более важный вопрос — **как хранить контент**: одним JSON-документом или таблицей блоков.
Notion-подобный редактор соблазняет смоделировать каждый блок строкой в БД
(`Block` с `parentBlockId` и `orderKey`).

## Решение

**Редактор — BlockNote. Контент документа хранится как один JSONB в `DocPage.content`. Экспорт в
Markdown реализуется с первого релиза функции.**

**Почему один JSONB, а не таблица блоков:**

- Документ **всегда читается и сохраняется целиком** — это единица консистентности редактора.
  Таблица блоков означает 200 строк на чтение одной страницы и рекурсивный CTE вместо одного
  `SELECT`.
- Undo/redo и версионирование естественно ложатся на снапшот документа (`DocPageVersion` с полем
  `content Json`), а не на дифф по сотням строк.
- Цена — невозможность сослаться на конкретный блок из другой таблицы средствами FK и отсутствие
  построчных прав. Первое решается **стабильными `id` внутри JSON** (якоря для комментариев и
  ссылок), второе не входит в скоуп продукта.

**Модель данных** (подробно — в [`../data-model.md`](../data-model.md), раздел 5):

| Сущность | Ключевые поля |
|---|---|
| `DocPage` | `title`, `icon`, `content Json` (весь документ), `parentPageId?`, `path` (materialized path), `depth`, `orderKey`, `projectId?`, `publishedAt?`, `deletedAt?` |
| `DocPageVersion` | `docPageId`, `version`, `content Json`, `authorId`, `changeSummary` |

Дерево страниц — materialized path (`.uuid1.uuid2.`), поддерево берётся одним
`WHERE path LIKE '.uuid1.%'` без рекурсии.

**Конкурентное редактирование — оптимистическая блокировка с версиями**, не CRDT. Одновременное
посимвольное редактирование сознательно исключено из скоупа (см. «Что осознанно НЕ делаем сейчас» в
[`../overview.md`](../overview.md)): для команды из 5–20 человек блочные документы с версиями
закрывают реальный сценарий, а CRDT требует отдельного слоя синхронизации и хранения истории
операций.

**Экспорт в Markdown — с первого дня**, а не «когда попросят». BlockNote предоставляет
преобразование блочного JSON в Markdown; экспорт покрывается тестами round-trip там, где
преобразование обратимо, и явным списком «что теряется» там, где нет (например, специфичные
callout-блоки деградируют в цитаты). Это делает JSON-формат не ловушкой, а внутренним
представлением.

### Лицензии подключённых пакетов BlockNote

**Ядро — MPL-2.0** (в allow-list, совместимо с AGPL-3.0):

| Пакет | Лицензия | Статус |
|---|---|---|
| `@blocknote/core` | MPL-2.0 | подключён |
| `@blocknote/react` | MPL-2.0 | подключён |
| `@blocknote/mantine` | MPL-2.0 | подключён (тематизация токенами Mantine) |

**Пакеты `@blocknote/xl-*` дуально лицензированы GPL-3.0 / коммерческая.** Для нашего
AGPL-3.0-проекта применима ветка **GPL-3.0** — использование допускается (GPL-3.0 совместима с
AGPL-3.0), но требует явной фиксации. **Правило: каждый подключённый `xl`-пакет фиксируется в этой
таблице с указанием лицензии и причины подключения. Подключение `xl`-пакета без строки в таблице —
нарушение политики зависимостей.**

| `xl`-пакет | Лицензия | Подключён | Примечание |
|---|---|---|---|
| `@blocknote/xl-multi-column` | GPL-3.0 / commercial | нет | подключать только при явной продуктовой необходимости |
| `@blocknote/xl-docx-exporter` | GPL-3.0 / commercial | нет | экспорт в DOCX — вне скоупа MVP |
| `@blocknote/xl-pdf-exporter` | GPL-3.0 / commercial | нет | экспорт в PDF — вне скоупа MVP |
| `@blocknote/xl-ai` | GPL-3.0 / commercial | нет | AI-функции реализуются через собственный `AIProviderPort` ([ADR-0014](0014-ai-provider-abstraction.md)) |

Последствие выбора ветки GPL-3.0: коммерческое суб-лицензирование продукта под несвободной
лицензией становится невозможным. Для AGPL-проекта это не ограничение, а согласованность.

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **TipTap напрямую (ProseMirror)** | Максимальная гибкость и контроль над схемой документа; огромная экосистема расширений; можно построить ровно тот редактор, который нужен; MIT-ядро | Блочный UX (drag-handle блоков, вложенные блоки, slash-меню, боковая панель) собирается вручную — это и есть то, что BlockNote уже сделал поверх TipTap; больше кода на поддержке; часть коллаборативных расширений TipTap платные | BlockNote — это TipTap с уже собранным блочным UX. Мы получаем гибкость ProseMirror под капотом (BlockNote на нём и построен) без месяцев работы над UI блоков |
| **Plate (Slate)** | Богатая экосистема плагинов; хорошая интеграция с shadcn/Tailwind; гибкая модель документа | Slate исторически имеет проблемы со стабильностью выделения и IME (ввод иероглифов, автозамена на мобильных); интеграция ориентирована на Tailwind, которого у нас нет ([ADR-0006](0006-mantine-css-modules-no-tailwind.md)); больше ручной сборки | Стабильность редактирования — базовое требование для инструмента, в котором пишут ежедневно. Плюс стилевая экосистема не наша |
| **Lexical (Meta)** | Отличная производительность на больших документах; хорошая a11y; активно развивается; MIT | Требует значительно больше кода для блочного UX; экосистема готовых блоков меньше; модель документа менее «блочная» по своей природе — вложенные блоки и drag-handle придётся строить | Тот же аргумент, что и с TipTap, но с меньшей экосистемой готовых решений |
| **Собственный редактор** | Полный контроль | Годы работы; редактор — одна из самых сложных клиентских задач (выделение, IME, undo/redo, буфер обмена, вставка из Word) | Несоразмерно ресурсам и не создаёт продуктовой ценности |
| **Markdown-редактор и для документов тоже** (единый формат с базой знаний) | Один формат на весь продукт; переносимость по определению; простая модель хранения; git-friendly | Markdown не выражает блочную структуру с якорями, вложенными базами данных, встроенными задачами и callout'ами; WYSIWYG поверх markdown — компромисс, теряющий и то, и другое; аудитория документов не техническая | Два разных продукта с разными аудиториями. Попытка свести их к одному формату ухудшила бы оба (см. ADR-0013 — там markdown правильный выбор именно потому, что там другие требования) |
| **Хранение HTML** | Универсально, легко отобразить где угодно | Структура теряется: невозможно надёжно вытащить «третий блок» или программно изменить документ; санитизация становится постоянной задачей безопасности; диффы нечитаемы | HTML — формат представления, а не хранения структурированного документа |
| **Таблица блоков** (`Block` со `parentBlockId` и `orderKey`) | Настоящие FK на блок — комментарии и ссылки ссылаются реляционно; построчные права теоретически возможны; частичное обновление одного блока — один `UPDATE`; диффы версий по блокам | 200 строк на чтение одной страницы; рекурсивный CTE вместо `SELECT`; версионирование превращается в дифф по сотням строк; каждая операция редактора (перенос блока в другой родитель) — транзакция с пересчётом порядка | Документ читается и сохраняется целиком — это единица консистентности редактора. Таблица блоков платит на самом частом пути (открытие страницы) за возможности, которые нужны редко. Решение помечено как подлежащее пересмотру при переходе на CRDT |
| **CRDT (Yjs) с первого дня** | Настоящее одновременное редактирование; офлайн-режим; отсутствие конфликтов | Отдельный слой синхронизации, хранение истории операций, рост объёма документа, сложность отладки; требует постоянного WebSocket-канала на документ | Явно вынесено за скоуп. Оптимистическая блокировка с версиями закрывает сценарий команды из 5–20 человек |

## Последствия

### Положительные

- **Открытие документа — один `SELECT`.** Самый частый путь остаётся дешёвым.
- **Версионирование тривиально**: снапшот в `DocPageVersion`, сравнение — дифф двух JSON.
- **Блочный UX получен готовым**: drag-handle, slash-меню, вложенные блоки, боковая панель.
- **Тематизация совпадает с остальным UI** через `@blocknote/mantine` и токены темы.
- **Экспорт в Markdown с первого дня** делает формат не ловушкой: пользователь может забрать
  документы.
- **Якоря на блоки внутри JSON** дают комментарии и ссылки на фрагмент без реляционной модели
  блоков.
- **Лицензионная чистота проверяема**: ядро MPL-2.0, каждый `xl`-пакет — строкой в таблице этого
  ADR.

### Отрицательные / цена

- **Нельзя обновить один блок частично** — сохраняется весь документ. При больших страницах это
  трафик и риск потери при конкурентной записи (снимается версионированием).
- **Нет FK на блок.** Комментарий ссылается на `blockId` внутри JSON; целостность держится
  use-case'ом и джобом-сверкой, а не базой.
- **Нет построчных прав.** Права — на уровне страницы (`ResourceAcl` с типом `DOC_PAGE`).
- **JSONB-схема — недокументированный контракт.** Формат задаётся BlockNote; его изменение при
  обновлении библиотеки затрагивает все сохранённые документы.
- **Поиск по содержимому требует извлечения текста из JSON** для индексации
  ([ADR-0011](0011-meilisearch-permission-aware-search.md)) — отдельный преобразователь, который
  нужно поддерживать при добавлении новых типов блоков.
- **Привязка к BlockNote в формате данных**, а не только в UI-слое.
- **Ветка GPL-3.0 у `xl`-пакетов** исключает возможность коммерческого суб-лицензирования продукта
  (для AGPL-проекта это согласованно, но должно быть осознано).

### Что становится трудно изменить позже

- **Формат контента — это данные пользователей на чужих инсталляциях.** Смена редактора требует
  конвертера JSON → новый формат, который придётся прогнать на всех документах при миграции. Ошибка
  конвертера означает повреждение содержимого, которое владелец инсталляции заметит не сразу.
- **Схема блоков BlockNote становится де-факто нашим форматом хранения.** Мажорное обновление
  библиотеки, меняющее схему, требует миграции всех `DocPage.content` и всех `DocPageVersion.content`
  — включая исторические версии, которые нельзя «пересохранить» из редактора.
- **Переход на таблицу блоков** после накопления документов — это разбор каждого JSON на строки с
  восстановлением порядка и вложенности, плюс переписывание всех запросов и редакторского слоя.
  Решение сознательно помечено как подлежащее пересмотру при переходе на CRDT, но пересмотр будет
  дорогим.
- **Стабильные `id` блоков внутри JSON** становятся точками привязки комментариев, ссылок и
  якорей URL. Любая операция, регенерирующая id (неаккуратная миграция, копирование документа),
  «отвязывает» комментарии без сообщения об ошибке.
- **Отсутствие CRDT** зафиксировано в модели хранения: добавление одновременного редактирования
  позже потребует и нового слоя синхронизации, и пересмотра единицы консистентности (документ
  целиком перестанет ею быть).
- **Таблица `xl`-пакетов** — часть лицензионного соответствия проекта. Подключённый и не
  зафиксированный `xl`-пакет создаёт незадокументированное GPL-обязательство.

## Проверяемость

- **Тест round-trip экспорта в Markdown**: набор эталонных документов экспортируется и
  импортируется обратно; для обратимых конструкций — совпадение, для необратимых — соответствие
  явному списку деградаций в тесте. Изменение списка требует правки теста, то есть видно на ревью.
- **Тест стабильности `id` блоков**: сохранение и повторное открытие документа не меняет
  идентификаторы блоков; копирование страницы генерирует новые id и переносит привязки корректно.
- **Тест извлечения текста для индексации**: для каждого поддерживаемого типа блока преобразователь
  «JSON → plain text» покрыт тестом; новый тип блока без теста ломает сборку (проверяется по
  перечислению типов схемы).
- **Тест версионирования**: сохранение создаёт `DocPageVersion`; откат к версии восстанавливает
  контент побайтно.
- **Тест оптимистической блокировки**: конкурентное сохранение с устаревшей версией отклоняется с
  внятной ошибкой, а не перезаписывает чужие изменения.
- **Лицензионный гейт**: `license-checker` с allow-list в CI; отдельный шаг проверяет, что каждый
  установленный пакет `@blocknote/xl-*` присутствует в таблице этого ADR — расхождение ломает
  сборку. Это и есть механизм принуждения к правилу «каждый `xl`-пакет фиксируется здесь».
- **`size-limit` на чанк редактора** — редактор грузится лениво вместе с маршрутом документов.
- Гейт-агент `production-readiness` (правила проекта) — при обновлении мажорной версии BlockNote
  обязателен план миграции контента.
