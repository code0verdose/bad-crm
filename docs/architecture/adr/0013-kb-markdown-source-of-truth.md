# ADR-0013 — База знаний: чистый Markdown как источник истины

## Контекст

База знаний Bad CRM — Obsidian-подобный раздел: заметки со ссылками друг на друга, граф связей,
теги, пространства (spaces). Целевой сценарий взят из практики команд разработки: инженерная
документация уже существует и живёт в двух местах — **в git-репозитории** (`docs/`, ADR, runbooks)
и **в Obsidian-вольте** отдельных людей. Обе формы — обычные `.md`-файлы с frontmatter и
wiki-ссылками.

Отсюда требования, которых нет у Notion-подобных документов
([ADR-0012](0012-docs-editor-blocknote-json-content.md)):

1. **Импорт из существующего вольта или репозитория должен работать без потерь.** Не «мы прочитаем
   ваш markdown и превратим в свой формат», а «файлы остаются файлами».
2. **Экспорт должен возвращать то же самое.** Заметка, приехавшая из git, должна уехать обратно
   так, чтобы `git diff` показал только реальные правки, а не переформатирование всего файла.
3. **Синхронизация с git** — заявленный сценарий (`KbSpace.sourceKind = GIT`, `gitRepoUrl`,
   `defaultBranch`, `sourceCommitSha`). Это возможно только если хранимое и есть содержимое файла.
4. **Граф ссылок и backlinks** строятся из `[[wiki-links]]`, а обратные ссылки вычисляются, а не
   вводятся руками.
5. **Переносимость данных пользователя — часть обещания AGPL-продукта.** Если инсталляцию решат
   бросить, база знаний должна остаться работоспособной пачкой файлов, а не дампом чужого JSON.

Пятое требование — принципиальное. Для документов переносимость решается экспортом; для базы знаний
она должна быть свойством хранения, потому что источником данных часто является внешний git, и
двусторонний обмен — норма, а не разовая операция.

## Решение

**`KbNote.contentMd` — сырой Markdown, и он является источником истины. Редактор сменяем; формат —
нет.**

**Модель данных** (подробно — [`../data-model.md`](../data-model.md), раздел 5):

| Сущность | Ключевые поля |
|---|---|
| `KbSpace` | `name`, `slug`, `sourceKind NATIVE\|GIT\|OBSIDIAN_IMPORT`, `gitRepoUrl?`, `defaultBranch?`, `lastSyncedAt?` |
| `KbNote` | `spaceId`, `path` (`arch/rls.md`), `title`, `contentMd Text`, `frontmatter Json`, `checksum` (sha256 сырого файла), `sourceCommitSha?`, `wordCount` |
| `KbLink` | `sourceNoteId`, `linkType WIKI\|EMBED\|TAG`, `targetNoteId?`, `targetTitleRaw`, `anchor?`, `isBroken` |
| `KbTag`, `KbNoteTag` | теги; `source FRONTMATTER\|INLINE\|MANUAL` |
| `KbImportJob` | процесс импорта: `status`, `sourceRef`, `stats`, `errorLog` |

Ключевые свойства решения:

- **`contentMd` хранится как есть.** Никакой нормализации «на входе»: если пользователь пишет
  списки через `*`, а не `-`, файл сохранит `*`. `checksum` (sha256 сырого файла) позволяет
  отличить «файл изменился» от «изменилось наше представление о нём».
- **`frontmatter` парсится в JSONB как производное**, но остаётся частью `contentMd`. Источник
  истины — текст файла; JSONB — индекс для запросов по метаданным. Расхождение между ними означает
  баг парсера, а не два источника правды.
- **`path` идентифицирует заметку внутри пространства** (`@@unique([spaceId, path])`) — как в
  файловой системе, а не суррогатным именем.
- **Ссылки и backlinks выводятся из AST**, а не хранятся вручную. Парсер (remark/mdast) строит
  список исходящих ссылок при каждом сохранении; `KbLink` — производное состояние, пересобираемое
  из `contentMd`. Backlinks — это обратный запрос по `KbLink`. `targetTitleRaw` хранит исходный
  текст ссылки, поэтому «битая» ссылка (`isBroken`) остаётся видимой и чинится при появлении цели,
  а не теряется.
- **Round-trip импорт/экспорт — требование, покрытое тестами.** Импорт вольта и немедленный экспорт
  обязаны дать те же файлы с теми же контрольными суммами. Это и есть проверка того, что markdown
  действительно источник истины, а не промежуточное представление.
- **Редактор — сменяемая деталь.** Для базы знаний используется markdown-редактор с превью;
  требование к нему одно: он не переписывает то, чего не трогал пользователь. Замена редактора не
  затрагивает данные — в отличие от [ADR-0012](0012-docs-editor-blocknote-json-content.md), где
  формат задаётся библиотекой.
- **Индексация для поиска** ([ADR-0011](0011-meilisearch-permission-aware-search.md)) идёт из
  `contentMd` через тот же AST; для RAG-эмбеддингов
  ([ADR-0014](0014-ai-provider-abstraction.md)) — чанкование по заголовкам.

**Явное разделение с документами.** `DocPage` и `KbNote` — две разные таблицы и два разных продукта.
Общая таблица заставила бы одну сторону жить в чужом формате: либо база знаний потеряла бы
переносимость, либо документы — блочную структуру.

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **Хранить AST/JSON, генерируя markdown при экспорте** | Быстрые структурные операции (переименование ссылки во всех заметках — обход дерева, а не regex по тексту); нет неоднозначностей парсинга; редактор работает с деревом напрямую; проще делать частичные обновления | **Экспорт перестаёт быть round-trip**: сериализатор нормализует markdown по своим правилам, и `git diff` после первого же сохранения показывает переформатирование всего файла; git-синхронизация становится бесполезной (каждый коммит — шум); нельзя гарантировать, что заметка вернётся такой, какой пришла; расширения markdown, не понятые парсером, теряются безвозвратно | Убивает главный сценарий — двусторонний обмен с git и Obsidian. Заметка, которую нельзя вернуть байт-в-байт, — это уже не «ваш файл», а «наша копия». Для базы знаний это разница между продуктом и ловушкой |
| **Блочный JSON, как у документов** (единый формат на весь продукт) | Один редактор, одна модель, одна схема, вдвое меньше кода; общий поиск и общие комментарии тривиальны | То же, что выше, плюс потеря wiki-ссылок как первоклассной сущности; импорт вольта становится односторонней конвертацией; пользователь Obsidian не может продолжать работать со своими файлами | Совместимость с Obsidian и git-экспортом — заявленная ценность раздела. Экономия кода не окупает потерю причины, по которой раздел существует |
| **Проприетарный формат** (собственная разметка или бинарное представление) | Можно выразить ровно то, что нужно продукту; нет ограничений синтаксиса markdown | Нулевая переносимость; невозможен импорт существующей документации; противоречит духу AGPL-продукта, где пользователь должен иметь возможность уйти | Прямое противоречие обещанию переносимости |
| **Хранить файлы в git-репозитории, а не в БД** (БД только индекс) | Настоящая история изменений бесплатно; git — естественное хранилище для markdown; конфликты разрешаются привычными инструментами | Требует git-сервера или рабочей копии на диске приложения — ломает горизонтальное масштабирование и усложняет бэкап (два источника данных вместо одного); права доступа к заметкам не выражаются средствами git; транзакционность с остальными данными теряется | Привлекательно, но конфликтует с моделью развёртывания и с моделью прав. Компромисс: истина в БД, а git — внешний источник и приёмник через `KbImportJob` и `sourceCommitSha` |
| **Markdown + отдельная таблица блоков для структуры** | Быстрые структурные запросы при сохранении текстового источника | Два представления одного содержимого, которые обязаны совпадать; рассинхронизация неизбежна и не диагностируется | Второй источник правды — то, чего решение как раз избегает. `KbLink` допустим именно потому, что он явно производное состояние, пересобираемое из текста |
| **Хранить HTML** | Легко отобразить | Не переносимо, не редактируемо в Obsidian, санитизация как постоянная задача | Не отвечает ни одному требованию раздела |

## Последствия

### Положительные

- **Импорт вольта или репозитория работает без потерь**, включая нестандартные конструкции: то,
  что не понял парсер ссылок, всё равно сохранено в тексте.
- **Экспорт возвращает те же файлы** — проверяется тестом round-trip.
- **Git-синхронизация осмысленна**: `checksum` и `sourceCommitSha` позволяют определить, что
  изменилось где, и коммит содержит только реальные правки.
- **Пользователь не заперт.** Он может забрать базу знаний и продолжить работать в Obsidian —
  и это работает не «в теории», а по построению.
- **Редактор сменяем без миграции данных.** Замена markdown-редактора — правка UI-слоя.
- **Граф и backlinks всегда актуальны**, потому что выводятся из текста, а не поддерживаются
  вручную.
- **Битые ссылки видимы и самовосстанавливаются**: `targetTitleRaw` + `isBroken` позволяют связать
  ссылку с заметкой, которая появится позже.

### Отрицательные / цена

- **Структурные операции дороже.** Переименование заметки требует обновления ссылок в тексте
  других заметок — обработка текста, а не обход дерева. Массовая операция должна быть транзакционной
  и покрытой тестами.
- **Markdown неоднозначен.** Диалекты (CommonMark, GFM, Obsidian-расширения: `![[embed]]`, callout,
  dataview) различаются; парсер обязан быть терпимым и не терять непонятое.
- **Парсер — производное состояние с риском расхождения.** `KbLink`, `frontmatter`, `wordCount`,
  теги пересобираются из текста; ошибка парсера даёт неверный граф при верном содержимом.
- **Конкурентное редактирование сложнее**: слияние текстовых правок без CRDT — это оптимистическая
  блокировка и ручное разрешение конфликта.
- **WYSIWYG ограничен.** Богатый редактор поверх markdown всегда компромисс; часть пользователей
  будет писать разметку руками.
- **Два раздела вместо одного** — документы и база знаний — означают два редактора, две модели
  комментариев, два пути индексации. Это осознанное удвоение.

### Что становится трудно изменить позже

- **Отказаться от markdown как источника истины практически невозможно.** Обещание переносимости —
  публичное, оно опирается на формат хранения и проверяется пользователем в первый же день. Переход
  на AST/JSON означал бы отзыв этого обещания, а не техническую миграцию.
- **Диалект markdown и набор поддерживаемых расширений** становятся контрактом: заметки, написанные
  с расчётом на `![[embed]]` или на конкретный синтаксис callout, при смене парсера отобразятся
  иначе — при том, что текст не изменился.
- **Схема `path` как идентификатора внутри пространства** попадает во все ссылки: и внутренние
  wiki-ссылки, и внешние URL вида `/kb/$spaceId/$path`. Смена схемы путей ломает и то, и другое.
- **Правило «`KbLink` — производное»** должно соблюдаться всегда. Если однажды появится ссылка,
  создаваемая только через UI и не выводимая из текста, экспорт перестанет быть полным, и
  переносимость сломается тихо.
- **Разделение `DocPage` / `KbNote`** зафиксировано в модели данных, в правах, в поиске и в
  навигации. Слияние разделов позже потребовало бы выбрать один формат — то есть принять ровно то
  решение, которое здесь отвергнуто.
- **Round-trip как тестируемое требование** — если его однажды ослабить («нормализуем при
  сохранении, так чище»), обратный путь закроется: заметки в БД уже будут переформатированы.

## Проверяемость

- **Round-trip тест (главный)**: эталонный набор заметок (включая нестандартные конструкции
  Obsidian, YAML-frontmatter с разными типами, вложенные списки, таблицы, код-блоки с
  тильдами и бэктиками) импортируется и экспортируется; сравниваются sha256 файлов. Расхождение —
  падение.
- **Тест «сохранение без правок не меняет файл»**: открыть заметку в редакторе и сохранить без
  изменений — `checksum` не меняется. Это ловит нормализующие редакторы.
- **Тесты парсера ссылок**: `[[note]]`, `[[note|alias]]`, `[[note#anchor]]`, `![[embed]]`,
  `#tag`, ссылки в код-блоках (не должны распознаваться), ссылки на несуществующие заметки
  (`isBroken = true`), появление цели позже (ссылка «чинится»).
- **Тест пересборки графа**: удаление всех `KbLink` и повторный разбор всех `contentMd`
  восстанавливает граф идентично — подтверждает, что связи производны.
- **Тест переименования**: перемещение заметки обновляет ссылки на неё во всех других заметках в
  одной транзакции; заметки, где ссылка была в код-блоке, не изменяются.
- **Тест `frontmatter`**: JSONB-представление соответствует YAML в тексте; правка текста
  пересобирает JSONB; правка JSONB напрямую невозможна (нет такого API).
- **Тест частичного импорта**: `KbImportJob` со статусом `PARTIAL` фиксирует ошибочные файлы в
  `errorLog` и импортирует остальные — импорт не «всё или ничего».
- **Тест извлечения текста для индексации и чанкования для эмбеддингов** — общий парсер, покрытый
  теми же тестами, что и граф.
- Гейт-агент `test-coverage` (правила проекта) — парсер и round-trip обязаны быть покрыты полностью;
  это ядро обещания переносимости.
