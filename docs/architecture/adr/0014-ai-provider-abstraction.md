# ADR-0014 — Абстракция AI-провайдера: порты и фабрика, настройка администратором

## Контекст

Bad CRM включает AI-ассистента: ответы по базе знаний и документам (RAG), суммаризация обсуждений и
звонков, помощь в формулировках задач, разбор онбординг-материалов. Условия, в которых эта функция
должна существовать, отличаются от типового SaaS-сценария.

**Продукт self-hosted, и мы не платим за токены.** Ключ провайдера принадлежит владельцу
инсталляции. Значит, вендор выбираем не мы: одна организация уже платит Anthropic, другая — OpenAI,
третья гоняет локальную модель через Ollama или vLLM, четвёртая ходит через OpenRouter ради
дешёвого доступа к нескольким моделям.

**AI полностью опционален.** Профиль `minimal` не имеет AI-ключей
([ADR-0020](0020-self-host-packaging-docker.md)); приложение обязано стартовать и работать без них,
скрывая функции, а не падая.

**Ключи — секреты высшей категории.** Утёкший API-ключ — это чужие деньги и чужие данные. Он не
может лежать в переменных окружения, если организаций несколько, и не может попадать в API-ответы
или логи.

**Ответ должен стримиться.** Ожидание в 20 секунд без обратной связи неприемлемо; интерфейс
показывает токены по мере генерации.

**RAG обязан учитывать права.** Ассистент, который цитирует документ приватного проекта человеку,
не входящему в проект, — это утечка, причём особенно неприятная: она выглядит как «ответ модели», а
не как ошибка доступа.

## Решение

**Три порта в `application/ai/ports` и фабрика провайдеров в `infrastructure/ai`. Провайдер
настраивает администратор организации в UI, ключи хранятся зашифрованными.**

```
application/ai/use-cases
   ├─► AIProviderPort.chatStream()  → AsyncIterable<StreamEvent>
   ├─► EmbeddingProviderPort.embed(texts)
   └─► RetrievalPort.search(query, principals)

infrastructure/ai/provider-factory.ts
   ├─► anthropic        (@anthropic-ai/sdk)
   ├─► openai           (openai)
   ├─► openai_compat    (openai SDK с собственным baseURL — Ollama, vLLM, LM Studio, любой шлюз)
   └─► openrouter       (openai SDK с baseURL OpenRouter)

RetrievalPort ─► pgvector: EmbeddingChunk + фильтр по принципалам + RLS
presentation/http: SSE-контроллер транслирует AsyncIterable в поток
```

**Стриминг унифицирован на уровне порта.** `chatStream()` возвращает
`AsyncIterable<StreamEvent>` — нормализованные события (`delta`, `tool_call`, `usage`, `done`,
`error`). Различия форматов провайдеров скрываются в адаптере, а не «сглаживаются» постфактум на
клиенте. Контроллер транслирует поток в SSE — это тот случай, где SSE и есть правильный транспорт
(односторонний поток от сервера), в отличие от realtime-подсистемы
([ADR-0010](0010-realtime-socketio-redis-adapter.md)).

**Конфигурация — данные, а не окружение.** Сущность `AIProvider` (под RLS, то есть на организацию)
хранит: `kind` (`anthropic` / `openai` / `openai_compat` / `openrouter`), `baseUrl?`, `model`,
зашифрованный ключ и `apiKeyTail` — последние 4 символа для отображения. Правила обращения с ключом:

- **Ключ шифруется** ключом инсталляции (`infrastructure/crypto`, KMS-подобный конверт), а не
  хранится в открытом виде.
- **API никогда не возвращает ключ** — ни целиком, ни частично: только `apiKeyTail`, чтобы
  администратор узнал, какой ключ настроен.
- **Ключ не попадает в логи** — редактирование секретов в логгере обязательно.
- **Ключ не попадает в клиент** ни при каких обстоятельствах: все обращения к провайдеру идут с
  сервера.

**RAG permission-aware.** Retrieval по pgvector фильтрует чанки теми же принципалами, что и поиск
([ADR-0011](0011-meilisearch-permission-aware-search.md)), и тем же `organizationId` под RLS.
**Фильтр применяется до формирования контекста**, поэтому недоступный документ не может попасть в
промпт даже частично. Это ключевое свойство: пост-фильтрация ответа модели невозможна в принципе —
из ответа нельзя «вычесть» уже использованный источник.

**Деградация.** В профиле `minimal` порты не резолвятся, фичи скрыты флагом, эндпоинты отвечают
«функция отключена». Отсутствие AI — состояние, а не ошибка.

**Векторы — в pgvector того же Postgres.** Отдельная векторная БД (Qdrant/Weaviate) отвергнута на
уровне обзора архитектуры: pgvector даёт транзакционную консистентность эмбеддингов с данными и не
добавляет контейнер в compose.

**Промпты и содержимое сообщений не логируются** — только идентификаторы, размеры и `usage`.

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **Интеграция с одним вендором** (только Anthropic или только OpenAI) | Минимум кода; можно использовать вендор-специфичные возможности (prompt caching, structured outputs, batch API) на полную; проще тестировать и документировать | Владелец инсталляции обязан завести аккаунт именно у этого вендора; локальные модели невозможны — а для части аудитории (данные не должны покидать периметр) это блокирующее требование; вендор-лок в open-source-продукте выглядит как навязывание | Мы не платим за токены и не можем выбирать за пользователя. Требование «локальная модель через Ollama» само по себе закрывает вопрос |
| **LangChain / LlamaIndex** | Готовые абстракции провайдеров, RAG-пайплайны, сплиттеры, множество интеграций; быстрый старт | Крупная зависимость с частыми ломающими изменениями; собственные абстракции поверх наших портов — двойная косвенность; RAG-логика уходит в фреймворк, где фильтрацию по правам нужно встраивать в чужой пайплайн (и легко встроить неправильно); отладка стриминга через несколько слоёв | Наш RAG критически зависит от **фильтрации по правам до формирования контекста**. Отдавать этот шаг фреймворку — принимать риск утечки ради экономии, которой почти нет: `chatStream` и `embed` — это два метода |
| **Vercel AI SDK** | Отличная унификация провайдеров и стриминга; хорошие типы; активно развивается | Ориентирован на Next.js-стек и на клиентский стриминг; тянет свои соглашения о маршрутах; наш стриминг всё равно должен пройти через use-case с проверкой прав и учётом лимитов | Часть работы (унификация формата провайдеров) полезна, но она же — единственное, что нам нужно, и она укладывается в один адаптер на вендора |
| **Ключи в переменных окружения** (`ANTHROPIC_API_KEY` в `.env`) | Просто; привычно; ключ не хранится в БД, значит не утечёт с дампом | Один ключ на всю инсталляцию — несколько организаций не могут иметь разных провайдеров и разных бюджетов; смена ключа требует рестарта контейнера, то есть доступа к серверу, а не к админке; ротация неудобна | Мульти-тенантность делает env-конфигурацию непригодной. Плюс продуктовое требование: администратор организации настраивает AI сам, без обращения к владельцу хоста |
| **Ключи в открытом виде в БД** | Проще некуда | Дамп БД раскрывает ключи всех организаций; противоречит правилам обращения с секретами | Неприемлемо. Шифрование ключом инсталляции — минимальная планка |
| **Проксирование через собственный шлюз** (LiteLLM, свой gateway-контейнер) | Единый интерфейс ко всем вендорам, готовые лимиты, метрики и кеширование; смена вендора без правки кода | Ещё один контейнер в compose и ещё одна точка отказа; конфигурация вендоров уезжает из админки в файл шлюза; отладка через дополнительный хоп | Противоречит «одной команде». Сценарий шлюза при этом поддержан: `openai_compat` с `baseUrl` на LiteLLM работает без изменений в коде |
| **Отдельная векторная БД** (Qdrant, Weaviate, Pinecone) | Лучше по производительности на больших объёмах; богаче фильтрация и гибридный поиск | Ещё один контейнер; эмбеддинги перестают быть транзакционно консистентными с данными (удалили документ — чанк остался); внешние SaaS-варианты неприемлемы для self-host | pgvector в уже существующем Postgres даёт консистентность и не расширяет compose. Зафиксировано в «Что осознанно НЕ делаем сейчас» |
| **Пост-фильтрация ответа модели по правам** | Не требует передавать принципалы в retrieval | Технически невозможно: из сгенерированного ответа нельзя удалить влияние источника, который уже попал в контекст | Не альтернатива, а ошибка. Фиксируется здесь, чтобы к ней не возвращались |

## Последствия

### Положительные

- **Владелец инсталляции выбирает вендора сам**, включая локальную модель — данные могут не
  покидать периметр вообще.
- **Смена провайдера не затрагивает `application`** — только фабрику. Use-cases не знают, кто
  отвечает.
- **Четыре вида провайдера покрываются двумя SDK**: `openai_compat` и `openrouter` — это тот же
  клиент с другим `baseUrl`, что резко снижает стоимость поддержки.
- **Стриминг единообразен** — клиент имеет один формат событий независимо от вендора.
- **RAG не может процитировать недоступное** — фильтр стоит до формирования контекста.
- **Ключи не утекают**: шифрование в БД, `apiKeyTail` в API, редактирование в логах, отсутствие в
  клиенте.
- **AI отключается целиком** без ветвлений в бизнес-логике — порты просто не резолвятся.
- **Эмбеддинги консистентны с данными** — они в том же Postgres и в тех же транзакциях.

### Отрицательные / цена

- **Порт ограничен пересечением возможностей вендоров.** Prompt caching Anthropic, structured
  outputs OpenAI, специфичные параметры сэмплирования — либо не используются, либо требуют
  расширения порта опциональными полями, которые часть адаптеров игнорирует.
- **Качество ответов зависит от выбранной модели**, а промпты пишутся под некоторое «среднее»
  поведение. Локальная 7B-модель и Claude дают несопоставимый результат при одинаковом промпте —
  это придётся объяснять пользователям.
- **`openai_compat` — обещание, которое трудно выполнить полностью**: совместимые API отличаются в
  деталях (поддержка стриминга, tool calls, формат ошибок). Часть проблем будет приходить как
  «у меня не работает с моим шлюзом».
- **Шифрование ключей вводит ключ инсталляции** — ещё один секрет, требующий ротации и попадающий
  в процедуры восстановления.
- **Тестирование требует моков на каждый адаптер** плюс контрактный тест порта; реальные вызовы в
  CI невозможны (деньги, недетерминизм).
- **Стоимость и лимиты — забота владельца.** Продукт обязан показывать `usage` и давать лимиты,
  иначе счёт станет неприятным сюрпризом.

### Что становится трудно изменить позже

- **Контракт `StreamEvent`** потребляется контроллером SSE, клиентским хуком стриминга и UI. Его
  изменение — сквозная правка через все три слоя плюс несовместимость со старым клиентом при
  rolling-обновлении.
- **Набор `kind` провайдера** (`anthropic` / `openai` / `openai_compat` / `openrouter`) хранится в
  БД у всех инсталляций. Переименование или удаление значения — миграция данных на чужих серверах.
- **Схема хранения ключей** (алгоритм конверта, привязка к ключу инсталляции) определяет процедуру
  восстановления: восстановление БД без ключа инсталляции делает все настроенные провайдеры
  нерабочими. Смена схемы требует перешифрования при миграции.
- **Схема чанкования и размерность эмбеддингов** зашиты в таблицу `EmbeddingChunk` и в индекс
  pgvector. Смена модели эмбеддингов с другой размерностью требует **полной переиндексации всего
  содержимого** — а это платный вызов провайдера на каждый чанк, то есть операция, стоящая денег
  владельцу инсталляции.
- **Правило «фильтр по правам до контекста»** должно соблюдаться в каждом новом AI-сценарии.
  Однажды добавленный путь, где контекст собирается без принципалов, создаёт утечку, замаскированную
  под ответ модели, — то есть почти не диагностируемую.
- **Опциональность AI** пронизывает UI (скрытие функций), конфигурацию и эндпоинты; отказ от неё
  ради упрощения сломал бы профиль `minimal`.

## Проверяемость

- **Контрактный тест порта**: один набор тестов прогоняется против всех адаптеров через общий
  мок-транспорт — проверяются нормализация событий стрима, обработка ошибок вендора, отмена запроса,
  корректный `usage`.
- **Permission-тест RAG (обязательный)**: пользователь без доступа к приватному проекту задаёт
  вопрос, ответ на который содержится только в его документах, — ни один чанк этого проекта не
  попадает в контекст. Проверяется на уровне `RetrievalPort`, то есть до вызова модели.
- **Тест «ключ не покидает сервер»**: снапшот-тест ответов API сущности `AIProvider` — присутствует
  только `apiKeyTail`; тест логгера — ключ редактируется; проверка клиентского бандла на отсутствие
  обращений к API вендоров напрямую.
- **Тест шифрования ключа**: в БД лежит шифротекст; чтение без ключа инсталляции невозможно; смена
  ключа инсталляции покрыта процедурой перешифрования.
- **Тест старта без AI**: приложение поднимается без настроенных провайдеров; AI-эндпоинты
  возвращают «функция отключена»; health-check зелёный; UI не показывает AI-разделов.
- **Тест отмены стрима**: разрыв SSE-соединения клиентом прекращает генерацию и освобождает
  соединение с провайдером (не «висит до конца»).
- **Тест лимитов**: превышение лимита организации отклоняет запрос до обращения к вендору — то есть
  до траты денег.
- **Тест «промпты не в логах»**: содержимое сообщений и контекста отсутствует в выводе логгера при
  включённом debug-уровне.
- Гейт-агент `security-auditor` (правила проекта) — обязателен для изменений в хранении ключей и в
  сборке контекста RAG.
