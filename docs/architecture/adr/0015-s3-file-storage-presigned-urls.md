# ADR-0015 — Файлы в S3-совместимом хранилище через presigned URL

## Контекст

Файлы в Bad CRM — сквозная функция: вложения к задачам, документам, заметкам, комментариям, вехам и
рискам; аватары; материалы онбординга; экспорты и отчёты; записи и артефакты звонков. Размеры
варьируются от аватара в 20 KB до видеозаписи созвона в сотни мегабайт.

Технические ограничения:

**Node.js однопоточен.** Приём тела файла в API-процессе занимает event loop и память; несколько
параллельных загрузок по 200 MB на инстансе с 2 GB RAM — это отказ обслуживания для всех остальных
запросов.

**Проксирование удваивает трафик.** Файл идёт клиент → API → хранилище и обратно, то есть
инсталляция платит за пропускную способность дважды и добавляет задержку.

**Горизонтальное масштабирование.** В профиле `scaled` работают несколько экземпляров API
([ADR-0020](0020-self-host-packaging-docker.md)); файл, записанный на локальный диск экземпляра A,
недоступен экземпляру B.

**Права обязаны проверяться.** Доступ к файлу определяется доступом к объекту, к которому файл
прикреплён (`ResourceAcl`, `ProjectMember`, личный скоуп) —
[ADR-0008](0008-permission-model-rbac-plus-acl.md).

**Изоляция арендаторов должна быть выражена и в хранилище**, а не только в БД
([ADR-0004](0004-multi-tenancy-postgres-rls.md)).

**Self-host не должен требовать облака.** Инсталляция на одном VPS обязана работать без учётной
записи AWS.

## Решение

**S3-совместимое объектное хранилище (MinIO в compose, любой S3 в проде) с загрузкой и скачиванием
через presigned URL. Тело файла не проходит через API-процесс.**

**Загрузка — трёхшаговый протокол:**

```
1. POST /files/upload-intent {name, size, mime, target}
   → API: проверка capability + ACL цели, лимиты размера и типа
   → INSERT FileObject(status='pending', key='org/{orgId}/...')
   → presign PUT (TTL минуты)
   ← {uploadUrl, fileId}

2. PUT <uploadUrl> — браузер отправляет тело напрямую в хранилище

3. POST /files/{id}/commit
   → API: HeadObject — фактический размер и content-type
   → UPDATE FileObject SET status='ready' + INSERT OutboxEvent (одна транзакция)
   ← метаданные файла
```

**Скачивание:**

```
GET /files/{id}/download-url
   → RLS + capability + ACL
   → presign GET (короткий TTL)
   ← {url}
```

Свойства, каждое из которых существенно:

- **Проверка прав происходит до выдачи ссылки**, а не при обращении к хранилищу. Хранилище
  доверяет подписи; вся авторизация — в API.
- **TTL presigned URL — не более 300 секунд.** Ссылка на скачивание живёт ровно столько, сколько
  нужно браузеру, чтобы начать загрузку.
- **Ключ объекта всегда начинается с `org/{organizationId}/`.** Префикс проверяется при commit,
  поэтому подменённый ключ не привяжет чужой объект. Это выражение tenancy на уровне хранилища.
- **Заявленные клиентом `size` и `mime` не доверяются.** Истина — ответ `HeadObject` на шаге
  commit. Без этого клиент мог бы объявить 1 KB и загрузить гигабайт.
- **Публичного бакета нет.** Любое чтение — presigned GET после проверки ACL. Ни один объект не
  доступен по стабильному URL.
- **Незакоммиченные `FileObject`** старше порога и осиротевшие объекты в бакете чистит фоновая
  джоба. Состояние `pending` без commit — норма (пользователь передумал), а не ошибка.
- **Событие о готовности файла пишется в outbox в той же транзакции**, что и переход в `ready`
  ([ADR-0021](0021-transactional-outbox.md)) — индексация, уведомления и превью запускаются оттуда.
- **MinIO в docker compose** для локальной разработки и для типового self-host; продакшен может
  указать любой S3-совместимый endpoint (AWS S3, Cloudflare R2, Backblaze B2, Wasabi, собственный
  MinIO-кластер) — конфигурацией, без правки кода.

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **Файлы в БД (`bytea` / large objects)** | Транзакционная консистентность метаданных и содержимого — файл не может «потеряться» относительно записи; бэкап один; права проверяются той же RLS; нет второго хранилища в compose | Раздувание базы: WAL, репликация и `pg_dump` начинают возить гигабайты бинарных данных; кеш Postgres вытесняется содержимым файлов; чтение всё равно проходит через API-процесс и память Node; практический потолок — единицы мегабайт на файл | Видеозапись созвона в БД делает бэкап и восстановление неуправляемыми. Транзакционная консистентность — реальное преимущество, но она покупается ценой работоспособности БД |
| **Локальный диск + том Docker** | Предельно просто; никакого дополнительного сервиса; быстро; понятно любому администратору | Ломает горизонтальное масштабирование (экземпляр B не видит файл экземпляра A) — нужен сетевой том со своими проблемами; бэкап становится отдельной процедурой поверх файловой системы; отдача файлов всё равно через Node либо через конфигурацию reverse-proxy, которую нужно описывать пользователю; квоты и сроки хранения приходится реализовывать самому | Отсекается требованием горизонтального масштабирования и удобством бэкапа. MinIO в compose даёт ту же простоту («один контейнер») и при этом сразу S3-совместимость |
| **Проксирование через приложение** (файл идёт клиент → API → S3) | API полностью контролирует каждый байт: можно проверять права на лету, отзывать доступ мгновенно, антивирус в потоке, точный аудит скачиваний | Тело файла занимает event loop и память Node; трафик удваивается; таймауты reverse-proxy на больших файлах; масштабирование API становится функцией объёма загрузок, а не числа запросов | Прямое противоречие ограничениям Node и модели «маленький VPS». Плюсы реальны — и именно поэтому проксирование остаётся допустимым исключением для узких случаев (генерируемые на лету экспорты небольшого размера), но не как основной путь |
| **Прямая отдача из публичного бакета** | Максимально дёшево и быстро; CDN-совместимо | Любой, кто узнал URL, скачивает файл вечно; невозможно связать доступ с правами; утечка ссылки = утечка файла | Неприемлемо для инструмента, где во вложениях лежат договоры и внутренние документы |
| **Presigned URL с длинным TTL** (часы, сутки) | Меньше запросов к API; ссылку можно положить в письмо | Presigned URL **неотзываем**: отозвать доступ до истечения TTL невозможно, кроме удаления объекта или ротации ключей хранилища | TTL ≤ 300 с — компромисс между удобством и окном экспозиции. Осознанный остаточный риск (см. ниже) |
| **Собственный шлюз отдачи** (`X-Accel-Redirect` / `X-Sendfile` через nginx) | Проверка прав в API, отдача — nginx: не занимает Node и не удваивает трафик | Требует конкретного reverse-proxy и его настройки на стороне владельца инсталляции; работает с локальным диском, то есть возвращает проблему масштабирования | Перекладывает сложность на пользователя и не решает задачу общего хранилища |

## Последствия

### Положительные

- **Тело файла не занимает event loop** — загрузка сотен мегабайт не влияет на отзывчивость API.
- **Трафик не удваивается**: клиент говорит с хранилищем напрямую.
- **Горизонтальное масштабирование работает** — общее хранилище для всех экземпляров.
- **Изоляция арендаторов выражена в ключах объектов** (`org/{orgId}/...`) и проверяется при commit.
- **Права проверяются до выдачи ссылки**, тем же policy-слоем, что и остальное чтение.
- **Нет публичных URL** — ни один объект не доступен без свежей подписи.
- **Переносимость**: MinIO локально, любой S3 в проде, смена — вопрос конфигурации.
- **Метаданные не подделываются**: `HeadObject` на commit устанавливает истину.
- **Бэкап понятен**: `pgdata` (истина по метаданным) и `minio-data` (тела), обе процедуры описаны.

### Отрицательные / цена

- **Presigned URL неотзываем — остаточный риск, принятый сознательно.** Выданная ссылка действует
  до истечения TTL, даже если права отозваны в ту же секунду. Смягчение: TTL ≤ 300 с; ссылки
  выдаются по одной на операцию, не пачками; факт выдачи пишется в аудит. Полностью устранить риск
  можно только проксированием, которое отвергнуто выше.
- **Двухфазная загрузка сложнее одного POST**: клиент обязан выполнить три шага, и промежуточное
  состояние `pending` — нормальная часть модели, а не аномалия.
- **Возможны осиротевшие объекты**: клиент загрузил тело и не вызвал commit. Требуется джоба
  уборки — то есть отдельный движущийся элемент.
- **Нет транзакционной консистентности между БД и хранилищем.** Файл может существовать без записи
  (сирота) или запись без файла (если объект удалили извне). Лечится сверочным джобом, а не БД.
- **Ещё один контейнер и ещё один набор секретов** (ключи доступа MinIO) в развёртывании.
- **CORS-конфигурация бакета** обязательна для прямой загрузки из браузера — типовой источник
  проблем при самостоятельной настройке.
- **Антивирусная проверка возможна только асинхронно** (после commit, через outbox), а не в потоке
  загрузки.
- **Аудит скачиваний неточен**: мы фиксируем выдачу ссылки, а не факт скачивания.

### Что становится трудно изменить позже

- **Схема ключей объектов `org/{organizationId}/...`** становится структурой уже существующих
  бакетов на чужих инсталляциях. Смена схемы требует переименования (то есть копирования) всех
  объектов — операции, стоящей времени и трафика владельцу.
- **Трёхшаговый протокол загрузки** — публичная часть API ([ADR-0003](0003-openapi-as-source-of-truth.md)),
  которой пользуются интеграции. Переход на однофазную загрузку означает новую версию контракта при
  сохранении старой.
- **Отказ от проксирования** зафиксирован в модели ресурсов: API не рассчитан на пропускание
  больших тел, а лимиты reverse-proxy в документации по развёртыванию выставлены исходя из этого.
  Возврат к проксированию поменял бы требования к железу.
- **Неотзываемость presigned URL** — свойство, с которым продукт живёт постоянно. Требование
  «мгновенный отзыв доступа к файлу» невыполнимо без смены всей модели отдачи.
- **S3-совместимость как контракт хранилища** ограничивает выбор: переход на модель, где файлы
  лежат в БД или на диске, потребует переписать `FileStoragePort` и все процедуры бэкапа и
  восстановления, уже выполняемые владельцами инсталляций.
- **Разделение бэкапов на две системы** (`pgdata` + `minio-data`) закреплено в runbook'ах;
  восстановление на точку во времени требует согласования двух источников — и это свойство
  архитектуры, а не процедуры.

## Проверяемость

- **Тест проверки прав до выдачи ссылки**: пользователь без доступа к задаче не получает
  `download-url` для её вложения — ни 200 с ссылкой, ни 403 с раскрытием существования (для
  приватных объектов — 404).
- **Тест префикса ключа**: попытка закоммитить `FileObject` с ключом, не начинающимся с
  `org/{текущий orgId}/`, отклоняется. Проверяется и подмена на префикс другой организации.
- **Тест TTL**: выданный URL перестаёт работать после истечения; конфигурационный тест утверждает,
  что TTL ≤ 300 с — увеличение порога ломает сборку.
- **Тест `HeadObject`-верификации**: клиент заявляет 1 KB и загружает больше — commit отклоняется;
  заявленный `mime` расходится с фактическим — commit отклоняется или тип корректируется по факту.
- **Тест лимитов**: превышение лимита размера или запрещённый тип отклоняются на шаге
  `upload-intent`, то есть до загрузки тела.
- **Тест уборки**: `FileObject` в статусе `pending` старше порога удаляется вместе с осиротевшим
  объектом; закоммиченные файлы не затрагиваются.
- **Сверочный джоб «БД ↔ бакет»**: расхождение (объект без записи, запись без объекта) даёт метрику
  и алерт, а не тихую коррекцию.
- **Тест атомарности commit**: переход в `ready` и запись `OutboxEvent` происходят в одной
  транзакции; сбой после `HeadObject` не оставляет файл в `ready` без события.
- **E2E-сценарий полного цикла** (Playwright + MinIO в Testcontainers): intent → PUT → commit →
  скачивание по свежей ссылке; повторное использование старой ссылки после TTL — отказ.
- Гейт-агент `security-auditor` (правила проекта) — обязателен для изменений в выдаче presigned URL
  и в проверке прав файлового пути.
