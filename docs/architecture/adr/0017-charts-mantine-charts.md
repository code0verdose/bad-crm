# ADR-0017 — Графики на `@mantine/charts`, ECharts точечно, данные из rollup-таблиц

## Контекст

Аналитическая часть Bad CRM — дашборд, отчёты и drill-down по сотруднику — состоит в основном из
простых визуализаций: динамика часов по дням, распределение billable/non-billable, состав времени по
видам активности, здоровье проектов, burndown спринта, выработка команды, маржинальность.

Три обстоятельства определяют решение.

**Первое: графики — часть интерфейса, а не отдельный продукт.** Они соседствуют с карточками,
таблицами и фильтрами Mantine на одном экране. Второй источник стилевой правды (собственная палитра
библиотеки графиков, собственные шрифты, собственная тёмная тема) немедленно даёт визуальный
диссонанс и удваивает работу при смене темы ([ADR-0006](0006-mantine-css-modules-no-tailwind.md)).

**Второе: источник данных важнее библиотеки отрисовки.** Дашборд «часы команды за квартал» по сырой
`TimeEntry` — это скан десятков тысяч строк на каждое открытие экрана каждым пользователем. При
целевом железе (2 vCPU / 4 GB) это не оптимизация, а вопрос работоспособности.

**Третье: один экран обслуживает три роли.** Разработчик, менеджер и админ видят один и тот же
дашборд; различается только скоуп данных (`me` / `team` / `org`) и набор карточек, отфильтрованный
по правам. Принцип зафиксирован в [`../ux-architecture.md`](../ux-architecture.md) как «три роли —
один код»: никаких `AdminDashboard`.

## Решение

**`@mantine/charts` (обёртка над Recharts) — основа. ECharts подключается точечно и только там, где
`@mantine/charts` не справляется. Данные для дашбордов берутся из rollup-таблиц. Один кодовый путь
на все роли с инжектируемым `AccessScope`.**

**Отрисовка.** `@mantine/charts` покрывает подавляющее большинство потребностей: `LineChart`,
`AreaChart`, `BarChart`, `DonutChart`, `PieChart`, `Sparkline`, `CompositeChart`,
`RadarChart`. Ключевое свойство — он использует **ту же тему и те же CSS-переменные**, что весь
остальной UI: цвета серий берутся из палитры Mantine, тёмная тема работает без отдельной настройки,
шрифты и отступы совпадают с окружением.

**ECharts — точечно и осознанно.** Есть визуализации, которых в Recharts либо нет, либо они
неприемлемого качества: граф связей базы знаний, тепловые карты активности, сложные комбинированные
диаграммы с несколькими осями и зумом, диаграммы Ганта для delivery. Для них подключается ECharts
(Apache-2.0) **лениво, в отдельном чанке, только на тех маршрутах, где он нужен**, с темой,
собранной из тех же CSS-переменных. Правило: ECharts не является «второй библиотекой по умолчанию»;
каждое его использование — обоснованное исключение.

**Данные — из rollup-таблиц, а не из сырых записей.** `TimeRollupDaily` с уникальным ключом
`(organizationId, date, userId, projectId, activityId)` — преагрегат, пересчитываемый **через
outbox** ([ADR-0021](0021-transactional-outbox.md)) при изменении фактов, включая сторно
([ADR-0016](0016-time-tracking-single-entry-model.md)). Дашборд читает готовые суммы за диапазон
дат, а не сканирует `TimeEntry`. Аналогичные rollup'ы заводятся для других аналитических разрезов
по мере появления экранов.

Rollup — **производное состояние**: его можно удалить и восстановить пересчётом из фактов. Это
свойство важно эксплуатационно (см. [ADR-0011](0011-meilisearch-permission-aware-search.md), где то
же верно для поискового индекса).

**Один кодовый путь на три роли.** Реестр карточек дашборда — декларативный массив в
`units/dashboard/model/constants/dashboard-cards.constant.ts`:

```
{ id, titleKey, permission, minScope, span, lazyComponent }
```

Хук `useDashboardCards()` фильтрует реестр по правам и скоупу; компонент раскладывает `Grid` и
рендерит `<Suspense>` вокруг каждой карточки. **`AccessScope` (`me` / `team` / `org`)
инжектируется**: он приходит из URL, валидируется схемой ([ADR-0007](0007-tanstack-router-and-query.md))
и передаётся в запрос, где сервер применяет к нему policy. Доступные значения переключателя зависят
от прав.

Следствия принципа:

- **Нет отдельного административного пути** — значит нет второй реализации, которая забудет
  проверку прав.
- **Карточка без права не рендерится вовсе** (не `disabled`) — её отсутствие ничего не раскрывает.
- **Ошибка изолирована на уровне карточки**: `errorComponent` внутри карточки, retry там же; падает
  карточка, а не дашборд.
- **Loading — skeleton-сетка тех же размеров**, что реальные карточки, без сдвига layout.

**Авторитет — на сервере.** Клиентская фильтрация реестра по правам — подсказка UI; запрос всё равно
проверяется policy и RLS ([ADR-0008](0008-permission-model-rbac-plus-acl.md),
[ADR-0004](0004-multi-tenancy-postgres-rls.md)).

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **Recharts напрямую** (без обёртки Mantine) | Полный доступ ко всем возможностям и пропсам; больше контроля над композицией; та же библиотека под капотом | Тематизация делается вручную: цвета серий, сетка, подсказки, легенда, тёмная тема — всё нужно связать с CSS-переменными самостоятельно и поддерживать при изменении темы; это ровно то, что `@mantine/charts` уже сделал | Отличие только в объёме собственной работы. При нехватке возможностей обёртки всегда можно опуститься на уровень Recharts — она не скрыта |
| **ECharts везде** (как основная библиотека) | Огромный набор типов диаграмм; отличная производительность на больших массивах благодаря canvas; богатые взаимодействия (зум, brush, drill-down); хорошая поддержка графов и тепловых карт; Apache-2.0 | Императивный API, чуждый React-модели (инстанс, ручное обновление опций, ручной resize); собственная система тем — второй источник стилевой правды; заметный вес бандла; canvas хуже для доступности и текстового поиска по подписям | Как основная библиотека даёт визуальный и архитектурный разрыв с остальным UI ради возможностей, которые нужны на нескольких экранах. Поэтому — точечно, лениво, там где действительно нужна |
| **Chart.js (react-chartjs-2)** | Лёгкий, популярный, простой API, хорошая производительность на canvas | Тематизация опять вручную; canvas-рендеринг хуже интегрируется с CSS-переменными и с доступностью; кастомизация подсказок и легенды ограниченнее | Не даёт преимущества над Recharts в наших сценариях и проигрывает в интеграции с темой |
| **D3 напрямую** | Абсолютная гибкость; можно построить что угодно | Каждая диаграмма — самостоятельный проект: оси, шкалы, подсказки, легенда, адаптивность, доступность пишутся руками; императивная работа с DOM конфликтует с React | Несоразмерно задаче. Простые линейные и столбчатые графики не требуют D3 |
| **Visx (Airbnb)** | D3-примитивы в React-модели; отличная композируемость; полный контроль | Низкоуровневый: подсказки, легенды, оси собираются вручную; больше кода на каждую диаграмму | То же соотношение «свобода против объёма работы», что и с D3, только мягче |
| **Отдельный административный дашборд** (`AdminDashboard` рядом с обычным) | Проще писать: не нужно думать о скоупе и правах в общем коде; можно оптимизировать под конкретную роль | Две реализации одних и тех же карточек расходятся; проверка прав дублируется, и в одной из копий её однажды забудут; добавление новой карточки требует правки в двух местах | Прямое нарушение принципа «три роли — один код». Класс уязвимостей «в админском пути забыли фильтр по организации» возникает именно так |
| **Сканирование сырых `TimeEntry` на каждом запросе** | Всегда актуальные данные; нет расхождения между фактами и агрегатами; нет джоба пересчёта | Дашборд за квартал по команде = десятки тысяч строк на каждое открытие каждым пользователем; на 2 vCPU это секунды ожидания и конкуренция за БД с оперативной работой | Неприемлемо по производительности на целевом железе. Rollup — не преждевременная оптимизация, а следствие известного паттерна доступа |
| **Материализованные представления Postgres вместо rollup-таблиц** | Меньше кода: пересчёт декларативен; `REFRESH MATERIALIZED VIEW CONCURRENTLY` | Полный пересчёт вместо инкрементального; блокировки и нагрузка при обновлении; хуже сочетается с RLS; трудно обновлять точечно по одному дню и одному человеку | Инкрементальный пересчёт через outbox точнее и дешевле: изменилась одна запись — пересчитан один день одного человека |

## Последствия

### Положительные

- **Графики визуально неотличимы от остального UI** — одна палитра, одна типографика, одна тёмная
  тема.
- **Смена темы меняет графики автоматически** — нет второго набора цветов для поддержки.
- **Дашборд открывается быстро** — чтение готовых сумм вместо скана фактов.
- **Rollup восстановим**: его можно удалить и пересчитать из `TimeEntry`.
- **Один кодовый путь на роли** — карточка пишется один раз, проверка прав в одном месте.
- **Реестр карточек декларативен**: добавление карточки — строка в массиве плюс ленивый компонент.
- **Отказ изолирован**: падает карточка, а не экран.
- **Ленивая загрузка ECharts** не утяжеляет основной бандл.

### Отрицательные / цена

- **Потолок возможностей `@mantine/charts` принят осознанно.** Сложные комбинированные диаграммы,
  синхронизированный зум по нескольким графикам, drill-down по клику в сегмент — либо реализуются
  ограниченно, либо требуют перехода на ECharts для конкретного экрана.
- **Две библиотеки графиков в проекте.** Даже при дисциплине «ECharts точечно» это два API, две
  тематизации (пусть и из одних переменных) и два набора знаний.
- **Rollup — производное состояние с задержкой.** Между записью времени и обновлением дашборда
  проходит обработка outbox; пользователь может не увидеть только что записанные часы.
- **Рассинхронизация rollup и фактов возможна** при ошибке обработчика — требуется сверочный джоб и
  процедура пересчёта.
- **Сторно усложняет пересчёт**: отрицательная запись должна уменьшить показатели **дня исходной
  записи**, а не дня сторно — неочевидная логика, требующая явного теста
  ([ADR-0016](0016-time-tracking-single-entry-model.md)).
- **`AccessScope` нужно продевать через весь путь** — от URL до SQL; забытое звено даёт либо
  «пусто», либо, что хуже, данные шире положенного (защищено policy и RLS, но всё равно баг).
- **Recharts на больших массивах (тысячи точек) деградирует** — SVG-рендеринг; требуется
  агрегация по времени на стороне сервера, что rollup и обеспечивает.

### Что становится трудно изменить позже

- **Гранулярность rollup-таблиц** (`день × пользователь × проект × активность`) определяет, какие
  разрезы вообще возможны на дашборде. Добавление нового измерения (например, разбивка по
  контракту) требует изменения уникального ключа и **полного пересчёта всей истории**.
- **Сама схема rollup становится контрактом** между обработчиком outbox, отчётами и экспортами;
  ошибка в пересчёте, не замеченная сразу, портит агрегаты за период, и восстановление возможно
  только полным пересчётом из фактов.
- **Реестр карточек с полями `permission` и `minScope`** — механизм, определяющий видимость всех
  аналитических данных. Изменение его семантики затрагивает каждую карточку и каждую роль.
- **Отказ от отдельного административного пути** должен соблюдаться постоянно. Первый же
  «временный» `AdminDashboard` создаёт вторую реализацию, которую нужно синхронизировать вечно.
- **Правило «ECharts точечно»** держится дисциплиной. Как только ECharts окажется на дашборде
  «заодно», он станет второй темой по умолчанию, и вернуть единообразие будет дорого.
- **Привязка к теме Mantine** в графиках означает, что смена UI-kit ([ADR-0006](0006-mantine-css-modules-no-tailwind.md))
  затрагивает и аналитику: цвета серий, сетка и подсказки придётся тематизировать заново.

## Проверяемость

- **Тест «один кодовый путь»**: в кодовой базе отсутствуют компоненты с ролевыми именами
  (`AdminDashboard`, `ManagerReport`); проверяется грепом по именам файлов и экспортов в CI.
- **Тест реестра карточек**: каждая карточка объявляет `permission` из каталога прав; карточка без
  объявленного права ломает сборку (аналог правила «нет маршрута без permission» из
  [ADR-0008](0008-permission-model-rbac-plus-acl.md)).
- **Permission-тесты дашборда**: пользователь без права не получает карточку ни в реестре, ни в
  ответе API; переключатель скоупа не предлагает недоступных значений; запрос с подделанным
  `scope=org` отклоняется сервером.
- **Тест корректности rollup**: сумма по `TimeRollupDaily` за период равна сумме
  `durationMinutes` по `TimeEntry` за тот же период **со знаком** (включая сторно). Прогоняется на
  сгенерированном наборе данных с коррекциями.
- **Тест пересчёта после сторно**: сторно уменьшает показатели дня **исходной** записи; отдельный
  тест на границу месяца (исходная запись — 31-го, сторно — 2-го числа следующего).
- **Тест восстановимости**: полное удаление rollup и пересчёт из фактов дают идентичный результат —
  подтверждает, что rollup производен.
- **Сверочный джоб «rollup ↔ факты»**: расхождение даёт метрику и алерт, а не тихую коррекцию.
- **Тест производительности дашборда**: запрос дашборда за квартал по организации укладывается в
  бюджет времени на эталонном наборе данных; регрессия ломает сборку.
- **Визуальная регрессия графиков** в светлой и тёмной теме; тест контраста цветов серий по WCAG.
- **`size-limit`**: чанк с ECharts не входит в основной бандл — проверяется отдельной строкой
  бюджета.
- Гейт-агент `db-reviewer` (правила проекта) — для изменений в схеме rollup и в аналитических
  запросах.
