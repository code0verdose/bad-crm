# ADR-0019 — Локализация EN/RU на i18next, серверные ошибки как коды

## Контекст

Bad CRM с первого релиза говорит на двух языках: английском и русском. Причина не в размере
аудитории, а в природе задачи: **второй язык, введённый с первого дня, не даёт накопиться
хардкод-строкам.** Ретроспективная интернационализация приложения на десятки экранов — это недели
механической работы и гарантированные пропуски в `aria-label`, `title`, `placeholder`,
`document.title` и текстах live-region, которые забывают в первую очередь.

Особенности, влияющие на решение:

**Строки живут не только в JSX.** Label-map статусов, заголовки колонок таблиц, названия видов
активности, тексты состояний — всё это объявляется в `.ts`-файлах доменных юнитов
([ADR-0005](0005-fsd-units-frontend-architecture.md)).

**Ошибки приходят с сервера.** Сервер отдаёт `application/problem+json` (RFC 9457) —
[ADR-0003](0003-openapi-as-source-of-truth.md). Он не знает и не должен знать язык пользователя:
одна и та же ошибка может пойти в браузер, в лог, в интеграцию и в CLI.

**Русский требует трёх форм множественного числа** (`one` / `few` / `many`) против двух в
английском, и это ломает наивную схему «строка + счётчик».

**Русский длиннее английского на 15–30 %**, отдельные термины — вдвое («Settings» → «Настройки»,
«Time tracking» → «Учёт рабочего времени»). Это вопрос вёрстки, а не перевода.

**Деньги и даты не следуют из локали.** Валюта — свойство контракта или счёта, а не языка
интерфейса: русский интерфейс может показывать USD.

## Решение

**`i18next` + `react-i18next`. Ресурсы разбиты по namespace, совпадающим с юнитами. Серверные
ошибки — коды, переводимые на клиенте. Непереведённые ключи проверяются в CI.**

**Раскладка namespace:**

```
src/shared/i18n/locales/
  en/
    common.json        # кнопки, действия, состояния, единицы
    validation.json    # тексты ошибок Zod
    errors.json        # серверные коды ошибок → человеческий текст
    nav.json           # названия разделов
    auth.json  projects.json  tasks.json  docs.json  kb.json
    chat.json  files.json  vault.json  time.json  reports.json
    delivery.json  onboarding.json  admin.json  ai.json
  ru/ … (та же структура)
```

`common` и `validation` загружаются всегда; доменные namespace — **лениво вместе с чанком
маршрута**, что совпадает с границами code-splitting ([ADR-0007](0007-tanstack-router-and-query.md)).

**Правила ключей.** Иерархические и семантические (`tasks.board.column.empty.title`), не по тексту
(`tasks.click_here` — плохо). Ключ **никогда не собирается конкатенацией в рантайме** — иначе его
нельзя найти статически, и проверка полноты перевода становится невозможной.

**Никаких хардкод-строк в JSX.** Правило ESLint `i18next/no-literal-string` с разумным whitelist
(числа, `·`, `—`, коды и ключи задач); нарушение ломает сборку. Пользовательский текст в
`.ts`-файлах хранится **как ключ**, а не как готовая строка:

```ts
{ value: 'paid', labelKey: 'delivery.invoice.status.paid' }
```

Перевод происходит в компоненте через `t(labelKey)`. Тексты для `aria-label`, `title`,
`placeholder`, `document.title` и сообщений live-region переводятся так же.

**Серверные ошибки — коды, а не строки.** Сервер возвращает `problem+json` со стабильным `type`-URI
и машиночитаемым кодом; человеческий текст живёт в `errors.json` на клиенте. Следствия:

- один и тот же отказ читается по-русски в UI, по-английски в логе и разбирается программно в
  интеграции;
- сервер не содержит текстов интерфейса и не зависит от локали запроса;
- `DenyReason` из модели прав ([ADR-0008](0008-permission-model-rbac-plus-acl.md)) попадает в тот же
  словарь: «не хватает права X» и «нет доступа к этому объекту» — разные сообщения.

Исключение: тексты, которые сервер отправляет **вне** интерфейса (письма, экспорт) — они
рендерятся по локали получателя из профиля.

**Плюрализация — через `Intl.PluralRules` в i18next:**

```json
// en/tasks.json
{ "selected_one": "{{count}} task selected", "selected_other": "{{count}} tasks selected" }
// ru/tasks.json
{ "selected_one": "{{count}} задача выбрана",
  "selected_few": "{{count}} задачи выбрано",
  "selected_many": "{{count}} задач выбрано" }
```

Ноль обрабатывается отдельным ключом там, где «0 задач» звучит плохо. **Никакой сборки предложений
из кусков** («Удалено » + n + « задач») — только интерполяция с плюрализацией. Перечисления —
`Intl.ListFormat`, а не `join(', ')`.

**Даты, числа, валюты — только `Intl.*`** (`DateTimeFormat`, `NumberFormat`, `RelativeTimeFormat`),
обёртки в `shared/lib/format`. Хранение и передача — всегда ISO 8601 в UTC; отображение — в часовом
поясе пользователя. Первый день недели — из локали (RU — понедельник), что влияет на раскладку
таймшитов и календаря. Деньги — минорные единицы целым числом на бэкенде, форматирование
`Intl.NumberFormat` с валютой из документа, а не из локали.

**Длина строк — вопрос вёрстки:** кнопки, вкладки, чипы и пункты навигации без фиксированной
ширины (`min-width`, не `width`); заголовки колонок не обрезаются многоточием там, где текст несёт
смысл; все компоненты `shared/ui` проверяются в Storybook с **псевдолокалью, удлиняющей строки на
40 %**.

**Выбор языка** хранится в профиле (переносится между устройствами) и дублируется в `localStorage`
для мгновенного применения до загрузки сессии. Порядок: профиль → `localStorage` →
`navigator.language` → `en`. Язык влияет на `<html lang>` — это нужно скринридерам.

**RTL не поддерживается**, но стили пишутся логическими свойствами (`margin-inline-start`,
`inset-inline-end`), чтобы будущая поддержка была правкой темы, а не переписыванием.

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **Только английский** | Вдвое меньше работы; нет словарей, нет плюрализации, нет проблем с длиной строк; проще ревью | Целевая аудитория проекта включает русскоязычные команды, для которых английский интерфейс — барьер; главное — **ретроспективная интернационализация дороже в разы**: тысячи строк по всему коду, включая незаметные `aria-label` и `title` | Второй язык с первого дня — это дисциплина, которая стоит дёшево сейчас и очень дорого потом. Решение не про перевод, а про предотвращение долга |
| **react-intl (FormatJS)** | Полноценный ICU MessageFormat с богатыми конструкциями (`select`, вложенная плюрализация, `selectordinal`); отличные инструменты извлечения сообщений; строгая типизация | Сообщения по умолчанию определяются в коде (`defineMessages`) и извлекаются сборкой — расходится с моделью «словари как данные, которые правит переводчик»; тяжелее ленивая подгрузка по namespace; больше церемонии | i18next даёт нужное подмножество ICU через `Intl.PluralRules` при более простой модели «JSON-словари, лениво загружаемые по namespace», что прямо ложится на FSD-раскладку |
| **Lingui** | Компактный синтаксис, извлечение сообщений из JSX без ручных ключей, компиляция каталогов, хорошая типизация | Требует babel/swc-плагина в сборке; сообщения-как-ключи усложняют повторное использование одной строки в разных контекстах; экосистема меньше | Хороший инструмент; проигрывает по простоте интеграции и по объёму материалов для контрибьютора |
| **Собственный словарь** (`const t = { ru: {...}, en: {...} }`) | Ноль зависимостей; полный контроль | Плюрализация русского, интерполяция, ленивая загрузка, fallback и определение локали пишутся руками; отсутствие инструментов проверки полноты | Изобретение велосипеда в области с готовыми решениями |
| **Перевод серверных ошибок на сервере** (по заголовку `Accept-Language`) | Клиенту не нужен словарь ошибок; текст ошибки одинаков во всех каналах | Сервер обрастает текстами интерфейса и словарями; ошибка в логе оказывается на языке пользователя, что усложняет поддержку; интеграции получают человеческий текст вместо машиночитаемого кода; локаль в заголовке не совпадает с настройкой профиля | Коды на сервере, тексты на клиенте — разделение, которое сохраняет и машиночитаемость, и переводимость. Обратный порядок теряет и то, и другое |
| **Автоматический перевод (машинный) недостающих ключей** | Быстрое покрытие; нет «пустых» мест в интерфейсе | Терминология домена переводится некорректно и непоследовательно; ошибочный перевод в интерфейсе прав или в предупреждении о разрушающем действии — это риск, а не косметика | Недостающий ключ должен быть виден и починен, а не замаскирован |
| **Ключи, собираемые конкатенацией** (`t('status.' + value)`) | Меньше кода, компактно | Ключ невозможно найти статически — проверка полноты перевода и удаление мёртвых ключей перестают работать | Прямо запрещено правилом; label-map с явными `labelKey` решает ту же задачу без потери статичности |

## Последствия

### Положительные

- **Хардкод-строки не накапливаются** — правило линтера ловит их в момент написания.
- **Словари — данные**, которые может править переводчик без доступа к коду.
- **Namespace совпадают с юнитами**, поэтому словарь грузится вместе с чанком маршрута и не
  утяжеляет первую загрузку.
- **Серверные ошибки машиночитаемы** и одновременно переводимы: один код — три потребителя (UI,
  лог, интеграция).
- **Плюрализация корректна для русского** без ручных правил.
- **Даты, числа и валюты форматируются `Intl`** — нет ручных шаблонов `dd.MM.yyyy`, разбросанных по
  компонентам.
- **Смена языка не требует перезагрузки** и переносится между устройствами через профиль.
- **Псевдолокаль ловит переполнение вёрстки до появления перевода.**
- **Логические CSS-свойства** оставляют дверь для RTL открытой почти бесплатно.

### Отрицательные / цена

- **Каждая строка — это ключ в двух файлах.** Дисциплина требуется постоянно, и она замедляет
  написание кода.
- **Именование ключей — отдельная работа.** Плохая иерархия делает словарь неподдерживаемым так же,
  как плохие имена переменных делают неподдерживаемым код.
- **Перевод отстаёт от разработки.** Между добавлением функции и переводом строк проходит время;
  нужен явный fallback и его политика (показывать английский, а не ключ).
- **Мёртвые ключи накапливаются**, если их не чистить: удалённый компонент оставляет строки в
  словарях.
- **Разная длина строк усложняет вёрстку** — часть решений (перенос вместо обрезки, `min-width`)
  принимается ради русского и слегка ухудшает плотность английского интерфейса.
- **Двойное место для текстов ошибок**: код на сервере, текст на клиенте — расхождение возможно,
  если код добавлен, а строка нет.
- **Whitelist правила `no-literal-string`** требует поддержки: слишком строгий — мешает, слишком
  мягкий — пропускает.

### Что становится трудно изменить позже

- **Ключи становятся структурой словарей**, которые могут переводиться внешними участниками (или
  сервисами перевода). Массовое переименование ключей обесценивает уже сделанные переводы и
  ломает историю их изменений.
- **Разбиение по namespace** связано с code-splitting'ом и с границами юнитов: перекройка namespace
  требует одновременного пересмотра ленивой загрузки словарей.
- **Коды серверных ошибок — часть публичного контракта API** ([ADR-0003](0003-openapi-as-source-of-truth.md)).
  Внешние интеграции разбирают их программно; переименование кода — ломающее изменение, а не
  правка текста.
- **Схема плюрализации** (суффиксы `_one` / `_few` / `_many`) зашита во все счётные строки; переход
  на другую библиотеку с другим синтаксисом — массовая конвертация словарей.
- **Правило «валюта из документа, а не из локали»** заложено в форматтеры и в модель данных;
  обратное решение потребовало бы пересмотра всех финансовых экранов.
- **Добавление третьего языка дешёво** (это как раз то, ради чего решение принято), но
  **добавление RTL-языка** потребует ревизии всех стилей, где логические свойства были нарушены —
  а нарушения накапливаются незаметно, если их не проверять.

## Проверяемость

- **CI-проверка непереведённых ключей (обязательная)**: скрипт сравнивает наборы ключей `en` и `ru`
  по всем namespace. Ключ, присутствующий в одном языке и отсутствующий в другом, — падение
  сборки. Это основной механизм, не дающий переводу отстать незаметно.
- **CI-проверка мёртвых ключей**: ключи, не встречающиеся в исходниках (с учётом `labelKey`-полей),
  выводятся отчётом; порог допустимого количества — ноль для новых.
- **ESLint `i18next/no-literal-string`** с whitelist — литеральные строки в JSX ломают сборку.
- **Тест на конкатенацию ключей**: правило линтера запрещает `t()` с вычисляемым аргументом, кроме
  явных `labelKey` из типизированных label-map.
- **Тесты плюрализации** для русского: 1 / 2 / 5 / 21 / 0 дают корректные формы; аналогично для
  английского.
- **Тесты форматирования**: даты в часовом поясе пользователя, первый день недели по локали, деньги
  с валютой документа (RU-локаль + USD), длительности (`7:30`, `7 ч 30 мин`) и парсинг ввода
  (`7:30`, `7.5`, `450m`) Zod-схемой.
- **Storybook с псевдолокалью +40 %** — все компоненты `shared/ui` проверяются на переполнение.
- **Тест `<html lang>`**: атрибут меняется вместе с локалью — проверяется в e2e.
- **Тест публичных экранов**: `/login` и `/link/$token` имеют собственный переключатель языка (до
  логина профиля нет).
- **Тест соответствия кодов ошибок**: каждый код ошибки, объявленный в спеке OpenAPI и в
  `DenyReason`, имеет строку в `errors.json` обоих языков — расхождение ломает сборку.
- Гейт-агент `accessibility-expert` (правила проекта) — проверка переведённых `aria-label` и
  сообщений live-region для новых интерактивных компонентов.
