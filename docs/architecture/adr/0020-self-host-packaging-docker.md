# ADR-0020 — Пакетирование self-host: docker compose с профилями `full` и `minimal`

## Контекст

Bad CRM распространяется под AGPL-3.0 ([ADR-0018](0018-license-agpl-3.md)) как self-hosted продукт.
Способ установки — не деталь эксплуатации, а часть продукта: он определяет, сколько людей вообще
попробуют систему.

Портрет типового пользователя: небольшая студия или команда разработки, у которой есть один VPS и
администратор с базовым опытом Docker. У него нет кластера Kubernetes, нет платформенной команды и
нет желания разбираться в устройстве приложения, чтобы его запустить.

Из этого следует ключевое требование, зафиксированное в [`../stack.md`](../stack.md): **любой
человек должен уметь поднять проект одной командой `docker compose up`.** Оно определило и
консервативность стека, и опциональность всего «дорогого» (поиск, AI).

Второе требование — **работа на скромном железе**. Полный стек (приложение + Postgres + Redis +
MinIO + Meilisearch) не помещается в 2 GB RAM с комфортом. При этом отказывать пользователю с
маленьким VPS нельзя.

Третье — **обновление выполняет владелец инсталляции, а не мы**. Он не читал наш код, не знает
порядка миграций и не будет вручную выполнять шаги. Обновление обязано быть одной командой и не
должно ломать данные.

Четвёртое — **безопасные значения по умолчанию**. Опыт индустрии однозначен: инсталляция с
дефолтным паролем базы, открытым наружу портом Postgres и сгенерированным «на всякий случай»
секретом JWT — это будущий инцидент.

Пятое — приложение должно **честно сообщать о неверной конфигурации при старте**, а не падать через
час на первом обращении к недоступному сервису.

## Решение

**Основной путь установки — Docker + docker compose. Два профиля ресурсов. Миграции выполняются при
старте отдельным одноразовым контейнером. Конфигурация валидируется схемой с fail-fast.**

**Один образ, три роли.** `ROLE=api` (HTTP + Socket.IO), `ROLE=worker` (обработка outbox и очередей),
`ROLE=migrate` (одноразовый job). Разделение по роли, а не по образу: сборка одна, поведение задаётся
переменной. Это позволяет в профиле `scaled` вынести воркеры в отдельные контейнеры без второй
сборки.

**Профили развёртывания:**

| Профиль | Сервисы | CPU / RAM | Аудитория |
|---|---|---|---|
| `minimal` | app + Postgres + Redis + MinIO | 2 vCPU / 2 GB | до ~20 активных пользователей, без поиска и AI |
| `default` (`full`) | + Meilisearch | 2 vCPU / 4 GB | до ~100 пользователей |
| `scaled` | + отдельные worker-контейнеры, внешний S3 / managed Postgres | 4+ vCPU / 8+ GB | 100+ пользователей, несколько организаций |

В профиле `minimal` контейнер Meilisearch не поднимается: `SearchPort` резолвится в
`postgres-fts.adapter.ts` ([ADR-0011](0011-meilisearch-permission-aware-search.md)), AI-функции
отключены флагом и скрыты в UI ([ADR-0014](0014-ai-provider-abstraction.md)). **Приложение обязано
стартовать и работать без Meilisearch и без AI-ключей — деградация функций, а не отказ.** Переход
`minimal → full` — поднять контейнер и запустить полную переиндексацию из БД, без миграции данных.

**Миграции при старте.** Одноразовый контейнер `migrate` выполняется до старта `api` и `worker`.
Роль-владелец схемы (`app_migrator`) отличается от роли приложения (`app_user`, без `BYPASSRLS`) —
см. [ADR-0004](0004-multi-tenancy-postgres-rls.md). Стратегия миграций — `expand → migrate →
contract`: миграции совместимы вперёд на один релиз, поэтому сначала применяется схема, потом
стартует новый код, и обновление одноинстансной инсталляции не требует окна простоя больше рестарта.

**Безопасные дефолты.** Ни одного «работающего из коробки» секрета: `docker compose up` без
подготовленного `.env` **не стартует**, а печатает, чего не хватает. Скрипт первичной настройки
генерирует случайные значения для паролей БД, ключей MinIO, секретов JWT и ключа инсталляции.
Порты Postgres, Redis, MinIO и Meilisearch **не публикуются наружу** — только во внутреннюю сеть
compose; наружу смотрит один reverse-proxy с TLS.

**Fail-fast проверка окружения при старте:**

1. Env валидируется Zod-схемой ([`../stack.md`](../stack.md), «Конфигурация и env») — отсутствующая
   или некорректная переменная останавливает старт с внятным сообщением, а не с трассировкой стека.
2. Проверяются связность и версии: Postgres доступен и имеет требуемые расширения (`pgvector`,
   `btree_gist`), Redis отвечает, бакет MinIO существует.
3. Проверяется роль БД: если `current_user = app_migrator` — отказ стартовать (роль приложения не
   должна обходить RLS).
4. Опциональные сервисы (Meilisearch, AI) проверяются мягко: недоступность переводит функцию в
   отключённое состояние и пишет предупреждение, но не блокирует старт.

**Reverse-proxy** (Caddy / nginx / Traefik) терминирует TLS и обеспечивает **sticky sessions** на
`/socket.io`, пока разрешён polling-fallback ([ADR-0010](0010-realtime-socketio-redis-adapter.md)).

**Тома и бэкап:**

- `pgdata` — истина по всем данным, включая шифротекст vault. **Бэкап обязателен.**
- `minio-data` — тела файлов. **Бэкап обязателен.**
- `meili-data` — **не бэкапится**: индекс восстанавливается переигрыванием из БД.
- `redis-data` — не критичен: очереди восстанавливаются из outbox
  ([ADR-0021](0021-transactional-outbox.md)), presence эфемерен.

**Kubernetes не является основным путём.** Манифесты или Helm-чарт возможны как community-дополнение,
но они не определяют архитектуру. Это зафиксировано в «Что осознанно НЕ делаем сейчас».

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **Helm / Kubernetes как основной путь** | Промышленный стандарт для крупных инсталляций; декларативное описание, автоматическое восстановление, готовые механизмы масштабирования и rolling-обновлений; хорошо ложится на профиль `scaled` | Требует кластера — то есть отсекает основную аудиторию с одним VPS; порог входа несопоставимо выше; отладка «почему не поднялось» требует навыков, которых у целевого пользователя нет; чарт нужно поддерживать наравне с compose | Прямо противоречит «одной команде». Оставлено как community-дополнение: архитектура (один образ, роли через env, отсутствие локального состояния) чарту не мешает |
| **Единый бинарник** (embedded Postgres/SQLite, всё в одном процессе) | Максимально просто: скачал и запустил; ноль зависимостей; привычно по опыту Gitea, Grafana, Plausible | Продукту нужны PostgreSQL 16 с RLS, pgvector и `btree_gist` — встроить это в бинарник нереально; Redis, MinIO и Meilisearch тоже внешние; SQLite не даёт RLS и части ограничений, на которых держится модель данных ([ADR-0004](0004-multi-tenancy-postgres-rls.md), [ADR-0016](0016-time-tracking-single-entry-model.md)) | Архитектурно невозможно без отказа от гарантий, ради которых выбран Postgres |
| **Только облачная версия (SaaS)** | Простейшая эксплуатация; контроль над окружением; понятная монетизация | Противоречит сути продукта: self-hosted, AGPL, «данные не покидают ваш периметр»; обещание E2EE в SaaS теряет часть смысла ([ADR-0009](0009-e2ee-vault-key-hierarchy.md)) | Не рассматривалось как основной путь: это другой продукт |
| **Только исходники** (собери и настрой сам) | Ноль работы по пакетированию; максимальная гибкость | Отсекает почти всех: настройка Postgres с расширениями, ролями, RLS, MinIO, Redis и reverse-proxy вручную — часы работы и множество способов ошибиться; воспроизводимость сборки для E2EE теряется | Барьер входа убивает распространение продукта |
| **Docker без compose** (документация с командами `docker run`) | Меньше файлов | Сеть, тома, порядок запуска и зависимости описываются вручную в документации, которая устаревает; обновление превращается в последовательность команд | Compose и есть декларативное описание того же самого, только проверяемое |
| **Миграции вручную перед обновлением** (отдельная команда для администратора) | Полный контроль: администратор видит, что применяется, и может сделать бэкап | Шаг, который забудут; приложение стартует на несовместимой схеме и падает в рантайме; поддержка получает поток одинаковых обращений | Автоматический одноразовый контейнер с совместимыми вперёд миграциями надёжнее. Бэкап перед обновлением остаётся требованием runbook'а |
| **Миграции внутри процесса приложения** (при старте `api`) | Одним контейнером меньше | При нескольких экземплярах API миграции стартуют параллельно — гонка; приложению потребовались бы DDL-права, то есть роль с `BYPASSRLS` — прямое нарушение модели изоляции | Отдельный контейнер с отдельной ролью — единственный безопасный вариант |
| **Дефолтные секреты «для быстрого старта»** | Меньше трения при первом запуске: `docker compose up` работает сразу | Инсталляции с дефолтным паролем БД и предсказуемым секретом JWT попадают в интернет — это класс инцидентов, повторяющийся в индустрии годами | Отказ стартовать без подготовленного `.env` — небольшая цена за отсутствие категории уязвимостей |

## Последствия

### Положительные

- **Порог входа минимален**: `docker compose up` после генерации `.env` даёт рабочую систему.
- **Профиль `minimal` работает на 2 GB RAM** — продукт доступен владельцам самых дешёвых VPS.
- **Обновление — одна команда**: `pull` + `up`, миграции применяются сами и совместимы вперёд.
- **Нет инсталляций с дефолтными секретами** — они не стартуют.
- **Неверная конфигурация обнаруживается за секунды**, а не через час в проде.
- **Внутренние сервисы не торчат наружу** — только reverse-proxy.
- **Один образ на три роли** упрощает сборку, версионирование и переход к профилю `scaled`.
- **Бэкап понятен**: два тома, остальное восстановимо.
- **Архитектура остаётся совместимой с Kubernetes** (нет локального состояния, роли через env),
  поэтому чарт от сообщества возможен без переделок.

### Отрицательные / цена

- **Docker обязателен.** Установка без него не поддерживается; пользователи без Docker остаются за
  бортом.
- **Compose не даёт высокой доступности**: один хост — единая точка отказа. Для целевой аудитории
  приемлемо, но это ограничение нужно называть прямо.
- **Профили нужно тестировать отдельно.** `minimal` без Meilisearch — это отдельная конфигурация,
  которая тихо ломается, если её не проверять в CI.
- **Миграции при старте требуют дисциплины «expand → migrate → contract»** на каждом релизе. Одна
  несовместимая вперёд миграция — и обновление ломает работающую инсталляцию у чужого человека.
- **Sticky sessions** — требование к reverse-proxy, о котором владелец должен знать; забытая
  настройка даёт трудноуловимые обрывы realtime.
- **Обновление образа перезапускает сервис** — короткий простой при одноинстансной установке.
- **Разные профили дают разное поведение продукта** (поиск, AI), что усложняет поддержку: первый
  вопрос при обращении — «какой у вас профиль».
- **Требование `.env` перед первым запуском** добавляет шаг, который придётся объяснять в README и
  который часть пользователей воспримет как неудобство.

### Что становится трудно изменить позже

- **Имена сервисов, томов и переменных окружения** становятся частью инсталляций на чужих серверах.
  Переименование тома означает потерю данных при обновлении, если владелец не выполнит ручную
  миграцию, — то есть его нельзя делать вообще, только через слой совместимости.
- **Схема миграций при старте** зафиксирована как контракт обновления: любое изменение (например,
  переход к ручным миграциям) ломает ожидания уже установленных систем.
- **Совместимость миграций вперёд на один релиз** — обещание, на которое опирается обновление без
  простоя. Его нарушение обнаруживается только у пользователя.
- **Границы профилей** (`minimal` = без Meilisearch и AI) зашиты в composition root, в UI-флаги и в
  документацию. Перенос функции между профилями меняет требования к железу у существующих
  инсталляций.
- **Правило «Meilisearch не бэкапится»** попадает в runbook. Если однажды в индексе окажутся данные,
  которых нет в БД, процедура восстановления станет разрушительной
  ([ADR-0011](0011-meilisearch-permission-aware-search.md)).
- **Разделение ролей БД** (`app_user` / `app_migrator` / `app_auth`) выполнено на чужих серверах;
  изменение схемы ролей требует ручных действий владельца, то есть перестаёт быть «одной командой».
- **Отказ от Kubernetes как основного пути** означает, что чарт, если он появится, всегда будет
  вторичным и будет отставать от compose.

## Проверяемость

- **CI-тест «поднимается одной командой»**: workflow генерирует `.env`, выполняет
  `docker compose up`, дожидается health-check и прогоняет smoke-набор e2e. Ломается — ломается
  сборка.
- **CI-тест профиля `minimal`**: тот же сценарий без Meilisearch и без AI-ключей; проверяется, что
  поиск работает через Postgres FTS, AI-эндпоинты возвращают «функция отключена», health-check
  зелёный. Это единственная защита от тихой деградации профиля.
- **Тест отказа при дефолтных секретах**: запуск без `.env` или с плейсхолдерами завершается
  ненулевым кодом и внятным сообщением; тест утверждает наличие сообщения, а не только код возврата.
- **Тест fail-fast валидации env**: для каждой обязательной переменной отдельный кейс —
  отсутствующее и некорректное значение останавливают старт.
- **Тест проверки роли БД**: старт под `app_migrator` отклоняется.
- **Тест расширений**: отсутствие `pgvector` или `btree_gist` останавливает старт с указанием, чего
  не хватает.
- **Тест обновления (upgrade path)**: разворачивается предыдущий релиз, наполняется данными,
  обновляется до текущего — миграции применяются, данные целы, приложение работает. Прогоняется на
  каждый релиз.
- **Тест совместимости вперёд**: новая схема применяется, **старый** код продолжает работать —
  проверка дисциплины `expand → migrate → contract`.
- **Тест портов**: сканирование опубликованных портов в compose — наружу смотрит только
  reverse-proxy.
- **Тест восстановления из бэкапа**: `pgdata` + `minio-data` восстанавливаются, индекс
  переигрывается, система работает — подтверждает, что список бэкапируемых томов полон.
- Гейт-агент `production-readiness` (правила проекта) — обязателен для изменений в compose,
  миграционном тракте и конфигурации; изменения фиксируются в журнале devops-истории.
