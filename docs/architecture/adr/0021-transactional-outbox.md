# ADR-0021 — Транзакционный outbox как единственная точка побочных эффектов

## Контекст

Практически каждое изменение данных в Bad CRM порождает побочные эффекты за пределами транзакции:

| Изменение | Побочные эффекты |
|---|---|
| задача перемещена | обновить поисковый индекс, разослать realtime-событие, создать уведомления наблюдателям |
| документ отредактирован | переиндексация, пересчёт эмбеддингов, realtime |
| время подтверждено | пересчёт `TimeRollupDaily`, уведомление, влияние на счёт |
| ACL проекта изменён | переиндексация **всех** вложенных сущностей (иначе человек, лишённый доступа, продолжит находить документы поиском) |
| файл закоммичен | индексация, превью, уведомление |

Наивная реализация — вызвать индексатор, отправить событие и создать уведомление прямо в use-case,
после `COMMIT`. Это классический **dual-write**, и он ломается предсказуемо:

- **Транзакция зафиксировалась, вызов индексатора упал** (сеть, рестарт Meilisearch) → данные и
  индекс разошлись, и никто об этом не узнает: HTTP-ответ был 200.
- **Индексация прошла, транзакция откатилась** (конфликт, ошибка позже в коде) → в индексе есть
  документ, которого нет в БД.
- **Процесс убит между `COMMIT` и вызовом** → эффект потерян бесследно.

Особенность продукта: **потребителей эффекта пять и их число растёт** — поиск
([ADR-0011](0011-meilisearch-permission-aware-search.md)), realtime
([ADR-0010](0010-realtime-socketio-redis-adapter.md)), уведомления, rollup-таблицы
([ADR-0017](0017-charts-mantine-charts.md)), эмбеддинги для RAG
([ADR-0014](0014-ai-provider-abstraction.md)). Прямые вызовы означают, что каждый use-case знает
про всех пятерых, и добавление шестого — правка всех use-cases.

Ограничение развёртывания: любое решение должно работать в `docker compose up`
([ADR-0020](0020-self-host-packaging-docker.md)) — то есть без дополнительной инфраструктуры.

## Решение

**Единая таблица `OutboxEvent`. Событие записывается в той же транзакции, что и доменное изменение.
Воркер на BullMQ разбирает очередь с ретраями, DLQ и reconciliation. Прямых побочных эффектов из
use-case не существует.**

**Модель:**

| Поле | Назначение |
|---|---|
| `aggregateType`, `aggregateId` | что изменилось |
| `eventType` | что произошло |
| `payload Json` | минимальный контекст |
| `status` | `PENDING` → `PROCESSING` → `SENT` / `FAILED` / `DEAD` |
| `attempts`, `availableAt` | экспоненциальный backoff |
| `lockedBy`, `lockedAt` | владелец обработки, поиск зависших |
| `lastError`, `processedAt` | диагностика |

Таблица под RLS, как и все данные арендатора ([ADR-0004](0004-multi-tenancy-postgres-rls.md)).

**Запись — атомарна с изменением:**

```
BEGIN + SET LOCAL app.organization_id
UPDATE task ...
INSERT OutboxEvent(type, payload, orgId)
COMMIT
```

Событие не может потеряться при успешной записи и не может появиться при откате. Это единственное
свойство, ради которого решение принимается.

**Выборка воркером:**

```sql
UPDATE outbox_events SET status='PROCESSING', locked_by=$worker, locked_at=now()
WHERE id IN (
  SELECT id FROM outbox_events
  WHERE status='PENDING' AND available_at <= now()
  ORDER BY available_at
  FOR UPDATE SKIP LOCKED LIMIT 100
) RETURNING *;
```

`FOR UPDATE SKIP LOCKED` — ключевая деталь: несколько воркеров разбирают очередь параллельно, не
блокируя друг друга и не обрабатывая одно событие дважды.

**Дальше — BullMQ поверх уже имеющегося Redis:** воркер ставит задания по типу события, BullMQ даёт
ретраи с экспоненциальной задержкой, отложенные и повторяющиеся задания и dead-letter очередь.
После исчерпания попыток событие остаётся в БД со статусом `DEAD`, **а не исчезает** — его можно
разобрать вручную.

**Reconciliation-джоб** периодически возвращает в работу: события `PENDING` старше порога (воркер
упал между выборкой и постановкой в очередь) и события `PROCESSING`, зависшие дольше таймаута
(воркер умер во время обработки). Индекс `idx_outbox_stuck (locked_at) WHERE status = 'PROCESSING'`
существует именно для этого.

**Свойства и их прямые следствия:**

- **Доставка at-least-once** → **каждый обработчик обязан быть идемпотентным**. Ключ
  идемпотентности — `outboxEventId` + имя обработчика. Это не рекомендация: повторная обработка
  гарантированно случится.
- **Воркер выставляет tenant-контекст на каждое событие отдельно** — пачка принадлежит разным
  организациям.
- **Поисковый индекс и rollup-таблицы — производное состояние**: их можно удалить и восстановить
  переигрыванием из БД. Это же делает Meilisearch не-бэкапируемым
  ([ADR-0020](0020-self-host-packaging-docker.md)).
- **Индексы под нагрузку**: `idx_outbox_pending (status, available_at) WHERE status IN
  ('PENDING','FAILED')` — узкий частичный индекс, в который не входят обработанные события (99 %
  таблицы), поэтому опрос очереди остаётся дешёвым независимо от размера истории.

**Правило для разработчика формулируется одной строкой: побочный эффект — это `INSERT` в
`OutboxEvent`, а не вызов сервиса.**

## Альтернативы (и почему отвергнуты)

| Альтернатива | Плюсы | Минусы | Почему отвергнута |
|---|---|---|---|
| **Прямая публикация из use-case** (вызвать индексатор, broadcast и уведомления после commit) | Проще всего; эффект наступает мгновенно, без задержки воркера; меньше движущихся частей; легче отлаживать «здесь и сейчас» | Классический dual-write: расхождение при падении между commit и вызовом, и это расхождение **не диагностируется** — ответ уже 200; откат транзакции после успешной публикации даёт фантомные события; каждый use-case знает про всех потребителей; ретраи и обработка ошибок дублируются в каждом месте | Единственная альтернатива, дающая мгновенность, но она теряет данные тихо. Для системы, где индекс и rollup участвуют в финансовых отчётах, тихое расхождение неприемлемо |
| **Dual-write с ретраями в памяти** (очередь в процессе, повтор при ошибке) | Не требует таблицы; быстрее | Рестарт процесса теряет очередь; при нескольких экземплярах нет координации; ровно те же гонки, только замаскированные | Половинчатая мера, создающая иллюзию надёжности |
| **CDC / Debezium** (чтение WAL PostgreSQL, публикация в Kafka) | Приложение вообще не думает о событиях — они выводятся из журнала БД; невозможно «забыть» опубликовать; строгий порядок; отличная масштабируемость | Требует Kafka (или Redpanda) плюс Debezium-коннектор — два дополнительных сервиса, несовместимых с «одной командой»; события получаются на уровне строк, а не доменных фактов («изменилась строка tasks» вместо «задача перемещена») — семантику приходится восстанавливать; logical replication требует настройки Postgres, которую владелец инсталляции делать не будет | Инфраструктурная цена несовместима с моделью поставки. Плюс row-level события хуже доменных: обработчик уведомлений должен знать, что именно произошло, а не какие колонки изменились |
| **Kafka как шина событий** (без CDC, публикация приложением) | Промышленный стандарт; порядок, партиционирование, ретеншн, много потребителей; отличная пропускная способность | Несоразмерна масштабу (десятки событий в секунду в пике); ещё один тяжёлый сервис в compose с собственной эксплуатацией; **и всё равно не решает исходную задачу** — публикация в Kafka из use-case это тот же dual-write | Kafka — транспорт, а не гарантия атомарности. Проблему решает outbox, а не брокер |
| **Только BullMQ без таблицы outbox** (ставить задание в очередь из use-case) | Меньше кода, нет своей таблицы, ретраи и DLQ уже есть | Постановка в Redis-очередь не атомарна с транзакцией БД: commit прошёл — постановка упала, или наоборот; Redis не является durable-хранилищем в той же мере, что Postgres | То же самое дублирование записи, только в Redis. BullMQ используется — но **после** outbox, как транспорт заданий, а не как источник истины |
| **Триггеры БД, пишущие события** | Невозможно забыть: событие пишется базой; атомарность гарантирована | Бизнес-логика уезжает в SQL-триггеры — плохо тестируется, плохо ревьюится, скрыто от разработчика; доменная семантика события в триггере невыразима; конфликтует с гексагональной архитектурой ([ADR-0002](0002-hexagonal-backend-express-prisma.md)) | Гарантия покупается ценой размазывания логики по слоям, которые мы намеренно держим тонкими |
| **Отдельная таблица outbox на каждый тип потребителя** | Независимые очереди, изоляция отказов, разные политики ретраев | Умножение одинаковой инфраструктуры; событие, нужное трём потребителям, пишется трижды; reconciliation дублируется | Единая таблица с маршрутизацией по `eventType` в воркере даёт то же самое без дублирования |

## Последствия

### Положительные

- **Событие и запись атомарны.** «Задача перемещена, но уведомление не ушло» невозможно при
  успешной транзакции.
- **Одна точка ретраев, DLQ и наблюдаемости** вместо разбросанной обработки ошибок.
- **Use-case не знает потребителей.** Добавление шестого (например, вебхуков наружу) — новый
  обработчик, а не правка всех сценариев.
- **Производное состояние восстановимо**: индекс и rollup переигрываются из БД; это упрощает и
  бэкап, и восстановление после аварии.
- **Ничего не теряется молча**: неудачное событие остаётся в БД со статусом `DEAD` и последней
  ошибкой.
- **Reconciliation закрывает разрывы**, вызванные падением воркера.
- **Не требует новой инфраструктуры** — Postgres и Redis уже в compose.
- **Прослеживаемость**: `requestId` кладётся в payload и восстанавливается воркером, поэтому цепочка
  «HTTP-запрос → событие → job → broadcast» видна по одному идентификатору
  ([`../overview.md`](../overview.md), «Observability»).

### Отрицательные / цена

- **Все побочные эффекты асинхронны.** Пользователь может не увидеть только что созданную задачу в
  поиске, а дашборд — свежие часы. Это меняет UX-ожидания и требует объяснения в интерфейсе.
- **Идемпотентность обязательна для каждого обработчика.** At-least-once означает, что повтор
  случится; необработанный повтор даёт дубли уведомлений или двойной инкремент rollup — то есть
  порчу данных.
- **Таблица растёт.** Требуется политика очистки обработанных событий (или партиционирование);
  без неё таблица становится крупнейшей в БД.
- **Дополнительная запись в каждой транзакции** — небольшая, но постоянная нагрузка.
- **Лавинообразные события.** Изменение ACL на проекте порождает переиндексацию всех вложенных
  сущностей; без пакетирования и защиты от перегрузки это забивает очередь.
- **Отладка сложнее**: эффект отделён от причины во времени и в процессе; нужна сквозная
  трассировка по `requestId`.
- **Порядок событий не гарантирован строго.** Параллельные воркеры и `SKIP LOCKED` означают, что
  два события одного агрегата могут обработаться не по порядку; обработчики должны быть устойчивы
  к этому (например, сравнивать версии).
- **Ещё одна роль в развёртывании** (`ROLE=worker`) и ещё один источник отказа: остановившийся
  воркер копит `PENDING` тихо, пока не сработает алерт.

### Что становится трудно изменить позже

- **`eventType` и схема `payload` становятся внутренним контрактом** между продюсерами (use-cases)
  и всеми обработчиками. При rolling-обновлении в профиле `scaled` в очереди одновременно
  оказываются события старой и новой схемы — значит обработчики обязаны быть совместимы назад, и
  это требование действует постоянно.
- **События, накопленные в `PENDING`/`DEAD` во время обновления**, будут обработаны кодом новой
  версии. Изменение семантики типа события задним числом меняет то, как обработаются уже
  записанные факты.
- **Правило «побочный эффект только через outbox»** должно соблюдаться безусловно. Один прямой
  вызов индексатора, добавленный «для скорости», создаёт расхождение, которое невозможно обнаружить
  иначе как сверочным джобом.
- **Гарантия at-least-once** зашита в каждый обработчик через ключ идемпотентности; переход на
  exactly-once (который в распределённой системе достижим только приблизительно) потребовал бы
  пересмотра всех обработчиков.
- **Восстановимость производного состояния** — обещание, на котором держится решение не бэкапить
  Meilisearch и допустимость пересчёта rollup. Появление обработчика, порождающего данные, которых
  нет в БД (например, отправленное письмо), нарушает это обещание: переигрывание истории приведёт
  к повторной отправке.
- **Таблица `OutboxEvent` в БД арендатора** (под RLS) связывает эволюцию событий с миграциями
  схемы: изменение структуры таблицы — миграция на всех инсталляциях.

## Проверяемость

- **Тест атомарности**: откат транзакции не оставляет `OutboxEvent`; успешный commit оставляет ровно
  одно событие. Проверяется на реальном Postgres (Testcontainers) для каждого типа изменения.
- **Тест «нет прямых побочных эффектов»**: архитектурный тест — `application/**/use-cases/**` не
  импортирует `SearchPort`, `RealtimePort`, `NotificationPort` и клиентов очередей напрямую;
  единственный разрешённый путь — `OutboxPort`. Нарушение ломает сборку. Это главный механизм
  принуждения к правилу.
- **Тесты идемпотентности каждого обработчика**: повторная обработка того же `outboxEventId` не
  создаёт дублей уведомлений, не удваивает rollup и не порождает второй realtime-broadcast.
  Обязательны для каждого обработчика — отсутствие теста блокирует историю.
- **Тест `SKIP LOCKED`**: два параллельных воркера на общем наборе событий не обрабатывают одно
  событие дважды и не блокируют друг друга.
- **Тест tenant-контекста в воркере**: пачка событий разных организаций обрабатывается с
  выставлением контекста на каждое; событие организации B не видит данные организации A
  ([ADR-0004](0004-multi-tenancy-postgres-rls.md)).
- **Тест ретраев и DLQ**: обработчик, падающий N раз, приводит событие в `DEAD` с сохранённым
  `lastError`; событие остаётся в таблице.
- **Тест reconciliation**: событие, зависшее в `PROCESSING` дольше таймаута, возвращается в работу;
  событие `PENDING` старше порога — тоже.
- **Тест переигрывания**: полная переиндексация и полный пересчёт rollup из БД воспроизводят
  состояние — подтверждает, что производное состояние действительно производно.
- **Тест «переигрывание не отправляет письма»**: обработчики с внешними необратимыми эффектами
  помечены и исключены из режима переигрывания.
- **Метрики и алерты**: возраст самого старого `PENDING`, количество `DEAD`, длина очереди BullMQ.
  Растущий возраст `PENDING` — алерт «воркер стоит».
- Гейт-агенты `db-reviewer` и `production-readiness` (правила проекта) — обязательны для изменений
  в схеме событий и в обработчиках.
