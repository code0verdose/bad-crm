# Изоляция арендаторов и контракт API: две находки, которые отдаёт только живая база

Вторая половина EPIC-003. Первая — [[2026-07-27--epic-003-server-skeleton]].

## Простым языком

1. **Появилась первая миграция и слой доступа к базе.** Две таблицы, но с полным набором защит: у каждой строки есть владелец-организация, база сама отсеивает чужие строки, и приложение физически не может обратиться к таблице, не назвав, от чьего имени оно работает.

2. **Изоляция проверяется не рассуждением, а настоящим PostgreSQL.** Тесты поднимают базу в контейнере и пробуют прочитать, записать, посчитать, обновить, удалить и «переехать» в чужую организацию. В каждом наборе есть **положительный контроль** — «свою строку видно»: без него тест проходит и на сломанном соединении, то есть не проверяет ничего.

3. **Спецификация API стала источником правды.** Типы клиента генерируются из неё, а тест сверяет её с реальными маршрутами **в обе стороны**: маршрут без описания и описание без маршрута одинаково валят сборку.

4. **Первая находка: убрать защиту записи можно незаметно.** Если у политики убрать проверку на запись, все поведенческие тесты остаются зелёными — PostgreSQL молча подставляет проверку на чтение. Ловит это только запрос к системному каталогу. То есть «положился на подстановку» и «забыл» выглядят одинаково, пока политику не разделят по командам — и тогда защита исчезнет.

5. **Вторая находка серьёзнее: скрипт раздачи прав не видел корневую таблицу.** Он определял «таблица арендатора» по наличию колонки с идентификатором организации — а у самой таблицы организаций такой колонки нет по устройству. В итоге приложение не получало на неё **никаких** прав. Проявилось бы это не сразу: восстановление из бэкапа снимает все права, а этот скрипт — то, что их возвращает. То есть каждое восстановление заканчивалось бы полной неработоспособностью — вход, определение организации, регистрация. Не утечка, а отказ, и ровно там, где чинить некогда.

6. **Почему это не поймали раньше.** Тест проверял, что повторный запуск скрипта ничего не меняет, — но никогда не отзывал права первым. Пропущенная таблица выглядела точно так же, как обработанная правильно.

## Технически

1. **Миграция.** `organizations` + `teams`: `ENABLE` **и** `FORCE ROW LEVEL SECURITY`, политика `TO app_user` с `USING` **и** `WITH CHECK`, явные `GRANT` + `GRANT SELECT … TO backup_role`, `uq_teams_org_id (organization_id, id)` под будущий составной FK, `organization_id` первым в составных индексах, `SET lock_timeout`/`statement_timeout` в шапке. Повторный `migrate deploy` — no-op, проверено счётчиком `_prisma_migrations`.

2. **`withTenant`** — интерактивная транзакция + `set_config('app.organization_id', $1, true)` bind-параметром; отсутствие контекста даёт **отказ** (`42704`), а не пустую выборку. `guardedClient` через `$extends` ловит обращение к [T]-таблице вне контекста и называет модель и операцию вместо кода Postgres. Реестр `TENANT_TABLES` сверяется с DMMF в обе стороны.

3. **Находка про `WITH CHECK`** — подтверждена дважды, независимо. У политики `FOR ALL` PostgreSQL при отсутствии `WITH CHECK` использует `USING`, поэтому INSERT чужой строки всё равно отбивается и **все 55 поведенческих тестов остаются зелёными**. Падает только каталожная проверка (`pg_policy.polwithcheck` пуст). Вывод: поведенческий тест здесь принципиально не заменяет каталожный.

4. **Находка про классификатор прав.** `01-grants.sql` определял тенантную таблицу как `EXISTS (… attname = 'organization_id')`. У корня тенанта колонки нет — политика сравнивает `id`. Таблица не попадала ни в одну ветку → ноль грантов для `app_user`. Поскольку `pg_restore` идёт с `--no-privileges`, а этот файл объявлен источником правды по грантам, каждое восстановление заканчивалось `42501 permission denied for table organizations`.
   **Исправление:** классификатор переведён на `c.relrowsecurity` — то самое определение, которое даёт инвариант №1 («приложение трогает — значит строки фильтруются политикой»). Второй источник правды устранён по существу, а не подпорот. Список `no_delete` (сегодня — корень тенанта) добавлен отдельно, потому что удаление организации — процедура офбординга, а не запрос.
   **Регресс закрыт двумя тестами:** `REVOKE ALL → reapplyGrants → права восстановлены` (интеграционный, по таблице) и `grants-registry.test.ts` — парсит списки из SQL и сверяет с реестром TypeScript, плюс прямо запрещает возврат старого классификатора. Мутация «вернуть колоночную проверку» ловится.

5. **Контракт.** `openapi.yaml` 3.1.1 + `pnpm api:gen` → типы клиента, в CI проверяется пустой diff. Контрактный тест сверяет путь × метод в обе стороны — мутации подтверждены выводом. Служебные `/health` и `/ready` **не** в спеке, а в allow-list: агент следовал `docs/` против моей формулировки задачи, и это верный порядок источников истины.

6. **Валидация.** zod-middleware для `params`/`query`/`body`, `safeParse`, тип через `z.output`; `ZodError` разворачивается в `errors[]` с точечным путём (`amount.value`, `items[1].title`). Коды, не тексты — клиент маппит в i18n.

7. **Инфраструктура прогона.** `test:integration` получил `passThroughEnv` для `DOCKER_HOST`/`TESTCONTAINERS_*`: turbo фильтрует окружение, и без этого набор падал на colima/podman, тогда как прямой запуск пакета проходил — читается как «сломан turbo». Добавлена джоба CI `database isolation` (Testcontainers сам поднимает образ, `services:` не нужен). Инвариант «CI запускает ровно набор правила» уточнён: сверх набора допустимы только **объявленные** задачи с причиной — `test:integration` требует Docker, и заставлять контрибьютора держать демон перед каждым push было бы худшим разменом.

## Применённые технологии

- [[PostgreSQL]] — RLS как рубеж изоляции; `pg_policy`/`pg_class` как источник правды о защите.
- [[Prisma]] — `$extends` для tenant-контекста и предохранителя, миграции под ролью-владельцем.
- [[Testcontainers]] — настоящая база в тестах: свойство под проверкой живёт в политике БД, а не в коде.
- [[OpenAPI]] — контракт как источник истины, двусторонняя сверка с роутером.
- [[Zod]] — валидация на границе, тип из схемы.
