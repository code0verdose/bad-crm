# Документ — список, код — тип

STORY-011-01: каталог прав перенесён целиком (331 ключ), справочник заведён в БД, оба конца
скреплены гейтом.

## Простым языком

1. Каталог прав существовал в двух видах: полный список в `permission-model.md` §3 и заглушка из
   двадцати ключей в коде. Пока право проверяется в одном месте, это терпимо; как только права
   начнут проверять use-case'ы, расхождение станет тихой дырой — ключ есть в документе, а продукт
   его не знает, или наоборот.
2. Нужны оба. **Документ — источник правды для списка**: там право проектируют, обсуждают и
   помечают опасным. **Код — источник правды для типа**: ключ, который не компилируется, нельзя
   проверить по месту, и опечатка становится ошибкой сборки, а не открытым доступом.
3. Значит, нужен мост. Гейт разбирает таблицы документа и сверяет каждый ключ по всем полям —
   ресурс, действие, домен, требуемый уровень ACL, признак опасности — **и числа, которые документ
   называет прозой** («Итого: 331 ключ, из них 110 опасных»). Проза, которая расходится с кодом, —
   это то, как «318 ключей» становится фольклором.
4. Справочник в БД — единственная глобальная таблица модели: каталог определяется кодом, тенант не
   может изобрести право. Из этого следует важное: **приложение читает её и не пишет**. Приложение,
   способное писать каталог, может выдать себе право. Проверено тремя негативными тестами.
5. Право, исчезнувшее из кода, **не удаляется** — помечается. На него ссылаются выданные роли и
   персональные исключения; удаление строки сломало бы каждую инсталляцию, где админ успел его
   выдать. И обратный ход: вернувшийся ключ снимает пометку, иначе каталог нёс бы право, которое код
   проверяет, а policy-слой отвергает.

## Три расхождения, исправленные в документах первыми

**1. История говорила «307 ключей», документ — 331.** Правило проекта однозначно: `docs/` старше
`epics/`. Исправлена история. Заодно это ровно тот случай, ради которого гейт сверяет числа из прозы.

**2. `global_read` вёл в ветку тенант-таблиц.** Список назывался «таблицы, которые приложение
читает», а ветка выдавала `INSERT`, `UPDATE` и `DELETE`. Ни одна таблица его не использовала —
поэтому ничего не ломалось, и сломалась бы **первая же**, то есть моя. Теперь у списка своя ветка,
только на чтение, и в неё переехал `_prisma_migrations` (та же форма привилегии, та же причина).

**3. Реестр индексов объявлял `uq_permissions_key`** — уникальный индекс поверх колонки, которая
и есть первичный ключ. Второй индекс того же столбца не нужен; исправлен документ.

## Технически

1. `permissions.catalog.ts` — 331 ключ с метаданными; `deny-reason.enums.ts` — 15 причин отказа,
   тоже с гейтом паритета (причина едет в аудит, в `problem+json` и в интерфейс — отказ без причины
   отлаживается чтением кода).
2. Миграция `20260805090000_permission_catalog`: глобальная таблица, частичный индекс живёт только в
   миграции (Prisma его не выражает — тот же приём, что у `uq_users_org_email`).
3. Сид `pnpm db:seed:permissions`: планировщик отдельным `.util.ts` (семь тестов без БД), I/O —
   в скрипте; шаг 7c процедуры обновления рядом с `db:grants`.
4. Линтер миграций поймал две вещи, которые я забыл: преамбулу с `lock_timeout`/`statement_timeout` и
   индекс, разбитый на три строки, — построчная проверка не видела, что цель индекса создана в этом
   же файле.

## Что из этого правило, а не случай

- **Два источника правды допустимы, если между ними есть гейт.** Список и тип — разные вопросы;
  копия без проверки — обещание.
- **Числа, названные прозой, тоже надо гейтить.** Иначе документ начинает лгать раньше кода.
- **Справочник, который приложение может писать, — это не справочник.** Право писать каталог прав
  равносильно праву выдать себе право.
- **Список, названный «read», обязан быть read-only в коде, а не в комментарии.**

## Применённые технологии

- [[PostgreSQL]] — глобальная справочная таблица без RLS и привилегия только на чтение как граница.
- [[Prisma]] — частичный индекс мимо схемы, `upsert` пачкой в одной транзакции.
