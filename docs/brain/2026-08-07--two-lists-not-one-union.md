# Два списка вместо одного union

## Простым языком

1. Появился справочник сотрудников: поиск, фильтры по статусу, роли и команде, сортировка, страницы —
   и вторым видом оргструктура, дерево «кто кому подчиняется».
2. **Эта история была обязана принять решение, отложенное дважды.** Документ модели данных прямо
   писал: либо справочник склеивает учётные записи с приглашениями, либо приглашённый человек сразу
   получает учётную запись без пароля. Выбрано третье — **два списка**: справочник показывает
   аккаунты, непринятые приглашения живут на своём экране. Один человек не должен стоять в двух
   таблицах одновременно, а строка учётной записи без пароля — это заглушка в колонке, с которой
   однажды кто-нибудь сверит ввод.
3. **Порядок — это тоже право.** Отсортировать список по дате найма может только тот, кому эти даты
   видны: иначе, перелистывая страницы, их узнаёшь по одному сравнению за раз. Просьба отсортировать
   так отклоняется молча-но-честно — ответ говорит, каким порядком он на самом деле отсортирован.
4. **Уровень видимости считается для каждой строки, а не для запроса.** Свою собственную строку
   человек видит целиком, даже когда строки коллег видит наполовину.
5. Значения фильтров приходят **в том же ответе**, что и люди: спросить у справочника ролей нельзя —
   у разработчика нет на это права, а справочник ему открыт.
6. Дерево оргструктуры строит браузер и переживает данные, которых сервер обещает не присылать:
   руководителя не из списка, цикл, подчинение самому себе. Каждый человек нарисован ровно один раз.
7. По дороге починен бюджет первой загрузки — **на 55 килобайт**, одной строкой конфигурации.

## Технически

1. `EmployeeDirectoryRepositoryPort` — отдельный порт для read-модели: строка собирается из `users`,
   `employee_profiles`, `user_roles` и `team_members`, и ни одна из них не сущность, которую пишет
   порт профиля. **Базовая таблица — `users`**: принявший приглашение утром аккаунт есть, профиля
   нет, и справочник, начинающийся с профилей, потерял бы его.
2. `ListEmployeesQuery` принимает два решения, которых гвард принять не может — понижение порядка и
   уровень по строке. Оба вынесены в `domain`: `seesEmploymentOfOthers` выведен **из**
   `profileVisibility`, а не повторяет имена прав, иначе «что делает запись персональной» имело бы
   два ответа.
3. `GetOrgChartQuery` — плоский ответ, **не** рекурсивный CTE, вопреки строчке в списке задач эпика:
   ответ — вся организация, CTE вернул бы те же строки ценой запроса, который нельзя прочитать. Он
   окупится на «ветке под Иваном»; такого вопроса пока нет.
4. Отсутствие N+1 доказано **счётом операторов**, а не замером: страница из пятидесяти строк обязана
   стоить столько же вызовов драйвера, сколько страница из одной. Это единственная формулировка «нет
   N+1», которую тест может утверждать.
5. `?role=a&role=b` и `?role=a` нормализуются одним `preprocess` на границе. Неизвестное значение —
   **422**, тогда как клиентская схема на то же значение делает `.catch`: на сервере это дефект
   клиента, в адресной строке — опечатка человека, и правдоподобная страница спрятала бы первое.
6. `/employees` и `/employees/org-chart` объявлены **до** `/employees/:userId`. Express сопоставляет
   в порядке объявления; иначе параметрический маршрут проглотил бы литеральный и ответил 422 на
   `userId`, который не UUID. Ни один тип этого не ловит — только тест на живом роутере.
7. Изоляция проверена **самим репозиторием на живом Postgres**: две организации, одинаковые имена,
   одинаковые названия ролей и команд. Ни юнит-тесты (у записанного драйвера нет политик), ни
   реестровый RLS-набор (по таблице за раз) джойн из четырёх таблиц не видят.

## Бюджет бандла: `sideEffects` вместо ещё одного обхода

Экран поднял начальный JS до **250.14 kB** при лимите 250. Причина структурная, и та же, что у
barrel `@pages` две записи назад: маршрут обязан держать `validateSearch` в первом чанке, значит он
импортирует namespace-barrel юнита — а barrel тянет юнит целиком, вместе с формой профиля и её
`@mantine/form`.

Обходов было два, и оба плохие: импорт вглубь юнита (запрещён ESLint'ом и правилом FSD) или поднятие
лимита (лимит — это спецификация). Настоящая причина оказалась в другом: в `package.json` клиента не
было `sideEffects`. Без этой декларации сборщик обязан считать побочным эффектом **каждый** модуль и
не имеет права выбросить неиспользуемый namespace из barrel.

```json
"sideEffects": ["*.css"]
```

**250.14 → 195.01 kB.** Декларация честная: единственные модули клиента с побочным эффектом — четыре
импорта CSS в `main.tsx`; всё остальное — функции и компоненты, i18next инициализируется вызовом.
И касается это не одного экрана: тем же механизмом `@units/iam` целиком лежал в первом чанке с
EPIC-011.

## Дефект, который поймал тест

`buildOrgTree` рисовал участника цикла дважды: `nodes.filter(не посещён).map(expand)` вычисляет
фильтр **до** обхода, а `expand` первого узла цикла посещает второй. Сервер цикл создать не даёт
(422) и база запрещает подчинение самому себе — но «сервер обещал» не причина зависать на данных,
пришедших по сети от версии сервера, которой эта сборка не видела. Заменено на цикл с проверкой
перед каждым разворотом.

## Что отложено, и почему

`loader` через `ensureQueryData` — первая отрисовка здесь это фильтры и скелетон, они сети не ждут, а
loader сейчас означал бы дублирование ключа и параметров в маршруте и в хуке. Пикер команд — команд в
продукте пока нельзя создать (STORY-012-07); фильтр по команде при этом работает целиком, значения
приходят фасетом. Написание `role[]=` в адресной строке — TanStack Router сериализует массивы своим
способом, и переопределять его глобально ради пунктуации одного экрана значило бы переписать URL всех
остальных экранов.

## Применённые технологии

- [[PostgreSQL]] — offset-пагинация с tie-breaker'ом по колонке, которая никогда не null.
- [[Prisma]] — `distinct` для фасетов; связи, загружаемые за фиксированное число операторов.
- [[TanStack Router]] — `validateSearch` как состояние экрана; цена этого в байтах первого чанка.
- [[TanStack Query]] — `keepPreviousData`, чтобы список не мигал; `enabled` на второй вид.
- [[Zod]] — `.catch` в адресной строке против 422 на сервере: одна схема, две противоположные
  политики отказа, и обе правильные.
- [[Mantine]] — `Chip` вместо `MultiSelect` по бюджету; `SegmentedControl` для вида.
- [[Rollup]] — `sideEffects` как условие tree-shaking'а namespace-barrel'ов.
