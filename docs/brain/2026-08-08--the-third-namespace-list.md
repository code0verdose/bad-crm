# Третий список namespace: харнесс, который рендерил ключи, которых не бывает

## Простым языком

1. **Убрал второй список имён namespace.** Тестовый харнесс
   (`test/setup/testing-library.setup.ts`) перечислял namespace руками и отстал на четыре:
   `employee`, `members`, `offboarding`, `teams`. Теперь он берёт тот же список, что и приложение,
   — чтобы «держать в согласии» надо было одно место, а не два.

2. **Сделал минимальный экспорт вместо копии.** Продовый конфиг уже выводил список из `RESOURCES`
   — я вынес это выражение в именованную константу `NAMESPACES` и экспортировал её. Один расчёт,
   два потребителя.

3. **Проверил, во что именно превращался дрейф.** В режиме `cimode` незарегистрированный namespace
   — это не namespace, а первый кусок ключа в `common`: `t('teams.title')` возвращал
   `common.teams.title`. Такой строки не рендерит ни одна сборка продукта, а весь клиентский набор
   тестов сверялся именно с ней.

4. **Искал ассерты, которые проходили только из-за дрейфа. Не нашёл ни одного** — и это ответ,
   который стоит записать, а не спрятать. Ни один тест не сломался после фикса. Причина
   неприятнее, чем «повезло»: ассерты по этим четырём namespace написаны незаякоренными
   регулярками (`/teams\.delete\.action/`), которые одинаково довольны и правильным ключом, и
   ключом с чужим префиксом. Дрейф не ломал тесты, потому что тесты не умели его увидеть.

5. **Добавил регрессию.** Отдельный тест сверяет список namespace харнесса с продовым. Проверил,
   что он действительно падает: вернул руками старый список — тест показал ровно четыре
   недостающих имени.

## Технически

1. `packages/client/src/shared/i18n/i18n.config.ts:75` — `export const NAMESPACES: readonly
   string[] = Object.keys(RESOURCES.en)`; `createI18n` теперь передаёт `ns: NAMESPACES`. Экспорт
   минимальный: одна константа, комментарий объясняет, что источник один и кто второй потребитель.
2. `packages/client/test/setup/testing-library.setup.ts:9,102` — импорт
   `NAMESPACES` из `@shared/i18n/i18n.config.js`, `ns: NAMESPACES` вместо девяти литералов.
3. `packages/client/test/i18n/namespace-registration.test.ts:41` — новый `describe`: сравнение
   `i18next.options.ns` (глобальный инстанс, поднятый харнессом) с `NAMESPACES`, плюс контроль
   `NAMESPACES.length > 5`, чтобы сравнение не оказалось истинным «ни о чём».
4. Механика дрейфа (проверено, а не вычитано): при `nsSeparator === keySeparator === '.'`
   i18next отделяет namespace, **только** если первый сегмент есть в `options.ns` —
   `Translator.extractFromKey`. Иначе ключ целиком уходит в `defaultNS`. С
   `appendNamespaceToCIMode: true` результат — `common.teams.title`.
5. Ассерты не правились: ноль штук. `grep -rE "common\.(teams|members|employee|offboarding)"` по
   `packages/client` не находит ни одного литерала — дрейфовая форма нигде не была записана
   явно. 146 обращений к этим namespace идут через незаякоренные регулярки и через
   `i18n.t(...)` того же инстанса, то есть согласованы с любым из двух состояний.
6. Гейты: `pnpm turbo run typecheck lint build test` — зелёный (16 + 6 задач);
   `pnpm --filter @bad-crm/client test` — 87 файлов, 1098 тестов, lines 100 % (1570/1570),
   branches 100 % (557/557); `pnpm i18n:check` — 13 namespace, 386 ключей в обоих языках, 0
   непереведённых; `pnpm coverage:baseline` — без просадки.
7. Четвёртой копии нет: список в `test/i18n/pseudo-locale.test.tsx:42` выводится из
   `import.meta.glob` по каталогу локалей, а не пишется руками, и связан с `RESOURCES`
   существующим listing-тестом.

## Что осталось открытым

Слабость ассертов — не дрейф, но соседняя проблема: незаякоренная регулярка по ключу пройдёт и на
неправильном ключе. Чинить её массовым добавлением `^` в 146 мест я не стал — часть из них
намеренно нестрогая (интерполяция имени в `teams.members.remove`), и это записано в комментариях
самих тестов. Регрессионный тест закрывает конкретный класс, который реально случился.

## Применённые технологии

- [[i18next]] — `ns`/`defaultNS`, `nsSeparator` против `keySeparator`, `cimode` и
  `appendNamespaceToCIMode`, `options.ns` как наблюдаемое состояние инстанса.
- [[Vitest]] — setup-файл как общий инстанс для всего набора, проверка регрессии обратным
  экспериментом (вернуть дефект — увидеть красный).
- [[React]] / [[TypeScript]] — `readonly string[]` в публичном экспорте слоя `shared`.
