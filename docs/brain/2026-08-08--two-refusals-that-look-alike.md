# Два отказа, которые выглядят одинаково

## Простым языком

1. Появилась передача владения организацией — операция вместо правки базы руками. До неё уход
   основателя был обращением в поддержку.
2. **Ни одного мгновения без владельца.** Роли, указатель организации и версии прав обоих участников
   меняются в одной транзакции.
3. **Уходящий никогда не остаётся ни с чем.** По умолчанию он получает права администратора, и выбор
   показан в подтверждении.
4. **Два отказа выглядят похоже и требуют разного.** «Передаю самому себе» и «получатель отключён» —
   это неверное значение и неверное состояние; у второго есть следующий шаг, у первого нет.

## Технически

### Почему это одна транзакция и одна операция

Передача трогает четыре вещи: роль `owner` у получателя, роль `owner` у отдающего, `owner_id` у
организации и две версии прав. Любое разбиение оставляет достижимое состояние, где владельцев двое
или ни одного, — а «ни одного» означает установку, которую некому администрировать.

Порядок внутри — сперва выдать, потом снять — снаружи невиден: транзакция коммитится целиком. Но это
порядок, который хотел бы увидеть читатель частичного лога, и он записан в комментарии именно поэтому.

**Версия уходящего инкрементится не ради симметрии.** Его живой access-токен ещё утверждает власть,
которую он только что отдал; версия, оставшаяся прежней, честно бы его пропускала оставшиеся минуты
жизни токена. Тот же довод, что и в офбординге, только направленный на инициатора операции, а не на
её объект.

### Различие, ради которого заведены два кода

```
POST … { toUserId: <я сам> }        → 422 invalid_recipient
POST … { toUserId: <деактивирован> } → 409 recipient_not_active
```

Соблазн — один код «нельзя этому человеку». Разница в том, что делать дальше. Первое — неверное
значение в поле: никакое состояние системы не сделает его верным, исправляется другим значением.
Второе — неверное состояние: значение названо правильно, у отказа есть следующий шаг (вернуть
человека и повторить). Свести их к одному коду значило бы отправить администратора чинить то, что не
сломано, — или, наоборот, искать способ «активировать себя».

Отсюда и разные механизмы: первое — deny-reason рядом с `manager_cycle_detected` (у проекта уже есть
путь для «422 с именем»), второе — `ConflictError`, как `last_owner_required`.

### Что проверяется на клиенте, и почему это записано

История требует ввести `slug` организации для подтверждения. Проверка живёт **на клиенте**, и в
валидаторе стоит объяснение: серверная сверка не добавила бы ничего, чего не удовлетворит владелец
токена, зато сделала бы операцию непригодной для скрипта в установке, которая этого хочет. Контроль
существует против промаха мыши, а промах случается в браузере.

Это тот класс решений, который без записанной причины через полгода читается как забытая проверка.

### Мелочи, которые оказались не мелочами

- `previousOwnerRoleKey` не принимает `owner`: «остаться владельцем» не способ перестать им быть.
  Whitelist в схеме, тест на отказ.
- Отсутствие системной роли в организации — **громкий** отказ, а не тихая передача: отдать
  организацию и оставить получателя без роли хуже, чем отказать.
- `createMany({ skipDuplicates: true })`: администратор, ставший владельцем, сохраняет свою строку
  `admin`, и повторный прогон не сталкивается с уникальным ключом.

### Код отказа, который я не завёл

Критерий 5 требует `mfa_required_for_owner`, если в организации включена обязательная 2FA. TOTP —
EPIC-013, политики нет, проверять нечего. Код **не заведён**: отказ, который никогда не возвращается,
— обещание, которое нечем проверить, и следующий читатель каталога решит, что 2FA уже учтена.

Тот же довод, по которому в клиенте нет `reactivateUser`, и по которому справочник не считает
недостающие подсистемы нулями.

## Применённые технологии

- [[PostgreSQL]] — четыре записи в одной транзакции как условие существования инварианта.
- [[Prisma]] — `skipDuplicates` для идемпотентности; `increment` для обеих версий одним оператором.
- [[Vitest]] — записывающий драйвер фиксирует **порядок** вызовов, а не только их аргументы; но он
  же — причина, по которой гонка и формы SQL потребовали отдельного набора на живом Postgres.
