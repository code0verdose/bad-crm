# Границы, падавшие в английский Zod, и число, жившее в двух местах

**Дата:** 2026-09-06 · **Ветка:** `feat/marketing-landing`

## Что было

Накануне закрыли класс «форма печатает ключ вместо предложения»: двенадцать форм, гейт
`packages/client/test/architecture/form-issue-translation.test.ts`. Осталась вторая половина того же
дефекта, сознательно не тронутая: часть границ в схемах **не несёт ключа вовсе** и падает в
собственный английский Zod. Русскоязычный пользователь видел под полем
`Too big: expected string to have <=120 characters`.

Разведка по всем схемам форм (`packages/client/src/units/*/model/validation/*.schema.ts` и
примитивам `packages/shared/src/validation/*`) дала неожиданно узкий результат: **единственная
дефектная схема — `employee-profile.schema.ts`**, одиннадцать границ без ключа. Все примитивы
`shared` и тринадцать остальных форм ключи несут. Схемы `*-search.schema.ts` из подсчёта исключены: там везде `.catch(...)`,
мусор из адресной строки молча заменяется значением по умолчанию, и сообщение не показывается
никому — трогать их не надо и не нужно будет.

## Развилка, и почему выбран третий вариант

Сообщение с числом («не длиннее 120 символов») требует интерполяции, а `translateFormIssues`
принимала `(key: string) => string`.

1. **Ключ без числа** — дёшево, но человек не узнаёт предела.
2. **Число строкой в каталоге** — так уже сделано в восьми ключах (`teams.field.*`,
   `auth.register.field.*`, `permissions.field.reason*`, `validation.password.too_short`), и это ровно
   тот класс расхождений, который чинили весь предыдущий день: число живёт в схеме и в двух языках
   каталога, правят обычно одну копию.
3. **Значения едут вместе с ключом.** Выбран этот.

Ключевое наблюдение, которое сделало третий вариант дешёвым: **Zod-issue уже несёт число**.
`too_big` держит `maximum`, `too_small` — `minimum`. Ничего изобретать не нужно — нужно только не
терять это. Мантиновский `schemaResolver` теряет: он читает схему через Standard Schema, где у issue
есть только `message` и `path`.

Поэтому появился `packages/client/src/shared/lib/validation/zod-form-resolver.util.ts` — тонкий
резолвер поверх `schema.safeParse`, отдающий `Record<path, { key, values? }>`. Поведение мантиновского
скопировано намеренно: путь склеивается точкой, первый issue на путь побеждает. Все четырнадцать
форм дерева переключены с `schemaResolver` на него; гейт архитектуры перенацелен на новый символ и
отдельным утверждением запрещает встроенный резолвер — форма, написанная по прежней прозе правил,
иначе прошла бы молча.

**Самодельного протокола внутри строки нет.** Там, где у Zod своего предела нет (длина одного навыка
при одном общем поле ввода), число объявляется в `params: { count: 64 }` — типизированное поле issue,
а не число, зашитое в текст сообщения.

## Свойство, ради которого всё это

Число в переводе и число в схеме **не могут разойтись**, потому что в переводе числа нет: там
`{{count}}`, и подставляется тот самый предел, который отказал. Это сильнее теста на совпадение — тест
ловит расхождение, а здесь расходиться нечему. По той же причине восемь уже существовавших ключей с
зашитым числом переписаны на интерполяцию: держать две конвенции для одного предложения значит
гарантировать, что следующий скопирует не ту.

Русская плюрализация тут не украшение: «не больше 1 символа» против «не больше 120 символов»,
«не меньше 1 часа» против «не меньше 80 часов». Семьи `_one/_few/_many/_other` обязательны, и
`test/i18n/plural.test.ts` это и требует.

Отдельная ловушка, на которой я один раз ошибся и поймал себя рендерингом всех реальных пределов:
i18next-овские категории `few`/`many` описывают **именительное** счётное сочетание («64 символа»), а
конструкция «не больше 64 …» управляет родительным — там «символов» при любом числе, кроме единицы.
Ставить `few` = «символа» здесь неверно. Проверяется только тем, что предложения печатают целиком.

Заодно закрыт тот же класс в подсказке поля: `employee.capacityHint` говорил «От 0 до 80» строкой рядом
со схемой, свободной сказать 100. Теперь `{{min}}`/`{{max}}` из экспортированных констант.

## Чем это проверено

Таблица псевдолокали отправляла каждую форму **пустой**, поэтому доставала только `min(1)`. Все верхние
границы были вне поля зрения любого гейта — там дефект и выжил. Добавлен второй набор из тринадцати
кейсов: каждый подаёт форме значение, которое схема отвергает, и читает сообщение **того самого поля**,
которое заполнил, через `aria-describedby`. Мутация подтверждена — снятие `error` у трёх границ даёт:

```
× a profile whose every text field is longer than its bound
    /Job title/: Too big: expected string to have <=160 characters
× a weekly capacity that is not a whole number
    /Hours a week/: Invalid input: expected int, received number
× a weekly capacity above the range
    /Hours a week/: Too big: expected number to be <=80
× more skills than the list holds
    /Skills/: Too big: expected array to have <=50 items
```

Одна мутация сначала **не** покраснела и показала настоящий пробел: если у `refine` убрать `params`,
ключ остаётся на месте, сообщение переводится и остаётся помеченным, а `{{count}}` просто не
подставляется — «предложение ли это» такого не видит. Число разойтись по-прежнему не может, но может
пропасть. Закрыто ещё одним утверждением того же кейса — под полем не остаётся `{{`:

```
× a profile whose every text field is longer than its bound
    /Skills/: field.skillTooLong
```

## Правки, которых потребовала ревизия утверждений

Ревизор нашёл девять расхождений — почти все в прозе, но одно блокирующее: `rules/zod-validation.mdc`
§12, `rules/design-system.mdc` §11, `ux-architecture.md` и ADR-0006 продолжали предписывать
**встроенный** `schemaResolver`, а перенацеленный гейт ловил только новый символ. Форма, написанная
строго по правилу, прошла бы гейт молча и отгрузила ровно тот класс, ради которого гейт заведён.
Правила и ADR обновлены поправкой с датой, гейт получил второе утверждение.

Второе по цене: обоснование гейта («дефект невидим, потому что `cimode`») этот же коммит лишил силы.
Резолвер отдаёт объект, и форма без перевода не печатает ключ, а роняет рендер —
«Objects are not valid as a React child». Проверено зондом, а не рассуждением. Прозу поправил: отказ
теперь громкий, гейт остаётся как формулировка правила, а не как единственный способ его увидеть.

Третье, уже в коде: `isFormIssue` проверял только `typeof value.key === 'string'`, а **React-элемент
несёт `key`** — `<a key="terms">` прошёл бы за issue и уехал в `t`. Добавлена проверка `$$typeof` и
кейс с элементом в тесте.

## Что найдено и не закрыто

- `validation.password.too_long` и `validation.locale.unsupported` объявлены схемами
  `packages/shared/src/validation/**` и предложения в каталоге не имеют — пароль в 129 символов и
  неизвестная локаль печатают сырой ключ. Добавить предложение нельзя, не тронув гейт:
  `test/i18n/catalogue-parity.test.ts` считает «использованным» только то, что встречается в
  `packages/client/src`, и объявил бы новый ключ сиротой. `pnpm i18n:unused` эту сторону читает и
  держит оба в списке `deferred` из девятнадцати ключей — остальные семнадцать ни одним экраном не
  рендерятся и ждут своих форм. Чинится изменением области чтения parity-гейта — отдельной работой.
- Длина одного навыка проверяется по всему списку, а не поэлементно, намеренно: issue элемента
  приходит с путём `skills.3`, такого поля в форме нет, и Mantine показал бы отказ никому, оставив
  отправку заблокированной.

## Что и зачем сделано

### Простым языком

1. **Прошёл все схемы форм и разделил границы на видимые и молчащие.** Видимых — те, чьё сообщение
   человек читает под полем; молчащих — те, что стоят на разборе адресной строки и подменяются
   значением по умолчанию. Вторые трогать не нужно, и это записано, чтобы следующий не переделывал.
2. **Сделал так, чтобы число в сообщении бралось из самой схемы.** Раньше «не длиннее 120 символов»
   писалось руками в двух языках, а схема могла говорить 200. Теперь в переводе стоит пропуск, а
   число подставляет та самая проверка, которая отказала.
3. **Дал ключ каждой границе профиля сотрудника.** До этого девять его полей могли отказать
   по-английски независимо от языка интерфейса.
4. **Научил таблицу псевдолокали доходить до этих границ.** Она отправляла формы пустыми и видела
   только «поле обязательно»; теперь каждая граница получает значение, которое её нарушает.

### Технически

1. `packages/client/src/shared/lib/validation/zod-form-resolver.util.ts` — резолвер над
   `schema.safeParse`, отдаёт `Record<path, FormIssue>`; `issueValues` читает `maximum`/`minimum` у
   `too_big`/`too_small` и `params.count` у `custom`. Поведение мантиновского `schemaResolver`
   воспроизведено (склейка пути точкой, first-wins).
2. `translate-form-issues.util.ts` — вторым аргументом `t` уходят значения; тип
   `TranslateFormIssue = (key: string, values: Partial<CountValues>) => string`, второй аргумент
   обязателен и может быть пустым: под `exactOptionalPropertyTypes` i18next-овская `t` не
   присваивается сигнатуре, где options может быть `undefined`.
3. Четырнадцать компонентов форм переключены на `SharedLib.zodFormResolver`; `@mantine/form` больше
   не поставляет резолвер. `test/architecture/form-issue-translation.test.ts` перенацелен на новый
   символ и получил второе утверждение — ни один файл не вызывает `schemaResolver(`.
4. `employee-profile.schema.ts` — ключ у `max` имён, `optionalText`, `timezone`, у `int`/`min`/`max`
   недельной ёмкости, у `z.enum`, у длины списка навыков и у длины одного навыка (`refine` + `params`).
   `CAPACITY_MIN`/`CAPACITY_MAX` экспортированы для подсказки поля.
5. Каталог: новые `validation.text.tooLong`, `validation.number.notInteger`, `validation.choice.invalid`,
   `employee.field.{capacityTooSmall,capacityTooLarge,tooManySkills,skillTooLong}`; восемь
   существовавших числовых сообщений переписаны на `{{count}}` с полными семьями плюрализации в обоих
   языках.
6. `test/i18n/pseudo-locale.test.tsx` — блок «the boundaries of the forms in a pseudo locale»: 13
   кейсов, заполнение через `fireEvent.change`, чтение сообщения адресуемого поля через
   `aria-describedby`, CONTROL на непустоту сообщения.
