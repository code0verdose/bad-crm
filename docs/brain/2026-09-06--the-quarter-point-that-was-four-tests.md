# Четверть пункта, которая оказалась четырьмя тестами

## Простым языком

1. `pnpm coverage:baseline` устойчиво показывал по серверу 99.00 против записанных 99.23 по
   строкам и 97.41 против 97.50 по веткам. Обе просадки укладывались в допуск 0.5 п.п., поэтому
   сборка была зелёная и никто не смотрел. Разобрал, из чего они складываются.
2. Первым делом проверил версию «покрытие было и пропало» — самую ценную и самую неприятную.
   Она **не подтвердилась**. Взял каждую непокрытую строку сервера и спросил у истории
   (`git log -L <строки>:<файл>`), когда её написали. Все до одной появились **после** коммита,
   на котором записана базовая линия. Ни одна старая покрытая строка покрытие не теряла.
3. Значит просадка — разбавление: эпик второго фактора привёз около девятисот строк, из них
   шестнадцать непокрытых, и средний процент поехал вниз. Это не шум, но и не регресс: новый
   код пришёл с дырами, а допуск в полпункта их спрятал.
4. Разобрал эти шестнадцать строк по существу и получил два разных ответа, а не один.
   Десять строк — реальные пути, которые обязаны проверяться: проигранная гонка при включении
   2FA, учётная запись вовсе без строки с паролем (там намеренно тратится одна проверка против
   фиктивного хеша, чтобы по времени ответа нельзя было отличить «пароля нет» от «пароль не
   подошёл»), нечитаемый текущим ключом секрет при перевыпуске кодов, и успешный ответ ручки
   перевыпуска на проводе. Шесть строк непокрываемы честно — это одинаковые защитные проверки
   против нарушения контракта порта шифрования.
5. Самая интересная находка — в HTTP-наборе. Тест назывался «заменяет набор, когда пароль и
   живой код второго фактора оба верны», а проверял отказ 403. Рядом стоял комментарий,
   объясняющий, почему успешный путь недостижим: секрет якобы больше не возвращается, а второй
   заход на выпуск даст 409. Обе половины объяснения неверны — секрет лежал в переменной
   соседней строкой, помощник просто его выбрасывал. Успешный ответ ручки перевыпуска не
   проверялся **никогда**, включая заголовок «не кешировать» на ответе, который содержит десять
   кодов восстановления.
6. Написал четыре теста и починил этот. Каждый проверил мутацией: ломаю целевую строку — тест
   обязан покраснеть. Все пять мутаций убиты, каждая ровно одним тестом.
7. Двум из четырёх защитных проверок дописал объяснение, которое у двух других уже было.
   Базовую линию **не двигал**: после починки сервер даёт 99.25 и 97.58 — выше записанного.

## Технически

1. **Метод.** Не процент, а места: `packages/server/coverage/lcov.info`, записи `DA:` с нулём и
   `BRDA:` с нулём или прочерком. 39 непокрытых строк из 3905. Разбивка: 23 в коде, который
   старше эпика 2FA (`main.ts`, `defaultSeams` в `api-process.factory.ts`, репозитории под
   интеграционным набором — их в замере `pnpm test` нет по определению), 16 — новые.
2. **Гипотеза «покрытие пропало» закрыта историей строк.** `git log -L a,b:file -s` по каждому
   непокрытому месту. Последнее касание всех — `2026-08-05` и позже, базовая линия 99.23
   записана `c4df3a7` (2026-07-30), ветки 97.5 — `1619f37` (тот же день). Исключений нет.
   Отдельно проверены кандидаты «старая строка, у которой отняли тест»: `defaultSeams`
   (`2587420`, 2026-07-29) и `catch` в `api-process.factory.ts` (`27e4b5c`, 2026-07-27) — оба
   были непокрыты и на момент записи линии, и это их проектное состояние: тесты подставляют
   свои сшивки, дефолтная реализация вызывает `process.exit` по-настоящему.
3. **Исход 1 — написано четыре теста.**
   - `test/unit/application/confirm-totp.use-case.test.ts`, «losing the commit race»:
     `enrollment.vanished = true` заставляет `commitEnrollment` вернуть `false`.
     Покрывает `confirm-totp.use-case.ts:266-269` (`refuse('race_lost')` + `InvalidTotpCodeError`).
   - Там же, «an account with no credential row at all»: `users.credentials.delete(USER_ID)`.
     Покрывает `:301-304`. Утверждение — не «строка исполнилась», а наблюдаемое: в
     `hasher.verified` лежит пара с `dummyHash`, то есть временнáя планка уплачена.
   - `test/unit/application/regenerate-recovery-codes.use-case.test.ts`, «a TOTP secret this key
     cannot decrypt»: подменённый `fields.decrypt` бросает. Покрывает `:242,251`
     (`totp_secret_undecryptable` на `error` + `ServiceUnavailableError`). Этот случай дословно
     назван в комментарии кода как «то же самое, что в `ConfirmTotpUseCase`» — и там он был
     покрыт, а здесь нет.
   - Там же, «an account with no credential row at all»: покрывает `:187-193`.
4. **Исход 3 — починен один тест.** `test/integration/http/mfa-endpoints.test.ts`: помощник
   `enroll` теперь возвращает секрет; тест двигает `test.clock.advance(60)` (тот же код в том же
   шаге счётчика — реплей, счётчик после `confirm` уже стоит на нём) и получает 200 с десятью
   кодами и `Cache-Control: private, no-store`. Отказной случай, который тест проверял раньше,
   выделен отдельным `it` под своим именем — «refuses a wrong TOTP code presented with the right
   password». Покрывает `mfa.controller.ts:120-121`.
5. **Мутации.** Все прогоны — точечной правкой строки, не заменой по шаблону: первая попытка
   заменить `response.json(serializeRecoveryCodesIssued(...))` по тексту попала в обработчик
   `confirm`, уронила четыре теста и ничего не доказала про `regenerate`.
   | Мутация | Строка | Результат |
   |---|---|---|
   | убрать `refuse('race_lost')` | `confirm-totp:267` | 1 failed |
   | `InvalidTotpCodeError` → `RateLimitedError` | `confirm-totp:269` | 1 failed |
   | убрать проверку против `dummyHash` | `confirm-totp:302` | 1 failed |
   | `ServiceUnavailableError` → `throw cause` | `regenerate:251` | 1 failed |
   | убрать `logger.error(totp_secret_undecryptable)` | `regenerate:242` | 1 failed |
   | убрать проверку против `dummyHash` | `regenerate:191` | 1 failed |
   | удалить строку `setHeader('Cache-Control')` | `mfa.controller:120` | 1 failed |
   | `json(serialize(...))` → `json({})` | `mfa.controller:121` | 1 failed |
6. **Исход 2 — шесть строк оставлены непокрытыми осознанно.** Четыре одинаковых
   `if (decrypted === null) throw` в `confirm-totp`, `disable-totp`, `regenerate-recovery-codes`,
   `verify-second-factor`: `FieldEncryptionPort.decrypt` по своему контракту не возвращает `null`
   для не-`null` входа. Объяснение стояло только у `confirm-totp`; трём
   другим дописано тем же текстом — иначе одинаковые места выглядят по-разному и следующий
   читатель ищет разницу, которой нет. **Поправка того же дня:** здесь было написано «у
   `confirm-totp` и `verify-second-factor` уже стояло», и это нашла ревизия — у
   `verify-second-factor` гард стоял голым, а докстринг метода выше объясняет **бросающую**
   расшифровку и её `503`, то есть другое. Дописано и туда, иначе запись утверждала бы достигнутой
   цель, которой промахнулась на одном месте из четырёх. Плюс `otplib-totp.adapter.ts:119` (`catch`, отвечающий
   отказом вместо 500) и `require-permission.middleware.ts:73` (маршрут смонтирован без
   гарда — дефект проводки) — оба с комментариями с самого начала.
7. **Числа после.** 3876/3905 строк (99.25) и 1696/1738 ветвей (97.58) против записанных 99.23 и
   97.50. `pnpm coverage:baseline` зелёный без `--update`: линия была честной, разошёлся код.
8. **Осталось непокрытым и не тронуто:** 23 строки старше эпика — `main.ts` (4, точка входа,
   динамический импорт ради порядка инициализации OTel), `defaultSeams` и его `catch` (9),
   `role.repository`/`rls-catalog`/`detached-database`/`container.factory`/`accept-invitation`
   (10, из них часть покрыта интеграционным набором, которого нет в замере `pnpm test` —
   ровно тот случай, о котором предупреждает `CLAUDE.md`).
