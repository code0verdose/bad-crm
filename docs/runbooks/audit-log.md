# Runbook — журнал действий (`audit_logs`)

Операционная сторона журнала: партиции, объём, права, что делать, когда что-то пошло не так.
Нормативные документы — [`permission-model.md` §10](../security/permission-model.md),
[`rls-design.md`](../security/rls-design.md), [`data-model.md`, группа 14](../architecture/data-model.md).

## Что это за таблица

Append-only журнал привилегированных действий, партиционированный по месяцам
(`PARTITION BY RANGE (occurred_at)`). Приложение может **только** вставлять и читать: `UPDATE`,
`DELETE` и `TRUNCATE` у роли `app_user` отобраны, и это не соглашение, а привилегия — журнал, который
приложение может переписать, фиксирует то, что приложение решило признать.

Удаление старых данных — не оператор SQL, а процедура: `DETACH PARTITION` силами `app_migrator`
(`pnpm db:audit-retention`, раздел «Ретенция» ниже). Поэтому же партиции создаёт не приложение.

## Партиции

```bash
pnpm db:audit-partitions
```

Создаёт партиции на **текущий месяц и два следующих**; идемпотентно. Выполняется:

- на установке — после миграций (`docs/runbooks/install.md`);
- на каждом обновлении — шаг 7d процедуры ([`upgrade.md`](upgrade.md));
- при желании — из cron раз в сутки, той же ролью, что миграции (`DATABASE_MIGRATION_URL`).

Почему не фоновая задача приложения: создание партиции — это `CREATE TABLE`, а `app_user` ничего не
владеет и ничего создавать не может. Роль, которая могла бы создать таблицу, могла бы создать таблицу
без политики — это ровно та граница, на которой держится изоляция арендаторов.

> **Партицию заводит только `create_audit_partition(date)`. Руками `CREATE TABLE … PARTITION OF` —
> нельзя, и это не стилистика.**
>
> Замерено 2026-08-28 на PostgreSQL 16: партиция **не наследует** от родителя ни `ENABLE ROW LEVEL
> SECURITY`, ни `FORCE`, ни политики — `relrowsecurity = f`, `relforcerowsecurity = f`,
> собственных политик ноль, даже когда родитель получил всё это до её создания. Цена измерена там
> же: запрос **через родителя** вернул строки одной организации, запрос **напрямую к листу** —
> строки обеих.
>
> Функция выдаёт каждому листу `ENABLE`, `FORCE`, обе политики и свои `GRANT`/`REVOKE` явно —
> поэтому она длиннее, чем кажется нужным, и поэтому её нельзя «упростить».
>
> Проверить, что ни один лист не остался без защиты (все три числа должны совпасть с числом
> партиций):
>
> ```sql
> SELECT count(*) FILTER (WHERE c.relrowsecurity)                      AS enabled,
>        count(*) FILTER (WHERE c.relforcerowsecurity)                 AS forced,
>        count(*) FILTER (WHERE (SELECT count(*) FROM pg_policy p WHERE p.polrelid = c.oid) > 0) AS with_policy,
>        count(*)                                                      AS partitions
>   FROM pg_class c
>   JOIN pg_inherits i ON i.inhrelid = c.oid
>   JOIN pg_class parent ON parent.oid = i.inhparent
>  WHERE parent.relname = 'audit_logs';
> ```
>
> **Проверяется автоматически с 2026-08-28.** `pnpm check:rls` обходит партиции отдельным запросом
> и называет их в отчёте («… `N` partitions in schema "public"»), а незащищённый лист выдаёт
> находкой с ненулевым кодом возврата. Проверено на живой базе: партиция, созданная обычным
> `CREATE TABLE … PARTITION OF`, даёт `enabled=false, forced=false, policies=0`.
>
> До этого проверки не было: аудит каталога отбирал только `NOT c.relispartition`, то есть листья в
> него не входили по построению, и «OK» ничего о них не говорил. Запрос выше остаётся полезным как
> способ посмотреть глазами, но он больше не единственный.

**Горизонт в два месяца — это запас на пропущенный запуск.** Если запуск пропущен настолько, что
партиции на текущий месяц нет, вставка не падает: строки попадают в партицию `audit_logs_default`.
Это страховка, а не место, где данные должны жить.

Проверить состояние:

```sql
-- какие партиции есть
SELECT c.relname, pg_size_pretty(pg_total_relation_size(c.oid)) AS size
  FROM pg_inherits i
  JOIN pg_class c ON c.oid = i.inhrelid
  JOIN pg_class p ON p.oid = i.inhparent
 WHERE p.relname = 'audit_logs'
 ORDER BY c.relname;

-- сколько строк осело в страховочной партиции: в норме 0
SELECT count(*) FROM audit_logs_default;
```

Ненулевой `audit_logs_default` означает, что месяц наступил раньше, чем кто-то создал партицию.
Порядок действий: создать недостающие партиции (`pnpm db:audit-partitions`), затем перенести строки
из `audit_logs_default` в нужный месяц — `ATTACH` месяца, чьи строки лежат в DEFAULT, PostgreSQL не
разрешит, пока они там.

```sql
BEGIN;
SET LOCAL app.maintenance = 'on';
-- пример для августа 2026: сначала партиция, потом перенос
SELECT create_audit_partition(date '2026-08-01');
WITH moved AS (
  DELETE FROM audit_logs_default
   WHERE occurred_at >= date '2026-08-01' AND occurred_at < date '2026-09-01'
   RETURNING *
)
INSERT INTO audit_logs SELECT * FROM moved;
COMMIT;
```

Выполняется ролью `app_migrator` (у неё политика `maintenance_access`), не приложением.

## Права

| Роль | Что может |
|---|---|
| `app_user` | `INSERT`, `SELECT` на родительской таблице. На партициях — **ничего** |
| `app_migrator` | владелец: создание/отсоединение партиций, обслуживание в режиме `app.maintenance = 'on'` |
| `backup_role` | `SELECT` на таблице и на каждой партиции — `pg_dump` читает партиции по одной |

Приложение обращается только к родительской таблице: запрос к родителю применяет её политику ко всем
партициям и проверяет привилегии на родителе. Партиции при этом всё равно получают `ENABLE` + `FORCE`
и обе политики (функция `create_audit_partition`) — «сегодня недостижимо» не то свойство, на котором
стоит держать изоляцию.

Проверяется тестами `packages/server/test/integration/db/audit-log-append-only.test.ts` — включая
партицию, созданную после написания теста.

## Объём и рост

Оценка для организации на 50 человек: привилегированные действия (права, файлы, сессии, настройки)
дают порядка **1–3 тыс. записей в месяц на организацию**; при `before`/`after` из нескольких полей
это ~1–2 КБ на запись, то есть **единицы мегабайт в месяц на организацию** плюс индексы (три индекса
на партицию примерно удваивают объём). Инсталляция на 10 организаций — порядка 100–300 МБ в год.

Записи с большими `before`/`after` (полный набор из 331 ключа при правке роли) — единицы в месяц, но
именно они дают выбросы по размеру; смотреть на размер партиции, а не на число строк.

**Замерено 2026-09-06** (PostgreSQL 16, `pgvector/pgvector:0.8.5-pg16` в Testcontainers,
Apple M-series, Colima): 20 000 минимальных записей (без `before`/`after`) заняли **4.06 МБ** вместе
с тремя индексами — около **205 байт на запись**. Запись с `before`/`after` из нескольких полей
крупнее, оценка «1–2 КБ» выше — про неё, и она остаётся оценкой, а не замером.

Метрика для алерта — `audit_log_partition_bytes`, **экспортируется с 2026-09-06**: сумма
`pg_total_relation_size` по всем партициям вместе с их индексами. Три вещи про неё стоит знать
заранее.

- **Она без меток, и метки партиции у неё не будет.** Помесячная метка давала бы новый временной
  ряд каждый месяц на всю жизнь инсталляции, причём ряд, который замирает в день окончания своего
  месяца и никогда не удаляется. И отвечала бы хуже: «как быстро растёт» и «на сколько хватит
  диска» — это `rate()` и `predict_linear()` по одному непрерывному ряду, и ни то, ни другое не
  переживает нарезку на новый ряд каждый месяц. Какая именно партиция большая — вопрос, который
  задают один раз, после алерта, запросом ниже.
- **Значение обновляется не чаще раза в минуту**, сколько бы ни было скрейперов и как бы часто они
  ни ходили. Читать при каждом скрейпе значило бы отдать частоту запросов к рабочей БД чужому
  конфигу. Сам запрос дёшев — замерено p50 **0.48 мс**, max 2.3 мс на 10 партициях, — но дёшев он
  сегодня, а окно кеша не зависит от того, останется ли он таким.
- **Пока не удалось прочитать ни разу — ряда нет вовсе**, а не ноль. Ноль байт журнала — это
  утверждение, и притом успокаивающее; отсутствие ряда честнее.

Размер конкретной партиции по-прежнему смотрят запросом:
`SELECT pg_size_pretty(pg_total_relation_size('audit_logs_2026_08'))`.

**Отсоединённые месяцы в метрику не входят.** После `DETACH` (раздел «Ретенция») месяц — не
партиция, и `audit_log_partition_bytes` падает на его размер в тот же момент, хотя диск занят
по-прежнему до `--drop`. Падение метрики в день запуска ретенции — норма, а не потеря данных;
сколько лежит в ожидании удаления, показывают строка `awaiting drop` в выводе команды и тот же
`pg_total_relation_size` по имени отсоединённой таблицы.
Порог ставится по инсталляции: разумный ориентир — рост месячной партиции более чем вдвое
относительно медианы предыдущих трёх.

**Чего эта метрика не показывает — строк в дефолтной партиции.** Это отдельный сигнал (партиции на
месяц не создали, записи падают в `audit_logs_default`), и снять его тем же способом нельзя:
`REVOKE ALL` не даёт `app_user` посчитать строки листа, а размер дефолтной партиции растворён в
сумме. Считать их может `app_migrator` — то есть команда обслуживания, а не API-процесс; метрика
`audit_log_default_partition_rows`, упомянутая в комментарии миграции, **не экспортируется** и
ждёт своего носителя. До тех пор:
`SELECT count(*) FROM audit_logs_default` ролью `app_migrator` в режиме `app.maintenance = 'on'`.

## Запросы: что читает журнал и что при этом читает диск

**Замерено 2026-09-06**, `packages/server/test/integration/db/audit-partition-pruning.test.ts`:
шесть месяцев по 20 000 записей на две организации (240 000 строк, 9 партиций считая дефолтную и
две будущие), `ANALYZE`, параметры связанные — так, как их шлёт Prisma, а не подставленные в текст
запроса. `EXPLAIN (ANALYZE, BUFFERS)` от имени `app_user` внутри `withTenant`.

| Запрос | Партиций в плане | Страниц (8 КиБ) | Время |
|---|---|---|---|
| Лента за месяц (`occurred_at` в диапазоне, `LIMIT 50`) | **1** | 53 | 0.14 мс |
| Та же лента без фильтра по периоду | 9 | 79 | 0.26 мс |
| `count(*)` за месяц | **1** | 728 | 7.3 мс |
| `count(*)` по всей организации | 9 | 4 368 | 22.7 мс |

Читать это надо так, а не «партиционирование ускоряет всё в шесть раз».

**Отсечение работает, и работает до чтения данных.** Диапазон по ключу партиционирования
сопоставляется с границами партиций на этапе планирования, поэтому пустая таблица отсекает так же,
как полная. Прежняя формулировка в истории — «на пустой таблице `EXPLAIN` покажет одну партицию
просто потому, что данных нет» — неверна; объём нужен для другого (см. следующий абзац).

**На ленте с `LIMIT` выигрыш почти не виден** — 53 страницы против 79. Постраничный запрос
останавливается на пятидесятой строке, сколько бы партиций ни осталось в плане: узел слияния
открывает индекс каждой оставшейся партиции и почти сразу закрывает. Цену отсечение показывает там, где читать
приходится всё: `count(*)` за период — 728 страниц против 4 368, то есть **вшестеро** меньше работы
при шести месяцах истории, и разрыв растёт линейно с возрастом инсталляции. Отсюда практическое
следствие для экрана журнала (STORY-016-03): фильтр по периоду обязателен не ради ленты, а ради
всего, что считает, — счётчиков, графиков, экспорта.

**Три индекса используются каждым своим сценарием**, и каждый — на отсечённой партиции:

| Сценарий | Индекс на партиции |
|---|---|
| Лента за период | `…_organization_id_occurred_at_idx` |
| История объекта (`resource_type` + `resource_id`) | `…_organization_id_resource_type_resource_i_idx` |
| Действия сотрудника (`actor_id`) | `…_organization_id_actor_id_occurred_at_idx` |

Имена — автоматические, от родительских `idx_audit_logs_*`: PostgreSQL называет индексы партиций по
колонкам, а не по имени родительского индекса. Вот **для этого** и нужен объём: на партиции в
несколько строк планировщик предпочтёт последовательное чтение и будет прав, так что «использует
индекс» без засева не проверяется никак.

**Запрос без периода читает все партиции, включая будущие и дефолтную.** Это не дефект: месяцы
вперёд созданы заранее, они пусты и стоят одного обращения к индексу каждый. Но список партиций в
плане растёт с возрастом инсталляции, а `DETACH` старых (`pnpm db:audit-retention`, ниже) его
укорачивает — ещё одна причина, по которой ретенция это не только про диск.

## Стоимость записи внутри транзакции

Журнальная запись идёт **в той же транзакции**, что и действие, которое она фиксирует
(`rules/observability.mdc` §15) — значит её цена лежит на пользовательском пути, внутри 150 мс
бюджета NFR-2, на каждом привилегированном действии.

**Замерено 2026-09-06**, `packages/server/test/integration/db/audit-insert-cost.test.ts`: 300
итераций на плечо после 30 прогревочных, плечи чередуются; контрольное плечо — та же транзакция с
той же обычной записью (`UPDATE users`), но без строки журнала. Условия те же, что выше, плюс: клиент
на хосте, база в контейнере Colima, так что в дельту входит один дополнительный round-trip — ровно
тот, который `PrismaAuditLogger` и делает отдельным `INSERT`.

| Полезная нагрузка | Контроль, среднее | С журналом, среднее | **Дельта** | Доля бюджета 150 мс |
|---|---|---|---|---|
| Несколько изменённых полей | 3.42 мс | 4.34 мс | **0.92 мс** | 0.6 % |
| Правка роли, 331 ключ в `before` и `after` | 2.81 мс | 4.82 мс | **2.01 мс** | 1.3 % |

То есть журнал стоит меньше процента бюджета запроса на типовом действии и меньше полутора на
выбросе. Узким местом он не является и не станет от роста таблицы: вставка идёт в конец текущей
партиции, триггеров на таблице нет ни одного (проверяется тестом, а не обещанием), вычислений внутри
транзакции нет — `severity` берётся из каталога действий в памяти, адрес хешируется до входа в
транзакцию.

**Что этот замер пересматривает:** появление любого триггера на `audit_logs`, синхронной репликации
(`synchronous_commit = remote_apply` меняет цену `COMMIT`, а не `INSERT`, но платит её тот же
запрос), а также рост `before`/`after` за пределы единиц килобайт — на большем TOAST начнёт сжимать
и выносить значения, и линейности здесь больше не будет.

**Таблица выше — голая вставка; деградируемая запись (`INFO` без опасного права за ней) с 2026-09-06 стоит дороже на ограду** (раздел
«Сбой записи» ниже): адаптер добавляет `SAVEPOINT` до вставки и `RELEASE SAVEPOINT` после — два
служебных оператора, ничего в базе и по round-trip каждый на проводе. **Замерено** тем же тестом
третьим плечом, в одном прогоне с голым (сравнимы друг с другом, а не с таблицей: тот прогон был
медленнее целиком, контроль 4.5–5.3 мс):

| Плечо, типовая нагрузка | Дельта, среднее | p50 |
|---|---|---|
| Голая вставка (fail-closed действия) | 1.28 мс | 1.01 мс |
| С оградой `SAVEPOINT`/`RELEASE` (деградируемая `INFO`) | **2.96 мс** | 2.80 мс |

Ограда стоит около **1.7 мс** — два round-trip по ~0.85 мс на сокете клиент → Colima; на базе в
той же сети или на том же хосте она дешевле в той же пропорции, что и сама вставка. Это цена
свойства «сбой строки не откатывает действие» и платится только на деградируемых действиях; fail-closed
действия — включая `INFO` за опасным правом — стоят ровно столько, сколько в таблице.

### Стоимость порта — до базы

Вставка — то, что берёт база; порт — то, что процесс делает **перед** ней: редакция полей
(`audit-redaction.util.ts`, deny-list на каждой записи), вывод `severity` и `actorType`, ключевой
хеш адреса, решение об ограде, два декоратора. Замерено 2026-09-06,
`packages/server/test/unit/audit/audit-port-cost.test.ts`: настоящая цепочка из composition root
против транзакции, чья вставка разрешается мгновенно; контрольное плечо — та же фиктивная вставка
с теми же объектами `before`/`after`, но мимо порта; плечи чередуются, 2 000 итераций после 200
прогревочных, три прогона. Node 22.22, Apple M-series, `vitest run --coverage.enabled=false` — не
то, что делает `pnpm test` в пакете (там v8-покрытие включено конфигом, и под инструментированием
цифры выше). Потолки в тесте — по p50 дельты, на порядок выше замера: среднее по 2 000 итераций
сдвигает одна пауза сборщика мусора на занятом раннере CI, медиана её не видит.

| Полезная нагрузка | Контроль | Через порт | **Дельта (среднее)** | p95 | Доля бюджета 150 мс |
|---|---|---|---|---|---|
| Несколько изменённых полей, `INFO` (ветка с оградой) | 0.5 мкс | 9.8–11.1 мкс | **9–11 мкс** | 15–17 мкс | 0.007 % |
| Правка роли, 331 ключ в `before` и `after`, `WARNING` | 0.4 мкс | 48.5–55.4 мкс | **48–55 мкс** | 68–77 мкс | 0.04 % |

Выброс — целиком редакция: обход 662 строк с проверкой каждой по пяти формам значения. Порт стоит
примерно сороковую часть вставки той же строки (2.01 мс) и не является тем местом, где дорожает
привилегированное действие. Числа сдвинет только рост `before`/`after` или новая форма значения в
deny-list — регулярка на каждую строку полезной нагрузки.

## Сбой записи: что деградирует, а что откатывается

Запись идёт в транзакции действия, значит вопрос «что, если строка не записалась» — это вопрос о
самом действии. Ответ — **по действию, никогда по месту вызова**, и он складывается из двух
каталогов (STORY-016-02, критерий 9): severity действия (карта severity в `packages/shared/src/audit/audit-severity.enums.ts`) и опасность
права, за которым действие стоит (карта действие → право в `packages/shared/src/audit/audit-action-permission.enums.ts` × флаг `dangerous` каталога прав).

| Действие | Что с ним при сбое строки | Что видит оператор |
|---|---|---|
| `WARNING`, `CRITICAL` — любое | **откатывается** вместе с записью — привилегированное действие без следа хуже, чем несостоявшееся | запрос отвечает ошибкой; `audit_write_failed_total` +1; строка в логе от обработчика ошибок |
| `INFO`, за которым стоит ключ с `dangerous: true` (сегодня одно — `permission.inspected` за `permission:override_read`) | **откатывается**, как строка выше: чтение, о котором никому не сказали, — это как планируется запись | то же |
| `INFO` за обычным ключом или без ключа | **проходит** без строки журнала | `audit_write_failed_total` +1; строка `error` с `event: audit.write_degraded`, действием, `severity`, `requestId` (из события, иначе из контекста запроса) и ошибкой в виде `{ type, code, driverCode, message }` — без `before`/`after`, без объекта ошибки целиком |

Решение — одна функция `isDegradableAuditAction`
(`application/platform/audit/degradable-audit-actions.util.ts`), которой пользуются и адаптер, и
декоратор; какие действия деградируемы сегодня, выводит и печатает при расхождении
`packages/server/test/unit/audit/degradable-audit-actions.test.ts` — списка руками нигде нет.
Команда, `team.member_*`: с 2026-09-06 команда может быть субъектом гранта ACL, но опасное
действие — сам грант (`acl:grant`, `WARNING`), а `team:manage_members` флага не несёт, поэтому
эти три остаются деградируемыми по общему правилу.

**Почему для деградируемых нужен `SAVEPOINT`, а не просто «проглотить ошибку».** Упавший оператор
переводит транзакцию PostgreSQL в аборт: всё следующее, включая `COMMIT`, отвергается с `25P02`.
Декоратор, который глотает ошибку без ограды, отдаёт вызывающему успех, который база опровергнет на
коммите. Поэтому `PrismaAuditLogger` оборачивает деградируемую вставку в `SAVEPOINT audit_entry_<n>`
и на сбое делает `ROLLBACK TO SAVEPOINT`; для fail-closed действий ограды нет — абортированная
транзакция и есть нужный исход. Проверено на живом PostgreSQL 2026-09-06
(`packages/server/test/integration/db/audit-write-degradation.test.ts`): сбой наведён значением с
`\u0000` в `jsonb` (`22P05`), потому что этот отказ происходит **в базе**; `resourceId: 'not-a-uuid'`
для этого не годится — его отвергает движок Prisma до отправки, и транзакция не абортится. Там же
контроль без ограды: после проглоченного сбоя следующий `SELECT 1` отвечает «current transaction is
aborted».

**Имя точки — от счётчика, записи в одной транзакции — по очереди.** Savepoint — точка на стеке
соединения, и `ROLLBACK TO` откатывает всё, что было после неё, а не только «свою» вставку. Два
`record`, запущенных вместе на одной транзакции (`Promise.all`), при общем имени `audit_entry`
ставили обе точки до обеих вставок, и откат второй молча стирал успешную строку первого — при
одном сбое в счётчике и двух дырах в журнале. Адаптер сериализует свои записи по транзакции
(очередь на объекте транзакции) и нумерует точки; строка первого остаётся — тот же тест, случай
«two INFO records racing». Что адаптер сериализовать не может — собственный оператор вызывающего,
запущенный параллельно с `record`: его откатит та же ограда, и никто об этом не сообщит; `record`
ждут последовательно с изменением, которое он описывает (докстринг порта).

**Что не смягчается никогда:** `AuditTrailUnscopedError` — запись вне tenant-скоупа своего
изменения. Это ошибка вызывающего кода, а не хранилища, и до `7942a18` она молча становилась строкой
лога и успехом; деградировать её значило бы вернуть ту же дыру для деградируемой части каталога.
И `AuditFenceRollbackError` — вставка отвергнута, а `ROLLBACK TO SAVEPOINT` после неё тоже: транзакция
больше не известна как пригодная, «действие прошло без строки» было бы утверждением о коммите,
который может быть отвергнут. Ошибка несёт обе причины: отказ отката в сообщении, отказ вставки в
`cause` (сериализатор pino складывает `cause` в строку — проверено тестом).

**Сигнал для алерта — `audit_write_failed_total`**, один и без меток: любой ненулевой прирост
означает «след ломается», и разбираться надо в обоих случаях. Какой именно исход был — в логе:
`event=audit.write_degraded` для прошедшего действия, ошибка запроса для откаченного. Метка
`outcome` рассматривалась и отвергнута: оба значения ведут к одной проверке базы, а дашборд и
алерт по имени без меток уже существуют.

## Ретенция

```bash
# crontab того пользователя, которому принадлежит /opt/bad-crm; ролью миграций
# (DATABASE_MIGRATION_URL), AUDIT_RETENTION_MONTHS в .env. Вывод — в датируемый лог: без
# редиректа stdout cron никуда не пишется, а после `--drop` след в каталоге исчезает вместе
# с таблицей.
PATH=/usr/local/bin:/usr/bin:/bin
0 4 1 * * cd /opt/bad-crm && pnpm db:audit-retention >> /var/log/bad-crm/audit-retention.log 2>&1
```

`PATH=` в crontab обязателен: cron запускает команды с `/usr/bin:/bin`, а `pnpm` из corepack, nvm
или Homebrew лежит не там — без строки в лог попадёт только `pnpm: not found` (`127`). Куда
установлен `pnpm`, печатает `command -v pnpm` в интерактивной оболочке того же пользователя.
`AUDIT_RETENTION_MONTHS` задаётся **в `.env`, а не в окружении cron**: `turbo` в строгом режиме
переменных не пропускает в задачу то, чего нет в `turbo.json`, и значение из crontab команда не
увидит (замерено 2026-09-10: `AUDIT_RETENTION_MONTHS=6 pnpm db:audit-retention` прошёл с
настройкой из `.env`, тот же вызов с `--env-mode=loose` отказал с кодом `2`). Код выхода через
`pnpm` → `turbo` → `tsx` доходит до cron без изменений — тот же замер: `2` на выходе процесса.

**След ретенции — три места, и ни одно не появляется само.**

1. **Лог команды** — редирект в cron-строке выше обязателен. Это единственное место, где после
   `--drop` остаётся, *что* и *когда* было удалено: `pg_class` после `DROP` пуст, а stdout cron без
   редиректа не пишется никуда. Ненулевой код возврата обязан поднимать алерт — cron сам по себе
   не алертит; простейшая форма — `… || <оповещение>` в той же строке или проверка последней
   строки лога мониторингом. Коды: `1` — что-то не отсоединилось или не удалилось, либо
   `another run holds the lock` (второй запуск при незавершённом первом; ничего не тронуто);
   `2` — аргументы, конфигурация, роль без прав (`must be owner …`; подсказка про
   `DATABASE_MIGRATION_URL` печатается только если переменная не задана — заданная, но
   неверная, подсказки не получает) или партиция, чьи границы не совпадают с именем.
2. **Журнал PostgreSQL** — `log_statement = 'ddl'` в `postgresql.conf` записывает каждый
   `DETACH`/`DROP` с ролью и временем независимо от того, кто его выполнил. Оговорка та же, что в
   [`install.md`](install.md) (§ ротация паролей): при `ddl` в лог попадает и `ALTER ROLE …
   PASSWORD`; скрипт ротации глушит `log_statement` на свою сессию, а на управляемом инстансе без
   прав суперпользователя это не удаётся — там лог после ротации чистят.
3. **Devops-журнал** — каждый `--drop` записывается туда же, куда
   [`rls-design.md`](../security/rls-design.md) («Суперпользователь и владелец инсталляции»)
   требует записывать любую операцию под `app_migrator`: имя таблицы, дата, дамп, в котором она
   есть. Отсоединение записи не требует — оно обратимо и видно в `awaiting drop`.

**Один запуск за раз.** Команда берёт сессионный advisory lock (`pg_try_advisory_lock`,
ключ `AUDIT_RETENTION_ADVISORY_LOCK_KEY`) на всё время работы; второй запуск — cron поверх ручного
или наоборот — отвечает `another run holds the lock`, код `1`, и не трогает ничего. Без этого два
запуска гонялись за одним `DETACH`, проигравший падал с `is not a partition` как на сломанной
конфигурации и не обрабатывал остаток плана. Advisory lock не требует привилегий — ключ может
держать любая сессия, включая `app_user`; поэтому `another run holds the lock` при отсутствии
ручного запуска — повод посмотреть `pg_locks` (`locktype = 'advisory'`), а не ждать: удержание
ключа скомпрометированным приложением останавливает ретенцию, но не даёт ему удалить ни строки.

**Отсоединённый месяц не переименовывать.** Имя `audit_logs_YYYY_MM` — единственное, по чему
`pnpm db:grants` и проверка 4c из `rls-design.md` узнают отсоединённый месяц (регексп
`^(audit_logs|…)_[0-9]{4}_[0-9]{2}$`). Переименованный месяц выпадает из регекспа, и следующий
`pnpm db:grants` выдаст на него `app_user` `SELECT, INSERT, UPDATE, DELETE` веткой обычных
tenant-таблиц — append-only нарушен, а ни один тест этого не увидит. Нужно отличить его от
живых — `COMMENT ON TABLE`, не `RENAME`.

**По умолчанию ретенции нет.** `AUDIT_RETENTION_MONTHS` не задана — команда печатает, что
ретенция выключена, и ничего не отсоединяет. Это дефолт намеренно: срок хранения журнала у
self-hosted инсталляции диктует её аудитор, и он измеряется годами, которых продукт не знает.
Число, выбранное за оператора, было бы уничтожением улик по умолчанию. Диапазон `12`–`600`
месяцев: ниже года — почти наверняка ошибка единиц, «никогда» пишется отсутствием переменной,
`0` отвергается, а не читается как «выключено».

**Что делает запуск.** Месяц отсоединяется, когда **последняя** его запись старше порога: при
`AUDIT_RETENTION_MONTHS=12` и запуске 6 сентября 2026 отсечка — `2025-09-01`, отсоединяется
`audit_logs_2025_08` (закончился ровно на отсечке) и всё старше, `audit_logs_2025_09` остаётся.
Итого хранится порог полных месяцев плюс текущий. Отсечка считается в UTC. Границы самих партиций
— полночь месяца **в `timezone` сессии, в которой партицию создавали**: `create_audit_partition`
пишет `date`-литерал в ключ `timestamptz`, и инсталляция с `timezone = 'Europe/Moscow'` в
`postgresql.conf` получает границы за три часа до полуночи UTC (замерено 2026-09-10). Команда это
допускает: граница, отстоящая от полуночи UTC не более чем на часовой пояс (±14 ч), — тот же
месяц; граница другого месяца (минимум 28 дней) — отказ, см. ниже. Сверяются **обе** границы —
нижняя с началом месяца, верхняя с началом следующего: партиция на два месяца под именем одного
(`FROM ('2025-06-01') TO ('2025-08-01')`) отсоединила бы июль вместе с июнем.

- `DETACH PARTITION`, **не `DELETE`**: строки не удаляются, `DELETE FROM audit_logs` в коде
  запрещён тестом (`packages/server/test/unit/audit/audit-retention.test.ts`). Отсоединённый
  месяц — обычная таблица `audit_logs_YYYY_MM`: свои `ENABLE`/`FORCE` и обе политики при нём
  (они были его собственными с рождения — наследовать было нечего, терять нечего), `backup_role`
  читает его, `app_user` — нет, и `pnpm db:grants` этого не меняет (узнаёт месяц по имени;
  до 2026-09-06 выдал бы приложению `SELECT, INSERT, UPDATE, DELETE` — замерено до правки).
- `audit_logs_default` **не трогается никогда** и упоминается в каждом выводе: ненулевое число
  строк в ней — не старые данные, а признак, что `pnpm db:audit-partitions` не запускали; порядок
  действий — раздел «Партиции» выше.
- Партиция, которую команда не может датировать (имя не `audit_logs_YYYY_MM`), остаётся на месте.
  Партиция, чьё имя и граница (`relpartbound`) расходятся — `audit_logs_2025_03` с диапазоном
  апреля, — останавливает запуск целиком с кодом `2` **до первого `DETACH` или `DROP`** (в обоих
  режимах): такую делает только `CREATE TABLE … PARTITION OF` руками, и датировать её по имени
  значило бы отсоединить не тот месяц. Сообщение называет месяц из имени и фактическую
  границу (момент в UTC); расхождение на часы — часовой пояс, не ошибка, и запуск оно не
  останавливает.
- Команда не принимает `organizationId` и не знает организаций: отсоединяется месяц целиком.
  Разные сроки у организаций одной инсталляции этой командой не выражаются — физически удалить
  строки одной организации из общей партиции нельзя; порог на организацию и маскирование чтения
  ждут экран журнала (STORY-016-03).
- Код возврата: `0` — сделано; `1` — что-то не отсоединилось или не удалилось (вывод говорит
  что) либо `another run holds the lock`; `2` — аргументы, конфигурация (в том числе
  `AUDIT_RETENTION_MONTHS` вне `12`–`600`), роль или партиция с чужой границей.

Пример вывода:

```
audit retention: 12 months, cutoff 2025-09-01
  detached audit_logs_2025_08 (18948096 bytes, 1 ms) — back it up, then drop it
  kept 4 attached partition(s)
  audit_logs_default: empty
```

**Удаление — второй шаг, руками, по имени.** Отсоединённый месяц лежит, пока его не захватит
бэкап ([`backup-restore.md`](backup-restore.md), раздел 1: он попадает в `pg_dump` как любая
таблица). Убедившись, что дамп с ним снят и проверен:

```bash
pnpm db:audit-retention -- --drop audit_logs_2025_08
```

Команда отказывает всему списку целиком, если хоть одна таблица ещё присоединена, не существует
или не датирована: `--drop-all` нет намеренно — имя таблицы и есть подтверждение, что бэкап был
именно её. Сами `DROP` идут **одной транзакцией** с тем же `lock_timeout` 3 с, что у `DETACH`:
если вторую таблицу списка держит открытый читатель (например `pg_dump -t` именно этого месяца),
запуск отступает, первая таблица откатывается вместе с ней, и вывод говорит `FAILED <таблица>:
lock timeout` — половины списка, которую надо сверять с бэкапом, не бывает. Каждый следующий
запуск без аргументов перечисляет отсоединённые, но не удалённые месяцы строкой `awaiting drop`;
их размер — `pg_size_pretty(pg_total_relation_size('audit_logs_2025_08'))`, в метрику
`audit_log_partition_bytes` они не входят (см. «Объём и рост»).

**Восстановить отсоединённый месяц из дампа** — как отдельную таблицу, а не в `audit_logs`:
`pg_restore -U app_migrator -d bad_crm -t audit_logs_2025_08 --no-owner --no-privileges` вернёт
таблицу под тем же именем (имя должно быть свободно), после чего обязателен `pnpm db:grants` —
`--no-privileges` не вернёт `backup_role` её `SELECT`, а `app_user` не получит ничего. Читать —
`app_migrator` в режиме `app.maintenance = 'on'`. При необходимости месяц можно и присоединить
обратно (`ALTER TABLE audit_logs ATTACH PARTITION audit_logs_2025_08 FOR VALUES FROM ('2025-08-01')
TO ('2025-09-01')`) — при условии, что в `audit_logs_default` нет строк этого месяца. Проверить
перед `ATTACH`, ролью `app_migrator` в режиме `app.maintenance = 'on'`:

```sql
SELECT count(*) FROM audit_logs_default
 WHERE occurred_at >= date '2025-08-01' AND occurred_at < date '2025-09-01';  -- должно быть 0
```

Если не ноль — сначала перенести эти строки в присоединяемую таблицу процедурой из раздела
«Партиции» выше (`DELETE … RETURNING` из `audit_logs_default`, вставка в месяц), иначе `ATTACH`
откажет. Эта процедура **не прогонялась автоматически**: проверяйте её на копии перед тем, как
на неё рассчитывать, как того требует NFR-5 для любого бэкапа.

| `DROP` отсоединённого месяца, `pg_dump -t` одного месяца | **не замерено.** Порядок величин по устройству: `DROP` — правка каталога плюс удаление файлов таблицы и индексов, миллисекунды на десятки мегабайт; `pg_dump -t` — последовательное чтение таблицы, секунды на те же десятки мегабайт. Оба держат блокировку только на этой таблице, не на `audit_logs` |
| RLS отсоединённого месяца | `rls_enabled = true`, `rls_forced = true`, политики `tenant_isolation` и `maintenance_access` — свои, сохранились |
| Права отсоединённого месяца | `app_user` — ничего (и после повторного `01-grants.sql`), `backup_role` читает все 100 000 строк |

**Цена блокировки — очередь, а не работа.** Сам `DETACH` — миллисекунда, но `ACCESS EXCLUSIVE`
ждёт всех текущих читателей родителя, а пока ждёт, за ним встают все вставки журнала всех
организаций, то есть все привилегированные действия. Отсюда `lock_timeout` и cron в тихий час
рядом с бэкапом, но **не одновременно с ним**: `pg_dump` держит `ACCESS SHARE` на `audit_logs` всё
время выгрузки, и `DETACH` в этот момент гарантированно упрётся в таймаут.

**Чего здесь нет, и почему.** Автоматического запуска — в продукте нет носителя периодических
задач (та же причина, что у `db:audit-partitions`); cron хоста и есть носитель. Выгрузки в
объектное хранилище — ждёт EPIC-015; до него архив — `pg_dump`. Записи в сам журнал о том, что
месяц отсоединён, — у операции нет организации, а `organization_id` в журнале `NOT NULL`;
единственное действие без организации в каталоге — `rls.bypassed`, и расширять этот список
ради этой операции не стали. **Принятый риск, по факту:** после `--drop` `pg_class` о таблице не
помнит, а stdout cron без редиректа не пишется никуда — след ретенции существует только там, где
его оставили сами: датированный лог команды, `log_statement = 'ddl'` и devops-журнал (три пункта
в начале раздела). Без них удаление месяца — операция без следа.
Метрик — команда не процесс API, ей не с чего их отдавать; число строк в `audit_logs_default`
она печатает, и это не метрика `audit_log_default_partition_rows`, которая по-прежнему ждёт
носителя.

## Частые вопросы

**«Запись выглядит неправильной — можно поправить?»** Нет, и это не ограничение интерфейса: у
приложения нет привилегии. Исправление — новая запись, а не правка старой.

**«Нужно удалить данные уволенного сотрудника».** Журнал хранит `actor_id`, а не персональные
данные; сама запись — доказательство действия и удалению по запросу не подлежит (см. раздел о ПДн в
[`threat-model.md`](../security/threat-model.md)). Что удаляется — профиль, а не след действия.

**«Партиция за прошлый год занимает много места».** Ретенция — раздел выше: `AUDIT_RETENTION_MONTHS`
плюс `pnpm db:audit-retention` из cron, `DETACH PARTITION` силами `app_migrator`, удаление вторым
шагом после бэкапа. `DELETE` на миллионах строк не применяется никогда: это часы блокировок и
раздувание таблицы вместо операции над каталогом, которая замерена в одну миллисекунду.
