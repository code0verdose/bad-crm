## 1. Что бэкапим и что нет

| Что | Бэкапить | Почему |
|---|---|---|
| **`pgdata`** — PostgreSQL | **Да, обязательно** | Истина по всем данным: организации, проекты, задачи, документы, время, аудит и **весь шифротекст vault**. Без него теряется всё |
| **`minio-data`** — объектное хранилище | **Да, обязательно** | Тела файлов и вложений. В базе лежат только метаданные и ключи объектов; без хранилища они указывают в пустоту |
| **`.env` и ключи** | **Да, но отдельно** | `APP_ENCRYPTION_KEY` и `JWT_SECRET`. См. раздел 3 — их нельзя хранить рядом с дампом |
| **`meili-data`** — индекс Meilisearch | **Нет** | Производные данные. Индекс восстанавливается переигрыванием из базы; бэкапить его — тратить место на то, что и так есть, и рисковать восстановить рассогласованный с базой индекс |
| **`redis-data`** | Нет | Очереди восстанавливаются из таблицы outbox, presence эфемерен, сессии переживают потерю ценой повторного входа |
| **Логи** | По вашему усмотрению | Не нужны для восстановления работоспособности, но нужны для расследования инцидента. Считаются чувствительными |

**Правило:** производное не бэкапим, источник истины бэкапим обязательно. Поисковый индекс —
производное. Файлы — не производное, их восстановить неоткуда.

## 2. 🔴 Критично: `FORCE ROW LEVEL SECURITY` ломает `pg_dump`

Это самая опасная ловушка бэкапа в Bad CRM, и она **не проявляется как ошибка**.

Все мультиарендные таблицы имеют `FORCE ROW LEVEL SECURITY` — это часть модели изоляции: без `FORCE`
владелец таблицы обходит политики молча, и вся защита превращается в декорацию
([`../security/rls-design.md`](../security/rls-design.md)).

Побочный эффект: **`pg_dump`, снятый под ролью-владельцем таблиц, либо падает с ошибкой RLS, либо —
с флагом `--enable-row-security` — выгружает частичные данные.**

Второй сценарий страшнее первого. Дамп формально успешен, файл существует, размер выглядит
правдоподобно, восстановление проходит без ошибок — а данных внутри меньше, чем было. Обнаруживается
это в момент, когда вы восстанавливаетесь после аварии и видите пустые проекты.

### Правило

**Бэкап снимается суперпользователем или отдельной ролью с `BYPASSRLS`.** Не ролью приложения
(`app_user` — у неё политики применяются), не ролью-владельцем схемы.

```bash
# ПРАВИЛЬНО — роль с BYPASSRLS
docker compose exec -T postgres \
  pg_dump -U backup_role -d bad_crm -Fc --no-owner --no-privileges \
  > backups/$(date +%F)/db.dump

# НЕПРАВИЛЬНО — под владельцем таблиц; молча выгрузит частичные данные
docker compose exec -T postgres \
  pg_dump -U app_migrator -d bad_crm --enable-row-security -Fc > db.dump
```

Проверьте атрибут роли перед первым бэкапом:

```sql
SELECT rolname, rolsuper, rolbypassrls FROM pg_roles WHERE rolname = 'backup_role';
-- rolbypassrls должно быть true
```

### Обязательная сверка числа строк

Одной успешности `pg_dump` недостаточно. **При каждом восстановлении сверяйте число строк по
нескольким крупным таблицам** с тем, что было в источнике.

Снимайте счётчики вместе с дампом:

```bash
docker compose exec -T postgres psql -U backup_role -d bad_crm -At -F',' -c "
  SELECT relname, n_live_tup
  FROM pg_stat_user_tables
  WHERE n_live_tup > 0
  ORDER BY n_live_tup DESC
  LIMIT 25;
" > backups/$(date +%F)/rowcounts.csv
```

После восстановления выполните тот же запрос на восстановленной базе и сравните. Расхождение по
любой мультиарендной таблице означает, что дамп снимался под ролью, к которой применялись политики,
и бэкапу **нельзя доверять** — процедуру надо чинить, а не «списать на статистику».

> `n_live_tup` — оценка планировщика, не точный счёт. Для контрольных таблиц (те, где расхождение
> критично) используйте точный `COUNT(*)` под ролью с `BYPASSRLS`. Оценка годится для выявления
> катастрофического расхождения (10 000 против 0), точный счёт — для проверки целостности.

### Что именно должно быть выдано `backup_role`, чтобы дамп вообще снялся

`BYPASSRLS` снимает применение *политик*, но не отменяет проверку *грантов*. Забытый `GRANT` — это
не «таблица выгрузится частично», а падение всего дампа: `pg_dump` берёт `ACCESS SHARE` на все
таблицы одним `LOCK TABLE` до того, как прочитает первую строку. Три места, где это ловится:

| Объект | Нужен | Что видно без него |
|---|---|---|
| Доменная таблица | `GRANT SELECT … TO backup_role` | `ERROR: permission denied for table tasks` |
| **Лист партиции** | `GRANT SELECT … TO backup_role` | `ERROR: permission denied for table audit_logs_2026_07` |
| **Sequence** | `GRANT SELECT … TO backup_role` | `ERROR: permission denied for sequence audit_logs_id_seq` |

Партиции — самый неочевидный из трёх. `GRANT` на родительскую таблицу **не распространяется** на
листы, а `pg_dump` выгружает партиционированную таблицу полистно и проверяет права на листе. То
есть `audit_logs` — единственная таблица, ради которой бэкап нужен при разборе инцидента, — без
гранта на партиции роняет бэкап целиком. Правило и его связь с изоляцией арендаторов —
[`../security/rls-design.md`](../security/rls-design.md), раздел про партиционированные таблицы.

Ничего из этого не поддерживается вручную: гранты раздаёт `packages/server/prisma/sql/01-grants.sql`,
который обходит каталог и потому покрывает и таблицы, и партиции, и последовательности, созданные
любой будущей миграцией. Он запускается **после каждой миграции** и **после каждого восстановления**:

```bash
pnpm db:grants
```

### Смежное ограничение: `COPY FROM` не работает с RLS

PostgreSQL не поддерживает `COPY … FROM` в таблицу с включённым row-level security. Это касается
восстановления через текстовый дамп (`pg_dump` без `-Fc` использует `COPY`) и массового импорта.
Поэтому: **дамп снимается в custom-формате (`-Fc`), а восстановление идёт `pg_restore` под ролью с
`BYPASSRLS`**, где политики не применяются и `COPY` проходит.

## 3. Шифрование бэкапов и где хранить ключ

### Что лежит в дампе открыто

**Почти всё.** В базе зашифрованы только:

- содержимое E2EE-vault — ключами, которых на сервере нет вообще;
- секреты интеграций (`apiKeyEnc`, SMTP-пароли, GitHub-токены, webhook-секреты, TOTP-секреты) —
  ключом `APP_ENCRYPTION_KEY`;
- пароли пользователей — argon2id-хеши (не расшифровываются в принципе).

Всё остальное — проекты, задачи, документы, база знаний, чат, комментарии, email-адреса, ставки,
записи времени, инвойсы, журнал аудита — лежит **открытым текстом**. Дамп базы Bad CRM следует
считать настолько же чувствительным, насколько чувствительна сама система.

### Отсюда — два требования

**Первое: бэкапы шифруются.** Не «желательно», а обязательно, потому что бэкап обычно уезжает
туда, где контроль доступа слабее, чем на боевом хосте.

```bash
# симметрично, паролем
gpg --symmetric --cipher-algo AES256 -o db.dump.gpg db.dump

# или на публичный ключ — предпочтительнее: для создания бэкапа не нужен секрет
gpg --encrypt --recipient backup@example.com -o db.dump.gpg db.dump

# проверить, что зашифрованное читается тем, чем вы собираетесь читать
gpg --list-packets db.dump.gpg | head
```

**Второе: `APP_ENCRYPTION_KEY` не хранится там же, где единственная копия бэкапов.**

Типичная и опасная конфигурация: `.env` лежит на том же хосте, бэкап-скрипт складывает дамп рядом, и
всё это уезжает одним архивом. В результате тот, кто получил архив, получил и шифротекст секретов
интеграций, и ключ к ним. Шифрование секретов at rest в этой схеме не даёт ничего.

Правильно:

- дамп — в одно место (объектное хранилище, отдельный сервер, offline-носитель);
- `APP_ENCRYPTION_KEY` и `JWT_SECRET` — **в другое** (менеджер паролей, KMS, сейф);
- ни один человек и ни один автоматический процесс не должен иметь доступ к обоим местам без
  осознанного действия.

При этом ключ необходим для восстановления работоспособности: без `APP_ENCRYPTION_KEY`
восстановленная база не сможет расшифровать API-ключи AI-провайдеров, SMTP-пароли, GitHub-токены и
TOTP-секреты — их придётся вводить заново. Потеря ключа не теряет ваши проекты и задачи, но теряет
все настроенные интеграции и вторые факторы.

## 4. 🔴 Бэкап бесполезен для vault без ключей пользователей

Отдельное предупреждение, которое обязано быть донесено до владельца инсталляции — оно же
воспроизводится в интерфейсе администратора:

> Бэкап PostgreSQL содержит всё хранилище секретов **в зашифрованном виде** и **бесполезен без
> мастер-паролей пользователей**. Восстановление из бэкапа не восстанавливает доступ. Если все
> пользователи забыли мастер-пароли и не имеют Recovery Kit, данные vault утрачены навсегда, и
> никакой бэкап этого не исправит.

Практические следствия:

1. **`pgdata` бэкапить обязательно** — без него теряется даже шифротекст, и тогда не поможет уже
   ничего, включая известный мастер-пароль.
2. **Восстановление на другой хост не требует переноса каких-либо vault-ключей** — их на сервере
   нет. Пользователь разблокирует хранилище своим мастер-паролем на новом хосте так же, как на старом.
3. **Частичное восстановление «вернуть одно хранилище на вчера» ломает консистентность `keyVersion`**,
   если между этими моментами была ротация ключа. Если такой откат всё же нужен, после него
   **обязательна ротация** — иначе останутся элементы, зашифрованные ключом, который система считает
   отозванным. Отдельная процедура описана в
   [`../security/e2ee-design.md`](../security/e2ee-design.md).
4. **Recovery Kit — это ответственность пользователя, а не администратора.** Убедитесь, что
   сотрудники сохранили свои Recovery Kit при первой настройке vault. Администратор не может
   восстановить чужое личное хранилище — в этом и смысл.

## 5. RPO и RTO

**RPO** (recovery point objective) — сколько данных вы готовы потерять.
**RTO** (recovery time objective) — как быстро вы должны вернуться в строй.

Это ваши цифры, а не наши: они зависят от того, сколько стоит потерянный день работы команды.
Ориентиры для типичной инсталляции на 20–50 человек:

| Профиль | RPO | RTO | Что для этого нужно |
|---|---|---|---|
| **Базовый** | 24 часа | 4 часа | Ежесуточный полный дамп + зеркало MinIO, хранение 7 ежедневных / 4 еженедельных / 6 ежемесячных |
| **Повышенный** | 1 час | 2 часа | Ежесуточный дамп + непрерывная архивация WAL (PITR), зеркало MinIO чаще |
| **Строгий** | минуты | < 1 часа | Потоковая репликация PostgreSQL на резервный хост + PITR + реплицированное объектное хранилище |

Замечания, которые обычно выясняются поздно:

- **RTO определяется не скоростью `pg_restore`, а тем, есть ли у вас подготовленный хост.** Если
  восстановление начинается с «сейчас закажем сервер», четыре часа превращаются в сутки.
- **База и файлы должны бэкапиться согласованно.** Дамп в 03:00 и зеркало MinIO в 05:00 дают окно, в
  котором записи о файлах есть, а самих файлов нет. Снимайте их близко по времени и понимайте, какая
  сторона окажется «впереди».
- **Хранение по схеме 7/4/6** (ежедневные / еженедельные / ежемесячные) защищает не только от
  аварии, но и от медленной порчи данных, замеченной через месяц.
- **Бэкап, который никто не восстанавливал, — это гипотеза.** Тестовое восстановление — минимум раз в
  квартал, и его результат записывается.

## 6. Процедура бэкапа

```bash
#!/usr/bin/env bash
# Ориентировочный вид scripts/backup.sh — появится в EPIC-017
set -euo pipefail

DEST="backups/$(date +%F-%H%M)"
mkdir -p "$DEST"

# 1. база — под ролью с BYPASSRLS, custom-формат
docker compose exec -T postgres \
  pg_dump -U backup_role -d bad_crm -Fc --no-owner --no-privileges \
  > "$DEST/db.dump"

# 2. счётчики строк для последующей сверки
docker compose exec -T postgres psql -U backup_role -d bad_crm -At -F',' \
  -c "SELECT relname, n_live_tup FROM pg_stat_user_tables ORDER BY n_live_tup DESC LIMIT 25;" \
  > "$DEST/rowcounts.csv"

# 3. объектное хранилище
mc mirror --overwrite --remove local/bad-crm "$DEST/minio/"

# 4. манифест: что за версия, когда, чем снималось
{
  echo "date=$(date -Is)"
  echo "app_version=$(git describe --tags --always)"
  docker compose exec -T postgres psql -U backup_role -d bad_crm -At \
    -c "SELECT migration_name FROM _prisma_migrations ORDER BY finished_at DESC LIMIT 1;"
} > "$DEST/manifest.txt"

# 5. шифрование и отправка за пределы хоста
tar czf - "$DEST" | gpg --encrypt --recipient backup@example.com > "$DEST.tar.gz.gpg"
# ...дальше: rclone/rsync/mc на внешнее хранилище
rm -rf "$DEST"
```

Проверки, без которых бэкап не считается снятым:

- [ ] Файл существует и его размер правдоподобен (сравните с прошлым разом — резкое падение размера
      это сигнал).
- [ ] `pg_restore --list db.dump | head` выдаёт содержимое, а не ошибку.
- [ ] `rowcounts.csv` не пустой и цифры сопоставимы с предыдущим бэкапом.
- [ ] Зашифрованный архив уехал с хоста и на хосте не остался в открытом виде.
- [ ] Скрипт отработал с кодом 0 — молчаливо упавший `pg_dump` внутри пайпа это классика, поэтому
      `set -euo pipefail` обязателен.

## 7. Процедура восстановления

### 7.1 Подготовка

1. Понять, **на какой момент** восстанавливаемся и почему. Если причина — компрометация, сначала
   прочитайте [`incident.md`](incident.md): восстановление до момента компрометации может вернуть и
   бэкдор.
2. Приложение остановлено: `docker compose stop api worker`. Восстанавливать под работающим
   приложением нельзя.
3. Под рукой: дамп, `rowcounts.csv`, `manifest.txt`, `APP_ENCRYPTION_KEY`, `JWT_SECRET`, зеркало
   MinIO.
4. Проверить по `manifest.txt`, **какой версии приложения соответствует бэкап**. Поднимать нужно ту
   же версию — схема в дампе соответствует ей. Обновление делается уже после успешного
   восстановления, по [`upgrade.md`](upgrade.md).

### 7.2 Восстановление базы

```bash
# 1. расшифровать архив
gpg --decrypt backup-2026-07-26.tar.gz.gpg | tar xzf -

# 2. если восстанавливаемся поверх существующей базы — снести её ОСОЗНАННО.
#    На новом хосте этого шага нет: базы ещё нет и создаст её следующий шаг.
#    `-d postgres` обязателен: без него psql подключается к базе, одноимённой пользователю, и
#    команда падает с `cannot drop the currently open database`. `-v ON_ERROR_STOP=1` — чтобы
#    падение остановило процедуру, а не уехало в лог, оставив следующий шаг работать с непустой
#    базой: тогда `pg_restore` обрывается на `relation "…" already exists`.
#    Каждая команда отдельным `-c`: psql оборачивает несколько команд в одну транзакцию,
#    а DROP DATABASE внутри транзакции невозможен.
docker compose exec -T postgres \
  psql -U "${POSTGRES_USER:-bad_crm}" -d postgres -v ON_ERROR_STOP=1 -c "DROP DATABASE IF EXISTS bad_crm WITH (FORCE);"

# 3. РОЛИ И БАЗА. Идёт первым и создаёт всё, чего нет: четыре роли, саму базу
#    (`CREATE DATABASE … OWNER app_migrator`), владельца схемы `public`, CONNECT и USAGE.
#    Именно поэтому шага «CREATE DATABASE вручную» здесь нет: на новом хосте он падал бы
#    с `role "app_migrator" does not exist` — роли к этому моменту ещё не создан.
pnpm db:bootstrap   # роли app_migrator / app_user / app_auth / backup_role + база, идемпотентно

# 4. СУПЕРПОЛЬЗОВАТЕЛЕМ создать расширения.
#    Дамп содержит `CREATE EXTENSION IF NOT EXISTS vector`, а pgvector не является
#    trusted-расширением — создать его может только суперпользователь. Без этого шага
#    `pg_restore --exit-on-error` под app_migrator оборвётся на
#    `permission denied to create extension "vector"`. После него команда из дампа
#    становится no-op: PostgreSQL проверяет существование раньше привилегий.
docker compose exec -T postgres \
  psql -U "${POSTGRES_USER:-bad_crm}" -d bad_crm -v ON_ERROR_STOP=1 -f /opt/bad-crm/sql/initdb/01-extensions.sql

# 5. ВЫРЕЗАТЬ ИЗ ОГЛАВЛЕНИЯ ДАМПА КОММЕНТАРИИ К РАСШИРЕНИЯМ.
#    pg_dump кладёт в дамп не только `CREATE EXTENSION`, но и `COMMENT ON EXTENSION` — по одной
#    записи на каждое из пяти. `COMMENT ON EXTENSION` требует ВЛАДЕНИЯ расширением, владелец —
#    суперпользователь, а `ALTER EXTENSION … OWNER TO` в PostgreSQL не существует. Под
#    app_migrator восстановление обрывается на первой же такой записи (по алфавиту —
#    `btree_gist`), не восстановив ни одной таблицы:
#      pg_restore: error: could not execute query: ERROR:  must be owner of extension btree_gist
#    Отсюда фильтрация оглавления: пять записей выбрасываются, всё остальное восстанавливается.
#    Терять нечего — эти комментарии уже созданы в базе шагом 4 самим `CREATE EXTENSION`.
#    `--no-comments` не годится: он снёс бы и комментарии к таблицам и колонкам, которых нет
#    больше нигде, кроме дампа.
docker compose cp backups/<дата>/db.dump postgres:/tmp/db.dump
docker compose exec -T postgres sh -c \
  "pg_restore -l /tmp/db.dump | grep -v 'COMMENT - EXTENSION' > /tmp/db.toc"

# 6. восстановить ПОД ВЛАДЕЛЬЦЕМ СХЕМЫ — он создаёт объекты и не подчиняется политикам,
#    пока FORCE ещё не восстановлен вместе со схемой
docker compose exec -T postgres \
  pg_restore -U app_migrator -d bad_crm --no-owner --no-privileges --exit-on-error \
  -L /tmp/db.toc /tmp/db.dump

# 7. ВЕРНУТЬ ГРАНТЫ. `--no-privileges` на обеих сторонах цикла означает, что ни один GRANT
#    не пережил дамп: после восстановления app_user не видит ни одной таблицы, а backup_role
#    не может снять следующий бэкап. Их возвращает идемпотентный `01-grants.sql`, который
#    обходит каталог и раздаёт права по правилам, а не по списку таблиц.
pnpm db:grants

# 8. ANALYZE. pg_restore не собирает статистику: `pg_statistic` после восстановления пуст,
#    планировщик строит планы вслепую, а партиционированную родительскую таблицу автовакуум
#    не анализирует вообще никогда — без явного ANALYZE у неё так и останется `reltuples = -1`.
#    Через vacuumdb со `--schema=public`, а не голым `ANALYZE;`: последний под app_migrator
#    пытается зайти и в общие каталоги (`pg_authid`, `pg_database`, …) и печатает десяток
#    `WARNING: permission denied to analyze`, за которыми не видно настоящих проблем.
docker compose exec -T postgres \
  vacuumdb --analyze-only --schema=public -U app_migrator -d bad_crm

# 9. убрать дамп из контейнера — он не должен там жить
docker compose exec -T postgres rm -f /tmp/db.dump /tmp/db.toc
```

Почему `--exit-on-error`: без него `pg_restore` продолжает после ошибок и оставляет базу частично
восстановленной, отрапортовав об успехе.

**Почему не `pnpm db:migrate` для возврата грантов.** Это выглядит естественно и не работает по
трём независимым причинам. `prisma migrate deploy` применяет только **pending**-миграции, а
`_prisma_migrations` приезжает из дампа, где все миграции уже помечены применёнными, — команда
печатает «No pending migrations to apply» и выходит с нулём, не выполнив ни одного `GRANT`. В dev
`pnpm db:migrate` — это `prisma migrate dev`, который при расхождении схемы предлагает **reset базы**;
в раннбуке аварийного восстановления это прямой путь к потере только что восстановленных данных. И
сами миграции не идемпотентны: обычный `CREATE TABLE` без `IF NOT EXISTS` упадёт, если бы они всё же
запустились.

**Почему снимает дамп `backup_role`, а восстанавливает `app_migrator` — разные роли.**
Восстановление создаёт таблицы, индексы и политики, то есть выполняет DDL; `backup_role` создана
read-only и права на запись не имеет **специально** — роль, которой достаточно прав, чтобы
перезаписать базу, не должна лежать в кроне бэкапа. Владелец схемы (`app_migrator`) при
`FORCE ROW LEVEL SECURITY` тоже подчиняется политикам, но на момент `pg_restore` политик ещё нет:
они приезжают из дампа вместе с таблицами и начинают действовать после восстановления. Если
восстанавливаете в базу, где схема уже есть, включите режим обслуживания
(`SET app.maintenance = 'on'`, политика `maintenance_access` в
[`../security/rls-design.md`](../security/rls-design.md)) или восстанавливайте суперпользователем.

### 7.4 Проверка — обязательная часть, а не «если будет время»

```bash
# 1. сверка числа строк
docker compose exec -T postgres psql -U backup_role -d bad_crm -At -F',' \
  -c "SELECT relname, n_live_tup FROM pg_stat_user_tables ORDER BY n_live_tup DESC LIMIT 25;" \
  > /tmp/rowcounts-after.csv
diff <(sort backups/<дата>/rowcounts.csv) <(sort /tmp/rowcounts-after.csv)
```

- [ ] **Числа строк совпадают** с `rowcounts.csv`. Любое расхождение по мультиарендной таблице —
      стоп: скорее всего, дамп снимался под неправильной ролью (раздел 2). Сверка имеет смысл
      только **после** `ANALYZE` (шаг 8): `n_live_tup` — счётчик, который восстановление наполняет
      по ходу вставки, а планировочную статистику не собирает вовсе. У партиционированной
      родительской таблицы (`audit_logs`) значение равно нулю с обеих сторон — строки лежат в
      партициях, и это не расхождение.
- [ ] **Гранты вернулись** — иначе восстановлена база, к которой нет доступа: приложение не видит
      ни одной таблицы, а следующий бэкап падает на первой же из них.
      ```sql
      SELECT c.relname,
             has_table_privilege('app_user',    c.oid, 'SELECT') AS app_user,
             has_table_privilege('backup_role', c.oid, 'SELECT') AS backup_role
      FROM   pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
      WHERE  n.nspname = 'public' AND c.relkind IN ('r','p')
      ORDER  BY 1;
      -- backup_role = true везде, включая партиции; app_user = true на доменных таблицах
      -- и false на партициях (к ним приложение не обращается).
      ```
- [ ] RLS включён и форсирован на всех таблицах:
      ```sql
      SELECT relname FROM pg_class
      WHERE relkind = 'r' AND relnamespace = 'public'::regnamespace
        AND (relrowsecurity IS FALSE OR relforcerowsecurity IS FALSE);
      ```
      Пусто (кроме задокументированных исключений). Восстановление под `--no-owner` не должно терять
      политики, но проверить обязательно.
- [ ] Роль приложения по-прежнему **без** `BYPASSRLS` и не владеет таблицами.
- [ ] Приложение поднимается: `docker compose up -d`, `/healthz` и `/readyz` отвечают.
- [ ] Вход работает, данные на месте, файлы открываются (проверяет весь путь база → presigned URL →
      MinIO).
- [ ] **Кросс-тенантная проверка:** войти пользователем организации A и убедиться, что данных
      организации B не видно. Восстановление — момент, когда ломается изоляция, если что-то пошло не
      так с политиками.
- [ ] Секреты интеграций расшифровываются: открыть настройки AI-провайдера и убедиться, что
      отображается хвост ключа (`sk-…a91f`), а не ошибка. Если ошибка — не тот `APP_ENCRYPTION_KEY`.
- [ ] Пользователь может разблокировать vault своим мастер-паролем.
- [ ] **Переиндексация поиска** запущена — индекс не восстанавливался и сейчас пуст или устарел.

### 7.5 После восстановления

- Снять **новый бэкап** восстановленной системы: она стала текущей точкой отсчёта.
- Записать в операционный журнал: на какой момент восстановились, что потеряли, сколько заняло.
  Сравнить с заявленными RPO/RTO — обычно после первого реального восстановления цифры
  пересматриваются.
- Сообщить пользователям, какой период работы потерян. Люди должны знать, что нужно переделать.
- Если восстановление было вызвано инцидентом — [`incident.md`](incident.md), раздел про сбор
  доказательств и ротацию.

## 8. Регулярная проверка бэкапов

Раз в квартал, на отдельном хосте или в отдельном compose-проекте:

1. Взять последний боевой бэкап.
2. Восстановить по разделу 7 целиком, включая файлы.
3. Пройти чек-лист 7.4 полностью.
4. Замерить фактическое время — это ваш реальный RTO, а не тот, что записан в плане.
5. Записать результат. Если проверка провалилась, чинить процедуру бэкапа нужно сейчас, а не в день
   аварии.
6. Тестовое окружение удалить, чтобы копия боевых данных не жила вечно на чьём-то ноутбуке.
