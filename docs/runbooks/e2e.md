# Runbook: запуск и отладка e2e

Как прогнать сценарии Playwright локально, что делать, когда они падают, и почему харнесс устроен
именно так. Конфигурация — [`packages/e2e/playwright.config.ts`](../../packages/e2e/playwright.config.ts),
контракт на неё зафиксирован тестом `test/e2e/playwright-config.test.ts`.

## Что нужно до первого запуска

E2E — единственный уровень тестов, которому нужен **поднятый стек целиком**: БД, Redis, сервер и
клиент. Ничего из этого харнесс не поднимает сам и не подменяет: он подключается к тому, что уже
работает, и знает о приложении ровно то, что видно снаружи по HTTP и в браузере.

```bash
pnpm docker:up
```

```bash
pnpm dev
```

**`pnpm dev` годится, чтобы посмотреть на приложение руками, но не для прогона набора** — почему
именно, и чем его заменить, написано ниже в разделе «Прогон против собранного клиента». Этот же
раздел объясняет, почему `APP_URL` придётся поправить: шаблон `.env.example` отдаёт
`APP_URL=http://localhost:3000`, а браузер в прогоне живёт на 5173.

Браузеры Playwright ставятся **отдельной командой**: `pnpm install` их не тянет, потому что
`onlyBuiltDependencies` в корневом `package.json` разрешает postinstall-скрипты только `esbuild` —
пакет не качает 300 МБ в чужой контейнер без спроса.

```bash
pnpm --filter @bad-crm/e2e exec playwright install chromium
```

Данные — отдельной командой. Сценарии не создают себе организации сами: регистрация закрыта на
инсталляции с уже созданной организацией, и сценарий, который зависел бы от порядка запуска, ловил
бы это как «форма входа не работает».

```bash
pnpm db:seed:permissions
pnpm db:seed
```

Каталог прав — первым: роль выдаёт права **по имени**, и сид организации до появления каталога
нарушает внешний ключ. На инсталляции порядок тот же — шаг 7c процедуры обновления выполняется до
того, как кто-либо что-либо создаёт.

## Что создаёт сид

Идемпотентно: повторный запуск ничего не дублирует и ничего не перезаписывает. Источник правды —
[`packages/server/scripts/seed-data.constant.ts`](../../packages/server/scripts/seed-data.constant.ts),
копия для сценариев — `packages/e2e/fixtures/seed-data.ts`; расхождение между ними валит
`test/e2e/seed-fixture-parity.test.ts`.

| Организация | slug | Владелец | Язык | Валюта | Таймзона |
|---|---|---|---|---|---|
| Seed Organization A | `seed-org-a` | `owner@org-a.local` | en | EUR | Europe/Berlin |
| Seed Organization B | `seed-org-b` | `owner@org-b.local` | ru | USD | UTC |

Пароль обоих — `seed-only-not-a-real-password`, он же в константе. Две организации различаются
**всем**, чем могут: сценарий изоляции сравнивает A и B, и фикстура, где они совпадают хотя бы
в одном поле, не докажет ничего. Разные язык и валюта заодно делают дефект форматирования видимым
в самой фикстуре.

**Ролей в сиде нет, и это состояние продукта, а не упущение.** Роли приходят с EPIC-011; сегодня у
`users` нет колонки роли, и единственная различимая учётная запись — владелец организации.
`admin@`/`lead@`/`dev@` с правами, равными владельцу, но названные иначе, — фикстура, которая врёт;
они появятся вместе с ролями (STORY-010-03).

**Сид отказывается работать не в `development`/`test`.** Он создаёт учётные записи с паролем,
опубликованным в этом репозитории; на инсталляции, обслуживающей живую команду, это чёрный ход,
выглядящий как обычный аккаунт. Проверяется `NODE_ENV`; осознанный обход — `SEED_ALLOW_PRODUCTION=true`.

Сброс к чистому состоянию (drop → migrate → seed):

```bash
pnpm db:reset
```

## Запуск

```bash
pnpm test:e2e
```

| Команда | Когда |
|---|---|
| `pnpm test:e2e` | обычный прогон, репортер `list` + HTML-отчёт |
| `pnpm --filter @bad-crm/e2e run test:e2e:ui` | режим UI: дерево сценариев, time-travel по шагам, повтор одного теста |
| `pnpm --filter @bad-crm/e2e run test:e2e:debug` | пошаговая отладка с инспектором и подсветкой локаторов |

### Прогон против собранного клиента

Подготовка стека и данных — как выше по этой странице (`pnpm docker:up`, миграции, `pnpm
db:seed:permissions`, `pnpm db:seed`). Отличается последний шаг: клиент для прогона **собирается**,
а не запускается dev-сервером.

```bash
pnpm --filter @bad-crm/client build
```

Затем два процесса, каждый в своём терминале:

```bash
pnpm --filter @bad-crm/server dev
pnpm --filter @bad-crm/client exec vite preview --port 5173 --strictPort
```

И только после этого — `pnpm test:e2e`.

**Почему собранный клиент, а не `pnpm dev`.** Dev-сервер Vite компилирует чанк маршрута при первом
заходе на него, и на холодном чанке это занимает больше, чем ждёт веб-ассерт
(`E2E_EXPECT_TIMEOUT_MS`, пять секунд). Получается ложное падение с пустым `main` — сценарий,
который «сломан», хотя сломан стенд. Измерено 2026-08-28: `auth/enable-2fa` падал на холодном чанке
и проходил на прогретом, то есть **зависел от порядка запуска**. В CI этого не бывает вовсе, потому
что там `vite preview` отдаёт уже собранный бандл; ложное падение существует только локально и
только у того, кто прогоняет набор поверх `pnpm dev`.

**Почему именно 5173 и почему `APP_URL` придётся поправить.** Шаблон `.env.example` отдаёт
`APP_URL=http://localhost:3000` — адрес самого API, потому что на инсталляции собранный клиент
раздаёт контейнер сервера. Локально браузер живёт отдельно, на 5173, и `POST /auth/refresh` отвергнет
его Origin. Перед прогоном в `.env` должно стоять `APP_URL=http://localhost:5173` — либо этот origin
должен быть в `CORS_EXTRA_ORIGINS`; сервер после правки перезапускается. Джоба `end-to-end` делает
ровно то же самое одной строкой `sed` сразу после копирования шаблона, с тем же обоснованием в
комментарии — сверять локальный стенд стоит с ней, а не с памятью.

**Сбрасывать Redis между прогонами.**

```bash
docker compose exec -T redis redis-cli FLUSHALL
```

Счётчики ограничителя частоты живут в Redis и переживают перезапуск процессов
(`infrastructure/rate-limit/rate-limit-policy.constant.ts`): `auth_attempt` — пять попыток на пару
«адрес + email» за 15 минут, с удвоением блокировки до часа. Успешный вход свой счётчик сбрасывает,
а вот неудачные попытки, которые сценарии делают **намеренно** (`wrong-password-entirely` в
`smoke/sign-in`, код `000000` в `login-with-2fa`), накапливаются между прогонами.
Второй-третий прогон подряд упирается в `429` на **подготовке данных**, и падение выглядит как
дефект приложения. Это третий ложный диагноз подряд у того, кто про счётчики не знает.

Перед первым сценарием выполняется [`global-setup.ts`](../../packages/e2e/global-setup.ts): он
опрашивает `/ready` до готовности стека. Это не украшение — без него неподнятая БД превращается в
стену падений, у каждого из которых первая строка «не видно форму входа», то есть ложь о причине.
С ним получается одно сообщение с адресом эндпоинта, который не ответил, и подсказкой, что запустить.

## Сценарии

**Числа сценариев здесь нет намеренно** — один спек-файл содержит несколько тестов, и любое
записанное число расходится с деревом на следующем коммите. Актуальный список печатает сам
Playwright, и он же показывает, что попадёт в CI (файл, лежащий в рабочем дереве, но не в индексе,
в прогоне на `main` не участвует):

```bash
pnpm --filter @bad-crm/e2e exec playwright test --list
```

| Файл | Что доказывает |
|---|---|
| `tests/smoke/sign-in.spec.ts` | вход посеянного владельца доходит до оболочки; неверный пароль не выдаёт, существует ли адрес; **контроль** — без входа оболочки нет |
| `tests/smoke/sign-out.spec.ts` | выход завершает сессию, и «назад» не возвращает оболочку — ни из истории, ни прямым переходом |
| `tests/smoke/accessibility.spec.ts` | axe на экране входа и на оболочке: ноль нарушений A и AA (best-practice-правила намеренно не включены — на советах набор глушат) |
| `tests/smoke/locale-switch.spec.ts` | переключатель языка меняет форму в обе стороны; подписи сверяются с каталогом продукта гейтом `test/e2e/locale-labels-parity.test.ts` |
| `tests/auth/storage-state.spec.ts` | сессия, отчеканенная для теста, открывает защищённый маршрут; анонимный контекст уходит на `/login` |
| `tests/auth/enable-2fa.spec.ts` | включение TOTP из `/settings/security` до десяти кодов восстановления, которые экран отказывается показать второй раз |
| `tests/auth/login-with-2fa.spec.ts` | пароль перестал быть входом: весь цикл «включил → вышел отовсюду → вошёл паролем → предъявил живой код → попал в оболочку» |
| `tests/rbac/admin-user-overrides.spec.ts` | персональное исключение права, снятое на экране владельцем, меняет **ответ на следующий запрос коллеги**, а не только строку в таблице |
| `tests/tenancy/cross-tenant-api.spec.ts` | ресурс чужой организации отвечает 404, а не 403; **контроль** — свой ресурс отвечает успехом |

Два самых новых спека, `auth/enable-2fa` и `rbac/admin-user-overrides`, до 2026-08-28 не выполнялись
против живого приложения ни разу. Прогон нашёл в них то, чего не видит ни один статический гейт:
сценарий отзыва и возврата права занимает ~42 с при бюджете теста 30 с
(`E2E_TEST_TIMEOUT_MS`), то есть **не мог пройти с первого дня**. Отсюда правило: спек, который не
запускали против поднятого стека, — это заявка, а не тест.

**Сессия чеканится на каждый тест, а не сохраняется в файл.** Это вынуждает продукт, а не вкус:
клиент обменивает refresh-cookie при загрузке, а ротация с обнаружением повторного использования
делает сохранённую cookie **одноразовой** — второй контекст, предъявивший её (повтор, параллельный
воркер), неотличим от украденного токена, и семейство отзывается. Измерено в CI: первая попытка
дошла до оболочки, повтор ушёл на `/login`. Фикстура `fixtures/session.fixture.ts` логинится по API
на каждый тест; форму по-прежнему кликает ровно один сценарий — тот, который её проверяет.

**Origin имеет значение.** `POST /auth/refresh` — единственный эндпоинт, который авторизует одна лишь
cookie, поэтому он защищён проверкой Origin (`presentation/http/middleware/same-origin.middleware.ts`
против списка `APP_URL` + `CORS_EXTRA_ORIGINS`). Клиент обязан быть отдан с того же origin, что в
`APP_URL` инсталляции; `strictPort` в `vite.config.ts` удерживает 5173 и у dev-сервера, и у
`preview`. Запуск на другом порту даёт валидную сессию, которую приложение отказывается возобновить,
— симптом выглядит как «гард сломан».

**Проверку выполняет фикстура, на каждый тест, а не подготовка прогона.**
[`fixtures/session.fixture.ts`](../../packages/e2e/fixtures/session.fixture.ts) после входа по API
делает тот же `POST /auth/refresh`, что делает браузер при загрузке, и падает с формулировкой
«The session is valid; what the installation rejects is where the browser is served from».
В [`global-setup.ts`](../../packages/e2e/global-setup.ts) этого нет — он опрашивает только
`${E2E_API_URL}/ready`. Следствие: сценарии, которым сессия не нужна, при неверном origin
выполняются как обычно, а падают ровно те, что входят.

## Переменные окружения

Все со значениями по умолчанию под локальный quickstart — обычный запуск не требует ни одной.

| Переменная | По умолчанию | Зачем менять |
|---|---|---|
| `E2E_BASE_URL` | `http://localhost:5173` | прогон против preview-сборки или стенда |
| `E2E_API_URL` | `http://localhost:3000` | там же живёт `/ready`; клиент проксирует только `/api`, поэтому адрес отдельный |
| `E2E_BROWSERS` | chromium | `all` — добавляет firefox и webkit (ночной прогон) |
| `E2E_READY_TIMEOUT_MS` | `60000` | холодный старт с миграциями на слабой машине |
| `E2E_TEST_TIMEOUT_MS` | `30000` | бюджет одного сценария |
| `E2E_EXPECT_TIMEOUT_MS` | `5000` | бюджет одного веб-ассерта |
| `CI` | не задана | включает `retries: 1`, запрет `it.only` и репортер GitHub |

## Когда падает

1. **Смотреть HTML-отчёт**, а не только вывод: `pnpm --filter @bad-crm/e2e exec playwright show-report`.
2. **Trace** сохраняется при повторной попытке (`on-first-retry`), скриншот и видео — только у
   упавшего теста. Trace открывается тем же `show-report` или на <https://trace.playwright.dev> —
   это запись шагов с DOM-снимками, сетью и консолью; по ней видно состояние страницы в момент
   падения, а не после него.
3. **Локально повторов нет намеренно.** Тест, который падает раз и проходит со второго, — это
   определение flaky; спрятать это локально значит отдать находку следующему человеку в CI на
   постороннем изменении.
4. **Падает всё сразу** — почти всегда стек, а не сценарии: `curl localhost:3000/ready` и логи
   `pnpm docker:logs`.

## В CI

Джоба `end-to-end` собирает установку целиком: поднимает backing services профилем `minimal`,
создаёт роли, применяет миграции и гранты, сеет две организации, ставит браузер, собирает клиент и
сервер, запускает их и прогоняет сценарии. Это единственное место, где origin клиента совпадает с
`APP_URL` **по построению**, поэтому сценарии с сохранённой сессией там осмысленны.

Артефакты асимметричны намеренно: HTML-отчёт выгружается **всегда**, а trace, скриншоты, видео и
логи контейнеров — **только при падении**, и всё со сроком хранения. Trace успешного прогона — это
десятки мегабайт, которые никто не откроет.

Перед выгрузкой запускается `scripts/ci/scrub-e2e-artifacts.ts`:

- файлы сохранённых сессий и `.env` — **удаляются**;
- trace, в котором встретилась сессионная cookie, — **называется, но не переписывается**: trace,
  отредактированный скриптом, это trace, которому нельзя верить. Публиковать такой bundle разрешено
  только флагом `--ephemeral`, и он означает ровно одно утверждение: инсталляция создана и
  уничтожена внутри этого прогона. Против stage-стенда флага нет, и bundle не публикуется.

Открыть trace локально:

```bash
pnpm --filter @bad-crm/e2e exec playwright show-trace <файл-из-артефактов>
```

## Чего в этом харнессе нет и не будет

- **Фиксированных ожиданий.** `waitForTimeout` запрещён линтом (`no-restricted-syntax` в
  `eslint.config.js`) и проверяется тестом: слишком мало — падение на загруженном раннере, слишком
  много — каждый прогон платит за худший случай. Ждать нужно состояние: `expect(locator).toBeVisible()`,
  `page.waitForURL(...)`, `waitForResponse(...)`.
- **Импортов из `server` и `client`.** Пакет `e2e` — чёрный ящик: тест, знающий внутренности, может
  пройти против кода, который не задеплоен. Данные готовятся через публичный API и seed-скрипт.
  Запрет держит ESLint, и он же проверен на файлах в корне пакета, а не только под `src`/`tests`.

## Чего в харнессе ещё нет

Раздел «что появится в следующих историях» держался здесь после того, как перечисленное в нём
отгрузили: сид двух организаций
([STORY-010-02](../../epics/epic-010-e2e-harness/stories/story-010-02-seed-script-and-fixtures.md)),
smoke и axe ([STORY-010-04](../../epics/epic-010-e2e-harness/stories/story-010-04-smoke-register-login-logout.md)),
изоляция арендаторов ([STORY-010-05](../../epics/epic-010-e2e-harness/stories/story-010-05-tenant-isolation-e2e.md)),
артефакты и джоба в CI ([STORY-010-06](../../epics/epic-010-e2e-harness/stories/story-010-06-ci-artifacts-on-failure.md))
— всё это описано выше как работающее. Открытым осталось одно:

- **Ролевые фикстуры** — [STORY-010-03](../../epics/epic-010-e2e-harness/stories/story-010-03-storage-state-auth-fixtures.md),
  единственная история эпика в `in-progress`. Отгружена чеканка сессии на каждый тест
  (`fixtures/session.fixture.ts`), и она же **заменила** заявленный историей общий `storageState` —
  причина в комментарии фикстуры: ротация refresh-токена с обнаружением повторного использования
  делает сохранённую cookie одноразовой. Не отгружены типизированные фикстуры под роли
  (`asAdminOfOrgA`, `asDeveloperOfOrgA` и т. п.): сценариям, которым нужна роль, сегодня приходится
  приглашать и принимать коллегу через публичный API самим — так делают `rbac/admin-user-overrides`,
  `auth/enable-2fa` и `auth/login-with-2fa`. Роли в продукте уже есть (EPIC-011), так что препятствие
  снято и остался сам код фикстур.

Отдельно, вне EPIC-010: у джобы `end-to-end` не закрыт критерий приёмки
[STORY-002-03](../../epics/epic-002-ci-and-commit-gate/stories/story-002-03-e2e-job-with-services.md)
о прогоне без исходящего интернета (NFR-9), нет кеша браузеров Playwright, и там же записано
расхождение бюджетов ожидания между критерием и кодом.
