# Runbook — сервер и инфраструктура для self-host

> **Статус: расчётная оценка, а не результат замеров.** Продукт в фазе M1: приложения ещё нет,
> нагрузочных прогонов не было. Все числа ниже получены из модели данных
> ([`../architecture/data-model.md`](../architecture/data-model.md)), состава сервисов
> ([`../architecture/stack.md`](../architecture/stack.md)) и известного поведения PostgreSQL,
> pgvector, Meilisearch и Node. Каждая цифра сопровождается расчётом — чтобы её можно было
> пересчитать под свои данные, а не принимать на веру. После первых нагрузочных замеров
> (NFR-2, сценарий на сид-данных) цифры уточняются, и этот документ правится.

Связанные документы: [`install.md`](install.md) (установка и чек-лист безопасности) ·
[`backup-restore.md`](backup-restore.md) (процедура бэкапа) · [`upgrade.md`](upgrade.md) ·
[`incident.md`](incident.md) · [`../architecture/overview.md`](../architecture/overview.md)
(раздел «Развёртывание») · [`../security/threat-model.md`](../security/threat-model.md)
(раздел про self-host, `T-SH-*`).

**Область документа:** сколько железа нужно, какого, где его взять и как настроить PostgreSQL и
reverse-proxy под эту конкретную нагрузку. Как ставить — в [`install.md`](install.md); что
бэкапить — в [`backup-restore.md`](backup-restore.md). Дублировать их этот документ не должен.

**Позиция по объёму конфигурации.** Ниже описан **полный** продукт: PostgreSQL с pgvector,
Redis, MinIO, Meilisearch, API с Socket.IO, отдельный worker, AI-ассистент с RAG, файлы и
бэкапы. Не «минимальный вариант, где половина выключена». При этом без запаса «на всякий
случай» и без облачных сервисов, которых архитектура не требует.

## 1. Что вообще крутится

Восемь компонентов. Профиль потребления — не «сколько выделено», а **какой ресурс каждый из них
реально упирает**: перепутать это и есть главный способ купить не тот сервер.

| Компонент | Что делает | Профиль потребления (CPU / RAM / диск / IO) | Растёт от чего |
|---|---|---|---|
| **PostgreSQL 16 + pgvector** | Единственный источник истины: 40+ таблиц, RLS-изоляция арендаторов, JSONB, полнотекст, векторы, партиции `audit_logs` | **RAM и random IO — главный потребитель.** CPU умеренный (всплески на параллельных агрегатах и построении индексов). Диск — random-чтение 8 KB страниц индексов + последовательная запись WAL с `fsync` на каждый commit | Число строк (`audit_logs`, `messages`), число индексов, объём эмбеддингов, глубина ретеншна |
| **pgvector HNSW-индекс** | Семантический поиск для AI-ассистента (RAG) | **RAM под граф.** Один поиск обходит десятки узлов графа, каждый — случайное чтение страницы. В кеше — доли миллисекунды, с диска — десятки | Число чанков `Embedding`. Размерность зафиксирована: `vector(1536)` |
| **Redis 8** | Брокер BullMQ, backplane Socket.IO (Redis Streams), счётчики rate-limit, денилист сессий, presence, кеш AI-лимитов | **RAM небольшая и ограниченная сверху.** CPU почти нулевой. Диск — AOF `everysec`, последовательная запись | Глубина очередей, длина стримов Socket.IO, число активных сессий. Всё эфемерное — с TTL |
| **MinIO** | S3-совместимое хранилище: тела файлов и вложений, presigned PUT/GET мимо Node | **Диск — единственный значимый ресурс**, растёт быстрее всех. RAM — буферы, ~0.5–1 GB. Сеть — крупные последовательные потоки, которые **вымывают page cache PostgreSQL** | Число и размер загруженных файлов, глубина `FileVersion` |
| **Meilisearch** | Поиск с учётом прав по задачам, документам, KB, сообщениям | **RAM под индекс** (LMDB через mmap: чем больше кеша, тем быстрее) плюс **RAM под индексацию** — по умолчанию до 2/3 всей памяти хоста, это ловушка на общем хосте. CPU — многопоточные всплески при переиндексации | Объём индексируемого текста. Индекс производный — не бэкапится, пересобирается из БД |
| **API-процесс (Express 5 + Socket.IO)** | HTTP `/api/v1`, WebSocket, presigned-URL, SSE-стрим AI, раздача статики SPA | **CPU на пиках, одно ядро на процесс** (Node однопоточен). RAM ~0.4–0.6 GB. Всплеск CPU — argon2id при логине (19 MiB, `timeCost 2`). Диска не касается: тела файлов идут мимо него | Число одновременных запросов и WebSocket-соединений |
| **worker (BullMQ)** | outbox-диспетчер, индексация в Meilisearch, эмбеддинги (батчи по 32), rollup'ы, почта, GitHub-sync | **CPU на пиках + сетевое ожидание** внешних API. RAM ~0.4–0.5 GB, всплески на батчах эмбеддингов | Поток доменных событий; полная переиндексация — разовый тяжёлый всплеск |
| **Статика клиента** | React-бандл, отдаётся тем же API-процессом или прокси | Пренебрежимо. Бюджет маршрута < 300 KB gzip; крипто-чанк vault ~375 KB грузится лениво | — |
| **Reverse-proxy (Caddy)** | TLS, HTTP→HTTPS, WebSocket-upgrade, SSE, sticky sessions, access-лог | ~50–100 MB RAM, CPU только на TLS-рукопожатиях | Число соединений |

**Что из этой таблицы следует практически:**

1. **Деньги идут в RAM и в NVMe, а не в ядра.** Node-процессов два, каждый занимает одно ядро;
   PostgreSQL распараллеливается умеренно. Восьми физических ядер хватает с запасом любому
   размеру из раздела 2 — а вот памяти не хватает быстро.
2. **Три компонента конкурируют за одну и ту же память**: `shared_buffers` PostgreSQL, page cache
   для его же индексов и HNSW, и Meilisearch. Ни один из них не умеет «подвинуться» — они просто
   вытесняют друг друга, и первым это чувствует p95 списочных запросов.
3. **MinIO на одном диске с PostgreSQL — источник неочевидной деградации.** Загрузка файла на
   200 MB — это 200 MB последовательного чтения/записи, которое выкидывает из page cache горячие
   индексы БД. Работает, но p95 «плавает» без видимой причины.

## 2. Три размера с конкретными числами

Три профиля соответствуют допущению PRD: типовая инсталляция — до 50 сотрудников
([`../product/prd.md`](../product/prd.md), «Допущения», п. 1).

### 2.1 Модель роста данных

Расчёт делается из **дневной активности человека**, а не из «ощущения объёма». Допущения —
консервативные для команды разработки; их и надо перепроверять после первого месяца
эксплуатации.

| Что | На человека в рабочий день | Обоснование |
|---|---|---|
| Сообщений чата | 40 | Slack-подобная интенсивность технической команды |
| Изменяющих действий в `AuditLog` | 150 | Каждое создание/изменение сущности, вход, изменение прав; аудит по определению плотнее продуктовых таблиц |
| Задач создано | 0.8 | ~200 задач на человека в год |
| Комментариев | 3 | |
| Записей времени | 4 | Таймер + ручные записи |
| Файлов загружено | 0.8, средний размер 1.5 MB | Скриншоты, PDF, архивы; медиа-тяжёлые команды дают ×5–10 |
| Чанков эмбеддингов | 2 (≈ 500 в год) | Документы и KB по ~6 чанков, задачи по 1 |

Рабочих дней в году — **250**.

### 2.2 Сколько занимает одна строка

Это вторая половина расчёта, и её обычно пропускают. Размер — **heap плюс индексы**, потому что
на диске лежит и то, и другое.

| Данные | На единицу | Из чего складывается |
|---|---|---|
| `Message` | **1.5 KB** | `body` JSONB ~250 B + `plainText` ~150 B + ~15 колонок (uuid, timestamps, счётчики) ~200 B + заголовок кортежа 23 B ≈ 650 B heap; ×2.3 на индексы, включая GIN по `plain_text` для полнотекста |
| `AuditLog` | **1.7 KB** | `before` + `after` JSONB ~800 B + фиксированные поля (`actorId`, `action`, `resourceType`, `ipHash`, `userAgent`, `requestId`) ~250 B ≈ 1.3 KB heap; ×1.3 на два индекса на каждой партиции |
| `Embedding` — таблица | **9 KB** | `vector(1536)` = 1536 × 4 байта = **6144 B** + заголовок varlena; `chunkText` ~2.5 KB (500 токенов, кириллица в UTF-8 — до 2 байт на символ); фиксированные поля ~200 B |
| `Embedding` — HNSW | **+8 KB** | HNSW хранит **полную копию вектора в индексе** (6 KB) плюс списки соседей (`m = 16` → до 32 связей на нижнем уровне) ≈ 1.5–2 KB |
| `Task` / `Comment` / `DocPage` | **1.2 KB** | Текст + материализованная колонка `searchVector tsvector` + GIN по ней |
| `TimeEntry` | **0.4 KB** | Плоская строка, три индекса |
| Файл в MinIO | **размер × 1.3** | Множитель — история `FileVersion` |

> **Про эмбеддинги честно: 17 KB на чанк.** Это самая дорогая строка в базе — в десять раз
> дороже сообщения чата. Вектор нельзя сжать (это 1536 случайных float, `pg_dump -Fc` их тоже не
> ужмёт), и он лежит **дважды**: в таблице и внутри HNSW-графа. Формула на будущее — из
> документации pgvector: память на построение индекса ≈ `N × D × 4 × 2` байт, то есть для
> 1536 измерений — **12 KB на вектор**. Если `maintenance_work_mem` меньше этой величины,
> PostgreSQL пишет `hnsw graph no longer fits into maintenance_work_mem` и переключается на
> дисковую сборку, которая медленнее в 10–50 раз.

### 2.3 Объёмы за первый год

| | 10 человек | 25 человек | 50 человек |
|---|---|---|---|
| Сообщения | 100 тыс. × 1.5 KB = **150 MB** | 250 тыс. = **375 MB** | 500 тыс. = **750 MB** |
| Аудит | 375 тыс. × 1.7 KB = **640 MB** | 938 тыс. = **1.6 GB** | 1.9 млн = **3.2 GB** |
| Эмбеддинги (таблица + HNSW) | 5 тыс. × 17 KB = **85 MB** | 12.5 тыс. = **210 MB** | 25 тыс. = **425 MB** |
| Задачи, комментарии, документы, KB | **~70 MB** | **~170 MB** | **~330 MB** |
| Время, уведомления, rollup'ы, outbox | **~30 MB** | **~80 MB** | **~160 MB** |
| **Итого «чистых» данных** | **~1.0 GB** | **~2.4 GB** | **~4.9 GB** |
| + 30 % на bloat, FSM, visibility map, незачищенные мёртвые кортежи | 1.3 GB | 3.2 GB | 6.4 GB |
| + `pg_wal` (рабочий набор, `max_wal_size`) | 4 GB | 8 GB | 8 GB |
| **Каталог PostgreSQL через год** | **~5.5 GB** | **~11 GB** | **~15 GB** |
| Объекты в MinIO за год | 2 тыс. файлов × 1.5 MB × 1.3 = **4 GB** | **10 GB** | **20 GB** |
| Индекс Meilisearch | **~0.3 GB** | **~0.6 GB** | **~1.1 GB** |

Три вывода, которые здесь важнее самих чисел:

1. **База маленькая, файлы большие.** Через три года у команды в 50 человек будет ~25 GB
   PostgreSQL и ~60 GB файлов. Диск покупается под MinIO, а не под БД.
2. **На этих объёмах `pg_wal` — крупнейшая статья каталога БД.** Это не факт о данных, а
   следствие настройки `max_wal_size`; уменьшать её ради места нельзя (участятся чекпоинты).
3. **Аудит растёт быстрее всего** и партиционирован по месяцам именно поэтому. Ретеншн через
   `DETACH`/`DROP PARTITION` — это операция за миллисекунды; `DELETE` по 2 млн строк — это часы
   и раздувание таблицы.

> **Верхняя граница для сравнения.** Нагрузочный датасет из
> [`../architecture/data-model.md`](../architecture/data-model.md) («Как проверять миграцию на
> объёме») — 5 млн сообщений и 20 млн строк аудита — это ~40 GB только аудита. Он моделирует
> **не** типовую инсталляцию на 50 человек, а стресс-профиль в 10 раз плотнее. Не путать эти
> два числа при планировании диска.

### 2.4 Итоговые конфигурации

| | **10 человек** | **25 человек** | **50 человек** |
|---|---|---|---|
| **vCPU** | 4 выделенных ядра | 4–6 выделенных | 8 физических ядер |
| **RAM** | 8 GB минимум, **16 GB рекомендуется** | **16 GB** | **32 GB** |
| Диск: система, образы, логи | 30 GB | 40 GB | 40 GB |
| Диск: данные PostgreSQL | 50 GB | 100 GB | 200 GB |
| Диск: объекты MinIO | 50 GB | 150 GB | 300 GB |
| Диск: индекс Meilisearch | 10 GB | 20 GB | 20 GB |
| Диск: Redis (AOF) | 2 GB | 2 GB | 2 GB |
| **Диск всего** | **~150 GB** | **~320 GB** | **~560 GB** |
| **Тип диска** | **локальный NVMe, RAID1** | то же | то же |
| **Сеть** | 1 Gbit/s, ≥ 1 TB трафика | то же | то же |

**Почему диск под PostgreSQL втрое больше данных.** Не «на вырост», а по процедуре: апгрейдер
снимает `pg_dump` **перед** каждой миграцией и кладёт его локально
([`../architecture/data-model.md`](../architecture/data-model.md), «Backup-first для self-host»),
а квартальная проверка бэкапа разворачивает вторую копию базы рядом
([`backup-restore.md`](backup-restore.md), раздел 8). Итого в пиковый момент на диске лежат: сама
база, её дамп и восстановленная копия.

**Почему у «10 человек» рекомендуется 16 GB, хотя расчёт даёт 8.** На 8 GB продукт работает, но
без запаса: нет памяти ни на восстановление из бэкапа рядом с работающей базой, ни на полную
переиндексацию Meilisearch, ни на первичное построение HNSW. Практически это значит, что любая
операция обслуживания требует остановки сервиса. Разница в деньгах при аренде выделенного
сервера — ноль (см. раздел 4), поэтому экономить тут не на чем.

### 2.5 Почему NVMe обязателен

Не «желателен» — обязателен, и по двум независимым причинам.

**Причина первая: random IO PostgreSQL.** Все запросы продукта — tenant-scoped, то есть идут по
составным индексам `(organization_id, …)`. Это index scan: набор случайных чтений страниц по
8 KB, а не последовательное сканирование. Порядок величин на одно чтение:

| Носитель | Задержка случайного чтения 8 KB | Запрос, читающий 500 страниц индекса |
|---|---|---|
| Локальный NVMe | 50–100 мкс | 25–50 мс |
| Сетевой SSD (облачный том) | 0.5–1 мс | **250–500 мс** |
| SATA SSD | 0.2–0.4 мс | 100–200 мс |

Целевой показатель NFR-2 — **p95 < 300 мс на списочных эндпоинтах**. На сетевом томе он
недостижим в принципе, если данные не помещаются в page cache целиком.

Вторая половина той же причины — **`fsync` при коммите**. Каждая транзакция ждёт, пока WAL
физически ляжет на носитель. NVMe корпоративной серии с защитой от потери питания (DC Edition)
подтверждает запись за 50–100 мкс, потребительский NVMe без такой защиты — иногда за миллисекунду
и больше. Это прямой потолок числа транзакций в секунду.

**Причина вторая: обход HNSW-графа.** Один векторный поиск обходит `ef_search` кандидатов (по
умолчанию 40) по нескольким уровням графа, и каждый — случайное чтение страницы. Итого 40–200
случайных чтений на запрос:

- граф в RAM — ~0.5 мс;
- граф на NVMe — ~5 мс;
- граф на сетевом томе — **50–200 мс на один поиск**, а RAG делает несколько поисков на реплику
  ассистента.

Отсюда же требование к RAM: NVMe спасает, когда граф не поместился в память, но по-настоящему
быстро только тогда, когда поместился.

**Что ещё следует из выбора носителя:** дефолтный `random_page_cost = 4.0` в PostgreSQL описывает
вращающийся диск. На NVMe он врёт в четыре раза, и планировщик выбирает seq scan там, где нужен
index scan. Настройка — в разделе 5.

## 3. Рекомендуемая базовая конфигурация

**Один хост: 8 физических ядер / 32 GB ECC RAM / 2 × 1 TB (или больше) NVMe в RAID1 / 1 Gbit/s.**

Одна конфигурация на все три размера из раздела 2. Причина — в разделе 4: при аренде выделенного
сервера разница между «под 10 человек» и «под 50 человек» стоит порядка десяти евро в месяц,
поэтому три отдельные спецификации создают выбор там, где выбора нет. Реально масштабируется
только **диск**.

### 3.1 Откуда каждая цифра

**32 GB RAM — постатейно (профиль «50 человек», полный стек):**

| Статья | Сколько | Почему столько |
|---|---|---|
| `shared_buffers` PostgreSQL | **8 GB** | 25 % RAM — классический ориентир: больше начинает дублировать page cache ОС, меньше — заставляет ходить в ядро за каждой страницей |
| Page cache ОС под данные PostgreSQL | **~8 GB** | Сюда должны помещаться горячие индексы, свежие партиции `audit_logs` и **весь HNSW-граф**. HNSW на 25 тыс. чанков — 200 MB, горячие индексы — 1.5–2 GB; остальное — запас на рост и на чтение при бэкапе |
| Пиковый `work_mem` бэкендов | **~2 GB** | 30 соединений × 2–3 узла плана × 32 MB. Ограничивается не настройкой, а размером пула приложения (см. 5.3) |
| `maintenance_work_mem` | **2 GB** | Разово: `VACUUM`, `CREATE INDEX CONCURRENTLY`, построение HNSW. Пересекается с предыдущей статьёй редко |
| Meilisearch: кеш индекса | **2 GB** | Индекс через год ~1.1 GB; хотим его целиком в памяти |
| Meilisearch: пик индексации | **2 GB** | **Жёстко ограничивается** `MEILI_MAX_INDEXING_MEMORY`. По умолчанию — 2/3 всей памяти хоста, то есть на 32 GB он попытается взять 21 GB и убьёт PostgreSQL |
| API-процесс Node | **0.6 GB** | Базовая куча ~200 MB + буферы запросов + состояние WebSocket-соединений |
| worker Node | **0.5 GB** | Батчи эмбеддингов по 32 чанка + буферы стриминга LLM |
| Redis | **0.5 GB** | Реальный рабочий набор < 200 MB; `maxmemory` ставится с запасом (см. 5.6) |
| MinIO | **1 GB** | Буферы одноузлового режима |
| Caddy | **0.1 GB** | |
| ОС, ядро, демон Docker | **1 GB** | |
| **Сумма** | **~28 GB** | Остаток ~4 GB — не «свободная память», а обязательный буфер: без него первый же `pg_restore` рядом с работающей базой упирается в OOM killer |

**8 ядер:**

- Node занимает **два** ядра постоянно (api + worker, по одному потоку на процесс) — это потолок
  архитектуры, а не настройки.
- PostgreSQL: `max_parallel_workers_per_gather = 2` плюс автовакуум на четырёх воркерах.
- Meilisearch при полной переиндексации многопоточен и заберёт всё, что найдёт.
- argon2id при входе: 19 MiB × `timeCost 2` ≈ 50–80 мс CPU на попытку. 50 человек, входящих в
  09:00, — это ~4 секунды суммарной работы одного ядра. Не проблема, но это то, что видно в
  профиле, и то, что нельзя выносить за пределы CPU.

Ядра должны быть **выделенными**. На shared-vCPU steal time добавляется к каждому запросу
неравномерно, и p95 (а NFR-2 сформулирован именно в p95) перестаёт быть предсказуемым — не
«медленнее», а «непредсказуемо».

**RAID1:** не про производительность, а про RTO. Смерть одного NVMe при зеркале — это замена
диска без остановки. Без зеркала — полное восстановление из бэкапа, то есть заявленные
[`backup-restore.md`](backup-restore.md) 4 часа RTO вместо пятнадцати минут.

**ECC:** база с RLS и деньгами (инвойсы, подтверждённые часы, `AuditLog` как доказательство).
Тихий битфлип в странице индекса — это повреждение, которое обнаружится через недели, когда все
бэкапы уже содержат его. На выделенных серверах ECC обычно уже в базовой конфигурации.

**1 Gbit/s:** трафик мал (файлы за год — десятки гигабайт, WebSocket-события — единицы килобит),
но канал нужен для **восстановления**: скачать 60 GB бэкапа с внешнего хранилища на 100 Mbit/s —
это 1.5 часа, что съедает половину RTO.

### 3.2 Что произойдёт, если взять меньше

Разложено по тому, **какой сервис упрётся первым** и как это выглядит для администратора.

| Урезание | Кто упирается первым | Как проявляется |
|---|---|---|
| **RAM 4 GB** (профиль `default` из `stack.md`) | PostgreSQL: `shared_buffers` ~1 GB | Индексы не держатся в кеше → списочные эндпоинты уходят за 300 мс, p95 «плавает» в зависимости от того, что делал сосед по хосту. HNSW читается с диска → ассистент отвечает секундами. Формально всё работает — просто медленно и невоспроизводимо |
| **RAM 8 GB без `MEILI_MAX_INDEXING_MEMORY`** | Meilisearch при первой полной индексации | Meilisearch берёт 2/3 памяти → OOM killer выбирает процесс с наибольшим RSS, то есть PostgreSQL → `postgres exited with code 137`, приложение отдаёт 503 на `/readyz`. Данные целы, простой — минуты. Повторяется при каждой переиндексации |
| **RAM 8 GB с корректным потолком Meilisearch** | Обслуживающие операции | Штатная работа нормальная. Но восстановление бэкапа рядом с живой базой, полная переиндексация и первичная сборка HNSW требуют остановки сервиса |
| **2 ядра** | Node | Api и worker делят два ядра с PostgreSQL. Тяжёлый job (эмбеддинги, экспорт) начинает влиять на время HTTP-ответа. Растёт `outbox_lag_seconds` |
| **Shared vCPU вместо выделенных** | Всё сразу, непредсказуемо | p95 скачет в 2–5 раз без корреляции с собственной нагрузкой. Отладить нельзя: причина вне вашей машины |
| **Сетевой том вместо NVMe** | PostgreSQL: fsync WAL и random-чтение индексов | Каждый коммит ждёт ~1 мс вместо 0.05 мс; index scan дороже в 5–10 раз. NFR-2 недостижим (см. 2.5) |
| **Один диск без RAID1** | Ничего — до отказа | Отказ NVMe = полное восстановление. RTO 4 часа вместо замены диска |
| **Диск «сколько данных, столько и купили»** | Апгрейдер | `pg_dump` перед миграцией не помещается → апгрейд останавливается либо (хуже) выполняется с `--skip-backup`. Отдельно: заполнение диска на 100 % — самая частая причина падения, и PostgreSQL из него выходит тяжелее прочих |

получает от облачных примитивов — ни автоскейлинга (stateful-инстанс), ни multi-AZ (одна БД), ни
managed-бэкапов (собственная процедура из-за `FORCE ROW LEVEL SECURITY`). Всё, что ему нужно, —
это память, NVMe и root. Ровно это выделенный сервер и продаёт дешевле всех.

**Отдельно про облачные снапшоты.** Их часто называют аргументом в пользу VPS. Для этого продукта
снапшот тома **не является бэкапом**: он не решает проблему `FORCE RLS` + `pg_dump`
([`backup-restore.md`](backup-restore.md), раздел 2), не даёт сверки числа строк и, что важнее,
живёт у того же провайдера, что и сам хост. Снапшот полезен как точка отката при апгрейде — но
процедура апгрейда уже требует `pg_dump` до миграции. То есть за снапшоты вы доплачиваете за
удобство, а не за сохранность.

## 5. Настройка PostgreSQL под эту нагрузку

Параметры для рекомендованной конфигурации (8 ядер, 32 GB, NVMe). Для 16 GB — делить память
пополам, для 8 GB — на четыре; остальное не меняется. Кладётся в `postgresql.conf` или
пробрасывается в контейнер аргументами `command:`.

### 5.1 Память

```conf
shared_buffers = 8GB                  # 25 % RAM
effective_cache_size = 20GB           # НЕ выделение, а подсказка планировщику:
                                      # сколько всего кеша (shared_buffers + page cache ОС)
work_mem = 32MB                       # на ОДИН узел плана, не на запрос и не на соединение
maintenance_work_mem = 2GB            # VACUUM, CREATE INDEX, построение HNSW
huge_pages = try                      # снижает накладные расходы TLB на большом shared_buffers
```

**`effective_cache_size` важнее, чем кажется.** Он ничего не выделяет, но напрямую определяет,
выберет ли планировщик index scan. Заниженное значение (дефолт — 4 GB) заставляет его считать,
что индекс придётся читать с диска, и предпочитать seq scan. На таблицах с RLS это особенно
больно: последовательное сканирование `audit_logs` вместо обхода индекса — разница на порядки.

**`work_mem` — самая опасная настройка.** Она действует на **каждый узел сортировки или хеша в
каждом соединении**. При 100 соединениях и трёх узлах на запрос 32 MB превращаются в 9.6 GB
теоретического потолка. Защита не в уменьшении `work_mem` (тогда сортировки уйдут во временные
файлы на диск), а в ограничении числа соединений — см. 5.3.

**`maintenance_work_mem` и pgvector.** Ставится по формуле из раздела 2.2: `N × 12 KB`. Для
25 тыс. чанков это 300 MB, то есть 2 GB покрывают инсталляцию с десятикратным запасом. Если
планируется разовая массовая генерация эмбеддингов (импорт существующего Obsidian-хранилища),
поднимайте адресно на время сессии: `SET maintenance_work_mem = '4GB';`.

### 5.2 Планировщик под NVMe

```conf
random_page_cost = 1.1                # дефолт 4.0 описывает вращающийся диск
seq_page_cost = 1.0
effective_io_concurrency = 200        # NVMe обслуживает сотни параллельных запросов
maintenance_io_concurrency = 200
```

`random_page_cost = 1.1` — не тюнинг, а исправление ошибки. Дефолт говорит планировщику, что
случайное чтение вчетверо дороже последовательного; на NVMe разница около 10 %. Продукт целиком
построен на составных индексах `(organization_id, …)`, и неверная оценка систематически
выталкивает планировщик в seq scan на тех самых списочных эндпоинтах, для которых заявлен p95.

### 5.3 Соединения: почему пул важнее большого `max_connections`

```conf
max_connections = 100
superuser_reserved_connections = 3
```

Сотни — это **потолок безопасности, а не рабочее число**. Реальное число соединений задаётся на
стороне приложения:

```
DATABASE_URL=postgresql://app_user@postgres/bad_crm?connection_limit=15&pool_timeout=10
# у worker-процесса — connection_limit=10
```

Три причины, по которым большой `max_connections` вреден именно здесь:

1. **Каждый бэкенд PostgreSQL — отдельный процесс** ценой ~5–10 MB плюс всплески `work_mem`.
   200 соединений — это гигабайты, отобранные у page cache.
2. **Соединений всё равно нужно мало.** Восемь ядер не выполняют больше восьми запросов
   одновременно; сверх этого соединения только конкурируют за блокировки и снапшоты. Рабочее
   правило — `ядра × 2 + 1`, то есть ~17 на процесс, а не сотня.
3. **Модель tenant-контекста удерживает соединение на всё время транзакции.** `withTenant`
   открывает интерактивную транзакцию, выставляет `set_config('app.organization_id', …, true)` и
   держит соединение до коммита ([`../architecture/stack.md`](../architecture/stack.md)). Значит
   каждое соединение занято дольше, чем при обычном автокоммите, и раздувать пул — прямой путь к
   исчерпанию `max_connections` при первом же всплеске.

**PgBouncer в transaction mode** объявлен обязательным в
[`../architecture/data-model.md`](../architecture/data-model.md). Он совместим с этой моделью:
`set_config(..., is_local = true)` живёт внутри транзакции, а transaction mode отдаёт серверное
соединение целиком на транзакцию. Единственное, что нужно помнить, — **Prisma должна отключить
серверные prepared statements** (`?pgbouncer=true` в строке подключения), иначе появятся ошибки
вида `prepared statement "s0" already exists`.

Для инсталляции до 50 человек PgBouncer можно вводить не сразу: при пуле в 25 соединений он не
даёт выигрыша. Он становится нужен на шаге «несколько API-процессов» из раздела 7 — там суммарный
пул умножается на число процессов.

### 5.4 WAL и чекпоинты

```conf
wal_level = replica                   # включить СРАЗУ: смена требует перезапуска
max_wal_size = 8GB
min_wal_size = 2GB
checkpoint_timeout = 15min
checkpoint_completion_target = 0.9
wal_compression = zstd
wal_buffers = 64MB
synchronous_commit = on
```

**`wal_level = replica` выставляется при установке, даже если PITR не нужен сегодня.** Изменение
требует перезапуска PostgreSQL. Разница между «включили заранее» и «включаем в момент, когда
понадобился PITR или реплика» — это плановое окно простоя посреди рабочего дня.

**`max_wal_size = 8GB` против дефолтных 1 GB.** С 1 GB чекпоинты запускаются не по таймеру, а по
переполнению WAL, — и каждый из них заставляет заново записывать полные страницы (full-page
writes) после следующего изменения. Итог: больше WAL, больше IO, дёрганый профиль записи.
Проверка, что значение подобрано: в `pg_stat_checkpointer` число **запрошенных** чекпоинтов
должно быть много меньше числа чекпоинтов по таймеру.

**`synchronous_commit = on` не отключаем.** Продукт хранит подтверждённые часы, инвойсы и
append-only `AuditLog`; `off` означает, что до одной секунды подтверждённых транзакций может
исчезнуть при отказе питания. Экономия не стоит расхождения между таймшитом и выставленным
счётом (риск R-16 из PRD).

**Отдельно — WAL и заполнение диска.** Если включена архивация WAL для PITR, а `archive_command`
перестал отрабатывать (недоступен внешний хост), PostgreSQL **перестаёт удалять сегменты WAL** и
заполняет диск до отказа. Это одна из двух самых частых причин смерти инсталляции, и она не
видна ни в одном продуктовом графике. Мониторинг — в разделе 9.

### 5.5 Автовакуум, партиции, блокировки

```conf
autovacuum_max_workers = 4
autovacuum_naptime = 30s
autovacuum_vacuum_cost_limit = 2000     # дефолт 200 рассчитан на медленный диск; NVMe тянет
autovacuum_vacuum_scale_factor = 0.05   # дефолт 0.2 = вакуум после изменения 20 % таблицы
autovacuum_analyze_scale_factor = 0.02

max_locks_per_transaction = 256         # см. ниже — это не «на всякий случай»
max_worker_processes = 8
max_parallel_workers = 8
max_parallel_workers_per_gather = 2
max_parallel_maintenance_workers = 4
```

**Почему `scale_factor` понижен.** Дефолт означает «вакуумируй, когда изменилось 20 % таблицы».
На `messages` в полмиллиона строк это 100 тыс. мёртвых кортежей до первой уборки — то есть
раздутая таблица и деградировавшие индексы. На горячих таблицах имеет смысл задать пер-табличные
настройки в миграции:

```sql
ALTER TABLE messages   SET (autovacuum_vacuum_scale_factor = 0.02, autovacuum_analyze_scale_factor = 0.01);
ALTER TABLE time_entries SET (autovacuum_vacuum_scale_factor = 0.02);
```

**`max_locks_per_transaction = 256` — обязательно, и вот почему.** PostgreSQL берёт блокировку на
**каждую** партицию, которую не удалось отсечь при планировании. `audit_logs` партиционирована
помесячно, `messages` — поквартально при достижении порога. Через два года это 24 + 8 партиций,
у каждой свои индексы. Отдельно: **`pg_dump` берёт `ACCESS SHARE` на все таблицы и все партиции
одним `LOCK TABLE`** до чтения первой строки ([`backup-restore.md`](backup-restore.md),
раздел 2). При дефолтном значении 64 бэкап однажды падает с `out of shared memory; You might need
to increase max_locks_per_transaction` — и это первое, что вы узнаете, когда бэкап понадобится.
Параметр требует перезапуска, поэтому ставится сразу.

**Заморозка закрытых партиций.** Партиции `audit_logs` append-only: после закрытия месяца они не
меняются, но автовакуум всё равно вернётся к ним ради предотвращения wraparound — в самый
неудобный момент и целиком. Правильнее сделать это самим, сразу после смены месяца, в том же
джобе, который создаёт партиции на будущее:

```sql
VACUUM (FREEZE, ANALYZE) audit_logs_2026_06;
```

**Наследование RLS партициями.** `ENABLE`/`FORCE ROW LEVEL SECURITY` применяется к **родительской**
таблице **до** создания партиций, иначе часть листов останется без защиты
([`../architecture/data-model.md`](../architecture/data-model.md)). Это ответственность миграции,
а не конфигурации сервера, но проверять надо здесь же, чек-листом из
[`install.md`](install.md) §5.4.

### 5.6 Таймауты

```conf
statement_timeout = 0                  # глобально 0; задаётся ПОРОЛЬНО, см. ниже
idle_in_transaction_session_timeout = 30s
lock_timeout = 0                       # в миграциях выставляется явно в 3s
```

```sql
ALTER ROLE app_user     SET statement_timeout = '15s';
ALTER ROLE app_migrator SET statement_timeout = '0';
ALTER ROLE backup_role  SET statement_timeout = '0';
```

Глобальный `statement_timeout` — распространённая ошибка: он одинаково обрывает и зависший
запрос приложения, и `VALIDATE CONSTRAINT` на миллионе строк, и `pg_dump`. Ограничивать надо
**роль приложения**, у которой транзакция и так ограничена пятью секундами на уровне Prisma
([`../architecture/stack.md`](../architecture/stack.md)), — и не трогать миграционную и
бэкапную роли.

`idle_in_transaction_session_timeout` защищает от главного побочного эффекта модели
`withTenant`: открытая транзакция, в которой приложение зависло на внешнем вызове, держит снапшот
и блокирует автовакуум по всей базе. Архитектура это запрещает (внешние вызовы только через
outbox), но предохранитель на уровне БД стоит копейки.

### 5.7 RLS и планы запросов

Что нужно знать про производительность RLS в этой схеме:

- Политика добавляет к **каждому** сканированию предикат
  `organization_id = current_setting('app.organization_id')::uuid`. Функция `current_setting`
  помечена `STABLE`, поэтому вычисляется один раз на запрос и **может использоваться как условие
  индекса** — накладных расходов почти нет.
- «Почти» превращается в «нет» ровно при одном условии: **`organization_id` — первая колонка
  составного индекса**. Это уже норматив модели данных, и вот его вторая причина, помимо
  изоляции: предикат политики и предикат запроса обслуживаются одним и тем же индексом.
- Предикаты политики, не помеченные `LEAKPROOF`, применяются **раньше** пользовательских условий.
  Практическое следствие: не усложняйте политику вызовами функций — канонический шаблон из
  [`../security/rls-design.md`](../security/rls-design.md) сравнивает колонку с настройкой, и так
  и должно остаться.
- **`EXPLAIN` надо смотреть под ролью `app_user` внутри `withTenant`.** Под `app_migrator`
  политики не применяются, план получается другим, и «оптимизированный» запрос в проде ведёт себя
  иначе. Требование прикладывать `EXPLAIN (ANALYZE, BUFFERS)` к PR для таблиц свыше 100 тыс.
  строк — из модели данных; здесь важно, что снимать его надо в правильном контексте.
- **HNSW не знает про RLS.** `ORDER BY vector <=> $1 LIMIT 10` сначала достаёт соседей по всему
  индексу и только потом отфильтровывает чужие строки — результатов может прийти меньше, чем
  просили. Компенсация зафиксирована как `LIMIT k × 4`; чтобы она работала, надо поднять и
  ширину поиска:

  ```sql
  SET hnsw.ef_search = 100;   -- дефолт 40; при выборке с четырёхкратным запасом его не хватает
  ```

### 5.8 Наблюдаемость на уровне БД

```conf
shared_preload_libraries = 'pg_stat_statements'
pg_stat_statements.max = 5000
pg_stat_statements.track = top
track_io_timing = on

log_min_duration_statement = 500ms
log_checkpoints = on
log_lock_waits = on
log_autovacuum_min_duration = 0
log_temp_files = 0
log_line_prefix = '%m [%p] %u@%d app=%a '
```

`pg_stat_statements` объявлен обязательным в поставке моделью данных: без него диагностика

`log_lock_waits` показывает те самые блокировки, ради которых в миграциях стоит `lock_timeout`.

## 6. Reverse-proxy и TLS

### 6.1 Выбор: Caddy

**Берём Caddy.** Обоснование — по трём пунктам, каждый из которых важен именно здесь:

1. **ACME из коробки.** Сертификат и его продление — ноль строк конфигурации и ноль cron-задач.
   Целевая аудитория продукта — «человек, способный запустить `docker compose` и настроить домен»
   (допущение 3 из PRD), а не инженер по эксплуатации.
2. **WebSocket и SSE работают без настройки.** В nginx каждый из них требует явных директив
   (`proxy_http_version 1.1`, проброс `Upgrade`/`Connection`, `proxy_buffering off`,
   `proxy_read_timeout`), и забытая директива даёт не ошибку, а тихую деградацию: чат
   переподключается каждые 60 секунд, ответ ассистента приходит одним куском в конце.
3. **Конфиг, который читается на ревью.** Поставляемый конфиг будет копироваться и правиться
   администраторами, которых мы не видим (правило `self-host-packaging`). Пятнадцать строк
   Caddyfile ревьюются, восемьдесят строк nginx.conf — нет.

nginx остаётся законным выбором, если он уже стоит на хосте и обслуживает другие сайты; тогда
см. 6.4 — там перечислены четыре директивы, без которых он ломает продукт.

### 6.2 Каноничный Caddyfile

```caddyfile
crm.example.com {
	encode zstd gzip

	# --- Access-лог с обрезкой токена защищённой ссылки (T-LINK-02) ---
	log {
		output file /var/log/caddy/access.log {
			roll_size 100MiB
			roll_keep 14
		}
		format filter {
			wrap json
			fields {
				# Токен secure-link передаётся В ПУТИ и обязан быть вырезан ДО записи на диск
				request>uri            regexp "/l/[^/?#]+" "/l/REDACTED"
				request>headers>Authorization delete
				request>headers>Cookie        delete
			}
		}
	}

	# --- SSE-стрим ассистента: буферизация запрещена ---
	handle /api/v1/ai/* {
		reverse_proxy api:3000 {
			flush_interval -1
		}
	}

	# --- Socket.IO: WebSocket + long-polling fallback, липкая сессия ---
	handle /socket.io/* {
		reverse_proxy api:3000 {
			lb_policy cookie bad_crm_lb
		}
	}

	# --- Остальной API: тело ограничено так же, как в приложении ---
	handle /api/* {
		request_body {
			max_size 1MB
		}
		reverse_proxy api:3000
	}

	# --- SPA и статика ---
	handle {
		reverse_proxy api:3000
	}
}
```

### 6.3 Почему каждый блок именно такой

**Sticky sessions — обязательны, даже когда инстанс один.** Socket.IO по умолчанию сохраняет
HTTP long-polling как fallback (часть корпоративных прокси режет WebSocket, поэтому отказываться
от fallback мы не стали — [`../architecture/overview.md`](../architecture/overview.md)). При
long-polling рукопожатие и все последующие polling-запросы **обязаны** попадать в тот же процесс,
иначе клиент получает `Session ID unknown` и уходит в бесконечный цикл переподключений. При одном
инстансе `lb_policy cookie` — не-операция; она стоит в конфиге, чтобы добавление второго инстанса
было одной строкой, а не разбором инцидента.

**`flush_interval -1` для SSE.** Caddy распознаёт `Content-Type: text/event-stream` и не
буферизует такой ответ, но явная директива снимает зависимость от того, выставил ли сервер
заголовок правильно на всех путях ошибок. Без неё стриминг ответа ассистента приходит одним
блоком в конце — функционально «работает», но продукт теряет смысл стриминга.

**Таймауты.** Caddy не ставит таймаут на тело ответа по умолчанию, поэтому WebSocket и SSE живут
сколько нужно, — специально настраивать нечего. Это и есть причина пункта 2 из 6.1: в nginx
дефолтный `proxy_read_timeout 60s` рвёт WebSocket раз в минуту.

**Лимит тела.** `max_size 1MB` на `/api/*` зеркалит ограничение приложения. Он **не** должен
стоять на пути к объектному хранилищу: файлы идут presigned-запросом браузер → MinIO и через этот
блок не проходят. Если MinIO по каким-то причинам проксируется через тот же домен, его маршрут
описывается отдельным `handle` **без** `request_body`.

**Обрезка токена secure-link — это `T-LINK-02` из модели угроз.** Токен передаётся в пути URL и
без фильтра попадает в access-лог прокси открытым текстом; ключ во фрагменте (`#key=`) браузер на
сервер не отправляет, но токена достаточно, чтобы сжечь ссылку. Фильтр обязан стоять именно в
прокси: приложение маскирует токен в **своих** логах, до логов Caddy оно не дотягивается.

**Проброс заголовков.** Caddy сам выставляет `X-Forwarded-For` и `X-Forwarded-Proto`. Обязательное
парное условие на стороне приложения — `app.set('trust proxy', …)` в Express: без него
`rate-limiter-flexible` увидит один IP прокси для всех и заблокирует всю инсталляцию после пяти
неудачных входов одного пользователя, а cookie не получат `Secure`.

### 6.4 Если всё-таки nginx

Минимальный набор, без которого продукт ломается:

```nginx
location /socket.io/ {
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;          # без этого WebSocket не поднимется
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;                        # дефолт 60s рвёт соединение раз в минуту
    proxy_pass http://api:3000;
}

location /api/v1/ai/ {
    proxy_buffering off;                             # иначе SSE не стримит
    proxy_read_timeout 600s;
    proxy_pass http://api:3000;
}

client_max_body_size 1m;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

Плюс отдельно: sticky sessions в open-source nginx — только `ip_hash` (сессия ломается при смене
IP клиента, что для мобильного интернета обычное дело), обрезка токена из лога — через
`map`-подмену `$request_uri`, сертификат — через certbot с собственным таймером. Это и есть цена
выбора nginx, выраженная в работе.

### 6.5 Заголовки безопасности и CSP

**Правило: CSP выставляет приложение (helmet), а не прокси.** Два источника CSP — это не «двойная
защита»: браузер применяет **обе** политики, пересечение оказывается строже задуманного, и часть
приложения молча перестаёт работать. Прокси не добавляет и не переписывает `Content-Security-Policy`.

Что прокси всё же делает:

- Терминирует TLS и редиректит HTTP → HTTPS (Caddy — автоматически).
- Не трогает `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy`,
  `Cross-Origin-Opener-Policy` — они приходят от приложения.
- Не логирует то, что нельзя логировать (см. 6.3).

**Два практических следствия CSP для web-E2EE.** Оба были найдены при этом расчёте и **решены** —
[ADR-0023](../architecture/adr/0023-csp-for-wasm-crypto.md), норматив
[`../security/e2ee-design.md`](../security/e2ee-design.md) §12 приведён в соответствие. Здесь они
остаются потому, что администратор столкнётся с их симптомами, если политику соберут неправильно:

1. **WASM и `script-src`.** Крипто-модуль vault — `libsodium-wrappers-sumo`, то есть WebAssembly.
   Политика вида `script-src 'self' 'nonce-…'` **блокирует** `WebAssembly.instantiate`. Решение:
   `'wasm-unsafe-eval'` в `script-src` — он разрешает только компиляцию WASM, источник модуля
   по-прежнему ограничен `script-src`, а `eval` остаётся запрещён. **`'unsafe-eval'` не
   используется** ни как основной вариант, ни как запасной. Симптом при ошибке — vault не
   открывается, в консоли ошибка CSP на компиляции модуля, остальное приложение работает.
2. **`Cross-Origin-Embedder-Policy` не выставляется.** `require-corp` блокирует любой кросс-origin
   ресурс без `Cross-Origin-Resource-Policy`, а presigned-ссылки на вложения ведут на MinIO/S3,
   который его не отдаёт. Изоляция, которую покупает эта политика, нужна для `SharedArrayBuffer` —
   в продукте его нет. Остаётся `Cross-Origin-Opener-Policy: same-origin`. Симптом при ошибке —
   вложения-картинки не отображаются, файлы не загружаются.

Прокси политику **не выставляет и не переписывает** — её собирает приложение, потому что
`connect-src` и `img-src` включают origin объектного хранилища из конфигурации. Проверка — e2e в
реальном браузере (открыть vault, расшифровать элемент, показать вложение), а не тест на заголовок:
обе ошибки выше дают зелёный тест на строку политики и чёрный экран у пользователя.

## 7. Что делать, когда одного хоста мало

Порядок вынесения — не произвольный. Он выстроен по правилу «сначала то, что даёт больше всего
при наименьшем усложнении эксплуатации».

### Шаг 1. PostgreSQL — на отдельный хост

**Первым, потому что** это единственный компонент, чья нехватка ресурсов бьёт по **каждому**
пользовательскому запросу, и единственный, который нельзя разгрузить добавлением процесса. Всё
остальное на хосте (MinIO, Meilisearch, Node) конкурирует с ним за page cache и IO — вынос БД
решает эту конкуренцию целиком.

Что нужно:

- Приватная сеть между хостами. **Задержка критична**: `withTenant` открывает транзакцию на
  каждый запрос, то есть платит минимум два round-trip. 0.1–0.3 мс в пределах одного ЦОД —
  нормально; межрегиональная связность (5–30 мс) складывается с каждым запросом и убивает p95.
- PostgreSQL слушает **только** приватный интерфейс; `pg_hba.conf` — по подсети приложения,
  `scram-sha-256`. Публичный порт 5432 — грубейшее нарушение чек-листа из
  [`install.md`](install.md) §5.1.
- `DATABASE_URL` и `DATABASE_MIGRATION_URL` меняются, `sslmode` — по политике сети.
- Теперь появляется смысл в PgBouncer (см. 5.3) и открывается путь к горячей реплике и PITR.

### Шаг 2. Объектное хранилище — наружу (внешний S3)

**Вторым, потому что** MinIO — самый прожорливый по диску компонент и единственный, чей профиль
IO (крупные последовательные потоки) вытесняет из page cache горячие страницы БД. Вынос
одновременно снимает главную статью роста диска и главную статью бэкапа.

Что нужно: заменить `S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_REGION`,
`S3_FORCE_PATH_STYLE` — код не меняется, работа идёт через `@aws-sdk/client-s3`
([ADR-0015](../architecture/adr/0015-s3-file-storage-presigned-urls.md)). Два условия, которые
легко упустить:

- **Endpoint должен быть доступен браузеру**, а не только контейнеру: presigned PUT/GET выполняет
  клиент. Это ровно та строка в таблице симптомов [`install.md`](install.md) §6.
- **CORS на бакете** должен разрешать `PUT` и `GET` с `APP_URL`, иначе загрузка падает в браузере
  без внятной ошибки на сервере.

### Шаг 3. Несколько API-процессов за прокси

**Третьим, потому что** до этого шага упирались не в Node. Node становится узким местом только
когда CPU одного процесса насыщен — а это заметно раньше по метрике `http_request_duration_seconds`,
чем по жалобам.

Что для этого уже готово и что нужно доделать:

| Что нужно | Состояние |
|---|---|
| Redis-адаптер Socket.IO для fan-out между процессами | **Есть с первого дня** — `@socket.io/redis-streams-adapter`, [ADR-0010](../architecture/adr/0010-realtime-socketio-redis-adapter.md) |
| Общее объектное хранилище (не локальный диск) | **Есть** — S3-совместимое хранилище, шаг 2 |
| Приложение stateless | **Есть по проекту** — состояние только в PostgreSQL, Redis и S3 (NFR-4) |
| Воркер отдельным процессом | **Есть** — `RUN_WORKERS_IN_PROCESS=false` по умолчанию |
| Sticky sessions на `/socket.io` | **Одна строка в Caddyfile** — уже стоит (6.2) |
| Миграции ровно один раз | Одноразовый контейнер `migrate` **до** старта api и worker; параллельный `prisma migrate deploy` из двух процессов — гонка |
| `/ready` → 503 при shutdown, чтобы прокси увёл трафик | **Есть по проекту** — graceful shutdown в `main.ts` |

Воркеров при этом остаётся **один** до тех пор, пока не растёт `outbox_lag_seconds`: диспетчер
использует `SELECT … FOR UPDATE SKIP LOCKED` и допускает несколько реплик без дублей, но пока лаг
нулевой, вторая реплика ничего не ускоряет.

### Шаг 4. Meilisearch — отдельно

**Последним, потому что** поиск деградируем по проекту: без Meilisearch `SearchPort` уходит в
`postgres-fts.adapter.ts`, и продукт продолжает работать
([ADR-0011](../architecture/adr/0011-meilisearch-permission-aware-search.md)). Выносить его
имеет смысл ровно тогда, когда полная переиндексация начинает мешать остальным — то есть при
большом объёме контента, а не при большом числе людей. `meili-data` не бэкапится: индекс
переигрывается из БД.

### Чего делать НЕ надо

| Не надо | Почему |
|---|---|
| **Kubernetes ради шести контейнеров** | Добавляет к эксплуатации control plane, ingress, CNI, storage class и собственный жизненный цикл обновлений — больше движущихся частей, чем во всём продукте. Прямо зафиксировано как отложенное решение в [`../architecture/overview.md`](../architecture/overview.md). Манифесты как community-дополнение возможны, но они не должны определять архитектуру |
| **Managed PostgreSQL «чтобы не администрировать»** | Стоит в 3–5 раз дороже, а модель изоляции требует того, что managed-движки ограничивают: создание ролей с `BYPASSRLS` (нужна `backup_role`), собственный bootstrap ролей, расширения `vector`/`btree_gist`/`pg_trgm`/`citext`/`pgcrypto`, партиционирование ручным SQL. Проверяйте каждый пункт **до** миграции |
| **Managed Redis, managed поиск, managed очередь** | Redis для этой нагрузки — 200 MB рабочего набора и ноль администрирования; BullMQ и так поверх него. Платить за это отдельным сервисом не за что |
| **Отдельная векторная БД (Qdrant, Weaviate, Pinecone)** | Решение зафиксировано: pgvector даёт транзакционную консистентность эмбеддингов с данными и не добавляет контейнер. Объёмы (десятки тысяч чанков) на порядки ниже порога, где выделенная векторная БД что-то даёт |
| **Elasticsearch вместо Meilisearch** | Гигабайты RAM на self-host-инстансе плюс лицензия, несовместимая с AGPL-3.0 |
| **CDN перед SPA** | Бандл маршрута < 300 KB gzip, пользователей — десятки, все в одной стране. CDN добавляет внешнюю зависимость, которую NFR-9 запрещает делать обязательной |
| **Вторая реплика приложения «для надёжности»** без разделения БД | Целевая доступность 1.0 — 99.5 % при **одном** инстансе приложения (NFR-4). Второй инстанс без вынесенной БД не добавляет отказоустойчивости — общая точка отказа остаётся ровно там же |

## 8. Бэкапы и хранилище под них

Процедура — в [`backup-restore.md`](backup-restore.md); здесь только **сколько места, где и как
часто**.

### 8.1 Сколько места

Схема хранения из [`backup-restore.md`](backup-restore.md) — **7 ежедневных / 4 еженедельных /
6 ежемесячных**, то есть 17 копий базы.

Размер одного дампа `pg_dump -Fc` (со сжатием) ≈ **25–35 % каталога данных**, но с важной
поправкой: **векторы не сжимаются**. `Embedding` — это случайные float, и его доля переезжает в
дамп почти один в один. Для 50 человек через год: (15 GB каталога − 8 GB WAL) × 0.3 + 0.4 GB
векторов ≈ **~2.5 GB на дамп**.

| | 10 человек | 25 человек | 50 человек |
|---|---|---|---|
| Один дамп БД | ~0.5 GB | ~1.2 GB | ~2.5 GB |
| 17 копий по схеме 7/4/6 | ~9 GB | ~20 GB | ~43 GB |
| Зеркало объектного хранилища (инкрементальное, одна копия) | ~4 GB | ~10 GB | ~20 GB |
| Архив WAL, если включён PITR (7 дней) | ~5 GB | ~8 GB | ~15 GB |
| **Хранилище под бэкапы, первый год** | **~20 GB** | **~40 GB** | **~80 GB** |
| **С трёхлетним горизонтом** | **~50 GB** | **~110 GB** | **~220 GB** |

**Про зеркало объектного хранилища.** Держать 17 полных копий файлов не нужно и дорого:
`mc mirror` инкрементален, а защита от «удалили файл месяц назад и заметили сейчас» решается
версионированием объектов или снапшотами на стороне приёмника, а не умножением полных копий.
Оценивать это надо честно при выборе приёмника: провайдер, у которого нет версионирования, ломает
эту схему.

**Про архив WAL.** Оценка ~1–2 GB в сутки для 50 человек — это не объём данных, а объём WAL:
full-page writes после каждого чекпоинта дают многократный множитель к чистому приросту данных.
Число проверяется на месте: `pg_stat_wal` даёт `wal_bytes`, и после недели работы оценка
заменяется фактом.

### 8.2 Куда

**Отдельный хост или отдельный бакет — не тот же диск.** Это не перестраховка, а покрытие трёх
разных сценариев, каждый из которых убивает локальную копию вместе с оригиналом:

1. отказ носителя (RAID1 не спасает от отказа контроллера или хоста целиком);
2. `docker compose down -v` — команда, которая существует в документации проекта и удаляет тома;
3. компрометация хоста: атакующий с root видит и данные, и бэкапы.

**Требования к приёмнику:** доступ на запись, но **не на удаление и перезапись** (append-only
или WORM-политика бакета) — иначе третий сценарий закрывается только наполовину. Шифрование —
до отправки (`age`/`gpg`), ключ хранится **не рядом с бэкапом** (`T-SH-05`).

Отдельно и без исключений: **`APP_ENCRYPTION_KEY` не хранится там же, где единственная копия
бэкапов**. Он не восстанавливается ниоткуда, и без него дамп бесполезен для секретов интеграций,
SMTP-паролей, GitHub-токенов и TOTP-секретов пользователей ([`install.md`](install.md) §2.2).

### 8.3 Роль, под которой снимается дамп

Напоминание, потому что это самая дорогая ошибка эксплуатации в этом продукте: **дамп снимается
под `backup_role` (с `BYPASSRLS`)**, а не под владельцем схемы. Под владельцем при
`FORCE ROW LEVEL SECURITY` `pg_dump` либо падает, либо — с флагом `--enable-row-security` —
**молча выгружает частичные данные**: файл есть, размер правдоподобный, восстановление проходит,
а внутри меньше, чем было.

Инфраструктурное следствие для этого документа: `backup_role` нужны `GRANT SELECT` на **каждую
таблицу, каждый лист партиции и каждую последовательность**, и раздаёт их `pnpm db:grants` после
каждой миграции и после каждого восстановления. Плюс `max_locks_per_transaction = 256` из 5.5 —
иначе `pg_dump` упрётся в блокировки на партициях. Полностью — в
[`backup-restore.md`](backup-restore.md), раздел 2.

### 8.4 Связь с RPO/RTO

| Профиль | RPO | RTO | Что требуется от инфраструктуры |
|---|---|---|---|
| **Базовый** (NFR-5 по умолчанию) | 24 ч | 4 ч | Ежесуточный дамп + зеркало объектов, внешнее хранилище на ~80 GB, **подготовленный запасной хост** |
| **Повышенный** | 1 ч | 2 ч | + `wal_level = replica` (включён с установки, см. 5.4), `archive_mode = on`, приёмник WAL, мониторинг `archive_command` |
| **Строгий** | минуты | < 1 ч | + потоковая репликация на второй хост + реплицированное объектное хранилище. Это уже двухсерверная конфигурация — считайте её стоимость отдельно |

**RTO определяется наличием подготовленного хоста, а не скоростью `pg_restore`.** Если
восстановление начинается со слов «сейчас закажем сервер», четыре часа превращаются в сутки.
Практический вывод для планирования инфраструктуры: под базовый профиль нужен либо второй
арендованный хост, либо провайдер, у которого машина той же конфигурации поднимается за минуты,
либо честно записанный RTO в сутки.

## 9. Мониторинг по минимуму

Цель — заметить проблему **до** пользователя, не разворачивая наблюдательный стек, сопоставимый
по весу с продуктом.

### 9.1 Что смотреть

| # | Сигнал | Откуда берётся | Порог | Почему именно он |
|---|---|---|---|---|
| 1 | **Свободное место на диске** | `df` по разделам данных | ⚠️ 80 %, 🔴 90 % | **Первая причина падения.** PostgreSQL при заполнении диска останавливает запись и выходит из этого состояния тяжелее прочих; MinIO перестаёт принимать загрузки |
| 2 | **Рост `pg_wal` при работающей архивации** | Размер каталога `pg_wal`; `pg_stat_archiver.last_failed_time` | любой провал архивации | Неудачный `archive_command` заставляет PostgreSQL **удерживать** сегменты WAL. Диск заполняется за часы, а продуктовые графики при этом идеальны |
| 3 | **Чекпоинты** | `pg_stat_checkpointer`: `num_requested` против `num_timed` | requested > 10 % от timed | Много «запрошенных» чекпоинтов = `max_wal_size` мал: лишний IO и рваный профиль записи |
| 4 | **Глубина очередей BullMQ** | `bullmq_queue_depth{queue}` на `/metrics` | растёт монотонно > 15 мин | Воркер упал, залип или не справляется. Очередь `outbox` — самая критичная |
| 5 | **`outbox_lag_seconds`** | `/metrics` | 🔴 > 60 с | Возраст самого старого необработанного события — единственный сводный признак «система отстаёт» |
| 6 | **DLQ** | `bullmq_jobs_total{status="failed"}` | > 0 за 15 мин | Задание исчерпало ретраи; дублируется строкой в `dead_letter` |
| 7 | **Отставание индексации поиска** | глубина очереди `search-index` | 🔴 > 5 мин | Порог из митигации риска R-05: поиск начинает молча отдавать устаревшие данные |
| 8 | **Расход токенов AI** | `AIUsageDaily`, `AIRateLimit.blockedAt` | ⚠️ 80 % лимита организации | Триггер эскалации риска R-07. Жёсткий стоп сработает сам, но администратор должен узнать раньше пользователя |
| 9 | **`/readyz` снаружи** | HTTP-проба с **другой** машины | 2 подряд неуспеха | См. ниже — это единственная проба, которая переживает падение хоста |
| 10 | **Память Redis** | `used_memory_rss` против `maxmemory` | ⚠️ 70 % | При `noeviction` (см. 9.3) исчерпание памяти превращается в отказы записи, а не в тихую потерю ключей |
| 11 | **Топ запросов** | `pg_stat_statements`, раз в неделю глазами | — | Не алерт, а регулярный обзор: `total_exec_time` сверху даёт список того, что стоит смотреть в `EXPLAIN` |

### 9.2 Чем это поднять, не разворачивая Prometheus-стек

Ответ зависит от размера, и он честно разный:

- **До ~10 человек:** cron-скрипт раз в 5 минут — `df`, `curl /readyz`, `curl /metrics` с
  выборкой трёх чисел, письмо при выходе за порог. Это 40 строк bash и ноль контейнеров.
  Метрики приложение уже отдаёт в формате Prometheus; парсить их grep'ом допустимо.
- **От ~25 человек:** локальный Prometheus с ретеншном 15 дней — это ~200 MB RAM и ~1 GB диска,
  то есть 1 % от рекомендованной конфигурации. Это уже оправдано: без исторического ряда
  невозможно ответить «стало медленнее, чем на прошлой неделе?». Grafana при этом
  **не обязательна** — Prometheus умеет alerting и собственный UI для разовых запросов.
- **Логи:** `docker compose logs` плюс ротация. Loki/ELK для одной инсталляции — это контейнеры
  и память, отобранные у PostgreSQL, ради поиска по логам, который делается `grep`. Обязательно
  при этом: ротация настроена (логи содержат `userId`/`organizationId` и считаются
  чувствительными — [`install.md`](install.md) §5.7).

**Отдельно и обязательно: внешняя проба.** Мониторинг, живущий на том же хосте, молчит ровно
тогда, когда хост умер. Нужна проба `/healthz` **снаружи** — с любой другой машины, включая
самую дешёвую VPS за пару евро или бесплатный внешний сервис. Это единственный элемент
наблюдаемости, который нельзя размещать на наблюдаемом хосте.

### 9.3 Один параметр, который надо выставить руками

```
redis-server --appendonly yes --appendfsync everysec \
             --maxmemory 512mb --maxmemory-policy noeviction
```

**`maxmemory-policy noeviction` — требование BullMQ, а не рекомендация.** При любой политике
вытеснения Redis под давлением памяти удаляет ключи очередей, и задания исчезают молча. BullMQ
это обнаруживает и пишет в лог `IMPORTANT! Eviction policy is …. It should be "noeviction"` —
предупреждение, которое легко потерять в шуме старта.

**Осознанное напряжение, которое стоит знать.** BullMQ рекомендует **отдельный** Redis под
очереди, а мы держим один экземпляр на всё: очереди, стримы Socket.IO, rate-limit, денилист
сессий, кеш AI-лимитов. При `noeviction` исчерпание памяти превратится в ошибки записи по всем
этим функциям сразу. Компенсация на одном хосте: `maxmemory` с многократным запасом к реальному
рабочему набору (< 200 MB против 512 MB), TTL на **всём** эфемерном (presence, rate-limit,
денилист) и `maxlen` на стримах Socket.IO, плюс сигнал № 10 из таблицы выше. Разделение на два
экземпляра Redis — правильный ход на шаге «несколько API-процессов» из раздела 7, а не раньше:
до этого он покупает лишний контейнер за отсутствующую проблему.
