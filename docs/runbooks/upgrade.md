# Runbook — обновление инсталляции

> **Статус: процедура спроектирована, релизов ещё нет.** Первая self-hosted поставка — в
> [EPIC-017](../../epics/epic-017-self-host-alpha/epic.md) (майлстоун M2). Раздел

## 1. Главное правило: backup first

**Не начинайте обновление без свежего проверенного бэкапа.** Не «вчерашнего», не «наверное есть», а
снятого прямо сейчас и проверенного на читаемость.

Причина не в перестраховке. Миграция схемы — единственная операция в обновлении, которая **необратима
средствами приложения**. Образ можно откатить одной командой; применённую миграцию — нельзя.
Если после `prisma migrate deploy` выяснилось, что данные повреждены, единственный путь назад —
восстановление из бэкапа.

```bash
# 1. снять бэкап (полная процедура — backup-restore.md)
./scripts/backup.sh              # или ваша команда pg_dump + mc mirror

# 2. убедиться, что файл не пустой и читается
ls -lh backups/$(date +%F)/
pg_restore --list backups/$(date +%F)/db.dump | head
```

Если бэкап снять не удалось — **обновление не начинается**. Нет точки отката — нет необратимого
изменения.

## 2. Перед обновлением

- [ ] Прочитан [`CHANGELOG.md`](../../CHANGELOG.md) **за все версии между вашей и целевой**, а не
      только за целевую. Пропущенные релизы могут содержать обязательные шаги.
- [ ] Отмечены разделы `### Security` — если среди них есть исправление, которое вас касается,
      обновление становится срочным.
- [ ] Выписаны **новые обязательные переменные окружения** (см. раздел 7). Их отсутствие приведёт к
      отказу старта нового образа — приложение падает громко, а не работает наполовину.
- [ ] Отмечены изменения в `docker-compose.yml` (новый сервис, изменившийся том, новый healthcheck) —
      их придётся перенести в ваш файл, если вы его правили.
- [ ] Проверено, что вы не перепрыгиваете мажорную версию через одну, если в CHANGELOG указано, что
      так нельзя (миграции по циклу expand→migrate→contract рассчитаны на последовательные релизы).
- [ ] Выбрано окно обслуживания. Обновление одноинстансной инсталляции требует простоя примерно на
      время рестарта плюс время миграций; долгие миграции указываются в CHANGELOG отдельно.
- [ ] Пользователи предупреждены, если простой заметный.

## 3. Порядок обновления

Порядок жёсткий: **бэкап → образы → роли БД → миграции → гранты → запуск → проверка**.
Менять местами нельзя.

```bash
# 0. бэкап — уже снят и проверен (раздел 1)

# 1. зафиксировать текущую версию, чтобы было куда откатываться
docker compose images | tee /tmp/bad-crm-images-before.txt
git rev-parse HEAD > /tmp/bad-crm-rev-before.txt

# 2. получить новую версию описания стека
git fetch --tags
git checkout vX.Y.Z

# 3. сверить .env с новым .env.example — добавить новые обязательные переменные
diff <(grep -o '^[A-Z_]*' .env.example | sort -u) \
     <(grep -o '^[A-Z_]*' .env | sort -u)

# 4. вытянуть образы (сеть отдельно от старта — так простой короче)
docker compose pull

# 5. остановить приложение, оставив БД работать
docker compose stop api worker

# 6. обновить роли БД — ДО миграций, идемпотентно, обязательно на каждом обновлении
pnpm db:bootstrap

# 7. применить миграции
docker compose run --rm migrate

# 7b. переприменить гранты по каталогу — идемпотентно, обязательно после КАЖДОЙ миграции
pnpm db:grants

# 8. поднять новую версию
docker compose up -d

# 9. проверить
curl -fsS https://crm.example.com/healthz
curl -fsS https://crm.example.com/readyz
docker compose logs --tail=100 api worker
```

**Почему роли обновляются до миграций — и почему это не «на всякий случай».**
Роли базы данных создаёт не миграция, а `packages/server/prisma/sql/00-bootstrap-roles.sql`. На
инсталляции этот файл отрабатывает **только через `initdb`, то есть один раз, на пустом томе**:
после этого ни `docker compose up`, ни `docker compose pull` его не запускают. Релиз, который вводит
новую роль, приезжает на существующую базу, где этой роли нет, — и миграция, ссылающаяся на неё,
падает.

Так уже произошло: миграция `20260729120000_auth_owner_and_lookup_functions` передаёт владение
функциями роли `app_auth_definer`, появившейся в том же релизе. Без шага 6 обновление отвечает

```
Error: P3018
Database error code: 42704
ERROR: role "app_auth_definer" does not exist
```

Хуже, чем «повторите команду»: Prisma записывает миграцию в `_prisma_migrations` как **failed**
(`finished_at IS NULL`), и все последующие `migrate deploy` — включая запуск уже после того, как
роли починили, — отвечают `P3009` и не применяют **ничего**. Выход требует ручного
`migrate resolve --rolled-back` (раздел 6).

Шаг безопасен и на инсталляции, где ничего не менялось. Файл идемпотентен: он создаёт только
отсутствующие роли, а атрибуты (`NOINHERIT`, `NOBYPASSRLS`, лимиты) и пароли из `.env` переприменяет
на каждом запуске — то есть заодно чинит роль, которую кто-то поправил руками. Проверяется тестами
`test/infra/upgrade-runbook.test.ts` (порядок шагов и роли, на которые ссылаются миграции) и
`packages/server/test/integration/db/upgrade-path.test.ts` (обновление базы, забутстрапленной
предыдущим релизом, на живом PostgreSQL).

**Почему приложение останавливается до миграций.** Старый код и новая схема совместимы не всегда;
цикл expand→migrate→contract это гарантирует только для соседних релизов. Остановка исключает
запись старым кодом во время изменения схемы.

**Почему гранты переприменяются отдельным шагом.** Миграция раздаёт права на таблицы, которые сама
создаёт, но права — это не только таблицы. Последовательность (`SERIAL`/`IDENTITY`) — отдельная
сущность со своими правами, и `INSERT` в таблицу падает без `USAGE` на неё; партиция наследует
политику RLS, но не гранты; объект, пересозданный `pg_restore`, приходит с правами того, кто делал
восстановление. `01-grants.sql` обходит **каталог**, а не список имён, поэтому не забывает ни один
из этих случаев — но только если его запустить. Пропущенный шаг проявляется не при обновлении, а
позже и в другом месте: на первой записи в таблицу, которой приложение не может воспользоваться.
Команда идемпотентна, лишний запуск ничего не портит.

**Почему миграции — отдельный одноразовый контейнер.** Он ходит в БД под ролью-владельцем схемы, а
приложение — под ролью без `BYPASSRLS`. Смешивать эти роли нельзя: у приложения не должно быть прав
менять схему, а у миграционной роли не должно быть постоянно работающего процесса.

## 4. expand → migrate → contract

Схема меняется по трёхшаговому циклу, растянутому на **три релиза**. Как администратор вы этого не
делаете руками — но должны понимать, почему обновляться нужно последовательно.

| Шаг | Что происходит | Свойство |
|---|---|---|
| **expand** | Добавляется новое: nullable-колонка, новая таблица, новый индекс `CONCURRENTLY` | Старый код продолжает работать |
| **migrate** | Деплоится код, который пишет и читает по-новому; фоновый job заполняет данные батчами | Обе версии кода работают со схемой |
| **contract** | В следующем релизе удаляется старое — колонка, таблица | Никто больше не читает старое |

Жёсткие запреты, действующие в проекте (проверяются `db-reviewer` и `selfhost-upgrade-checker`):

- `DROP COLUMN` / `DROP TABLE` в том же релизе, что и смена кода;
- переименование колонки (только add → backfill → drop, через три релиза);
- `CREATE INDEX` без `CONCURRENTLY` на таблицах с данными;
- блокирующий `ALTER TABLE … SET NOT NULL` без предварительного `CHECK … NOT VALID` +
  `VALIDATE CONSTRAINT`;
- новая таблица без RLS-политики.

**Практическое следствие для вас:** пропуск релизов ломает цикл. Если вы стоите на `1.2` и хотите на
`1.5`, обновляйтесь по одному минору, если в CHANGELOG явно не сказано, что перескок безопасен.

## 5. Откат

### 5.1 Откат кода без отката миграций (быстрый путь)

Работает, если новый релиз содержал только expand-миграции (в CHANGELOG это отмечается как
«обратно совместимая миграция»). Старый код не знает о новых колонках и просто их не трогает.

```bash
docker compose stop api worker
git checkout <предыдущий-тег>
docker compose pull
docker compose up -d
```

Проверить `/healthz`, `/readyz` и функциональность. Данные, записанные новой версией в новые
колонки, останутся в базе — они станут видны, когда вы обновитесь снова.

> **⚠️ Не запускайте `pnpm db:bootstrap` при откате.**
>
> Шаг 6 раздела 3 обязателен при **обновлении** и вреден при откате. Файл ролей переприменяет
> атрибуты на каждом запуске, поэтому версия из старого тега вернёт роли те атрибуты, которые были
> в ней, — включая те, что новый релиз снял намеренно. Конкретный пример из этого релиза: `app_auth`
> потеряла `BYPASSRLS`, и откат с бутстрапом вернёт его. Функционально ничего не сломается, и
> именно поэтому опасно: снятая защита возвращается молча.
>
> Роли, созданные новой версией, откату не мешают: лишняя роль ни на что не влияет. Если откат
> постоянный — снимайте её отдельно и осознанно.

### 5.2 Откат с восстановлением базы (полный путь)

Нужен, если миграция была contract-шагом (удалила колонку или таблицу) или повредила данные.
**Всё, что пользователи сделали после снятия бэкапа, будет потеряно** — оценивайте это прежде, чем
начинать.

```bash
# 1. остановить всё, кроме БД
docker compose stop api worker

# 2. восстановить базу из бэкапа (полная процедура — backup-restore.md)
#    обратите внимание: восстановление тоже идёт под ролью с BYPASSRLS
./scripts/restore.sh backups/<дата>/db.dump

# 3. вернуть предыдущую версию кода
git checkout <предыдущий-тег>
docker compose pull
docker compose up -d

# 4. сверить число строк по крупным таблицам с ожидаемым (см. backup-restore.md)
```

Файлы в MinIO при откате базы **не откатываются автоматически**. Объекты, загруженные после бэкапа,
останутся в хранилище, но ссылок на них в базе не будет — это «мусор», а не повреждение. Обратная
ситуация опаснее: если вы восстанавливаете и MinIO тоже, файлы, загруженные после бэкапа, исчезнут,
а записи о них в восстановленной базе будут отсутствовать — консистентно.

## 6. Что делать при неудачной миграции

### Симптом: миграция упала с ошибкой

1. **Не запускайте её повторно вслепую.** Прочитайте текст ошибки — Prisma указывает конкретный шаг.
2. Проверьте состояние: `docker compose run --rm migrate npx prisma migrate status`.
3. Возможные состояния:
   - **Миграция не применялась вовсе** (упала на первом шаге) — база в исходном состоянии. Откатите
     код на предыдущую версию, поднимите старый образ, всё работает. Заведите issue с текстом ошибки.
   - **Миграция применена частично** — PostgreSQL выполняет DDL транзакционно, поэтому обычно откат
     происходит сам; исключения — `CREATE INDEX CONCURRENTLY`, который не может быть в транзакции и
     мог оставить невалидный индекс. Проверьте:
     ```sql
     SELECT indexrelid::regclass, indisvalid FROM pg_index WHERE NOT indisvalid;
     ```
     Невалидный индекс дропается вручную (`DROP INDEX CONCURRENTLY …`) и создаётся заново.
   - **Миграция помечена как failed в `_prisma_migrations`, но `applied_steps_count = 0`** — она
     упала на первом же операторе, база не тронута. Это единственный случай, когда `resolve` честен:

     ```sql
     SELECT migration_name, applied_steps_count, finished_at, rolled_back_at
     FROM _prisma_migrations ORDER BY started_at DESC LIMIT 3;
     ```

     Пока строка не разобрана, `migrate deploy` отвечает **`P3009`** и не применяет ничего — даже
     после того, как причина устранена. Порядок: сперва устранить причину, потом отметить откат,
     потом повторить:

     ```bash
     pnpm db:bootstrap                                        # если причина — отсутствующая роль
     docker compose run --rm migrate \
       npx prisma migrate resolve --rolled-back <имя-миграции>
     docker compose run --rm migrate
     ```

     Самая частая причина в этом продукте — пропущенный шаг 6 раздела 3: миграция сослалась на роль,
     которой на инсталляции нет (`ERROR: role "…" does not exist`, `P3018`, код `42704`).

     > **⚠️ Если упавшая миграция строила индекс `CONCURRENTLY` — проверьте валидность до повтора.**
     > Такая миграция несёт `CREATE INDEX CONCURRENTLY IF NOT EXISTS`, и после сорванной сборки в
     > базе остаётся индекс в состоянии **INVALID**. Повтор напечатает `already exists, skipping` и
     > **завершится успешно** — с невалидным индексом, которым планировщик не пользуется. Это не
     > гипотеза: единственный такой индекс сегодня обслуживает отзыв семейства сессий, то есть
     > реакцию на украденный токен, и без него запрос уходит в последовательное сканирование
     > организации. Ни один тест этого не увидит — контейнер в наборе всегда свежий.
     >
     > ```sql
     > SELECT c.relname FROM pg_index i JOIN pg_class c ON c.oid = i.indexrelid WHERE NOT i.indisvalid;
     > ```
     >
     > Нашли — вылечите **до** повтора миграции: `REINDEX INDEX CONCURRENTLY <имя>;` либо
     > `DROP INDEX CONCURRENTLY <имя>;` (тогда повтор построит заново).
   - **Миграция помечена как failed и `applied_steps_count > 0`** — часть операторов применилась,
     база в промежуточном состоянии. Здесь честный путь один: восстановление из бэкапа (5.2). Ручное
     «доправление» схемы приводит к тому, что следующая миграция не сойдётся, а `resolve
     --rolled-back` здесь — ложь: он говорит «ничего не применилось», хотя применилось.

### Симптом: миграция прошла, но приложение не стартует

Смотрите логи `api`. Чаще всего это **отсутствие новой обязательной переменной окружения** —
приложение падает при разборе конфигурации с указанием конкретной переменной. Добавьте её и
перезапустите; откат базы не нужен.

### Симптом: миграция идёт слишком долго

Долгие миграции помечаются в CHANGELOG. Если миграция идёт дольше ожидаемого, **не убивайте
контейнер** — прерванная миграция оставляет базу в неопределённом состоянии. Посмотрите, что
происходит:

```sql
SELECT pid, state, wait_event_type, wait_event, left(query, 120), now() - query_start AS duration
FROM pg_stat_activity WHERE state <> 'idle' ORDER BY duration DESC;
```

Если миграция ждёт блокировку (`wait_event_type = 'Lock'`), её держит другое соединение — убедитесь,
что `api` и `worker` действительно остановлены.

### После любого неудачного обновления

- Зафиксируйте, что произошло: версия «из», версия «в», текст ошибки, что сделали.
- Заведите issue — неудачная миграция в self-host продукте касается не только вас. Целевая метрика
  проекта: **≥ 99 % миграций без ручного вмешательства** (риск R-10 в PRD).
- Если вы подозреваете компрометацию, а не просто сбой, переходите к [`incident.md`](incident.md).

## 7. Переменные окружения по версиям

**Шаблон раздела — заполняется каждым релизом.** Правило: если релиз вводит новую переменную,
меняет её обязательность, значение по умолчанию или формат — здесь появляется строка. Отсутствие
строки блокирует релиз на ревью агента `selfhost-upgrade-checker`.

Формат строки: переменная · обязательная или опциональная · значение по умолчанию · что делать
администратору · что будет, если не сделать.

### EPIC-009 — наблюдаемость

| Переменная | Статус | По умолчанию | Что сделать | Если не сделать |
|---|---|---|---|---|
| `METRICS_ENABLED` | новая, опциональная | `false` | Ничего. Включать, только если есть кому скрести `/metrics` | Метрики не собираются, endpoint не смонтирован — остальное работает |
| `METRICS_TOKEN` | новая, обязательна **при** `METRICS_ENABLED=true` | нет | Сгенерировать ≥ 32 случайных символов и положить в `.env` вместе с включением метрик | Приложение не стартует: конфигурация «метрики включены без токена» отвергается схемой |
| `OTEL_TRACES_SAMPLER_ARG` | новая, опциональная | `1.0` в dev, `0.1` в production | Ничего. Менять, только если трейсов слишком много или слишком мало | Действует значение по умолчанию |

Токен передаётся скребком как `Authorization: Bearer <token>`. Неверный токен получает **404**, а не
401 — вызывающий без токена не может даже подтвердить, что endpoint здесь есть.

### vX.Y.Z — YYYY-MM-DD *(шаблон, скопировать при релизе)*

| Переменная | Статус | По умолчанию | Что сделать | Если не сделать |
|---|---|---|---|---|
| `EXAMPLE_VAR` | новая, обязательная | нет | Сгенерировать и добавить в `.env` до обновления | Приложение не стартует, в логе — имя переменной |
| `OTHER_VAR` | новая, опциональная | `false` | Ничего; включить при необходимости | Функция выключена, остальное работает |
| `OLD_VAR` | удалена | — | Удалить из `.env` | Игнорируется; предупреждение в логе при старте |
| `CHANGED_VAR` | изменился формат | — | Привести к новому формату (пример: …) | Отказ старта с ошибкой разбора конфигурации |

### Миграция `20260730120000_organization_owner_not_null` — что она проверяет

`organizations.owner_id` становится `NOT NULL`. Шаги идут в порядке
`CHECK … NOT VALID` → `VALIDATE CONSTRAINT` → `SET NOT NULL`, каждый под `lock_timeout = '3s'`;
`VALIDATE` сканирует таблицу под `SHARE UPDATE EXCLUSIVE`, то есть чтение и запись продолжаются.

**Если у какой-то организации владелец не проставлен, `VALIDATE CONSTRAINT` упадёт** — и это
намеренно: он назовёт таблицу и колонку, а не превратит нарушение в инвариант задним числом. Что
делать:

```sql
-- 1. Посмотреть, о каких организациях речь.
SELECT id, slug, created_at FROM organizations WHERE owner_id IS NULL;

-- 2. Для каждой — назначить владельцем активного пользователя ЭТОЙ организации.
--    Составной ключ (id, owner_id) → users (organization_id, id) не даст назвать чужого.
UPDATE organizations o
   SET owner_id = (SELECT u.id FROM users u
                    WHERE u.organization_id = o.id AND u.deleted_at IS NULL AND u.status = 'ACTIVE'
                    ORDER BY u.created_at LIMIT 1)
 WHERE o.id = '<organization-id>';
```

Если активных пользователей в организации нет вовсе, назначать некого: такая организация
администрируема быть не может, и решение о ней (архивировать или завести владельца вручную) —
операционное. После правки повторите обновление; частично применённая миграция помечена
`applied_steps_count > 0`, разбор — раздел 6.

Заодно оба действия внешнего ключа переводятся в `NO ACTION`: `ON DELETE SET NULL` против `NOT NULL`
мог только падать, а `ON UPDATE CASCADE` на неизменяемом uuid писал бы обе колонки пары. Следствие
для эксплуатации: **пользователя, владеющего организацией, теперь нельзя удалить физически** — сперва
передайте владение.

**Контрольные суммы миграций.** До первого релиза файлы миграций ещё правятся — в EPIC-006 у трёх
из них изменилась преамбула таймаутов. Для инсталляции это означало бы `P3019` (checksum mismatch)
и остановку обновления, поэтому: **после первого релиза файл применённой миграции неизменяем**, и
любая правка приезжает новой миграцией. Разработчику с локальной базой, где старая версия уже
применена, нужен `pnpm docker:reset`.

**Изменившееся поведение `SMTP_URL` (EPIC-006).** На `smtp://` к любому хосту, кроме loopback,
теперь по умолчанию требуется STARTTLS. Инсталляция с релеем без TLS на отдельном хосте **перестанет
отправлять письма**, пока в строку подключения не будет дописано `?requireTLS=false` — осознанно.
Причина умолчания: письмо сброса пароля несёт учётные данные, а конверт называет их владельца, тогда
как обычный `smtp://` договаривается о TLS оппортунистически — релей, не анонсирующий STARTTLS (или
активная атака, вырезающая анонс), получает всё это открытым текстом. `smtps://` не затронут, dev с
Mailpit на `localhost` — тоже.

**Изменившееся требование к существующей переменной.** `DATABASE_URL` теперь проверяется при
старте: инсталляция, где она указывает на роль-владельца схемы или на суперпользователя, **не
поднимется**. Если вы когда-то упростили себе жизнь и подключили приложение ролью-владельцем —
это обновление вас остановит, и это намеренно: такая роль обходит изоляцию арендаторов.
