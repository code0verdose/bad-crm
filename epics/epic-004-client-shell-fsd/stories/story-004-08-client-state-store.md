# STORY-004-08 — Слой клиентского состояния: zustand и граница вокруг него

**Как** разработчик клиента **я хочу** один принятый механизм для состояния, которое не серверное и
не помещается в URL, **чтобы** каждый следующий стор не был отдельным изобретением подписки, а
«это в Query или в сторе» не решалось заново в каждом ревью.

Основание — [ADR-0026](../../../docs/architecture/adr/0026-client-state-zustand.md) и правило 16
`rules/frontend-fsd.mdc`. Документы уже написаны; эта история приводит к ним код.

## Почему сейчас, а не в M3

Сегодня глобальный стор ровно один — сессия таба, — и он написан руками. Второй появляется в
**EPIC-015** (очередь загрузки файлов: прогресс по файлу, переживающий переход между экранами) — то
есть в текущем майлстоуне. Дальше их становится пять: жест drag-and-drop (EPIC-018), непрочитанные
и typing (M5), активный таймер в шапке (M6), unlock хранилища (M7). Каждый самописный — это ещё
`Set` слушателей, цикл уведомления и пара тестов на то, что `StrictMode` не ломает отписку.

## Acceptance (Given/When/Then)

1. **Зависимость добавлена и измерена.**
   Given бюджет initial JS 250 kB gzip и занятые 247.8 kB;
   When в `packages/client` добавлен `zustand@5`;
   Then `pnpm --filter @bad-crm/client build` зелёный, `size-limit` показывает **не более 249 kB**,
   и фактическая дельта записана в историю (ожидание — +0.75 kB).
   **Факт: 247.75 → 247.91 kB, +0.16 kB.** Меньше ожидаемого, потому что вместе с zustand ушли
   самописный `Set` слушателей, цикл уведомления и импорт `useSyncExternalStore`.

2. **Сессия переехала без изменения поведения.**
   Given `units/auth/service/stores/auth-session.store.ts` на самописном external store;
   When он переписан на `createStore` из `zustand/vanilla`;
   Then публичный API стора (`read`/`subscribe`/`bootstrap`/`start`/`end`) сохранён, все
   существующие тесты стора и `use-bootstrap-session.hook` проходят **без правок ожиданий**, а
   `app/router-auth.util.ts` продолжает читать статус синхронно из `beforeLoad`.

3. **Мемоизация `bootstrap` сохранена ровно как была.**
   Given ротация, которая не дошла до сервера (`unavailable`) или отклонилась;
   When вызывается `bootstrap()`;
   Then состояние остаётся `unknown`, промис-мемо **освобождается**, следующий вызов спрашивает
   снова — поведение, описанное в комментарии текущего стора как «реальный инцидент в ожидании».

4. **Хук подписки использует библиотечный `useStore`.**
   Given `use-bootstrap-session.hook.ts` на `useSyncExternalStore`;
   When он переписан;
   Then он вызывает `useStore(authSession, selector)`, ручного `useSyncExternalStore` в клиенте не
   остаётся, и `test/architecture/state-boundaries.test.ts` это подтверждает.

5. **Граница закреплена тестом, а не только текстом.**
   Given правило 16 `rules/frontend-fsd.mdc`;
   When запускается `test/architecture/state-boundaries.test.ts`;
   Then он падает на: `*.store.ts` вне `units/*/service/stores/`; импорте `zustand` за пределами
   `units/*/service/**` (стор создаёт его, хук подписывает — обоим можно, виджету нет); импорте
   `@tanstack/react-query` внутри `*.store.ts` (серверные данные в сторе); `create(` вместо
   `createStore(` в файле стора; оставшемся ручном `useSyncExternalStore`.
   **CONTROL:** тест обязан иметь фикстуру, на которой он падает, — иначе он проходит и на пустом
   списке файлов.

6. **Ключевой материал по-прежнему никуда не переезжает.**
   Given инвариант 3 и `rules/e2ee-crypto.mdc` §5;
   When добавляется стор;
   Then `persist` не подключается ни к одному стору этой истории, а access-токен остаётся модульной
   переменной в `units/auth/lib` (осознанное исключение, записанное в правило).

7. **Негативный сценарий — стор не становится вторым кешем.**
   Given разработчик добавляет в стор поле, приходящее из нашего API;
   When запускается линт и архитектурный тест;
   Then сборка красная с сообщением, называющим правило 16, а не «зелёная, но неправильная».

## Как оно оказалось устроено

Одна деталь разошлась с наивным ожиданием и стоит того, чтобы быть записанной: **операции живут не в
состоянии стора**, хотя большинство примеров zustand показывает обратное. Actions-in-state удобны
внутри React — один `useStore` отдаёт компоненту и значение, и способ его изменить, — но главный
читатель этого стора вообще не рендерится, а `subscribe` будит подписчика на любое поле состояния.
Состояние здесь — одно поле `session`; `bootstrap`/`start`/`end` — функции на возвращаемом объекте,
собранные `Object.assign` поверх `StoreApi`. Публичный API стора от этого не изменился ни на символ,
и ни один существующий тест не потребовал правки ожиданий.

Промис `bootstrap` тоже остался **вне** состояния: его никто не рендерит, а замена его в состоянии
разбудила бы каждого подписчика ради изменения, которого никто не видит.

Граница «zustand только в `service/stores`» из первоначальной формулировки оказалась на один шаг
строже, чем нужно: `useStore` по правилу 4 обязан жить в `service/hooks` — это публичное API юнита
для `ui`. Правило 16, тест и эта история поправлены согласованно: `zustand` называется внутри
`units/*/service/`, виджет берёт хук.

## Что **не** входит

- Очередь загрузки файлов — её стор пишется в EPIC-015 уже по готовому правилу.
- Черновик матрицы ролей (`use-role-matrix-draft.hook.ts`) **не переезжает**: он живёт и умирает с
  экраном, а это `useState` по таблице правила 16. Перенос в стор был бы ровно тем нарушением, от
  которого эта история ставит защиту.
- Access-токен не переезжает (см. п. 6).
- Чанкование `pages-*.js` — отдельная работа; после этой истории свободного бюджета остаётся ~1.4 kB,
  и до M3 его надо расширить независимо.
