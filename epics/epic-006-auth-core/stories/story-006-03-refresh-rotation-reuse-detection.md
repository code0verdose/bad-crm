# STORY-006-03 — Ротация refresh и обнаружение повторного использования

**Как** администратор системы **я хочу** чтобы украденный refresh-токен обнаруживался и обесценивал
всю цепочку сессий **чтобы** компрометация не оставалась незамеченной на месяц.

## Acceptance (Given/When/Then)

- **Given** валидный refresh в cookie **When** вызываю `POST /api/v1/auth/refresh` **Then** старая сессия помечается использованной, создаётся новая с тем же `family_id` и `rotated_from_id` на предыдущую, выдаются новый access и новый refresh-cookie.
- **Given** уже использованный (отозванный) refresh **When** он предъявляется повторно **Then** отзывается **всё семейство** одним `UPDATE ... WHERE family_id = $1`, текущий запрос получает 401, в аудит пишется событие `refresh_reuse_detected`, пользователю ставится в очередь уведомление по email.
- **Given** refresh с истёкшим `expires_at` **When** он предъявляется **Then** 401 `unauthenticated`, семейство не отзывается (это не признак кражи), cookie очищается.
- **Given** refresh, не существующий в БД **When** он предъявляется **Then** 401 без раскрытия причины; попытки учитываются rate-limiter'ом.
- **Given** два параллельных запроса на refresh с одним и тем же токеном (гонка вкладок) **When** оба доходят до сервера **Then** ровно один получает новую пару, второй — 401; семейство не отзывается ошибочно, поскольку ротация выполняется атомарно (`UPDATE ... WHERE id = $1 AND revoked_at IS NULL RETURNING`), и проигравший запрос отличается от настоящего reuse по признаку «токен отозван меньше N секунд назад тем же семейством» — поведение зафиксировано тестом.
- **Given** запрос на refresh **When** проверяется заголовок `Origin` **Then** запрос с чужого origin отклоняется — cookie сама по себе не авторизует ничего, кроме `/refresh`.
- **Given** отозванная сессия **When** её access-токен ещё не истёк **Then** он отклоняется по денилисту `sid` в Redis на остаток TTL.
- **Given** успешная ротация **When** смотрю БД **Then** цепочка `rotated_from_id` позволяет восстановить историю, а отзыв выполняется одним индексным апдейтом по `family_id`, а не рекурсивным обходом.

## Что осталось по требованию `rules/security.mdc` п. 8

Правило требует при обнаружении reuse **трёх** действий: отозвать семейство, записать событие в
аудит, уведомить пользователя письмом. Состояние на 2026-07-29 — честно, без округления вверх:

| Требование | Состояние | Чем заблокировано |
|---|---|---|
| Отзыв всего семейства | ✅ сделано | — |
| Событие, отличимое машинно | ✅ сделано — поле `event` в лог-линии, уровень `warn`, закрытый каталог `SECURITY_EVENTS` | — |
| Запись в `AuditLog` | ❌ **нет** | таблицы `AuditLog` нет в `prisma/schema.prisma`; её вводит эпик аудита. Заводить её из этой истории означало бы спроектировать схему аудита мимоходом и в одиночку |
| Письмо пользователю | ❌ **нет** | `MailPort` и `createMailer` написаны (STORY-006-08), но в композиционном корне не собраны; кроме того `rules/outbox.mdc` п. 2 запрещает SMTP-вызов из транзакции — письмо должно уходить через очередь `mail` из outbox (ADR-0021), а очереди ещё нет. Адреса получателя в `AuthSessionRecord` тоже нет: его пришлось бы дочитывать под tenant-скоупом |

**Практическое следствие для эксплуатации до закрытия этих двух пунктов:** обнаружение кражи видно
только в потоке логов и живёт до их ротации. Пока `AuditLog` нет, алерт на `event =
"refresh_reuse_detected"` в агрегаторе логов — обязательная часть установки, а не рекомендация.
