# STORY-006-08 — Сброс пароля по email с одноразовым токеном

**Как** разработчик (пользователь продукта) **я хочу** восстановить доступ по ссылке из письма
**чтобы** забытый пароль не требовал обращения к администратору инсталляции.

## Acceptance (Given/When/Then)

- **Given** существующий email **When** я запрашиваю сброс **Then** на почту уходит письмо с одноразовой ссылкой; в БД сохраняется только хеш токена, TTL — 60 минут.
- **Given** несуществующий email **When** я запрашиваю сброс **Then** ответ API идентичен успешному (текст «если адрес зарегистрирован, письмо отправлено»), письмо не отправляется — существование аккаунта не раскрывается.
- **Given** валидная ссылка **When** я открываю `/reset-password/$token` и задаю новый пароль **Then** пароль меняется, токен помечается использованным, **все** сессии пользователя отзываются, происходит автоматический вход или переход на `/login` с сообщением об успехе.
- **Given** уже использованный токен **When** я открываю ссылку повторно **Then** показывается сообщение о недействительности ссылки с предложением запросить новую; пароль не меняется.
- **Given** просроченный токен **When** я открываю ссылку **Then** тот же исход, что и при использованном, — без раскрытия, какой именно случай произошёл.
- **Given** новый пароль, не удовлетворяющий политике **When** я отправляю форму **Then** 422 с ошибкой по полю, токен остаётся действительным до истечения TTL.
- **Given** dev-окружение без реального SMTP **When** запрошен сброс **Then** письмо видно в Mailpit, ссылка рабочая.
- **Given** production без настроенного `SMTP_URL` **When** запрошен сброс **Then** операция завершается понятной ошибкой (`mail_not_configured`), а не молча «успехом» без письма.
- **Given** повторные запросы сброса для одного адреса **When** их больше лимита **Then** срабатывает rate limiting, ответ по-прежнему не раскрывает существование аккаунта.
