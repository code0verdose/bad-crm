**Закрыта 2026-08-04, с записанными границами проверки.**

Сделано: `infrastructure/tracing/tracing.factory.ts` — SDK стартует **только** при заданном
`OTEL_EXPORTER_OTLP_ENDPOINT`; инструментирование http, express, Prisma и ioredis перечислено
поимённо, а не через `auto-instrumentations-node` (тот тянет ~40 пакетов ради библиотек, которых
здесь нет, и каждая — поверхность цепочки поставки ради подсистемы, выключенной по умолчанию);
`ParentBasedSampler` поверх `TraceIdRatioBasedSampler`; `OTEL_TRACES_SAMPLER_ARG` с клампом вместо
отказа старта; `traceId` в каждой строке лога, когда span активен, и ничего, когда нет.

**Порядок в точке входа — главное здесь.** OpenTelemetry патчит модули **в момент их импорта**.
Статический импорт фабрики процесса затянул бы express, Prisma и ioredis раньше нашего кода, и SDK,
запущенный внутри неё, не пропатчил бы ничего — трейс без вложенных spans, тихо и правдоподобно.
Поэтому `main.ts` разбирает окружение (модуль, который ничего из этого не тянет), стартует SDK и
только затем берёт приложение динамическим импортом. Разобранное окружение передаётся дальше, так
что конфигурация читается по-прежнему один раз.

**Проверено:** `tracing.factory.ts` покрыт на 100 % (12/12 строк, 8/8 ветвей), 1177 тестов сервера,
покрытие пакета в допуске базовой линии. Тест на корреляцию лога и трейса **проверен на падение** —
с убранным полем он краснеет.

**Границы:** сквозная структура spans (HTTP → express → Prisma → Redis) на реальном коллекторе не
проверялась: для этого нужен поднятый OTLP-приёмник. *Уточнено 2026-08-30: вторая половина причины
(«`packages/e2e` — пустая заготовка») больше не верна — харнесс работает и гоняет сценарии против
поднятого стека (EPIC-010). Не хватает только приёмника: коллектора нет ни в `docker-compose.yml`,
ни в джобе `end-to-end`.*
Проверено то, что проверяемо без коллектора: включение/выключение, сэмплирование, отсутствие
накладных расходов при выключенном состоянии, корреляция.

**Не удалось прогнать полный `turbo run typecheck lint build test` и репозиторные тесты начисто:** в
рабочем дереве идёт параллельная незакоммиченная работа над `packages/landing` (EPIC-047), её
`index.html` ссылается на ещё не созданный `src/app/main.tsx`, и два репозиторных теста ссылаются на
её CSS. Сборка и `//#stylelint` падают на этом, а не на трассировке. Проверка велась по пакетам
`server`/`client`/`shared`.


# STORY-009-04 — OpenTelemetry-трейсы

**Как** администратор системы **я хочу** при необходимости включить распределённые трейсы
**чтобы** видеть, где именно уходит время медленного запроса, и при этом не платить за это
ресурсами на маленькой инсталляции.

## Acceptance (Given/When/Then)

- **Given** пустой `OTEL_EXPORTER_OTLP_ENDPOINT` **When** приложение стартует **Then** трассировка не инициализируется, spans не создаются, накладных расходов нет; логи и метрики работают.
- **Given** заданный `OTEL_EXPORTER_OTLP_ENDPOINT` **When** приложение обрабатывает запрос **Then** создаётся span HTTP-запроса с вложенными spans Express-маршрута, запросов Prisma и обращений к Redis.
- **Given** активный span **When** пишется строка лога **Then** в ней присутствует `traceId`, а в span-атрибутах — `requestId`: из лога можно перейти в трейс и обратно.
- **Given** span запроса к БД **When** он экспортируется **Then** в атрибутах нет значений параметров запроса и персональных данных — только имя операции и модель.
- **Given** production **When** применяется сэмплирование **Then** используется `parentbased_traceidratio` 10 %, в dev — 100 %; значение настраивается переменной окружения.
- **Given** недоступный OTLP-коллектор **When** приложение работает **Then** экспорт ошибок логируется с ограничением частоты и не влияет на обработку запросов; приложение не падает.
- **Given** фоновая задача **When** она выполняется **Then** её span связан с исходным HTTP-запросом через контекст, перенесённый в payload задачи.
