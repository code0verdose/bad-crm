# STORY-010-02 — Seed-скрипт и фикстуры двух организаций

**Как** разработчик Bad CRM **я хочу** воспроизводимые демо-данные с двумя организациями и
пользователями разных ролей **чтобы** e2e-сценарии и проверки изоляции опирались на известное
состояние, а не на случайные остатки от предыдущих прогонов.

## Acceptance (Given/When/Then)

- **Given** чистая БД **When** выполняю `pnpm db:seed` **Then** создаются две организации (A и B) с разными `slug`, в каждой — владелец, администратор, тимлид и разработчик со стабильными email вида `owner@org-a.local`.
- **Given** уже заполненная БД **When** выполняю `pnpm db:seed` повторно **Then** дублей не появляется: скрипт идемпотентен (`upsert` по стабильным идентификаторам), итоговое состояние совпадает с первым прогоном.
- **Given** сид-данные **When** смотрю пароли пользователей **Then** они заданы фиксированными значениями только для локального и тестового окружения; запуск сида при `NODE_ENV=production` без явного флага подтверждения отклоняется.
- **Given** организация A **When** смотрю её данные **Then** они не пересекаются с организацией B ни по одному идентификатору — это основа проверки изоляции.
- **Given** сид **When** он выполняется **Then** он проходит через те же use-cases и репозитории, что и приложение (или через API), а не вставляет строки в обход правил и RLS.
- **Given** e2e-прогон **When** он начинается **Then** состояние приводится к известному (сброс и повторный сид либо создание собственных данных тестом), и тесты не зависят от порядка выполнения.
- **Given** сид **When** он завершается **Then** он печатает сводку: организации, пользователи, роли — для использования в фикстурах и отладке.

## Что сделано (запись истории)

- `packages/server/scripts/seed-data.constant.ts` — декларация фикстуры; `scripts/seed.util.ts` —
  гейт окружения, сам сид и рендер сводки; `scripts/seed.ts` — обвязка (окружение → зависимости →
  печать, три кода выхода: 0 сделано, 1 отказано гейтом, 2 не смогло запуститься).
- **Идемпотентность читается из конфликта, а не из выборки** — и это свойство схемы, а не приём.
  `slug` уникален глобально, но `SELECT ... WHERE slug = $1` идёт под RLS: вне собственного скоупа
  он возвращает пусто и для существующей организации, и для свободного имени. Единственное место,
  которое знает правду, — уникальный индекс, а `organization_already_exists` — то, как он это
  сообщает. Доказано подсадкой: без перехвата конфликта тест «дважды — то же состояние» падает.
- Сид идёт через **тот же** `BootstrapOrganizationUseCase`, что и регистрация, то есть внутри
  `withTenant` и под теми же политиками. Интеграционный тест проверяет это в обе стороны: владелец
  виден в скоупе своей организации и не виден в чужом (с положительным контролем).

### Отклонения от задачи, принятые осознанно

- **Скрипт живёт в `scripts/`, а не в `prisma/seed.ts`.** `prisma/**` не входит ни в
  `tsconfig.test.json`, ни в ESLint-глобы — сид там отгружался бы не типизированным и не
  линтуемым. Прецедент рядом: `scripts/check-rls.ts`. Prisma резолвит сид по команде, путь свободен.
- **Ролей нет: сеются две организации и два владельца.** У `users` нет колонки роли — она приходит
  с [EPIC-011](../../epic-011-rbac-permissions/epic.md), а `organizations.owner_id` сегодня
  единственная различимая связь. `admin@`/`lead@`/`dev@` с правами, равными владельцу, но
  названные иначе, — это фикстура, которая врёт; они появятся вместе с ролями в
  [STORY-010-03](story-010-03-storage-state-auth-fixtures.md). Формулировка acceptance про четыре
  роли закрыта в части, которую продукт умеет выразить.
- **Хелпер создания данных через публичный API не написан.** Публичный API сегодня умеет создавать
  только организацию (регистрация); хелпер «создай себе сущность» был бы хелпером ни для чего. Он
  появляется вместе с первой доменной сущностью (M3).
- **Фикстура для e2e — копия, а не общий модуль.** `packages/e2e` не имеет права импортировать
  исходники продукта; копию стережёт гейт `test/e2e/seed-fixture-parity.test.ts`, который читает
  обе декларации и падает при расхождении (с контролем на непустоту).
- **Гейт окружения — allow-list, а не запрет `production`.** `staging`, `preview` и незаданный
  `NODE_ENV` (значение контейнера, запущенного без него) тоже отвергаются: deny-list отвергает
  только те имена, о которых кто-то вспомнил.
