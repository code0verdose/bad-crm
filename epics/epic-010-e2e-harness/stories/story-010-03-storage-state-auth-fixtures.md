# STORY-010-03 — Вход через storageState и фикстуры под ролью

**Как** разработчик Bad CRM **я хочу** запускать сценарий сразу под нужной ролью **чтобы** не
тратить по 3 секунды на прокликивание формы логина в каждом из десятков будущих тестов.

## Acceptance (Given/When/Then)

- **Given** глобальная подготовка прогона **When** она выполняется **Then** для каждой роли (владелец, администратор, тимлид, разработчик) в обеих организациях один раз выполняется вход через API, и состояние сессии сохраняется в файл `storageState`.
- **Given** фикстура `test.use({ storageState: asOwnerOfOrgA })` **When** сценарий стартует **Then** пользователь уже аутентифицирован: форма логина не открывается, первая же навигация ведёт на защищённый маршрут.
- **Given** истёкшее состояние сессии между прогонами **When** сценарий стартует **Then** подготовка перевыпускает `storageState`, а не падает с непонятным редиректом на `/login`.
- **Given** тест, проверяющий саму форму логина **When** он выполняется **Then** он запускается без `storageState` (анонимный контекст) — это единственное место, где форма прокликивается.
- **Given** сценарии под разными ролями **When** они выполняются параллельно **Then** их состояния не смешиваются: у каждой роли отдельный файл состояния и отдельный browser context.
- **Given** refresh-cookie в `storageState` **When** файл сохраняется **Then** он размещается во временном каталоге прогона, попадает в `.gitignore` и не выгружается в артефакты CI.
- **Given** сценарий, которому нужен «свежий» пользователь **When** он выполняется **Then** доступна фикстура, создающая пользователя через API и удаляющая его после теста.

> `packages/e2e/fixtures/session.fixture.ts`: ротация refresh с обнаружением повторного
> использования делает сохранённую cookie **одноразовой**, поэтому второй контекст с тем же файлом
> (повтор, параллельный воркер) выглядит как кража и уносит семью. Замерено в CI 2026-08-05: первая
> попытка доходила до `/dashboard`, повтор уходил на `/login`. Теперь сессия чеканится **на тест**
> через API (`mintSession`), и это стоит десятки миллисекунд против секунд на форму. Спека
> `tests/auth/storage-state.spec.ts` осталась и проверяет то же свойство: минтованная сессия
> открывает защищённый маршрут, анонимный контекст уходит на `/login?redirect=…`.
> Следствие для acceptance: критерии про файл `storageState`, его перевыпуск и его каталог в
> `.gitignore` описывают отменённый механизм — переписывать их эта сверка не стала, но принимать
> историю по ним нельзя.

**Две ошибки, пойманные первым же прогоном:**

1. **Каталог состояния ключевался по `process.pid`.** `globalSetup` и каждый воркер — разные
   процессы, поэтому воркеры искали файлы по другому пути и не находили ничего. Передача пути через
   переменную окружения — то, как это делает сам Playwright; она выставляется до запуска воркеров.
2. **Сохранённая сессия не возобновлялась в браузере, и симптом врал.** Тест видел редирект на
   `/login` — читается как «гард сломан» или «фикстура не загрузилась». На деле `POST /auth/refresh`
   защищён проверкой Origin (единственный эндпоинт, который авторизует одна лишь cookie), а клиент
   при занятом порте 5173 поднялся на 5174. Измерено: `Origin: http://localhost:5174` против
   инсталляции с `APP_URL=http://localhost:5173` → 401 `unauthenticated`; с `5173` → 200.
   Теперь `createSessions` делает то же обновление, что делает браузер, **с origin браузера**, и
   падает с точной формулировкой вместо загадочного редиректа. Побочно это оставляет сохранённую
   cookie свежей: refresh ротирует токен, и проверка после сохранения записала бы уже потраченный —
   первый же сценарий словил бы обнаружение повторного использования и отозвал всё семейство.

**Чего нет и почему:** фикстур ролей (`asAdminOfOrgA` и далее) — ролей в модели нет до
[EPIC-011](../../epic-011-rbac-permissions/epic.md), см. запись в
[STORY-010-02](story-010-02-seed-script-and-fixtures.md); фикстуры временного пользователя — нет
API, которым его создать. Обе появятся вместе с тем, чего ждут.
