# STORY-010-05 — E2E-проверка изоляции арендаторов

**Как** владелец инсталляции **я хочу** сквозную проверку, что пользователь одной организации не
получает данные другой ни через интерфейс, ни через API **чтобы** обещание изоляции подтверждалось
на уровне всей системы, а не только на уровне SQL-политик.

## Acceptance (Given/When/Then)

- **Given** пользователь организации A **When** он открывает интерфейс **Then** нигде — в списках, поиске, переключателях — не отображаются сущности организации B.
- **Given** идентификатор сущности организации B **When** пользователь A открывает прямую ссылку на неё **Then** он получает экран «не найдено» (404), а не 403 — API не подтверждает существование объекта в чужой организации.
- **Given** валидная сессия пользователя A **When** из неё выполняется прямой запрос к API за ресурсом организации B (в обход UI) **Then** ответ 404, тело не содержит данных объекта.
- **Given** валидная сессия пользователя A **When** выполняется попытка изменить или удалить ресурс организации B **Then** ответ 404, и последующая проверка под пользователем B показывает, что данные не изменились.
- **Given** попытка подменить `organizationId` в теле запроса или в заголовке при валидной сессии A **When** запрос выполняется **Then** контекст остаётся организацией A: подмена игнорируется, чужие данные не создаются и не читаются.
- **Given** тот же сценарий, но для **своей** организации **When** пользователь A запрашивает свой ресурс **Then** он его получает — положительный контроль подтверждает, что фикстуры и сценарий рабочие.
- **Given** прогон сценария **When** он завершается **Then** результат публикуется отдельной строкой в отчёте CI как «tenant isolation: passed/failed» — это гейт релиза по PRD.
