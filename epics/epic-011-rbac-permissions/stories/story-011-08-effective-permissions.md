# STORY-011-08 — Эффективные права и `GET /me/permissions`

**Как** разработчик Bad CRM **я хочу**, чтобы эффективные права пользователя собирались одним
чтением на запрос и отдавались клиенту отдельным эндпоинтом, **чтобы** проверка прав не стоила
десяти запросов на каждый HTTP-вызов, а изменение прав отражалось на следующем же запросе без
перелогина.

> **Кеш из заголовка и из критериев 2, 4, 5, 6 убран решением 2026-09-06** — по замеру, а не по
> усталости; разбор и числа ниже, в разделе «Кеш прав: замер и отказ». Формулировки критериев
> оставлены как есть намеренно: по ним принималось решение, и переписанный критерий не даёт
> прочитать, от чего именно отказались. Каждый несёт пометку об исходе.

## Acceptance (Given/When/Then)

1. **Сборка `Actor` одним запросом.**
   Given пользователь с 3 ролями, 2 оверрайдами и членством в 2 командах;
   When вызывается `EffectivePermissionsService.forUser(userId, organizationId)`;
   Then выполняется **один** SQL-запрос (три `LEFT JOIN LATERAL`), покрытый индексом
   `role_permissions (organization_id, role_id) INCLUDE (permission_key)`; возвращается `Actor` с
   `permissions` (роли ∪ ALLOW-оверрайды), `denied` (DENY-оверрайды), `roleIds`, `teamIds`,
   `isOwner`, `permissionsVersion`.

2. **Кеш по версии, а не по TTL.**
   Given ключ `perm:{userId}:{permissionsVersion}` в Redis с TTL 60 c;
   When админ меняет роль пользователя;
   Then версия инкрементится в той же транзакции, старый ключ становится недостижимым, следующий
   запрос собирает права заново — без ожидания TTL.
   **Закрыт отказом 2026-09-06:** кеша нет, инкремент версии в транзакции есть и остаётся.

3. **Одна сборка на HTTP-запрос.**
   Given внутри одного запроса `forUser` вызывается трижды;
   When запрос обрабатывается;
   Then Redis опрашивается один раз: `Actor` лежит в `AsyncLocalStorage` рядом с tenant-контекстом.
   **Выполняется по существу, механизм другой:** сборка на запрос ровно одна, но живёт она в
   `res.locals` гварда, а Redis не опрашивается вовсе — его на этом пути нет.

4. **Гонка «версия сдвинулась во время сборки».**
   Given версия прочитана как 7, во время сборки стала 8;
   When сборка завершается;
   Then результат **не кладётся** в кеш; следующий запрос собирает заново (тест с искусственной
   задержкой между чтением версии и `load`).
   **Закрыт отказом 2026-09-06:** гонка живёт между чтением версии и записью в кеш, записи нет.

5. **Защита от кеш-штампа.**
   Given у роли 200 носителей и версия сброшена всем одновременно;
   When все они делают запрос;
   Then сборка идёт под коротким локом `perm:lock:{userId}` (`SET NX PX 3000`); не получивший лок
   ждёт до 200 мс и собирает сам; тест на 50 конкурентных сборок не даёт ошибок и укладывается в SLA.
   **Закрыт отказом 2026-09-06:** штамп измерен в худшем виде (200 пересборок) и проходит без лока.

6. **Негативный сценарий — Redis недоступен.**
   Given Redis отключён;
   When выполняется запрос;
   Then `PermissionCachePort` логирует и возвращает `miss`; система работает корректно (не
   deny-всем и не allow-всем), p95 деградирует, метрика `permission_cache_error_total` растёт.
   **Закрыт отказом 2026-09-06:** порта нет, требование «не deny-всем и не allow-всем» выполняется
   по построению и проверено с остановленным Redis; метрика не заводится.

7. **Read-your-writes.**
   Given администратор изменил собственные права и сразу открыл страницу;
   When приходит следующий запрос;
   Then он видит новые права: версия читается из БД (`SELECT permissions_version FROM users WHERE id = $1`),
   а не из кеша, поэтому ключ гарантированно промахивается.

8. **Устаревшая версия в access-токене.**
   Given в токене `permissionsVersion = 5`, в БД — 6;
   When приходит запрос;
   Then токен **не** отвергается: права перечитываются, в ответ добавляется заголовок
   `X-Permissions-Stale: 1`, по которому клиент инвалидирует `me/permissions`. Разлогина не происходит.

9. **`GET /api/v1/me/permissions`.**
   Given аутентифицированный пользователь;
   When он запрашивает эндпоинт;
   Then 200 `{ permissions: PermissionKey[], denied: PermissionKey[], roles: string[], isOwner,
   version }`, заголовки `ETag: "perm-{userId}-{version}"` и `Cache-Control: private, must-revalidate`;
   повторный запрос с `If-None-Match` даёт 304.

10. **Негативный сценарий — чужие права не отдаются.**
    Given пользователь без `permission:override_read`;
    When он запрашивает `GET /api/v1/users/{otherUserId}/permissions`;
    Then 403 `permission_not_granted`; `me/permissions` отдаёт **только** собственные права и не
    принимает параметр `userId`.

11. **Клиент использует ту же функцию.**
    Given `useCan('project:update', { accessLevel: 'EDITOR' })` на клиенте;
    When он вычисляет результат;
    Then вызывается тот же `can()` из `@bad-crm/shared`, что и на сервере; один набор табличных
    тестов прогоняется в обоих пакетах.

12. **Клиент не вычисляет уровень ACL.**
    Given DTO проекта;
    When он сериализуется сервером;
    Then содержит `permissions: { canEdit, canDelete, canManageMembers }`, вычисленные сервером;
    клиент не резолвит цепочку наследования самостоятельно.

13. **Гард маршрута до рендера.**
    Given маршрут `/admin/roles` с `requirePermission('role:read')` в `beforeLoad`;
    When пользователь без права переходит по прямой ссылке;
    Then редирект на экран 403 **до** рендера React; расхождение «UI показал — сервер отказал»
    логируется как продуктовый дефект (метрика `ui_server_permission_mismatch_total`).

## Кеш прав: замер и отказ (2026-09-06)

Условие отсрочки наступило (админский экран отгружен), поэтому первым шагом была не реализация, а
**замер** — по правилу «замер вместо предположения». Стенд: `docker compose` этого репозитория
(PostgreSQL 16 на том же хосте, Node 22.22.2, Prisma 6.19.3), субъект — две системные роли
(`admin` + `manager`, 317 действующих ключей) и два персональных исключения; путь измерялся
настоящий — `BuildActorQuery` поверх `PrismaEffectivePermissionsReader` внутри `withTenant`.

| Что | Число |
|---|---|
| одна сборка `Actor` | mean 5.4 мс, p50 5.5, p95 6.0, p99 6.4, max 6.5 (n=200) |
| операторов на сборку | 11 (`BEGIN`, изоляция, два `set_config`, шесть чтений, `COMMIT`) |
| зависимость числа операторов от числа ролей | нет: 2 роли и 8 ролей — те же 11 |
| потолок | 700–840 сборок/с |
| 5 / 10 / 25 в полёте | p95 26 / 30 / 54 мс |
| 50 в полёте | p95 72–111 мс |
| 200 в полёте (сценарий критерия 5) | p95 237 мс, max 258, ноль ошибок, всё за ~1 с |
| `GET` из Redis + разбор 317 ключей | mean 0.23 мс, p95 0.35 |
| `SET NX PX` (лок критерия 5) | mean 0.23 мс, p95 0.26 |

Единица измерения — **одна** сборка. `GET /users/{userId}/permissions` стоит дороже: гвард собирает
актора вызывающего, а `GetUserPermissionsQuery` делает второе такое же чтение по субъекту и пишет в
аудит, — к этому экрану число ниже без удвоения применять нельзя.

Вывод: сборка стоит **4 % бюджета NFR-2** на чтение одиночной сущности (p95 150 мс), и это при том,
что кеш убрал бы не всю её стоимость — версия обязана читаться из БД на каждом запросе, иначе
умирает критерий 7. Кеш-штамп, ради которого спроектирован лок, измерен в собственном худшем виде и
проходит **без лока**; 200 носителей роли к тому же не помещаются в установку на 5–50 человек, для
которой продукт делается (PRD, персоны). Цена другой чаши — лок, режим деградации, гонка версий и
второй источник ответа о доступе — оплачивается в области инварианта №2, где ошибка не проявляется
функционально.

Поэтому **критерии 2, 4, 5 и 6 закрываются отказом**, а не реализацией:

- **2 (кеш по версии)** — не вводится. Условие корректности (инкремент версии в той же транзакции)
  выполнено и остаётся выполненным; кеша нет, поэтому инвалидировать нечего.
- **4 (гонка «версия сдвинулась во время сборки»)** — не возникает: гонка существует только между
  чтением версии и записью в кеш, а записи нет. Отдельно: до сборки доходит только запрос, чью
  версию в токене `AuthenticateSessionQuery` уже сверил со строкой пользователя (расхождение —
  401), то есть окно, о котором пункт, закрыто ещё и на уровень выше.
- **5 (защита от штампа)** — не вводится: защищаемое явление измерено и в бюджет укладывается.
- **6 (Redis недоступен)** — выполняется по построению, и это проверено, а не выведено: с
  остановленным контейнером Redis (`ECONNREFUSED`) сборка вернула из Postgres 258 прав субъекта с
  одной ролью `admin` — проверка шла на нём, а не на субъекте таймингов с двумя ролями и 317
  ключами, — разрешающий случай остался разрешён, запрещающий запрещён. Путь принятия решения о
  доступе не обращается к Redis ни разу, поэтому ни deny-всем, ни allow-всем невозможны. Метрика
  `permission_cache_error_total` не заводится: счётчик ошибок несуществующего кеша. Оговорка о
  границе: Redis остаётся fail-closed для ограничителя частоты (`login`, `refresh`) — это
  деградация **аутентификации**, а не решения о доступе, и читать пункт шире нельзя.
  Архитектурного запрета «путь решения не ходит в Redis» намеренно **не** заводится: слой
  `application` и так не может импортировать адаптеры
  (`packages/server/test/unit/architecture/layers.test.ts`, «keeps application away from adapters»),
  поэтому кеш способен приехать только портом — видимым в конструкторе и на ревью, — а жёсткий
  запрет противоречил бы записанной обратимости решения: он запрещал бы ровно то, что условия
  пересмотра предписывают сделать, если сработают.

Отказ **обратимый и с числовыми порогами**: кеш вводится, если

- **(а)** устойчиво держится 25 и больше сборок в полёте (p95 одной сборки — уже треть бюджета).
  Сигнал сегодня нечем снять: gauge сборок актора в `MetricsPort` нет, наблюдаемый заменитель —
  p95 `http_request_duration` на маршрутах с capability; заводить сам сигнал следует gauge по
  образцу `argon2_inflight`;
- **(б)** падает **первое** утверждение
  `packages/server/test/integration/db/effective-permissions-cost.test.ts` — «столько же операторов
  на двух ролях и на восьми», то есть единственное свойство, на котором стоит весь замер. Второе
  утверждение (ровно 11) держит абсолютную стоимость и может поехать вниз при апгрейде Prisma — это
  повод перевыверить число, а не строить кеш;
- **(в)** появляется ACL на ресурс (STORY-011-06, EPIC-014), добавляющий резолв на запрос, которого
  в замере нет.

Чего замер не показывает: сквозного времени HTTP-запроса — оно не мерилось, нагрузочного сценария в
CI нет (NFR-2). Числа выше — про компонент, а не про endpoint.

Попутно уточнён **критерий 3**. По существу он выполняется — на HTTP-запрос приходится ровно одна
сборка: гвард кладёт `Actor` в `res.locals`, контроллеры читают `readActor()`, а маршрут без
capability (`selfService`, например `GET /me/permissions` и `GET /employees/:userId`) собирает актора
один раз сам, потому что гвард на нём не смонтирован. Формулировка же критерия описывает механизм,
которого нет: `AsyncLocalStorage` для актора не используется, а Redis «опрашивается один раз» не
опрашивается вовсе.
