# STORY-011-10 — Админ-UI: матрица ролей с batch-применением

**Как** администратор системы (P5) **я хочу** видеть на одном экране, какая роль что может, и
менять состав прав пачкой — с предпросмотром «кого это затронет» перед сохранением, **чтобы**
понимать модель доступов без чтения документации и не раздавать лишние права по одному неверному
клику.

## Acceptance (Given/When/Then)

1. **Матрица читается и фильтруется из URL.**
   Given экран `/admin/roles`;
   When пользователь ищет `invoice`, сворачивает группы и включает «только различия»;
   Then состояние живёт в query-параметрах (`?q=invoice&group[]=delivery&diff=1&role=manager`),
   переживает перезагрузку, работает с кнопкой «назад»; схема — `rolesSearchSchema` (Zod,
   `validateSearch`), мусорные значения отбрасываются схемой.

2. **Строки — права по доменам, колонки — роли.**
   Given 331 право и 7 системных + N кастомных ролей;
   When экран отрисован;
   Then первый столбец и шапка «прилипшие», группы соответствуют доменам каталога, опасные права
   визуально помечены, deprecated — серым с плашкой «выведено из употребления».

3. **Ячейка роли бинарна.**
   Given ячейка (право × роль);
   When пользователь кликает;
   Then состояние переключается «входит / не входит» — трёхсостоятельности здесь нет, она
   существует только на экране персональных исключений (расхождение №3 §12 `permission-model.md`).

4. **Изменения копятся в черновике.**
   Given пользователь переключил 12 ячеек;
   When он не нажал «Сохранить»;
   Then ни одного запроса к серверу не отправлено (оптимистично только локальное состояние), внизу
   панель «12 изменений» с кнопками «Сохранить» и «Отменить»; черновик в URL не пишется.

5. **Предпросмотр «кого затронет».**
   Given черновик с изменениями;
   When нажата «Сохранить»;
   Then показывается сводка: по каждой роли — что добавлено/убрано и **число носителей**, а для
   опасных прав — отдельное предупреждение; применение требует подтверждения; серверный расчёт
   приходит из `POST /api/v1/roles/preview-changes` (read-only, право `role:read`).

6. **Применение — одна пессимистичная операция.**
   Given подтверждённый черновик;
   When он сохраняется;
   Then выполняется один batch-запрос в одной транзакции; при успехе — зелёный тост и
   инвалидация ключей `QueryKeys.Iam.roles`; частичного применения не бывает.

7. **Негативный сценарий — самоблокировка.**
   Given администратор снимает право `role:update` с роли, которая является его единственным
   источником этого права;
   When он кликает по ячейке;
   Then переключатель заблокирован с объяснением в тултипе; при обходе UI сервер отвечает 409
   `self_lockout`, черновик не теряется.

8. **Негативный сценарий — системная роль только для чтения.**
   Given колонка `admin` (`isSystem = true`);
   When пользователь пытается изменить ячейку;
   Then ячейка неактивна, у колонки виден замок с пояснением «состав системной роли задаётся кодом;
   нужно иначе — кастомная роль или персональное исключение».

9. **Негативный сценарий — нет права на экран.**
   Given пользователь без `role:read`;
   When он открывает `/admin/roles` по прямой ссылке;
   Then гард `beforeLoad` редиректит на экран 403 до рендера; кнопка входа в раздел в навигации
   отсутствует.

10. **Ошибка сохранения не теряет работу.**
    Given сервер вернул 409 на часть изменений;
    When приходит ответ;
    Then над панелью — inline-баннер с перечнем непринятых изменений, черновик сохранён, тост
    ошибки один (глобальный `MutationCache.onError` не дублируется локальным).

11. **Уход со страницы с несохранённым.**
    Given непустой черновик;
    When пользователь уходит с маршрута;
    Then срабатывает dirty-guard с подтверждением.

12. **a11y и i18n.**
    Given матрица;
    When она проверяется axe и с клавиатуры;
    Then 0 нарушений A/AA, полная навигация стрелками по ячейкам (роль `grid`), видимый фокус,
    все строки — из i18n-ключей EN и RU, ни одной хардкод-строки.

## Что уже сделано (2026-08-07)

### Сервер — два эндпоинта, которых требовал экран

- [x] `POST /api/v1/roles/preview-changes` (`role:read`) — «что будет, если сохранить»: по каждой
      роли что добавится, что уйдёт, какие из приходящих ключей опасны, **сколько человек держит
      роль** и приняло бы это сервер вообще. Два последних клиент вычислить не может, и оба считает
      та же policy, которая решает при сохранении, — сводка не может разойтись с результатом.
- [x] `POST /api/v1/roles/apply-changes` (`role:update`) — **всё или ничего** в одной транзакции.
      Один отказ отвергает запрос: одиннадцать изменений из двенадцати оставили бы экран описывать
      состояние, которого нет нигде. Какое именно отказано — клиент узнаёт повторным preview
      (тело отказа несёт код, не список: `details` идёт в лог и никогда в ответ).
- [x] `domain/iam/access/role-batch.policy.ts` — черновик судится **целиком**. Подмножество и
      неизменяемость системной роли — по каждому изменению; самоблокировка — **один раз, против
      конечного состояния**: перенос `role:update` из одной роли в другую законен, а по-штучно
      первая половина выглядит как блокировка. Отказ приписывается тому изменению, которое отбирает
      право, а не всему черновику — экран должен уметь показать пальцем. 14 табличных тестов.
- [x] Порт и репозиторий: `compositionsOf`, `holdingsOf`, `holderCounts` — по одному оператору на
      вопрос, а не по одному на роль. Роль, чей состав черновик не двигает, пропускается: никто не
      инвалидируется за клик, сделанный дважды.

### Расхождения с текстом истории

0. **Шесть пунктов acceptance описывают то, чего в продукте нет или что решено иначе.**
   П. 1 — параметр `group[]` зовётся `collapsed`, а `role` не заведён вовсе (экран одной роли — это
   фильтр по колонке, которого история не требует ни одним критерием). П. 4 — панель считает
   **роли**, а не ячейки: сохраняется композиция на роль, и число на панели обязано совпадать с
   числом строк в сводке. П. 6 — ключи инвалидации зовутся `QueryKeys.Roles.all` и
   `QueryKeys.Permissions.all` (фабрика не имеет группы `Iam`). П. 8 — замок не у колонки, а в самой
   ячейке: заблокирован именно контрол, и объяснение живёт там, где по нему кликают.
   П. 2 (плашка «выведено из употребления») — в каталоге **ноль** deprecated-ключей, поле объявлено и
   не используется; плашка была бы утверждением о несуществующем. П. 7 (тултип на самоблокировке в
   самой ячейке) — самоблокировка видна в предпросмотре, где она и вычисляется: ячейка не знает
   конечного состояния черновика, а предпросмотр знает. П. 10 (inline-баннер над панелью) — список
   отказов живёт в модалке, из которой сохранение и запускается; отдельный баннер повторял бы её.
1. **Гард отвечает `notFound()`, а не редиректит на 403 (п. 9).** `ux-architecture.md` прямо
   предписывает: «маршрут не отдаётся: бросает `notFound()` (не 403, см. раздел прав)» — экран,
   который говорит «вам нельзя», сообщает, что нечто существует. Документ выше истории по порядку
   источников истины.
2. **Предпросмотр — отдельный эндпоинт, применение — второй.** История называла только
   `preview-changes`; batch-применение получило собственный путь `apply-changes` вместо перегрузки
   `PATCH /roles`, потому что «сохранить черновик» и «изменить одну роль» — разные операции с
   разными правами и разной семантикой отказа.
3. **Отказ не несёт списка непринятых изменений (п. 10).** Тело ошибки несёт код; список приходит из
   повторного `preview-changes`, который для этого и существует. Иначе пришлось бы нарушить правило
   «`details` в тело не попадает».

### Что нашёл гейт и что из этого исправлено

- **Правка состава стирала описание роли** (Medium, security-auditor). `RoleComposition` не нёс
  `description`, и `apply-changes` подставлял `null`: админ создаёт роль с описанием, кликает одну
  ячейку на матрице — описание исчезает, и в журнале этого не видно, потому что там состав, а не
  проза рядом. Поле добавлено в композицию и проносится через правку.
- **Предпросмотр обещал «сервер это примет» тому, кто не может сохранить** (Medium). Экран открыт по
  `role:read`, preview — тоже, а `judgeRoleChanges` не спрашивал про `role:update`: читатель видел
  зелёную сводку и активную кнопку, а сохранение отвечало 403. Ровно то расхождение сводки с
  результатом, ради устранения которого эндпоинт и заведён. Проверка capability перенесена в policy.
- **64 роли × 6 обращений в одной транзакции с потолком 5 секунд** (High, production-readiness). На
  managed-базе с RTT 13 мс это ~389 последовательных обращений и `P2028` на ровном месте. Инвалидация
  носителей всего черновика свёрнута в **один** оператор (`bumpHoldersOfMany`, `role_id = ANY($1)`
  с `ORDER BY user_id` — заодно один и тот же порядок блокировок для двух одновременных сохранений,
  то есть и от дедлока).
- **Матрица перерисовывалась целиком на каждый клик** (High). 331 право × колонка на роль:
  `groupPermissions` пересчитывался на каждый рендер, группы не были мемоизированы. Теперь `useMemo`
  на группы, `memo` на группу строк, стабильная ссылка на массив ролей.
- **`?diff=no` включал фильтр** (Low). `z.coerce.boolean()` отвечает `true` на любую непустую строку;
  заменено на явный разбор двух написаний.
- **Мёртвый search-параметр `role`** — объявлен и нигде не читался, убран.
- **Число воркеров тестов** было прибито к десятиядерной машине; теперь считается от
  `availableParallelism()`, полное объяснение — один раз в корневом `vitest.config.ts`.

### Осталось (записано, чтобы не потерялось)

- **Навигация стрелками по ячейкам (`role="grid"`, п. 12).** Сейчас матрица — обычная таблица с
  фокусируемыми чекбоксами: клавиатурой достижима вся, но перемещение — Tab, а не стрелки. Полноценный
  grid-паттерн (roving tabindex, Home/End/PageUp) — отдельная работа, и делать её стоит сразу для
  всех табличных экранов, а не для одного.
- **E2E-сценарий** `admin-role-matrix.spec.ts` из плана не написан. `packages/e2e` — не заготовка
  (там 6 spec-файлов и 14 тестов, харнесс гоняется в CI), так что причина не «нечем», а «не в этой
  волне»: сценарий на матрицу требует посеянных ролей и людей, то есть seed-фикстуры, которой у
  харнесса пока нет.
- **axe покрывает модалку предпросмотра, но не саму матрицу.** Таблица на 331 строку под axe в
  jsdom — это минуты на прогон; для неё нужен e2e с `@axe-core/playwright`, вместе с пунктом выше.
- **Виртуализация строк.** 331 право × N ролей рендерится целиком; спасают memo и то, что поиск
  сужает список. При появлении второго такого экрана — общий компонент с виртуализацией.
- **Оптимистическая блокировка на сохранении черновика.** Черновик несёт абсолютные составы, версии
  у роли нет: два админа, сохранившие подряд, — и второй молча снимает то, что выдал первый (preview
  это покажет строкой «removed», но только если её прочитать). Тот же механизм закрывает и разрыв
  между preview и apply. Нужен общий для API механизм предусловий (`If-Match`/версия), а не частное
  решение здесь — записано и в STORY-011-03.
- **Ретрай на дедлок** (`40P01`): `bumpHoldersOfMany` сузил окно до одного оператора с фиксированным
  порядком, но общего ретрая на уровне `UnitOfWork` в проекте по-прежнему нет.
- **`ipAddress` в журнале** пуст во всех IAM-use-case'ах (унаследованный паттерн). Для массового
  изменения модели прав это заметнее, чем для одиночной правки.
- **`X-Confirm-Dangerous` клиент ставит сразу после модалки** — подтверждением служит сама модалка с
  красным блоком, которую человек прочитал и нажал «Применить». 428-ветка сервера остаётся для
  клиентов, которые модалку не показывают; это осознанно, а не упущение.
- **Rate limit на `/api/v1/roles/*`** — в контракте 429 объявлен, лимитера нет; пробел
  общепроектный (лимитер живёт внутри auth-use-case'ов), не регресс этой истории.
