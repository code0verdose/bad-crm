# EPIC-012 — Сотрудники, приглашения и офбординг

## Зачем (ценность)

Пункт 2 ТЗ — «добавление сотрудников с ролями и доступами». Продукт командный по определению: один
пользователь в Bad CRM бессмыслен. Пока нельзя пригласить человека, назначить ему роль и завести
кадровую запись, ни один последующий домен (проекты, задачи, время, чат) не имеет субъекта.

Вторая половина ценности — **офбординг одной операцией**. Это прямая боль персоны P5 из
[PRD](../../docs/product/prd.md#p5-администратор-системы): сегодня уход сотрудника — это шесть
отзывов доступа в шести сервисах, и один всегда забывают. Здесь деактивация обязана закрывать
всё сразу: сессии, WS-соединения, presigned-ссылки, членство в проектах и командах, назначенные
роли — и оставлять экспортируемый след в журнале. Это же митигация угроз `T-IAM-06` (действие с
отозванными правами) и `N4` (уволенный сотрудник) из
[`threat-model.md`](../../docs/security/threat-model.md).

Третья часть — `EmployeeProfile` как кадровая запись, отделённая от `User`: не каждый аккаунт
является сотрудником (подрядчик, контакт клиента, бот), у HR-полей другая чувствительность и другой
жизненный цикл. Это основание для будущей загрузки (`weeklyCapacityHours` в M6), оргструктуры
(`managerId`) и drill-down по сотруднику (M6).

## Scope

### В скоупе

- Приглашение по e-mail: `Invitation` с `tokenHash`, TTL, одноразовостью, привязкой к роли и
  командам; повторная отправка, отзыв; работа **без SMTP** — ссылка выдаётся в интерфейсе (NFR-9).
- Принятие приглашения: создание `User` строго на `Invitation.email`, установка пароля, применение
  роли и членств в одной транзакции.
- `EmployeeProfile`: должность, отдел, `managerId`, `weeklyCapacityHours`, тип занятости, даты найма,
  навыки; аватар через файловое хранилище ([EPIC-015](../epic-015-file-storage/epic.md)).
- Справочник сотрудников с фильтрами и состоянием в URL; оргструктура по `managerId`.
- Деактивация и офбординг одной операцией с чек-листом последствий и обратимой реактивацией.
- Передача владения организацией (`organization:transfer_ownership`).
- `Team` и `TeamMember` — команды как **субъект ACL** (`subjectType = TEAM`).

### Вне скоупа

- Аутентификация как таковая (логин, refresh, восстановление пароля) —
  [EPIC-006](../epic-006-auth-core/epic.md); 2FA — [EPIC-013](../epic-013-two-factor-totp/epic.md).
- Каталог прав, роли, ACL и их вычисление — [EPIC-011](../epic-011-rbac-permissions/epic.md);
  здесь роли только назначаются существующими use-case'ами.
- Себестоимость часа (`CostRate`), ставки и всё финансовое — M6/M9.
- Drill-down по сотруднику с графиками — [EPIC-032](../epic-032-employee-drilldown/epic.md), M6.
- Импорт сотрудников из CSV/LDAP, SSO/SCIM — вне 1.0 (backlog).
- HR-процессы (рекрутинг, ревью, компенсации) — вне продукта.

## Acceptance (эпик выполнен, когда)

- [ ] Администратор приглашает человека по e-mail с предустановленной ролью и командами; приглашение
      живёт ограниченное время, принимается один раз и только тем адресом, на который выдано.
- [ ] При отсутствующем SMTP приглашение остаётся рабочим: ссылка копируется из интерфейса.
- [ ] Принятие приглашения создаёт активного пользователя с ролью, кадровой записью и членствами в
      одной транзакции; повторное принятие невозможно.
- [ ] Профиль сотрудника заполняется и редактируется по правам; чувствительные поля не попадают в
      ответ API тем, у кого нет `employee:view_personal_data`.
- [ ] Справочник сотрудников фильтруется по роли, статусу, команде, руководителю и поиску; состояние
      полностью восстанавливается из URL.
- [ ] Деактивация сотрудника **одной операцией** отзывает сессии, разрывает WS-соединения,
      инкрементит `permissionsVersion`, закрывает членства и отзывает созданные им активные
      секретные ссылки; после неё доступ отсутствует во всех существующих доменах.
- [ ] Персональные данные при офбординге деактивируются, а не удаляются: ссылки из задач, времени и
      аудита остаются целыми (NFR-12).
- [ ] Передача владения атомарна и оставляет организацию ровно с одним активным владельцем.
- [ ] Команда может быть субъектом `ResourceAcl`; изменение состава команды инкрементит версию всем
      затронутым пользователям.
- [ ] Все привилегированные операции (приглашение, отзыв, деактивация, передача владения) — в
      `AuditLog`; офбординг даёт экспортируемый отчёт.
- [ ] Isolation-тесты RLS зелёные для `invitations`, `employee_profiles`, `teams`, `team_members`.

## Зависимости / риски

- **Зависит от:** [EPIC-006](../epic-006-auth-core/epic.md) (пароли, сессии, регистрация
  организации), [EPIC-011](../epic-011-rbac-permissions/epic.md) (роли, ACL, `permissionsVersion`),
  [EPIC-005](../epic-005-multi-tenancy-rls/epic.md) (RLS), [EPIC-015](../epic-015-file-storage/epic.md)
  (аватары), [EPIC-016](../epic-016-audit-log/epic.md) (журнал офбординга),
  [EPIC-009](../epic-009-observability/epic.md) (метрики и алерты).
- **Блокирует:** [EPIC-014](../epic-014-project-core/epic.md) (участники проекта),
  [EPIC-013](../epic-013-two-factor-totp/epic.md) (политика 2FA применяется к сотрудникам),
  M6 (загрузка и drill-down строятся на `EmployeeProfile`).
- **Риски:**
  - `T-IAM-10` — перехват приглашения: токен переслан, принят другим адресом, живёт вечно.
    Митигация: 32 байта энтропии, хеш в БД, TTL, одноразовость, строгая привязка к e-mail.
  - `T-IAM-06` — доступ переживает офбординг из-за живого access-токена или WS-соединения.
    Митигация: инкремент версии + отзыв сессий + разрыв сокетов + отзыв ссылок в одной операции.
  - Частичный офбординг (часть шагов прошла, часть упала) — самый опасный сценарий. Митигация:
    одна транзакция для БД + идемпотентный retry внешних шагов + отчёт с фактическим результатом.
  - Уникальность e-mail — **внутри организации**, а не глобально (`uq_users_org_email`): один
    человек может состоять в двух self-host организациях.
  - Утечка ПДн через справочник: `emergencyContactEnc`, домашние данные, `managerId`. Митигация —
    отдельные сериализаторы по правам, а не фильтрация на клиенте (`T-PROJ-05` по аналогии).
