# EPIC-014 — Проект как центральная модель

## Зачем (ценность)

Пункт 9 ТЗ формулирует это прямо: **проект и сотрудник — две ключевые модели**, к которым
пристёгнуто всё остальное. Задача, документ, файл, канал, запись времени, секрет, инвойс — каждая
сущность последующих майлстоунов отвечает на вопрос «к какому проекту относится». Без проекта
задачи висят в воздухе, а обещание продукта («связность вместо интеграций») не выполняется.

Вторая, менее очевидная ценность — **проект как узел модели прав**. `ProjectMember.projectRole` —
источник `implicitLevel` из [`permission-model.md`](../../docs/security/permission-model.md#слой-5--итоговое-решение):
`LEAD → MANAGER`, `MEMBER → EDITOR`, `REVIEWER → COMMENTER`, `OBSERVER → VIEWER`. Именно поэтому
99 % объектов в системе не имеют ни одной строки `ResourceAcl` и всё равно доступны правильным
людям. Проект — и корень цепочки наследования ACL для доски, задачи, папки, канала, спринта.

Для руководителя проекта (P2) это первый экран, где появляется «его» пространство; для
разработчика (P4) — переключатель контекста, после которого доски, файлы и документы фильтруются
сами.

## Scope

### В скоупе

- `Project`: `key` (человекочитаемый префикс задач вида `BAD`), `name`, `description`, `status`,
  `visibility PUBLIC_ORG | PRIVATE`, `leadId`, `startedAt`/`dueAt`, `color`, `taskCounter`,
  мягкое удаление.
- `ProjectMember`: `projectRole LEAD | MEMBER | REVIEWER | OBSERVER`, `allocationPct`, `joinedAt`,
  `leftAt` — и его роль как источника `implicitLevel`.
- Список проектов с фильтрами в URL, карточка проекта (обзор), архивация и восстановление.
- Переключатель проекта в шапке и контекст проекта в URL (`/projects/$projectId/**`).
- Привязка проекта к клиенту: `clientId` как **задел под M9** — колонка, связь и минимальный
  справочник-заглушка без домена контрактов и денег.
- Проверка прав на проект через policy + ACL с наследованием на дочерние ресурсы: единая функция
  «видимые пользователю проекты», обязательная во всех агрегирующих путях.

### Вне скоупа

- Доски, задачи, спринты — M3 ([EPIC-018](../epic-018-boards-and-columns/epic.md),
  [EPIC-019](../epic-019-tasks-core/epic.md)); здесь только точки привязки.
- Бюджет, ставки, burn, инвойсы, контракт и SOW — M9
  ([EPIC-041](../epic-041-client-and-contract/epic.md),
  [EPIC-042](../epic-042-billing-and-budget/epic.md)); поля `project:view_budget` /
  `project:manage_budget` объявлены в каталоге, но экранов в M2 нет.
- Шаблоны проектов, портфели и программы — backlog.
- Публичный доступ заказчика к проекту (клиентские порталы) — вне 1.0.
- Полнотекстовый поиск по проектам — [EPIC-024](../epic-024-search-meilisearch/epic.md), M4.

## Acceptance (эпик выполнен, когда)

- [ ] Проект создаётся, редактируется, архивируется и восстанавливается; `key` уникален внутри
      организации и служит префиксом номеров задач.
- [ ] Состав участников управляется по правам; `projectRole` определяет неявный уровень доступа без
      создания записей `ResourceAcl`.
- [ ] Приватный проект не виден пользователю без доступа **нигде**: ни в списке, ни в
      автодополнении, ни на дашборде, ни по прямой ссылке — везде 404, а не 403.
- [ ] Существует **одна** функция «видимые пользователю проекты», используемая всеми агрегирующими
      путями; появление второй ломает архитектурный тест.
- [ ] Доступ к дочерним ресурсам наследуется от проекта по цепочке `Task → Board → Project →
      Organization`; наследование покрыто тестами на реальных цепочках.
- [ ] Состояние списка проектов и контекст текущего проекта полностью живут в URL и переживают
      перезагрузку.
- [ ] Архивный проект доступен только на чтение; мягко удалённый не возвращается ни одним
      репозиторием (фильтр навешен в Prisma-`$extends`, а не расставлен руками).
- [ ] Финансовые поля проекта не попадают в ответ API пользователям без соответствующих прав.
- [ ] Изменение состава участников и видимости — записи в `AuditLog` с актором и before/after.
- [ ] Isolation-тесты RLS зелёные для `projects` и `project_members`; p95 списка проектов < 300 мс.

## Зависимости / риски

- **Зависит от:** [EPIC-011](../epic-011-rbac-permissions/epic.md) (policy, ACL, `implicitLevel`),
  [EPIC-012](../epic-012-employee-management/epic.md) (люди, которых назначают участниками),
  [EPIC-005](../epic-005-multi-tenancy-rls/epic.md) (RLS), [EPIC-004](../epic-004-client-shell-fsd/epic.md)
  (роутер и контекст), [EPIC-016](../epic-016-audit-log/epic.md) (аудит изменений состава).
- **Блокирует:** весь M3 (доски и задачи живут в проекте), [EPIC-015](../epic-015-file-storage/epic.md)
  (`scope = PROJECT`), M4 (документы и KB-пространства проекта), M5 (проектные каналы),
  M6 (время по проектам), M9 (контракты и бюджеты).
- **Риски:**
  - `T-PROJ-01` — приватный проект утекает через вторичные пути (поиск, дашборд, лента активности,
    автодополнение исполнителей, уведомления). Митигация: единая функция видимости + e2e
    `private-project-invisible-everywhere`.
  - `T-PROJ-02` — самоприсоединение к проекту через `POST /projects/{id}/members` со своим `userId`.
    Митигация: отдельное право `project:manage_members` + запрет добавлять самого себя.
  - `T-PROJ-03` — доступ к архивированному/удалённому проекту через отдельный эндпоинт или сырой
    SQL отчёта. Митигация: глобальный фильтр мягкого удаления в `$extends` + табличный тест по
    репозиториям.
  - `T-PROJ-05` — утечка финансовых полей `OBSERVER`-участникам. Митигация: разные сериализаторы по
    уровню доступа, снапшот-тест ответов по ролям.
  - `taskCounter` сериализует вставки задач внутри проекта. Осознанная цена ради непрерывной
    нумерации `BAD-14`; при реальных объёмах (единицы задач в секунду) узким местом не является.
