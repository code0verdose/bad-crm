# EPIC-016 — Журнал действий (audit log)

## Зачем (ценность)

[NFR-6](../../docs/product/prd.md#nfr-6-безопасность) требует: все привилегированные и изменяющие
действия попадают в журнал с актором, объектом, состоянием до и после и IP; журнал только на
добавление, удаление записей из UI невозможно. `T-PLAT-05` («подделка аудит-лога») входит в **топ-15
приоритетных угроз со сроком M2**: без целостности журнала ни один инцидент не расследуем и ни одна
гарантия продукта не доказуема.

Практическая ценность для персон:

- **P5 (администратор):** офбординг должен быть «доказуемо полным» — это ответ из журнала, а не из
  памяти; ревизия «кто выдал этому человеку доступ к финансам» решается за минуту.
- **P1 (владелец инсталляции):** чтение и выгрузка журнала перед аудитом заказчика — заявленный
  сценарий персоны в PRD.
- **Модель прав:** §10 `permission-model.md` требует писать изменения ролей, оверрайдов и ACL
  **в той же транзакции**, что и само изменение, с полными наборами прав до и после.

Ключевое архитектурное решение: `REVOKE UPDATE, DELETE ON audit_logs FROM app_user` — приложение
**физически** не может изменить или удалить запись аудита даже при полной компрометации кода.
Аудит, который приложение может переписать, аудитом не является.

## Scope

### В скоупе

- Таблица `AuditLog`: append-only, партиционирование `RANGE` по месяцам, индексы под три типовых
  запроса (по времени, по ресурсу, по актору).
- `AuditLoggerPort` и запись из use-cases в одной транзакции с изменением; `actorType`,
  `requestId`, `ipHash`, `severity`.
- Обязательный список логируемых событий: изменения прав и ролей, доступ к файлам и выдача
  presigned URL, действия с секретами, вход/выход и события сессий, изменения настроек организации,
  экспорт данных.
- Правила по отказам: что пишется, что только метрика, как агрегируются серии.
- Просмотр и фильтрация в админке (состояние в URL, keyset-пагинация), карточка события с
  diff `before`/`after`.
- Экспорт журнала (CSV/JSON) с ограничениями и обязательной записью самого факта экспорта.
- Ретенция: политика хранения, `DETACH PARTITION` силами `app_migrator`, архивация.

### Вне скоупа

- `VaultAccessLog` — отдельный журнал домена vault ([EPIC-034](../epic-034-vault-items/epic.md), M7);
  здесь только общий `AuditLog`.
- SIEM-интеграции, syslog-экспорт, стриминг событий наружу — backlog.
- Пользовательская «лента активности» по сущностям (`ActivityEvent`) — это другой механизм, M3
  ([EPIC-020](../epic-020-task-collaboration/epic.md)); не путать с аудитом.
- Метрики и трассировка — [EPIC-009](../epic-009-observability/epic.md).
- Подпись/цепочка хешей записей (tamper-evidence поверх БД) — рассматривается в
  [EPIC-045](../epic-045-security-hardening/epic.md), M9.

## Acceptance (эпик выполнен, когда)

- [ ] Роль приложения имеет `INSERT` и `SELECT` на `audit_logs`, но **не имеет** `UPDATE`, `DELETE`,
      `TRUNCATE` — проверяется структурным тестом по `information_schema.role_table_grants` и
      тестом «`UPDATE` из приложения падает».
- [ ] Таблица партиционирована по месяцам; создание партиций автоматизировано; запросы за период
      используют pruning.
- [ ] Каждое привилегированное действие из обязательного списка пишет запись **в той же
      транзакции**, что и само изменение; откат изменения откатывает и запись.
- [ ] Наборы прав в `before`/`after` пишутся целиком, а не дельтой; секреты, токены и расшифрованное
      содержимое в журнал не попадают никогда.
- [ ] Системные события имеют `actorType = SYSTEM` и `requestId`, протянутый через outbox и воркеры.
- [ ] Администратор фильтрует журнал по актору, действию, ресурсу и периоду; состояние живёт в URL;
      пагинация keyset; p95 < 300 мс на годовом объёме.
- [ ] Доступ к журналу разграничен: `audit:read` — общий журнал, `audit:read_security`
      (`dangerous`) — события безопасности, `audit:export` (`dangerous`) — выгрузка,
      `audit:manage_retention` — только владелец.
- [ ] Экспорт журнала сам логируется как событие `critical` с фильтром и числом строк.
- [ ] Ретенция реализована через `DETACH`/архивацию силами `app_migrator`, а не `DELETE` из
      приложения; процедура описана в runbook.
- [ ] Isolation-тест RLS зелёный для партиционированной `audit_logs` (включая проверку на уровне
      партиций).

## Зависимости / риски

- **Зависит от:** [EPIC-005](../epic-005-multi-tenancy-rls/epic.md) (RLS, роли БД, особый случай
  append-only журналов), [EPIC-003](../epic-003-server-skeleton-and-api-contract/epic.md)
  (`requestId`, слои), [EPIC-011](../epic-011-rbac-permissions/epic.md) (права `audit:*` и
  события изменения прав), [EPIC-009](../epic-009-observability/epic.md) (маскирование логов).
- **Блокирует:** [EPIC-012](../epic-012-employee-management/epic.md) (доказуемый офбординг),
  [EPIC-015](../epic-015-file-storage/epic.md) (аудит выдачи presigned URL), M7 (аудит vault и
  секретных ссылок), M9 (аудит финансовых операций, `EPIC-045`).
- **Риски:**
  - `T-PLAT-05` (топ-15, M2) — подделка аудита. Митигация: `REVOKE`, партиции, структурный тест.
  - `T-PLAT-09` — системные действия без актора: цепочку инцидента не восстановить. Митигация:
    обязательный `actorType` и сквозной `requestId` (HTTP → outbox → job → аудит).
  - `T-PLAT-06` — секреты в журнале. Митигация: whitelist полей в `before`/`after`, тот же
    `redact`-конвейер, что и для логов; тест `log-redaction-corpus`.
  - Рост объёма: аудит растёт быстрее всех таблиц. Митигация: партиционирование, узкие индексы,
    ретенция; `DELETE` на миллионах строк запрещён.
  - Производительность записи: аудит в той же транзакции удлиняет её. Митигация: одна вставка,
    без вычислений в транзакции, `before`/`after` формируются заранее.
  - Утечка через сам журнал: `before`/`after` могут содержать поля, недоступные читателю аудита.
    Митигация: whitelist полей и разделение `audit:read` / `audit:read_security`.
