# EPIC-017 — Self-host alpha

## Зачем (ценность)

Bad CRM — self-hosted продукт под AGPL-3.0. Всё остальное в нём не имеет значения, если владелец не
может поднять инсталляцию. [NFR-3](../../docs/product/prd.md#nfr-3-простота-развёртывания-и-эксплуатации)
формулирует контракт жёстко: **холодный старт менее 10 минут** на чистом хосте, `git clone` → `.env`
→ `docker compose up` → рабочий вход. Риск `R-14` («сложность самохостинга») в PRD имеет обе оценки
«высоко» и означает простую вещь: продукт без внедрений.

Вторая причина делать альфу **сейчас, в M2, а не в конце** — обратная связь до накопления долга.
Это явная митигация `R-08` (scope creep): ранняя альфа калибрует ожидания и вскрывает проблемы
развёртывания, пока их дёшево исправить.

Третья — безопасность. Самая вероятная причина компрометации self-host-инсталляции не уязвимость в
коде, а **дефолт, оставленный как есть** ([`threat-model.md`](../../docs/security/threat-model.md),
раздел «Self-host специфика»). Отсюда правило эпика: **небезопасный дефолт приводит к отказу
старта, а не к предупреждению в логе**.

## Scope

### В скоупе

- `docker-compose.prod.yml` с профилями **`full`** (app + Postgres + Redis + MinIO + Meilisearch +
  reverse-proxy) и **`minimal`** (без Meilisearch, поиск деградирует на Postgres FTS); версии
  зафиксированы.
- Entrypoint контейнера приложения: применение миграций при старте (с явным обоснованием
  компромисса и защитой от параллельного запуска).
- `.env.example` с разделением на обязательные и опциональные переменные; скрипт
  `bootstrap-secrets.sh` — CSPRNG-генерация `JWT_SECRET`, `APP_ENCRYPTION_KEY`, паролей БД, кредов
  MinIO, `MEILI_MASTER_KEY`.
- Preflight-проверка окружения при старте: слабые и примерные значения, отсутствие TLS, публичный
  бакет, привилегированная роль БД, открытые наружу порты — по чек-листу безопасной установки.
- Bootstrap первого владельца: через переменные окружения (неинтерактивно) либо интерактивным шагом
  первичной настройки в UI.
- Quickstart в `README.md` + `docs/runbooks/install.md`; smoke-тест «чистая установка» в CI.

### Вне скоупа

- Релизная сборка 1.0, версионирование, апгрейды с точкой отката, бэкапы и проверенное
  восстановление, экспорт данных организации — [EPIC-046](../epic-046-self-host-release-1-0/epic.md), M9.
- Kubernetes/Helm, Terraform-модули, managed-развёртывания — вне 1.0.
- Мастер первичной настройки со всеми разделами (AI-провайдеры, интеграции) — здесь только
  минимальный шаг создания организации и владельца.
- Автообновление и проверка новых релизов «домой» — запрещено NFR-9; проверка версий остаётся
  опциональной и выключенной.
- Подпись образов и SBOM — [EPIC-002](../epic-002-ci-and-commit-gate/epic.md) / M9.

## Acceptance (эпик выполнен, когда)

- [ ] На чистой VM по инструкции проходит путь `git clone` → `bootstrap-secrets.sh` → `.env` →
      `docker compose up` → вход в систему, **медиана < 10 минут** по протоколу проверки.
- [ ] Профиль `minimal` поднимается на 2 vCPU / 2 GB и работает без Meilisearch: поиск деградирует,
      ни один основной сценарий не отказывает.
- [ ] Ни один инфраструктурный сервис не публикует порты на хост в поставляемом compose.
- [ ] Приложение **не стартует**, если: секрет равен значению из примера, `APP_ENCRYPTION_KEY` не
      32 байта base64, `APP_URL` на `http://` вне разработки, роль БД является владельцем схемы или
      имеет `BYPASSRLS`, бакет публичен.
- [ ] Миграции применяются автоматически при старте, идемпотентно и без гонок при нескольких
      инстансах; сбой миграции останавливает старт с внятным сообщением.
- [ ] Первый владелец создаётся ровно один раз: повторный запуск не создаёт второго и не сбрасывает
      пароль; неинтерактивный и интерактивный пути дают одинаковый результат.
- [ ] `.env.example` содержит только плейсхолдеры `CHANGE_ME_…`, разделён на обязательные и
      опциональные переменные и валидируется той же Zod-схемой, что и рантайм.
- [ ] Quickstart и `docs/runbooks/install.md` описывают чек-лист безопасной установки из
      `threat-model.md` целиком.
- [ ] Smoke-тест «чистая установка» проходит в CI на каждый PR, затрагивающий развёртывание, и в
      сетевой песочнице без исходящего интернета (NFR-9).

## Зависимости / риски

- **Зависит от:** [EPIC-001](../epic-001-monorepo-and-dev-env/epic.md) (compose для разработки,
  образы), [EPIC-002](../epic-002-ci-and-commit-gate/epic.md) (сборка образов в CI),
  [EPIC-005](../epic-005-multi-tenancy-rls/epic.md) (роли БД `app_user` / `app_migrator` /
  `app_auth`, bootstrap-скрипт ролей), [EPIC-006](../epic-006-auth-core/epic.md) (создание
  организации и владельца), [EPIC-009](../epic-009-observability/epic.md) (`/healthz`, `/readyz`),
  [EPIC-015](../epic-015-file-storage/epic.md) (инициализация бакета и его preflight),
  [EPIC-013](../epic-013-two-factor-totp/epic.md) (пункт 7 чек-листа — включить обязательную 2FA).
- **Блокирует:** пилотные внедрения и обратную связь; [EPIC-046](../epic-046-self-host-release-1-0/epic.md)
  строится поверх этой поставки.
- **Риски:**
  - `R-14` — пользователь не доходит до рабочей системы. Митигация: разумные дефолты, генерация
    секретов скриптом, профиль `minimal`, внятная диагностика preflight, smoke-тест в CI.
  - `T-SH-01…T-SH-07` — дефолтные секреты, открытые порты, отсутствие TLS, слабый
    `APP_ENCRYPTION_KEY`, незашифрованные бэкапы, опасные миграции, инсталляция без обновлений.
  - **Миграции при старте — осознанный компромисс.** Плюс: обновление в одну команду, что и есть
    обещание продукта. Минус: при нескольких инстансах нужен лок, а неудачная миграция роняет старт.
    Митигация: advisory-lock, только обратимые изменения (expand → migrate → contract, `R-10`),
    рекомендация делать бэкап перед обновлением, документированная точка отката.
  - `T-FILE-04` — публичный бакет MinIO; preflight отказывает старту.
  - Ложные срабатывания preflight на нестандартных окружениях (внешний managed Postgres, S3 у
    провайдера). Митигация: каждая проверка объясняет, что именно не так, и имеет явный,
    задокументированный способ отключения с фиксацией в логе.
