# STORY-017-04 — Preflight-проверка окружения

**Как** владелец инсталляции (P1) **я хочу**, чтобы система отказывалась стартовать в небезопасной
конфигурации и объясняла, что именно не так, **чтобы** типовая ошибка self-host не превращалась в
тихую компрометацию, о которой я узнаю от заказчика.

## Acceptance (Given/When/Then)

1. **Preflight выполняется до подъёма HTTP.**
   Given старт приложения;
   When выполняется `runPreflight()`;
   Then проверки идут **до** открытия порта; результат печатается таблицей `OK / WARN / FAIL`;
   при любом `FAIL` процесс завершается ненулевым кодом.

2. **Блокирующие проверки (FAIL → отказ старта).**
   Given каждый из следующих случаев;
   When приложение стартует;
   Then старт отклоняется с сообщением, называющим переменную/сервис и способ исправления:
   - секрет равен значению из `.env.example` (`JWT_SECRET`, `APP_ENCRYPTION_KEY`, пароль БД,
     `MEILI_MASTER_KEY`, креды MinIO) — `T-SH-01`;
   - `APP_ENCRYPTION_KEY` не 32 байта base64 — `T-SH-04`;
   - `APP_URL` начинается с `http://` и `NODE_ENV !== development` — `T-SH-03`;
   - подключение к БД выполнено ролью-владельцем схемы или ролью с `BYPASSRLS` — `T-TENANT-04`;
   - бакет объектного хранилища допускает анонимный доступ или листинг — `T-FILE-04`;
   - на любой `[T]`-таблице отсутствует RLS-политика (структурная проверка каталога) — `T-TENANT-01`.

3. **Предупреждающие проверки (WARN → старт продолжается).**
   Given конфигурация без критических нарушений;
   When выполняется preflight;
   Then `WARN` выдаётся для: инфраструктурных портов, доступных с внешнего интерфейса
   (`T-SH-02`); незаданного SMTP (восстановление пароля и уведомления не работают); открытой
   регистрации (`SIGNUP_MODE != invite_only`); выключенной обязательной 2FA; отсутствия настроенного
   бэкапа; нехватки памяти под выбранный профиль.

4. **Негативный сценарий — ложное срабатывание.**
   Given внешний managed Postgres или S3 у провайдера, где проверка неприменима;
   When владелец не может её пройти по объективным причинам;
   Then у каждой проверки есть **документированный** способ отключения
   (`PREFLIGHT_SKIP=bucket_public,db_role`), факт отключения печатается в лог при каждом старте и
   попадает в `AuditLog` как `platform.preflight_skipped` (`severity = warning`) — «выключил и
   забыл» невозможно.

5. **Сообщения пригодны для действия.**
   Given любой `FAIL`;
   When он печатается;
   Then сообщение содержит: что проверялось, что найдено, чем это опасно, как починить (команда или
   пункт чек-листа установки) — без стектрейсов и без раскрытия значений секретов.

6. **Проверка RLS структурная, а не на веру.**
   Given каталог `pg_class` × `pg_policy`;
   When выполняется проверка;
   Then для каждой таблицы из реестра `tenant-tables.ts` подтверждается `ENABLE` + `FORCE` и
   наличие политики с идентичными `USING` и `WITH CHECK`; расхождение — `FAIL`.

7. **Идемпотентность и стоимость.**
   Given многократные перезапуски;
   When выполняется preflight;
   Then он не изменяет состояние (кроме одной записи аудита при пропущенных проверках) и занимает
   < 2 секунд на типовой инсталляции.

8. **Проверки доступны как команда.**
   Given работающая инсталляция;
   When администратор запускает `docker compose exec app node dist/preflight.js`;
   Then получает тот же отчёт без перезапуска сервиса — удобно для регулярной ревизии.

9. **Health-эндпоинты не раскрывают деталей.**
   Given результат preflight;
   When он отдаётся наружу;
   Then `/healthz` остаётся минимальным; детали доступны в `/readyz`, который доступен только из
   внутренней сети или под токеном (`T-PLAT-08`).

10. **Покрытие тестами.**
    Given каждая блокирующая проверка;
    When гоняется набор `preflight.spec.ts`;
    Then для каждой есть позитивный и негативный случай; отсутствие теста на новую проверку ломает
    структурный тест «каждая проверка покрыта».
