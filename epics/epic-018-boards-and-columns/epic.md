# EPIC-018 — Доски и колонки

## Зачем (ценность)

Канбан-доска — первый экран, ради которого команда открывает продукт каждый день, и физический
контейнер, внутри которого живут задачи (EPIC-019). Без досок и колонок задача не имеет места в
процессе: нечего перетаскивать, нечем показать «что в работе» и невозможно применить WIP-лимит.
Эпик закрывает структурный слой канбана — доски проекта, колонки с порядком и правилами, настройки
представления — и задаёт точку наследования прав `Board → Project`, на которую опирается EPIC-021.

## Scope

### В скоупе

- `Board` внутри проекта: `kind = KANBAN | SPRINT | BACKLOG`, `isDefault`, `settings Json`
  (версионированный JSONB со схемой `{"v":1,…}`), переименование, архивация и удаление.
- Проектные доски (`Board.projectId` обязателен) и «свободные» доски команды — доски, не привязанные
  к работе одного проекта, но живущие в организации; реализуются как доски проекта-контейнера либо
  через нуллабельный `projectId` (решение фиксируется ADR в рамках эпика, см. «Модель данных»).
- `BoardColumn`: имя, цвет, `orderKey` (fractional index), `wipLimit Int?`, `isDone Bool`;
  создание, переименование, перестановка колонок drag-and-drop, удаление с переносом задач.
- Правило WIP: превышение лимита не блокируется БД, а проверяется в use-case перемещения; обход
  требует `board:override_wip_limit` и подсвечивается в UI.
- Признак `isDone`: попадание задачи в такую колонку проставляет `Task.completedAt` (контракт с
  EPIC-019, реализуется на стороне use-case перемещения).
- Swimlanes как представление доски: группировка `none | assignee | epic` живёт в search-параметрах
  (`boardSearchSchema.swimlane`), а не в БД.
- Шаблоны досок: набор предустановленных конфигураций колонок (`Basic Kanban`, `Scrum`, `Bug flow`)
  при создании доски.
- Настройки доски: колонки по умолчанию, показ подзадач, поведение при закрытии спринта.
- Экраны `/projects/$projectId/boards` (`BoardListWidget`) и
  `/projects/$projectId/board/$boardId` (`KanbanBoardWidget`) — каркас доски и колонок; карточки
  задач и их перетаскивание — EPIC-019.
- Наследование ACL `Board → Project → Organization` в резолвере доступа; `ResourceAcl.resourceType`
  принимает `BOARD`.

### Вне скоупа

- Задачи, их карточки и drag-and-drop карточек между колонками — [EPIC-019](../epic-019-tasks-core/epic.md).
- Комментарии, вложения, лента активности — [EPIC-020](../epic-020-task-collaboration/epic.md).
- Приватные задачи, UI выдачи доступа, фильтрация списков по правам — [EPIC-021](../epic-021-task-access-control/epic.md).
- Живое обновление доски по WebSocket — [EPIC-025](../epic-025-realtime-infrastructure/epic.md) (M5),
  ретро-применяется к доскам этого эпика.
- Спринты и бэклог как процесс (`Sprint`, планирование, burndown) — [EPIC-043](../epic-043-sprints-and-delivery/epic.md) (M9);
  здесь только `Board.kind = SPRINT` как тип представления.
- Поиск по доскам — [EPIC-024](../epic-024-search-meilisearch/epic.md) (M4).

## Acceptance (эпик выполнен, когда)

- [ ] Создание проекта автоматически создаёт доску по умолчанию (`isDefault = true`) с колонками из
      выбранного шаблона; e2e-тест «новый проект → открыть доску → видны колонки шаблона» зелёный.
- [ ] Колонку можно создать, переименовать, перекрасить, переставить и удалить; при удалении колонки
      с задачами запрашивается целевая колонка, и ни одна задача не остаётся без `boardColumnId`
      (проверяется интеграционным тестом и integrity-джобом).
- [ ] Перестановка колонок меняет `orderKey` **ровно одной** строки (тест считает количество
      изменённых строк); порядок восстанавливается после перезагрузки.
- [ ] При достижении `wipLimit` перемещение задачи в колонку отклоняется с кодом ошибки
      `WIP_LIMIT_EXCEEDED`; пользователь с `board:override_wip_limit` может подтвердить перенос,
      и факт обхода пишется в `AuditLog`.
- [ ] Колонка с `isDone = true` при попадании задачи проставляет `completedAt`, при выносе —
      обнуляет; покрыто тестом на обе стороны перехода.
- [ ] Пользователь без `board:read` или без ACL-уровня `VIEWER` на доске получает 404 (не 403) и не
      видит доску в списке досок проекта.
- [ ] Состояние доски полностью в URL: `swimlane`, фильтры, открытая задача (`?task=`) переживают
      перезагрузку и корректно работают с кнопкой «назад».
- [ ] Отрисовка доски с 10 колонками и 10 000 задач в проекте укладывается в p95 < 300 мс на
      серверной части (запрос колонок + первая страница задач по индексу `idx_tasks_board_order`).
- [ ] Каждая мутация доски и колонки проходит единый policy-вызов; контрактный тест
      «route ↔ объявленная permission» не находит маршрута без объявленного права (`T-TASK-02`).

## Модель данных

- Затрагиваемые сущности: `Board` **[T]**, `BoardColumn` **[T]**, `Project` **[T]** (родитель),
  `ResourceAcl` **[T]** (`resourceType = BOARD`), `AuditLog` **[T]**, `OutboxEvent` **[T]**.
  Все `[T]` — tenant-scoped, обязательный `organizationId` + RLS-политика; новая таблица без политики
  ломает CI.
- Индексы из [data-model.md](../../docs/architecture/data-model.md): `idx_tasks_board_order
  (organization_id, board_column_id, order_key) WHERE deleted_at IS NULL` — главный индекс продукта,
  создаётся здесь вместе с колонками; FK `board_id`, `project_id` индексируются явно.
- `BoardColumn.orderKey String` — fractional index (алфавит base62), не `position Int`;
  ребалансировка ключей — фоновая задача при превышении длины ключа.
- **Закрыто (2026-07-26):** `Board.deletedAt` добавлен — доски удаляются **мягко**, как `Project` и
  `Task` (прежнее допущение эпика о физическом удалении отменено: удаление доски с сотней задач
  должно быть обратимым). Мягко удалённая доска скрывает свои задачи из списков, но **не** помечает
  их удалёнными — восстановление доски возвращает содержимое как было.
- **Закрыто (2026-07-26):** `Board.projectId` сделан **нуллабельным** — свободные (непроектные)
  доски выразимы. Следствие, обязательное к реализации: **цепочка ACL раздваивается** —
  `Task → Board → Project → Organization` у проектной доски и `Task → Board → Organization` у
  свободной; `resolveAcl` выбирает ветку по `projectId IS NULL`, а не предполагает наличие проекта.
  То же зафиксировано в [`permission-model.md`](../../docs/security/permission-model.md).
- **Пробел модели:** шаблоны досок не имеют сущности. На MVP шаблон — константа в коде
  (`units/board/model/constants/board-templates.constant.ts`), пользовательские шаблоны вне скоупа;
  если понадобятся — потребуется `BoardTemplate` **[T]**.
- Swimlanes намеренно не хранятся в БД: это представление, живущее в search-параметрах маршрута.

## Права

- Ключи из каталога [permission-model.md](../../docs/security/permission-model.md) §3.5:
  `board:read` (ACL `VIEWER`), `board:create` (`EDITOR`), `board:update` (`EDITOR`),
  `board:delete` (`MANAGER`), `board:manage_columns` (`EDITOR`),
  `board:override_wip_limit` (`EDITOR`).
- Сопутствующие: `project:read` (`VIEWER`) — доска не читается без доступа к проекту;
  `acl:read`/`acl:grant`/`acl:revoke` — управление доступом к доске (используется полноценно в EPIC-021).
- ACL-уровни и наследование: цепочка `Board → Project → Organization`
  (permission-model §«Наследование ACL»). Действует правило «ближайшая явная запись побеждает»;
  `NONE` на доске перебивает любой уровень, унаследованный от проекта. Разрешение —
  конъюнкция capability и уровня ACL: `board:update` без `EDITOR` на доске не даёт права.
- Отсутствующих ключей нет: отдельный `board:manage_acl` не требуется — управление ACL доски идёт
  через общие `acl:grant` / `acl:revoke` (`MANAGER`).

## Зависимости / риски

- Зависит от: EPIC-005 (RLS и tenant-контекст), EPIC-011 (каталог прав, `can()`, ACL),
  EPIC-014 (проект как родитель доски), EPIC-003/EPIC-004 (контракт API, каркас клиента),
  EPIC-007 (дизайн-система, состояния экрана).
- Блокирует: EPIC-019 (задачам нужна колонка), EPIC-021 (наследование `Task → Board → Project`),
  EPIC-025 (комнаты `org:{id}:board:{id}` и живое обновление канбана).
- Риски:
  - `R-08` (scope creep): соблазн затащить сюда спринты и бэклог из M9 — граница зафиксирована в
    «Вне скоупа», расширение только через ADR.
  - `T-TASK-02` (мутация без проверки): перестановка колонок и WIP-override — такие же мутации, как
    любые другие; митигация — единый policy-вызов в каждом use-case + контрактный тест route↔policy.
  - `T-PROJ-01` (приватный проект утекает вторичными путями): список досок обязан строиться поверх
    единой функции «видимые пользователю проекты», а не по `projectId` из URL.
  - Конкурентная перестановка колонок двумя пользователями: fractional index делает конфликт
    неразрушающим (меняется одна строка), но требует теста на одновременную вставку между теми же
    соседями.
