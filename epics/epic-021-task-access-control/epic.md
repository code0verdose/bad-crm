# EPIC-021 — Права на доски и задачи

## Зачем (ценность)

Модель прав (EPIC-011) существует с M2, но до появления задач её нечем было проверить на реальном
дереве ресурсов. Эпик применяет модель к первому глубокому дереву `Task → Board → Project →
Organization`: даёт приватные задачи, UI выдачи доступа, ответ 404 вместо 403 для скрытых объектов и
— главное — **фильтрацию списков по правам одним SQL-запросом**, а не построчным `can()`. Это условие
выхода M3: приватная задача не должна быть видна ни в списке, ни в поиске, ни по прямой ссылке, ни
через комментарий или вложение.

## Scope

### В скоупе

- Резолвер ACL для цепочек `Task → Board → Project → Organization` и
  `Comment/Attachment/ActivityEvent → родитель → …` — **одним SQL-запросом** (`resolve-acl.query.sql`,
  `ORDER BY depth LIMIT 1` реализует правило «ближайшая явная запись побеждает»).
- «Приватная задача»: `ResourceAcl` с `accessLevel = NONE` на потомке перебивает унаследованный
  уровень; обратный сценарий — точечная выдача `VIEWER`/`EDITOR` на одну задачу человеку, у которого
  нет доступа к проекту.
- UI выдачи доступа: панель «Доступ» на доске и в карточке задачи — список грантов
  (`USER | ROLE | TEAM`), уровень, срок действия (`expiresAt`), выдача и отзыв; экран «почему у
  пользователя есть этот доступ» на базе `permission:explain`.
- Политика ответов: **404 вместо 403** для ресурсов, существование которых пользователь не должен
  узнать (скрытая задача, доска приватного проекта); 403 — только там, где ресурс заведомо виден,
  но действие запрещено (правило из ux-architecture «403 vs 404»).
- **Фильтрация списков одним запросом:** множество доступных родителей (`ProjectMember` +
  `ResourceAcl` по субъектам актора) вычисляется один раз и подставляется как
  `WHERE project_id = ANY($accessible)`, с отдельным вычитанием поддеревьев, помеченных `NONE`.
  Построчный `can()` в списках запрещён архитектурно.
- Интеграционный тест **«список == построчный can()»** на небольшом наборе данных со всеми
  комбинациями грантов (пользователь, роль, команда, `NONE`, просроченный грант, владелец).
- Единая функция «видимые пользователю проекты/доски/задачи» — один источник, используемый списками,
  автодополнением исполнителей, счётчиками, лентой активности и (позже) поиском и дашбордами.
- Инвалидация: любое изменение `ResourceAcl`, `ProjectMember`, `UserRole`, `UserPermissionOverride`
  инкрементит `User.permissionsVersion` и порождает outbox-событие переиндексации (потребляется
  EPIC-024 в M4).
- Клиентские гарды `requireTaskAccess`, `requireProjectMember`, `requirePermission(p)` в `beforeLoad`
  + `use-can` как **подсказка UI**, не как безопасность.
- Аудит: выдача и отзыв доступа (`acl:grant`/`acl:revoke` — dangerous) пишутся в `AuditLog`
  с before/after; отказы в доступе логируются как события безопасности.

### Вне скоупа

- Каталог permissions, роли, персональные override и алгоритм разрешения как таковой —
  [EPIC-011](../epic-011-rbac-permissions/epic.md) (M2); здесь только применение к доскам и задачам.
- Права на документы, KB и файлы — [EPIC-022](../epic-022-docs-pages/epic.md),
  [EPIC-023](../epic-023-knowledge-base/epic.md), EPIC-015; наследование там строится по тем же
  правилам, но реализуется в своих эпиках.
- Permission-aware поиск — [EPIC-024](../epic-024-search-meilisearch/epic.md) (M4): здесь только
  выпуск события переиндексации при изменении ACL.
- Авторизация подписки на комнату сокета — [EPIC-025](../epic-025-realtime-infrastructure/epic.md) (M5),
  использует тот же policy-путь.
- Финальная ревизия прав по всем доменам — [EPIC-045](../epic-045-security-hardening/epic.md) (M9).

## Acceptance (эпик выполнен, когда)

- [ ] Приватная задача (`ResourceAcl` `NONE` на задаче) не видна пользователю без прав **нигде**:
      в списке `/tasks`, на доске, по прямой ссылке `/tasks/$taskId`, по номеру `BAD-42`, в ленте
      активности, в автодополнении, через комментарий и через вложение — e2e
      `private-task-hidden-everywhere` зелёный.
- [ ] Точечная выдача `VIEWER` на одну задачу человеку без доступа к проекту открывает **только**
      эту задачу и её обсуждение; соседние задачи и доска остаются недоступны.
- [ ] Ответ на недоступный ресурс — 404; 403 возвращается только при запрете действия над видимым
      ресурсом; покрыто тестовой матрицей «ресурс × уровень × ожидаемый код».
- [ ] Списочные эндпоинты задач и досок выполняют **ноль** построчных резолвов ACL: тест считает
      число вызовов policy на запрос списка из 200 задач (ожидается O(1)).
- [ ] Интеграционный тест «список == построчный `can()`» проходит на наборе, покрывающем: грант по
      пользователю, по роли, по команде, `NONE` на потомке, просроченный грант, владельца,
      участника проекта, постороннего.
- [ ] Правило «ближайшая явная запись побеждает» и «`NONE` побеждает всё на узле» покрыты табличным
      тестом истинности; просроченные записи (`expiresAt <= now()`) игнорируются.
- [ ] Обрыв цепочки (родитель удалён) даёт 404, а не «разрешить по организации».
- [ ] Изменение ACL инкрементит `permissionsVersion`, инвалидирует кеш эффективных прав и порождает
      outbox-событие; старый access-token перестаёт давать доступ немедленно (тест «отзыв доступа
      действует до истечения токена»).
- [ ] Экран «почему есть доступ» показывает решающий узел цепочки, субъект гранта и уровень;
      объяснение совпадает с фактическим решением policy (тест на согласованность объяснения и решения).
- [ ] Все мутации доступа пишутся в `AuditLog` c `severity` выше обычной; запись невозможно изменить
      из приложения (`REVOKE UPDATE, DELETE`).
- [ ] `permission-matrix` snapshot-тест включает вторичные пути (список, автодополнение, лента,
      счётчики) и падает при появлении нового маршрута без объявленной permission.

## Модель данных

- Затрагиваемые сущности: `ResourceAcl` **[T]** (`resourceType` ∈ `PROJECT | BOARD | DOC_PAGE |
  KB_SPACE | VAULT | FILE_FOLDER` — здесь используются `PROJECT` и `BOARD`), `ProjectMember` **[T]**,
  `UserRole` **[T]**, `UserPermissionOverride` **[T]**, `Permission` **[G]**, `Task` **[T]**,
  `Board` **[T]**, `User.permissionsVersion` **[T]**, `AuditLog` **[T]**, `OutboxEvent` **[T]**.
- Индексы: `uq_resource_acl (resource_type, resource_id, subject_type, subject_id)` — один субъект
  не может иметь два уровня на один объект; `idx_resource_acl_subject (organization_id,
  subject_type, subject_id, resource_type)` — обратный запрос «какие проекты видит пользователь»;
  `idx_resource_acl_resource (organization_id, resource_type, resource_id)` — покрывает join
  резолвера.
- Новых таблиц эпик не вводит.
- **Закрыто (2026-07-26):** `ResourceAcl.resourceType` содержит все 12 значений, включая `TASK`, —
  приватная задача выразима. Перечень синхронизирован между группой 2 и разделом «Полиморфные
  связи» в data-model.
- **Закрыто (2026-07-26):** `Task.boardId` денормализован (при сохранении `boardColumnId`), поэтому
  цепочка `Task → Board → Project → Organization` больше не требует двух лишних join на каждое
  чтение. Инвариант держит составной FK
  `(organization_id, board_id, board_column_id) → board_columns (organization_id, board_id, id)`:
  колонка чужой доски физически не вставится.
- **Закрыто (2026-07-26):** `idx_resource_acl_resource (organization_id, resource_type,
  resource_id)` добавлен в список индексов data-model. Уникальный индекс по четвёрке его не
  заменяет — он начинается с `resource_type` без `organization_id` и не годится для tenant-scoped
  выборки всех грантов объекта, а именно её `resolveAcl` выполняет на каждом узле цепочки.
- **Внимание при реализации:** с появлением свободных досок (`Board.projectId` нуллабелен,
  [EPIC-018](../epic-018-boards-and-columns/epic.md)) цепочка раздваивается —
  `Task → Board → Project → Organization` у проектной доски и `Task → Board → Organization` у
  свободной. Ветка выбирается по `projectId IS NULL`.

## Права

- Ключи из каталога §3.3: `acl:read` (`VIEWER`), `acl:grant` (`MANAGER`, **dangerous**),
  `acl:revoke` (`MANAGER`, **dangerous**), `permission:explain`, `permission:read`,
  `permission:override_read`, `permission:override` (**dangerous**).
- Ключи §3.5 и §3.4, к которым применяется модель: `board:read`, `task:read`, `task:update`,
  `task:move`, `comment:read`, `project:read`, `project:manage_visibility` (**dangerous**).
- ACL-уровни и наследование: шкала `NONE < VIEWER < COMMENTER < EDITOR < MANAGER`; итог —
  `DENY(override) > NONE(acl) > max(acl) ∩ permissions(roles ∪ ALLOW-overrides)`.
  Цепочки: `Task → Board → Project → Organization`; `Comment`/`Attachment`/`ActivityEvent` —
  цепочка родительской сущности; владелец получает `MANAGER` без обхода.
  `implicitLevel` (когда ни одной записи ACL нет) определяется `Project.visibility`:
  `PUBLIC_ORG` → `VIEWER` для сотрудника организации, `PRIVATE` → доступ только через
  `ProjectMember`/`ResourceAcl`.
- Отсутствующих ключей нет.

## Зависимости / риски

- Зависит от: EPIC-011 (модель прав, `can()`, `EffectivePermissionsService`),
  EPIC-018 (доски как узел цепочки), EPIC-019 (задачи), EPIC-020 (комментарии и вложения как
  наследники), EPIC-005 (RLS — независимый второй барьер), EPIC-016 (audit log).
- Блокирует: EPIC-024 (permission-aware поиск потребляет события переиндексации и функцию «видимые
  ресурсы»), EPIC-025 (авторизация подписки на комнату использует тот же policy-путь),
  EPIC-031 (дашборды агрегируют только видимое, M6).
- Риски:
  - `R-15` (модель прав ломается под кастомными override): единый детерминированный алгоритм,
    таблица истинности в тестах, UI-объяснение доступа, запрет второго места вычисления прав.
  - `T-TASK-01` (IDOR), `T-TASK-06` (доступ к вложению мимо родителя), `T-PROJ-01` (приватный проект
    утекает вторичными путями) — закрываются единой функцией видимости и матричными тестами.
  - `T-PLAT-04` (поиск отдаёт закрытое): изменение ACL обязано порождать событие переиндексации уже
    здесь, иначе в M4 индекс будет отставать от прав.
  - **Риск производительности:** «фильтрация одним SQL» — единственное место, где решение о доступе
    просачивается в SQL. Расхождение с policy закрывается интеграционным тестом «список ==
    построчный can()», иначе логика разъедется молча.
  - `R-01` (кросс-тенантная утечка): ACL — доменное правило, RLS — изоляция арендаторов; смешивать
    их запрещено, негативные тесты кросс-тенантного доступа обязательны на каждую новую сущность.
