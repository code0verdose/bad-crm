# EPIC-024 — Глобальный поиск на Meilisearch

## Зачем (ценность)

Связность — главное обещание продукта, а поиск — единственный интерфейс, где она становится
ощутимой: одна строка находит задачу, документ, заметку, файл и сообщение. Технически это самая
опасная подсистема: поисковый индекс — **вторая копия всего содержимого** с собственной моделью
доступа, поэтому эпик равной мерой про удобство и про то, чтобы индекс никогда не отдал чужое.
Два архитектурных инварианта задаются здесь и не пересматриваются: синхронизация только через
**transactional outbox** (никакого dual-write) и **права внутри самого документа** с фильтрацией на
стороне движка.

## Scope

### В скоупе

- Индексация задач, документов, заметок KB, файлов, каналов и сообщений чата (последнее
  подключается в M5 вместе с EPIC-026) **исключительно через `OutboxEvent`**: событие пишется в той
  же транзакции, что доменное изменение; воркер разбирает очередь
  `FOR UPDATE SKIP LOCKED` с ретраями и экспоненциальным backoff, доставка at-least-once,
  потребитель идемпотентен. Прямая запись в индекс из use-case запрещена архитектурно.
- **Permission-aware документ:** в индексируемый документ кладутся `organizationId`, `visibleTo`
  (список принципалов вида `user:<id>`, `role:<id>`, `team:<id>`, `project:<id>`), `projectId`,
  `entityType`. Фильтр по принципалам применяет **движок при выполнении запроса**;
  постфактум-фильтрация результатов в API запрещена (утечка через `estimatedTotalHits`, facets,
  порядок и тайминг).
- **Tenant token Meilisearch** с зашитым фильтром `organizationId` как второй независимый барьер;
  мастер-ключ существует только на сервере и не попадает в клиентский бандл (grep-тест по сборке);
  клиент никогда не ходит в Meilisearch напрямую.
- Переиндексация при изменении прав: любое изменение `ResourceAcl`, `ProjectMember`, `ChannelMember`,
  `Project.visibility`, `UserRole` порождает outbox-событие переиндексации затронутых документов;
  SLA отставания — 5 минут, превышение алертит.
- **Vault и секретные ссылки в индекс не попадают никогда** — ни `dataEnc`, ни `nameEnc`, ни
  расшифрованные значения; структурный тест на состав индексируемых полей.
- Деградация: профиль self-host `minimal` без Meilisearch → адаптер `postgres-fts` за тем же портом
  `SearchPort`, **с той же фильтрацией по принципалам** (права — часть сигнатуры порта, не опция).
- UI: `Cmd/Ctrl+K` Spotlight с мгновенными результатами и группировкой по типам, страница
  `/search?q=…&type=…` с фильтрами в URL, debounce 300 мс, отмена запроса по `signal`,
  подсветка совпадений, пустое состояние с подсказкой.
- Наблюдаемость и восстановление: метрики глубины очереди и возраста старейшего `PENDING`,
  индикатор «поиск догоняет» в UI, полная переиндексация по команде (`search:reindex`),
  **reconciliation-джоб «БД ↔ индекс»** (расхождения, сироты в индексе, зависшие `PROCESSING`).
- Настройки Meilisearch: индексы по типам сущностей, `filterableAttributes` (`organizationId`,
  `visibleTo`, `projectId`, `entityType`), `sortableAttributes`, typo-tolerance, синонимы,
  корректная работа с кириллицей и латиницей.

### Вне скоупа

- Семантический поиск и эмбеддинги (`Embedding`, pgvector) — [EPIC-039](../epic-039-ai-assistant/epic.md) (M8).
- Индексация сущностей доменов, которых ещё нет: время, инвойсы, созвоны — добавляются своими
  эпиками в M6/M9 по тому же контракту.
- Поиск по vault — только клиентский через `blindIndex*`, [EPIC-034](../epic-034-vault-items/epic.md) (M7).
- Конструктор отчётов и аналитика по индексу — вне продукта (PRD Won't).
- Публикация Meilisearch наружу и прямой клиентский доступ — запрещены архитектурно, не «вне скоупа».

## Acceptance (эпик выполнен, когда)

- [ ] Ни один путь записи в индекс не обходит outbox: архитектурный тест не находит вызовов клиента
      Meilisearch вне воркера-потребителя (`R-05`).
- [ ] Падение Meilisearch не ломает запись домена: задача создаётся, событие остаётся `PENDING`,
      после подъёма движка индекс догоняет; тест `search-outage-degrades-gracefully` зелёный.
- [ ] `search-acl-isolation`: пользователь не находит ни одного документа, к которому у него нет
      доступа — по задачам, документам, заметкам, файлам, каналам; проверяются также
      `estimatedTotalHits`, facets и порядок выдачи.
- [ ] Кросс-тенантный тест: запрос с подменённым фильтром и с чужим `organizationId` не возвращает
      ничего; tenant token не позволяет расширить область даже при полностью сломанном
      пользовательском фильтре (`T-PLAT-03`).
- [ ] Отзыв доступа приводит к исчезновению документа из выдачи в пределах SLA очереди (5 минут);
      тест «изменение ACL → переиндексация → документ пропал» (`T-PLAT-04`).
- [ ] Постфактум-фильтрация отсутствует: тест проверяет, что API не выполняет фильтрацию результатов
      после запроса к движку (запрос содержит фильтр по принципалам).
- [ ] `MEILI_MASTER_KEY` не попадает в клиентский бандл (grep по сборке); клиент обращается только к
      API приложения.
- [ ] Структурный тест состава индекса: поля таблиц группы vault и `SecureLink.payloadEnc`
      отсутствуют в любом индексируемом документе; появление нового поля из этих таблиц ломает CI.
- [ ] Профиль `minimal` (без Meilisearch) проходит тот же контрактный набор тестов `SearchPort`,
      включая фильтрацию по принципалам; e2e «поиск работает без Meilisearch» зелёный.
- [ ] Reconciliation-джоб на сид-данных находит ноль расхождений «БД ↔ индекс»; искусственно
      внесённое расхождение (документ удалён в БД, остался в индексе) обнаруживается и чинится.
- [ ] Отставание очереди > 5 минут отражается в UI («поиск догоняет») и поднимает алерт (`T-PLAT-07`).
- [ ] Глобальный поиск открывается по `Cmd/Ctrl+K`, не ломает историю браузера, отдаёт результаты
      p95 < 300 мс на сид-данных (10k задач, 10k сообщений, 1k файлов), группирует по типам.
- [ ] Поиск корректно работает с кириллицей и латиницей, включая опечатки (NFR-8).

## Модель данных

- Затрагиваемые сущности: `OutboxEvent` **[T]** (единственный канал доставки), `Task` **[T]**,
  `DocPage` **[T]**, `KbNote` **[T]**, `File` **[T]**, `Comment` **[T]**, `Channel`/`Message` **[T]**
  (в M5), `ResourceAcl` **[T]**, `ProjectMember` **[T]**, `Project` **[T]**, `AuditLog` **[T]**.
- Индексы: `idx_outbox_pending (status, available_at) WHERE status IN ('PENDING','FAILED')` —
  узкий частичный индекс, опрос очереди дешёвый независимо от истории;
  `idx_outbox_aggregate`, `idx_outbox_stuck (locked_at) WHERE status = 'PROCESSING'`.
  Для профиля `minimal` — существующие GIN-индексы: `idx_tasks_search`, `idx_doc_pages_search`,
  `idx_kb_notes_search`, `idx_messages_search`.
- Новых доменных таблиц эпик не требует; состояние индекса живёт в Meilisearch, а не в БД.
- **Закрыто (2026-07-26):** `SearchIndexState` **[T]** добавлена в data-model, группа 14
  (`entityType`, `lastIndexedAt?`, `lastIndexedEventId?`, `lagSeconds`, `docCount`, `pendingCount`,
  `lastFullReindexAt?`, `status HEALTHY|CATCHING_UP|DEGRADED|REBUILDING`, `lastError?`). Именно она
  питает индикатор «поиск догоняет, результаты могут быть неполными» — показывать его обязательно,
  иначе пользователь принимает неполную выдачу за правду (`T-PLAT-04`). Состояние в PostgreSQL, а не
  в Redis: оно переживает перезапуск по определению своей задачи и является tenant-scoped.
  Обновляется **одним `UPDATE` на пачку**, не на документ.
- **Закрыто (2026-07-26):** имя поля прав в поисковом документе — **`visibleTo`**
  (`["user:u1","team:t3","project:p7"]`), одно `filterable`-поле вместо трёх; `aclUserIds` /
  `aclRoleIds` из ранней постановки эпика не используются. `projectId` и `organizationId` остаются
  отдельными полями. Канон зафиксирован в
  [ADR-0011](../../docs/architecture/adr/0011-meilisearch-permission-aware-search.md) и в
  [`data-model.md`](../../docs/architecture/data-model.md) («Сведённые расхождения»).
- Воркер outbox обязан выставлять tenant-контекст **на каждое событие отдельно** — смешанная пачка
  событий разных арендаторов не должна обрабатываться под одним контекстом (особый путь RLS №3).

## Права

- Ключи из каталога: `search:reindex` (§3.18, **dangerous**) — полная переиндексация;
  `job:read`, `job:retry` (§3.18) — наблюдение за очередью и повтор зависших событий.
- Права на результаты — это права на сами сущности, отдельного «права на поиск» нет сознательно
  (правило каталога: «действие `list` не существует; список — это `read` с фильтрацией по ACL»):
  `task:read`, `doc:read`, `kb_note:read`, `file:read`, `channel:read`, `message:search` (§3.12),
  `project:read`.
- ACL-уровни и наследование: минимальный уровень для попадания в выдачу — `VIEWER` на самой
  сущности или на любом узле её цепочки; `NONE` на потомке исключает документ из `visibleTo`.
  Цепочки те же, что в EPIC-021/022/023 — поиск обязан использовать **ту же** функцию видимости,
  а не собственную копию правил.
- Отсутствующих ключей нет.

## Зависимости / риски

- Зависит от: EPIC-019 (задачи), EPIC-020 (комментарии и вложения), EPIC-021 (единая функция
  видимости и события переиндексации при изменении ACL), EPIC-022 (документы), EPIC-023 (заметки),
  EPIC-015 (файлы), EPIC-003 (outbox и воркеры), EPIC-009 (метрики и алерты),
  EPIC-017 (профиль `minimal` в self-host сборке).
- Блокирует: EPIC-026 (поиск по каналам и сообщениям), EPIC-039 (AI-ассистент опирается на поиск и
  на ту же модель видимости, M8), EPIC-031 (глобальные представления в дашбордах, M6).
- Риски:
  - `R-04` / `T-PLAT-03` — утечка через Meilisearch: изоляция арендатора tenant token'ом, права в
    документе, порт движка не публикуется наружу, preflight проверяет доступность извне.
  - `R-05` / `T-PLAT-07` — рассинхрон с БД и заклинившая очередь: outbox, ретраи, DLQ,
    reconciliation-джоб, метрики отставания, индикатор в UI, полная переиндексация по команде.
  - `T-PLAT-04` — поиск отдаёт закрытое после изменения ACL: переиндексация как обязательное
    следствие любого изменения прав; постфактум-фильтрация запрещена архитектурно.
  - `R-14` — сложность self-host: профиль `minimal` обязан быть полноценным, иначе владелец
    инсталляции получает «поиск, который не ищет».
  - Риск дрейфа правил: поиск и списки должны использовать одну функцию видимости; расхождение
    ловится тестом «выдача поиска ⊆ выдача списка при одинаковом фильтре».
