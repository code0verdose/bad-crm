# EPIC-028 — Уведомления

## Зачем (ценность)

Продукт заменяет шесть инструментов — и вместе с ними шесть источников оповещений. Если уведомления
не собрать в одном месте и не дать ими управлять, консолидация обернётся шумом: человек будет
получать четыре сигнала об одном событии. Эпик даёт центр уведомлений в приложении, настройки по
типам и каналам доставки, email-дайджесты и — главное — правило «одно событие = одно уведомление»,
которое зафиксировано критерием выхода M5.

## Scope

### В скоупе

- Центр уведомлений in-app: `/notifications` (фильтры `all | unread | mentions`, курсорная
  пагинация), значок с непрочитанным в шапке, всплывающая панель последних событий.
- Типы событий: упоминание в комментарии или сообщении, назначение задачи, ответ в треде или на
  комментарий, изменение статуса наблюдаемой задачи, приближение дедлайна (`Task.dueAt`),
  статус пайплайна (готовится к M8, тип заводится сразу), приглашение в проект/канал/организацию,
  выдача доступа к ресурсу, результат длительной операции (импорт KB, экспорт, переиндексация).
- `NotificationPreference` на пользователя и тип: `inApp`, `email`, `push` (задел, в 1.0 не
  активируется), `digestFrequency INSTANT | HOURLY | DAILY | NEVER`, тихие часы
  (`quietHoursStart/End` с таймзоной пользователя).
- Доставка realtime через [EPIC-025](../epic-025-realtime-infrastructure/epic.md): уведомление
  приходит в персональную комнату `org:{id}:user:{id}`, счётчик обновляется без перезагрузки.
- Email-дайджесты через **BullMQ**: отложенные и повторяемые джобы, агрегация событий за период,
  один письменный дайджест вместо потока писем; при отсутствии SMTP канал `email` деградирует молча
  (NFR-9), in-app продолжает работать.
- **Дедупликация и группировка**: одно доменное событие порождает ровно одну запись `Notification`
  независимо от числа каналов доставки; повторные события по одной сущности схлопываются
  («3 новых комментария в BAD-42»); `deliveredChannels` фиксирует, куда фактически доставлено.
- «Прочитать всё» и «прочитать по фильтру», отметка прочитанного при переходе к сущности,
  синхронизация состояния между вкладками и устройствами.
- Источник событий — **только `OutboxEvent`**: уведомление не создаётся из середины use-case;
  потребитель идемпотентен (at-least-once), повторная доставка не плодит записи.
- Уведомления формируются **только для тех, кто имеет доступ** к сущности на момент отправки:
  упоминание в приватном канале не уведомляет постороннего, назначение на приватную задачу не
  раскрывает её заголовок недоступному пользователю.
- Настройки на экране `/settings/notifications` (`NotificationPrefsWidget`).

### Вне скоупа

- Push-уведомления в браузере и мобильные push — задел в модели (`NotificationPreference.push`),
  в 1.0 не активируются (мобильное приложение — backlog).
- Шаблоны уведомлений, редактируемые администратором (`notification:manage_templates` существует в
  каталоге) — управление шаблонами выносится в M8 вместе с онбордингом; здесь шаблоны в коде + i18n.
- Уведомления по доменам, которых ещё нет: время и таймшиты (M6), инвойсы и приёмка майлстоунов (M9),
  AI (M8) — подключаются своими эпиками по этому контракту.
- Транспорт и комнаты — [EPIC-025](../epic-025-realtime-infrastructure/epic.md).
- Настройка SMTP инсталляции — [EPIC-017](../epic-017-self-host-alpha/epic.md) / EPIC-046.

## Acceptance (эпик выполнен, когда)

- [ ] **Одно событие — одно уведомление** независимо от числа каналов доставки: тест на событие,
      подходящее сразу под несколько правил (упоминание + назначение + наблюдение), даёт ровно одну
      запись `Notification` (критерий выхода M5).
- [ ] Повторная доставка события из outbox (at-least-once) не создаёт дубль: потребитель
      идемпотентен по ключу дедупликации; тест с трёхкратной доставкой одного события.
- [ ] Группировка работает: три комментария подряд в одной задаче дают одно сгруппированное
      уведомление, а не три; при открытии оно раскрывается в список.
- [ ] Уведомление не отправляется пользователю без доступа к сущности **на момент отправки**;
      упоминание в приватном канале или на приватной задаче не создаёт запись и не раскрывает
      заголовок (`T-CHAT-02`, `T-PROJ-01`).
- [ ] Настройки по типам работают: отключённый тип не приходит ни одним каналом; `digestFrequency`
      меняет поведение (мгновенно / раз в час / раз в день / никогда); тихие часы откладывают
      доставку до окончания окна в **таймзоне пользователя**, а не сервера.
- [ ] Email-дайджест собирает события за период в одно письмо; при отключённом или недоступном SMTP
      in-app-доставка не деградирует, письма не теряются молча (отчёт о неудачной доставке в логах и
      метриках).
- [ ] «Прочитать всё» обнуляет счётчик за один запрос, состояние синхронизировано между двумя
      вкладками (событие в персональной комнате).
- [ ] Уведомление приходит в реальном времени за p95 < 400 мс при 200 одновременных соединениях
      (совместно с EPIC-025).
- [ ] Лента непрочитанного отдаётся по частичному индексу `idx_notifications_user_unread`;
      p95 < 300 мс при 10 000 уведомлений на пользователя.
- [ ] Ни одно уведомление не создаётся вне потребителя outbox (архитектурный тест).
- [ ] Все тексты уведомлений локализованы EN/RU, хардкод-строк нет (NFR-8, `R-17`).

## Модель данных

- Затрагиваемые сущности: `Notification` **[T]**, `NotificationPreference` **[T]**,
  `OutboxEvent` **[T]**, `Mention` **[T]**, `Watcher` **[T]**, `ChannelMember` **[T]**
  (`notificationLevel`, `mutedUntil`), `User` **[T]** (`locale`, таймзона), `AuditLog` **[T]**.
- Индексы: `idx_notifications_user_unread (organization_id, user_id, created_at DESC) WHERE
  read_at IS NULL` — частичный, прочитанные в него не входят;
  `uq_notification_preferences (user_id, kind)`;
  `idx_outbox_pending (status, available_at) WHERE status IN ('PENDING','FAILED')`.
- `Notification.deliveredChannels String[]` фиксирует фактическую доставку по каналам — это и есть
  механизм «одно уведомление, несколько каналов».
- **Пробел модели:** у `Notification` нет ключа дедупликации и группировки (`dedupeKey` /
  `groupKey` + `count`). Без него «одно событие — одно уведомление» и схлопывание повторов
  реализуемы только эвристикой по (`userId`, `kind`, `entityId`). Требуется добавить `dedupeKey`
  (уникальный частичный индекс) и `groupKey`/`groupCount`.
- **Пробел модели:** `Notification.kind` — свободная строка; при этом `NotificationPreference.kind`
  должен ссылаться на то же множество. Требуется закрытый Prisma enum `NotificationKind`
  (список меняется релизом) либо справочная таблица — иначе настройки и события разъедутся молча.
- **Пробел модели:** нет полей отложенной доставки (`scheduledFor`) и статуса доставки по каналам
  (`emailSentAt`, `failedChannels`). Тихие часы и дайджесты требуют либо этих полей, либо отдельной
  очереди BullMQ как единственного носителя состояния — решение фиксируется ADR в эпике.
- **Пробел модели:** таймзона пользователя для тихих часов берётся из `EmployeeProfile.timezone`,
  но у `User` (не сотрудника — подрядчика, бота) её нет. Требуется `User.timezone` либо fallback на
  таймзону организации, зафиксированный явно.

## Права

- Ключи из каталога §3.18: `notification:manage_templates` — управление шаблонами (используется в
  M8; здесь только резервируется).
- Права на **содержимое** уведомления — это права на сущность-источник: `task:read`, `comment:read`,
  `channel:read`, `doc:read`, `project:read`; проверяются на момент формирования уведомления.
- ACL-уровни и наследование: уведомление наследует видимость сущности-источника
  (`Task → Board → Project → Organization`, `Channel → Project → Organization`, для `DM` — членство).
  Минимальный уровень — `VIEWER` на источнике; при отсутствии — уведомление не создаётся вовсе
  (не создаётся «пустое» уведомление без заголовка).
- **Закрыто (2026-07-26):** `notification:read_own` и `notification:manage_preferences_own`
  **уже в каталоге** ([`permission-model.md`](../../docs/security/permission-model.md) §3: домен
  `platform`, ACL `—`, не опасные, есть у всех ролей), плюс `notification:manage_templates` для
  администрирования шаблонов. Маршрутов без объявленной permission не остаётся, CI-правило
  «нет маршрута без permission» выполняется.

## Зависимости / риски

- Зависит от: EPIC-025 (доставка в реальном времени, персональные комнаты),
  EPIC-026 + EPIC-027 (события чата, упоминания, треды), EPIC-020 (упоминания и watchers задач),
  EPIC-019 (назначения и дедлайны), EPIC-021 (видимость сущности-источника),
  EPIC-003 (outbox, BullMQ), EPIC-008 (локализация текстов), EPIC-009 (метрики доставки).
- Блокирует: EPIC-030 (уведомления о таймшитах, M6), EPIC-037 (статусы пайплайнов, M8),
  EPIC-043/EPIC-044 (приёмка майлстоунов, напоминания о созвонах, M9).
- Риски:
  - **Дублирование уведомлений** (критерий выхода M5): при нескольких правилах и нескольких каналах
    легко получить N сигналов на одно событие. Митигация: `dedupeKey`, одна запись `Notification` на
    событие, `deliveredChannels` вместо отдельных записей на канал, тест на пересекающиеся правила.
  - `T-CHAT-02` / `T-PROJ-01` — уведомление как вторичный путь утечки закрытого: формирование только
    для имеющих доступ, заголовок не раскрывается недоступному пользователю.
  - `T-CHAT-06` — лавина уведомлений при массовом упоминании: агрегация, тихие часы, дайджесты,
    ограничение `@channel` (см. EPIC-027).
  - `T-PLAT-07` — заклинившая очередь: уведомления перестают доставляться молча. Митигация: метрики
    глубины очереди и возраста старейшего `PENDING`, алерт при отставании > 5 минут,
    reconciliation-джоб, DLQ с ручным разбором.
  - `R-17` — двуязычность деградирует: тексты уведомлений — часть DoD истории, отсутствие ключа в
    одном из языков ломает сборку.
  - Риск приватности: уведомления по email выносят содержимое за периметр инсталляции — по умолчанию
    в письме только факт события и ссылка, без тела комментария (настраивается администратором).
