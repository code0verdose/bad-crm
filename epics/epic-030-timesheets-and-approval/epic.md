# EPIC-030 — Таймшиты и подтверждение

## Зачем (ценность)

Записанное время становится управленческим фактом только после того, как его подтвердил руководитель.
До подтверждения это черновик; после — источник для инвойса, маржи и отчёта заказчику. Эпик вводит
недельный цикл «заполнил → отправил → подтвердили» и, главное, делает подтверждённую запись
**неизменяемой**.

Это не бюрократия, а защита от конкретного сценария: кто-то «просто поправил» час прошлого месяца,
и сумма в уже выставленном инвойсе перестала сходиться с суммой строк в базе — спор с заказчиком
становится неразрешимым (риск **R-16**). Решение — immutable ledger: исправление возможно только
**сторно-записью** в той же таблице. И вторая половина той же защиты — **снапшот ставок в момент
подтверждения**: без него повышение ставки сотрудника задним числом молча переписывает историческую
маржинальность и уже выставленные счета.

## Scope

### В скоупе

- **`Timesheet`** — недельный период на пользователя (`uq_timesheets (user_id, period_start)`) со статусами `DRAFT → SUBMITTED → APPROVED | REJECTED`; отклонение возвращает в `DRAFT` с обязательной `rejectionReason`.
- Экран недельного таймшита `/time/timesheets`: строки = задача/проект, колонки = дни, inline-правка ячеек, итоги по дню/строке/неделе, целевая норма с индикатором недобора, «Скопировать прошлую неделю», переключатель недель в URL (`?week=2026-W31`).
- Очередь подтверждения `/time/approvals` для руководителя: фильтры по неделе, сотруднику, статусу; массовое подтверждение с раскрытием состава.
- **`TimePolicy`** (`scope ORG|PROJECT`): `requireApproval`, `roundingMinutes` (округление), `minEntryMinutes` (минимальный интервал), `maxDailyMinutes`, `allowFutureEntries`, `lockAfterDays` — блокировка ввода задним числом.
- **Снапшот ставок при аппруве.** В момент перехода в `APPROVED` каждая запись получает `costRateSnapshotMicros` и `billRateSnapshotMicros`, вычисленные детерминированным резолвом: `project override → user rate → role rate → contract default`. Резолв — одна чистая функция, покрытая табличным тестом на каждую ветку и на «ставки нет ни на одном уровне».
- **`CostRate` и `BillRate` с версионностью по датам** (`effectiveFrom` / `effectiveTo?`): ставка не перезаписывается, а закрывается и заводится новая; перекрытие периодов для одного скоупа запрещено.
- **Сторно-записи** как единственный способ исправить подтверждённое время: новая строка `TimeEntry` с `reversesId` на исходную, отрицательным `durationMinutes`, равным по модулю исходному, обязательным `reversalReason`; наследует `projectId`, `taskId`, `activityId`, `billable`, `currency` и **снапшоты ставок исходной записи**, а не текущие ставки.
- Инвариант «одна сторно-запись на исходную» — частичный уникальный индекс `uq_time_entries_reverses (reverses_id) WHERE reverses_id IS NOT NULL`.
- Уведомления: напоминание о несданном таймшите (конец недели + эскалация), уведомление руководителю о поступившем на подтверждение, уведомление сотруднику об отклонении с причиной.
- Отчёт «кто не сдал» для руководителя и администратора.

### Вне скоупа

- Сам ввод времени, таймер, активности — [EPIC-029](../epic-029-time-tracking-core/epic.md).
- Пересчёт `TimeRollupDaily` при вставке сторно (событие в outbox генерируется здесь, обработчик — там) — [EPIC-031](../epic-031-dashboards/epic.md).
- Ставки по контракту (`ContractRate`) и потолок контракта — [EPIC-041](../epic-041-client-and-contract/epic.md); резолв ставок готов к их подключению как последнему звену цепочки.
- Инвойсы, `InvoiceLine.sourceTimeEntryIds`, пересчёт строки счёта при сторно — [EPIC-042](../epic-042-billing-and-budget/epic.md).
- Утверждение по произвольным периодам (двухнедельным, месячным) — только недельный период в 1.0.

## Acceptance (эпик выполнен, когда)

- [ ] Полный цикл проходит e2e: заполнить неделю → отправить → руководитель подтверждает → таймшит доступен только на чтение с бейджем «Утверждено {дата}, {кем}».
- [ ] `UPDATE` и `DELETE` (включая мягкое) записи с `approvalStatus = APPROVED` **невозможны**: попытка через API даёт 409 с объяснением, попытка прямым SQL — отклоняется триггером/ограничением БД (митигация `R-16`, `T-TIME-01`).
- [ ] Исправление подтверждённого часа выполняется сторно: обе строки — исходная и сторно — видны в журнале и в отчёте, сумма периода уменьшается ровно на модуль исходной, повторное сторнирование той же записи отклоняется уникальным индексом.
- [ ] Сторно без `reversalReason` или с неотрицательной длительностью отклоняется CHECK-ограничением БД.
- [ ] Снапшоты ставок проставлены у всех записей подтверждённого таймшита; изменение `CostRate`/`BillRate` **после** подтверждения не меняет ни одну сумму по этому таймшиту (регрессионный тест «ставка изменена задним числом → отчёт не поехал»).
- [ ] Резолв ставки покрыт таблицей истинности: `project override` побеждает `user rate`, тот — `role rate`, тот — `contract default`; отсутствие ставки на всех уровнях даёт явную ошибку подтверждения, а не молчаливый ноль.
- [ ] `lockAfterDays` работает: ввод и правка записи за период старше порога отклоняются; обход возможен только с `timesheet:unlock_period` и пишется в аудит с повышенной `severity`.
- [ ] Округление (`roundingMinutes`) и минимальный интервал применяются одинаково в UI, API и импорте — одна функция, один тест.
- [ ] Сотрудник не видит и не может подтвердить чужой таймшит: прямая ссылка даёт 404, `?user=` без `timesheet:read_team` игнорируется схемой.
- [ ] `CostRate` не попадает в ответы API сотруднику ни на одном эндпоинте этого эпика (митигация `T-TIME-02`), проверяется контрактным тестом сериализаторов.
- [ ] Напоминание о несданном таймшите приходит один раз на событие независимо от числа каналов доставки.

## Модель данных

- Затрагиваемые сущности: `Timesheet` [T], `TimePolicy` [T], `CostRate` [T], `BillRate` [T], `TimeEntry` [T] (поля `timesheetId`, `approvalStatus`, `costRateSnapshotMicros`, `billRateSnapshotMicros`, `reversesId`, `reversalReason`), `User` [T], `EmployeeProfile` [T] (`managerId` — кто подтверждает).
- Новые поля/таблицы:
  - `TimeEntry.approvalStatus` — enum в `data-model.md` не раскрыт (указано только имя поля). Требуется зафиксировать значения (`PENDING | SUBMITTED | APPROVED | REJECTED`) и их согласование со статусом родительского `Timesheet` — иначе появятся две несогласованные истины о состоянии записи.
  - `Timesheet.lockedAt` — **отсутствует**, требуется для фиксации момента, после которого действует `lockAfterDays` независимо от статуса.
  - `BillRate.roleKey` — в `data-model.md` у `BillRate` есть `scope`, `scopeId`, `userId?`, `activityId?`, но нет уровня «роль», при этом резолв ставок требует ступени `role rate` (она есть только у `ContractRate.roleKey`). Требуется либо добавить `BillRate.roleKey`, либо явно исключить ступень из резолва.
  - Ограничение непересечения периодов версионируемых ставок (`EXCLUDE USING gist` по `(user_id, daterange(effective_from, effective_to))`) — **не объявлено** в `data-model.md`, при этом без него две действующие ставки на одну дату дают недетерминированный резолв.
- Существующие CHECK группы 9 (`ck_time_entries_reversal_negative`, `ck_time_entries_reversal_reason`) обеспечиваются именно здесь.
- Вставка сторно и переход таймшита в `APPROVED` порождают события в **outbox** (`data-model.md` §14) для пересчёта `TimeRollupDaily`; прямая запись в преагрегат запрещена.

## Права

- Новые ключи (из каталога [`permission-model.md` §3.11](../../docs/security/permission-model.md)): `timesheet:read_own`, `timesheet:read_team`, `timesheet:read_all`, `timesheet:submit`, `timesheet:approve`, `timesheet:reject`, `timesheet:reopen`, `timesheet:unlock_period`, `time:manage_policy`, `time:view_cost`, `time:view_bill_rate`, `time:manage_bill_rate`, `time:override`.
- Из §3.2: `employee:view_cost_rate`, `employee:manage_cost_rate` — обе **опасные**, разделяют «видеть себестоимость» и «менять её».
- **Закрыто (2026-07-26):** `time:reverse_entry` **уже в каталоге** ([`permission-model.md`](../../docs/security/permission-model.md) §3, ресурс `time`, действие `reverse_entry`, **опасное**, домен `time`). Альтернатива «сторно под `time:override`» отвергнута: сторно — привилегированная коррекция финансовой истории, а не частный случай правки, и `time:update_any` над `APPROVED`-записью вообще не действует.
- Требуемые ACL-уровни: `timesheet:read_team` — `VIEWER` на проект; `time:reverse_entry` (если вводится) — `EDITOR`. Ключи подтверждения (`timesheet:approve`/`reject`) организационные, но use-case дополнительно требует, чтобы актор был руководителем (`EmployeeProfile.managerId`) либо имел `timesheet:read_all`.
- Опасные: `timesheet:read_all`, `timesheet:reopen`, `timesheet:unlock_period`, `time:manage_policy`, `time:view_cost`, `time:manage_bill_rate`, `time:override`, `employee:view_cost_rate`, `employee:manage_cost_rate`.

## Зависимости / риски

- Зависит от: [EPIC-029](../epic-029-time-tracking-core/epic.md) (факт-таблица и записи), [EPIC-011](../epic-011-rbac-permissions/epic.md), [EPIC-012](../epic-012-employee-management/epic.md) (`managerId` — кто чей руководитель), [EPIC-016](../epic-016-audit-log/epic.md), [EPIC-028](../epic-028-notifications/epic.md) (напоминания).
- Блокирует: [EPIC-031](../epic-031-dashboards/epic.md) (billable-доля и стоимость считаются по подтверждённым записям), [EPIC-032](../epic-032-employee-drilldown/epic.md), [EPIC-042](../epic-042-billing-and-budget/epic.md) (инвойс строится **только** из подтверждённых часов и снапшотов ставок).
- Риски:
  - **R-16** — центральный риск эпика; закрывается неизменяемостью `APPROVED`, сторно-механикой и снапшотами ставок. Триггер эскалации: появление в коде или миграции `UPDATE`/`DELETE` подтверждённой записи.
  - **`T-TIME-01`** (правка подтверждённого времени) — ограничение на уровне БД, а не только use-case.
  - **`T-TIME-02`** (утечка себестоимости) — `CostRate` за отдельным опасным capability и вне сериализаторов, доступных сотруднику.
  - **`T-ANLT-02`** (дифференциальная утечка через агрегаты) — отчёт «кто не сдал» по срезу из одного человека раскрывает его данные; минимальный размер среза фиксируется здесь и переиспользуется в EPIC-031.
  - Организационный риск: жёсткий `lockAfterDays` без внятного пути «запросить переоткрытие» приводит к тому, что люди перестают списывать время вовсе. Путь запроса переоткрытия обязателен в UI.
