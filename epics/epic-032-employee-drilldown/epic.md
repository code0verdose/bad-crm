# EPIC-032 — Drill-down по сотруднику

## Зачем (ценность)

Прямое требование пункта 13 ТЗ: администратор открывает карточку любого сотрудника и получает
максимум сводок, графиков и статистики. Практическая ценность — разговор один-на-один и планирование
недели ведутся по фактам (что человек делал, где залипло, какая реальная загрузка), а не по памяти
руководителя.

Ровно поэтому эпик опасен и требует явно очерченной **приватной границы**. Разрез по человеку — это
единственный экран продукта, где данные собираются вокруг личности, а не вокруг проекта. Без
дисциплины он превращается в слежку: время входа, активность в чате, «онлайн-статус в прошлом» — всё
это технически доступно и не должно быть показано. Эпик фиксирует, что администратор видит, чего он
не видит **никогда**, и что каждый просмотр сам попадает в журнал.

## Scope

### В скоупе

- Экран `/reports/people/$userId`: шапка с профилем, ролью, проектами и текущей загрузкой; период; вкладки `summary | tasks | time | activity` — состояние целиком в URL (`from`, `to`, `project[]`, `tab`, `page`).
- **Сводка загрузки и часов**: факт против `EmployeeProfile.weeklyCapacityHours`, динамика по неделям/месяцам, доля billable.
- **Распределение по проектам и активностям** — из `TimeRollupDaily`, с drill-down в сырые записи.
- **Throughput и цикл задач**: закрыто задач за период, среднее время в работе, распределение по типам и приоритетам, залипшие задачи.
- **Качество**: участие в код-ревью, доля падений CI по авторству (данные приходят из [EPIC-037](../epic-037-github-integration/epic.md); до его закрытия секция показывает пустое состояние «интеграция не подключена»).
- **История изменений прав и ролей** этого сотрудника — выборка из `AuditLog` по объекту, с указанием актора и состояния до/после.
- **Последние действия из `AuditLog`** и агрегированная лента активности (коммиты, комментарии, изменения документов) — тайм-лайн по рабочим артефактам.
- **Сравнение с медианой команды** — только как справочный контекст, без рейтингов и без ранжирования людей.
- **Запись факта просмотра в `AuditLog`** с повышенной `severity` + видимая пользователю строка в интерфейсе: «Просмотр отчёта фиксируется в журнале».
- Экспорт отчёта (пессимистично, тост-`loading` с тем же `id`, ссылка на файл), факт экспорта — в аудит.

### Вне скоупа

- Общие дашборды и реестр карточек — [EPIC-031](../epic-031-dashboards/epic.md).
- Изменение чего-либо: экран **только на чтение**, никакие действия над сотрудником отсюда недоступны (роли меняются в `/admin/members/$userId`).
- Оценка производительности, скоринг, рейтинги сотрудников — сознательно вне продукта (HR-процессы в списке Won't `prd.md`).
- Данные из личного хранилища секретов — недоступны в принципе, см. приватную границу.

## Приватная граница — что администратор видит и чего не видит

Это нормативная часть эпика, а не рекомендация. Нарушение — блокирующий дефект.

| Видит | Не видит **никогда** |
|---|---|
| Списанные часы, их распределение по проектам и активностям | Содержимое **личного хранилища секретов** (`Vault.kind = PERSONAL`) — ни имён, ни метаданных, ни счётчиков элементов; технически невозможно (нет ключей), но и метаданные на этот экран не выносятся |
| Задачи, их статусы, сроки, цикл | Личные заметки KB в приватном пространстве и личные файлы |
| Комментарии и изменения документов как **факты** активности | Тексты личных сообщений и содержимое ЛС |
| Коммиты и статусы CI по авторству | Время входа/выхода, длительность сессий, «онлайн-статус в прошлом» |
| Историю изменений его ролей, прав и ACL | Активность в чате как метрику продуктивности (число сообщений в единицу времени) |
| Себестоимость и ставку — **только** при наличии отдельного опасного права | IP-адреса и user-agent сессий (это домен безопасности, а не отчётности) |
| Прогресс онбординга | Персональные данные из `EmployeeProfile.emergencyContactEnc` |

Правило для новых секций: если метрика отвечает на вопрос «где человек был и когда он работал», а
не «что сделано по работе», — она не добавляется на этот экран.

## Acceptance (эпик выполнен, когда)

- [ ] Все вкладки собираются из фактических данных и преагрегатов, а не из отдельного хранилища, расходящегося с источником; цифра на любой вкладке кликабельна и ведёт в сырые записи.
- [ ] Открытие экрана пишет в `AuditLog` запись с актором, объектом (`userId` сотрудника), периодом и повышенной `severity`; запись невозможно удалить из UI.
- [ ] Пользователь без `report:read_people` получает 403-страницу (не 404 — существование сотрудника внутри организации не секрет), и ни одна вкладка не отдаёт данные предварительно.
- [ ] Себестоимость (`CostRate`) и ставки не появляются в ответе API без `employee:view_cost_rate` — проверяется контрактным тестом сериализаторов, а не только скрытием в UI (митигация `T-TIME-02`).
- [ ] Тест приватной границы: ответ API этого экрана не содержит ни одного поля из таблиц группы 7 (`Vault*`), из личных KB-пространств, из личных сообщений и сессий — проверка по списку колонок, а не по глазам ревьюера.
- [ ] Сотрудник может открыть собственный drill-down (`scope=me`) без `report:read_people`; его собственный просмотр в аудит с повышенной severity не пишется.
- [ ] Экран не показывает метрики «времени присутствия»: автотест на отсутствие полей `lastSeenAt`, `Session.*`, presence в контракте ответа.
- [ ] Сравнение с медианой команды не раскрывает данные конкретного человека при малом размере команды: при выборке меньше порога сравнение скрывается (митигация `T-ANLT-02`).
- [ ] Экспорт отдаёт ровно тот срез, который виден, с теми же правами; факт экспорта в аудите.
- [ ] Кросс-тенантный негативный тест: `userId` чужой организации даёт 404 на всех вкладках.

## Модель данных

- Затрагиваемые сущности: `User` [T], `EmployeeProfile` [T], `TimeRollupDaily` [T], `TimeEntry` [T] (drill-down), `Task` [T], `AuditLog` [T], `UserRole` [T], `UserPermissionOverride` [T], `ResourceAcl` [T], `CommitRef` [T] и `WorkflowRun` [T] (наполняются в [EPIC-037](../epic-037-github-integration/epic.md)).
- Новые поля/таблицы: **новых сущностей эпик не вводит** — это принципиально. Drill-down собирается из существующих проекций и преагрегатов; отдельное «хранилище статистики по сотруднику» отвергнуто, потому что оно неизбежно разъезжается с источником (критерий выхода M6 в [`roadmap.md`](../../docs/product/roadmap.md) требует именно этого).
- Пробел модели: агрегированная лента активности (`activity`-вкладка) читает `ActivityEvent` контекста `task`, `AuditLog` контекста `platform` и `CommitRef` контекста `integration`. Единой проекции для такой ленты в [`data-model.md`](../../docs/architecture/data-model.md) нет — требуется решить, собирается она запросом на лету (проще, дороже) или отдельной проекцией из outbox (быстрее, ещё одна консистентность). Решение — ADR до старта.
- Контекст `analytics` не ходит в чужие таблицы напрямую: чтение `Task`, `AuditLog`, `CommitRef` — через порты владельцев ([`overview.md`](../../docs/architecture/overview.md)).

## Права

- Новые ключи (из каталога [`permission-model.md`](../../docs/security/permission-model.md)): `report:read_people` (§3.13, **опасное**), `employee:view_cost_rate` (§3.2, **опасное**), `employee:read`, `employee:view_capacity`, `employee:view_org_chart`, `audit:read` (§3.17), `time:read_all`, `task:read`, `report:export` (**опасное**).
- **Закрыто (2026-07-26): выбран вариант 2.** `employee:view_drilldown` **уже в каталоге** ([`permission-model.md`](../../docs/security/permission-model.md) §3: ресурс `employee`, действие `view_drilldown`, ACL `—`, **опасное**, домен `iam`). Разграничение с `report:read_people` зафиксировано и обязательно к соблюдению, иначе появится второе место вычисления прав (**R-15**):
  - `employee:view_drilldown` — **персональный** разрез по конкретному человеку (активность, динамика, вклад по периодам). Это профилирование, поэтому ключ опасный и не достаётся вместе с `employee:read`;
  - `report:read_people` — **агрегированные** отчёты по людям без раскрытия персонального разреза.
  Экран drill-down требует `employee:view_drilldown`; собственный разрез не требует ни одного из двух ключей.
- Требуемые ACL-уровни: ключи организационные (ACL `—`); ограничение видимости по проектам выполняется `AccessScope` внутри запроса. Просмотр собственного разреза не требует `report:read_people`.
- Опасные: `report:read_people`, `employee:view_cost_rate`, `report:export`, `audit:read_security` (если открывается вкладка с событиями безопасности — по умолчанию не открывается).

## Зависимости / риски

- Зависит от: [EPIC-031](../epic-031-dashboards/epic.md) (преагрегаты, `AccessScope`, графики), [EPIC-029](../epic-029-time-tracking-core/epic.md), [EPIC-030](../epic-030-timesheets-and-approval/epic.md), [EPIC-016](../epic-016-audit-log/epic.md) (история прав и запись факта просмотра), [EPIC-012](../epic-012-employee-management/epic.md) (профиль, `weeklyCapacityHours`, `managerId`), [EPIC-011](../epic-011-rbac-permissions/epic.md).
- Блокирует: обязательных зависимостей нет — это завершающий эпик M6. Вкладка `activity` **расширяется** данными [EPIC-037](../epic-037-github-integration/epic.md) без изменения контракта экрана.
- Риски:
  - **`T-ANLT-02`** (дифференциальная утечка) — разрез по одному человеку раскрывает его часы и ставку; закрывается разделением прав на чувствительные поля и порогом на сравнение с медианой.
  - **`T-TIME-02`** (утечка себестоимости) — `CostRate` только за отдельным опасным capability.
  - **Репутационно-этический риск, не имеющий ID в модели угроз:** экран может быть воспринят как инструмент слежки, что убивает доверие к продукту у персоны P4 (разработчик). Митигация — приватная граница выше, видимая строка «просмотр фиксируется в журнале», отсутствие метрик присутствия и рейтингов.
  - **N5** (администратор организации как нарушитель) — по [`threat-model.md`](../../docs/security/threat-model.md) модель угроз «злонамеренный админ организации» строится **только** для личного vault; здесь это означает, что drill-down может показывать всё рабочее, но не должен становиться обходным путём к личным данным.
  - **R-15** — риск второго места вычисления прав при попытке «упростить» проверку на этом экране.
