# EPIC-033 — Криптографический фундамент E2EE

> **Эпик заблокирован намеренно.** Он не стартует, пока [`e2ee-design.md`](../../docs/security/e2ee-design.md)
> не принят как **ADR-0009** и не прошёл **внешнее криптографическое ревью** независимым
> специалистом. Это условие зафиксировано в самом документе («реализация до получения заключения не
> начинается — цена ошибки в этом модуле выше стоимости задержки») и является митигацией риска
> **R-03**. Снятие флага `blocked` — отдельное решение с заключением ревьюера в `docs/security/`.

## Зачем (ценность)

Продуктовое обещание Bad CRM состоит из трёх утверждений: сервер не может прочитать секреты;
администратор организации не может прочитать личное хранилище сотрудника; владелец инсталляции с
рутом, дампом PostgreSQL и бэкапами не может прочитать ни одно хранилище. Эти утверждения держатся
не на политике доступа, а на устройстве данных — и вся их несущая конструкция создаётся в этом
эпике.

Здесь нет ни одного пользовательского сценария: эпик закрывает круг «регистрация → разблокировка →
смена пароля → восстановление по Recovery Kit» и отдаёт остальным эпикам M7 крипто-модуль с
доказанным поведением. Делать иначе (писать крипту «по ходу» вместе с фичами хранилища) — гарантия
того, что ошибка в примитивах будет обнаружена после того, как ею зашифрованы реальные данные, то
есть необратимо.

## Scope

### В скоупе

- **Изолированный крипто-модуль `units/vault/lib/crypto`** — единственная зависимость `libsodium-wrappers-sumo` плюс WebCrypto из глобального объекта. Ни HTTP-клиента, ни сетевых вызовов, ни импортов слоёв приложения; проверяется архитектурным тестом. Ленивая загрузка отдельным чанком после аутентификации.
- **Иерархия ключей** ровно по [`e2ee-design.md`](../../docs/security/e2ee-design.md): Argon2id → MUK → `privateKeysBundle` (X25519 sk + Ed25519 seed) → публичные ключи.
- **Два независимых прогона KDF** с независимыми солями: `MUK = Argon2id(pwd, saltA)` и `authVerifier = Argon2id(pwd, saltB)`; на сервер уходит только `authVerifier`, который сервер хранит как `argon2id(authVerifier, serverSalt)` и сравнивает в постоянное время.
- **Параметры примитивов зафиксированы**: Argon2id `m = 64 MiB, t = 3, p = 1`, соли 16 B; XChaCha20-Poly1305-IETF с nonce 24 B из CSPRNG и **обязательным AAD**; `crypto_box_seal` (X25519) для обёртки ключей; Ed25519 для подписей; HKDF-SHA-256 и HMAC-SHA-256 (неэкспортируемый `CryptoKey`).
- **Самодостаточный формат блоба** `algoVersion(1B) || nonce(24B) || ciphertext || tag(16B)` — отдельных колонок под nonce не существует; канонический AAD-энкодер с длиной-префиксами и фиксированным набором меток (`user-keys`, `item-key`, `item-data`, `item-name`, `folder-name`, `tag-name`, `link-payload`).
- **Пороги параметров KDF на клиенте (fail-closed)**: `m < 64 MiB`, `m > 1 GiB`, `t < 3` или `t > 10`, `p ≠ 1`, длина соли ≠ 16, неизвестный `algoVersion` — отказ. Пороги — константы бандла, не настройка; параметры входят в AAD блоба приватных ключей, поэтому тихое понижение невозможно, возможен только явный сбой.
- **Серверная часть**: `UserKeyPair`, хранение `saltB` и хеша `authVerifier`, эндпоинты регистрации ключей, выдачи записи ключей, разблокировки (rate limit + аудит неуспешных попыток), смены пароля, восстановления.
- **Unlock-UX и дисциплина памяти**: MUK только в памяти вкладки в module-private closure, только `Uint8Array`; авто-lock по бездействию (15 мин с предупреждением за 30 с), по фону вкладки > 5 мин, по `beforeunload`, по «прыжку» системного времени > 90 с; `BroadcastChannel('vault-lock')` передаёт только сигнал, никогда ключевой материал; `memzero` в `finally`.
- **Ротация при смене пароля**: перешифровывается **ровно один блоб** `encryptedPrivateKeys`; `VaultKey`, `ItemKey`, элементы, blind-индексы и `recoveryBlobEnc` не трогаются. Все сессии кроме текущей отзываются, событие в `AuditLog`.
- **Recovery Kit при онбординге**: 16 случайных байт → 26 символов Crockford base32 + контрольная сумма, показывается один раз, обязательное подтверждение сохранения; до подтверждения хранилище в режиме «только чтение существующего» с несбрасываемым баннером. Восстановление по киту с обязательным перевыпуском кита.
- **`algoVersion` и план миграции**: клиент читает любую поддерживаемую версию, пишет только текущую; апгрейд верхнего уровня — при следующей успешной разблокировке; downgrade запрещён.
- **Тесты**: KAT-векторы для Argon2id, XChaCha20-Poly1305, HKDF, HMAC из официальных наборов; property-тесты round-trip (`fast-check`, payload 0…1 MiB, изменение любого байта шифротекста/nonce/AAD/ключа → исключение без частичного результата); тест неповторяемости nonce (100 000 шифрований → 100 000 различных nonce) + статическая проверка, что nonce нигде не приходит извне параметром; негативные тесты на подмену AAD, `keyVersion`, `kdfParams` ниже порога, `algoVersion` из будущего.
- **Проектный агент `e2ee-crypto-reviewer`** — создаётся здесь и становится обязательной частью commit-гейта для любого касания `**/crypto/**` и vault-моделей.

### Вне скоупа

- Хранилища, элементы, папки, теги, blind-индексы, история версий — [EPIC-034](../epic-034-vault-items/epic.md).
- Шаринг, `grantSignature`, ротация `VaultKey`, org escrow и Shamir — [EPIC-035](../epic-035-vault-sharing/epic.md).
- Защищённые ссылки — [EPIC-036](../epic-036-secure-links/epic.md).
- WebAuthn PRF, OPAQUE/augmented PAKE, desktop-клиент Tauri, постквантовый гибрид — открытые вопросы `e2ee-design.md`, вне 1.0.
- Собственная реализация Shamir — вводится в [EPIC-035](../epic-035-vault-sharing/epic.md) вместе с escrow.

## Acceptance (эпик выполнен, когда)

- [ ] Получено письменное заключение внешнего крипто-ревью схемы; расхождения между заключением и [`e2ee-design.md`](../../docs/security/e2ee-design.md) закрыты правкой документа **до** написания кода. Флаг `blocked` снят осознанным решением.
- [ ] Круг «регистрация → unlock → смена пароля → восстановление по Recovery Kit» проходит e2e без единого обращения к серверу за ключевым материалом.
- [ ] Покрытие крипто-модуля 100 % строк и ветвей; KAT-векторы проходят; обновление `libsodium` не может молча сломать совместимость (векторы падают).
- [ ] Property-тест: для произвольного payload `decrypt(encrypt(x)) === x`; изменение **любого** байта шифротекста, nonce, AAD или ключа даёт исключение и **не** возвращает частичный результат.
- [ ] Тест неповторяемости nonce на 100 000 итераций даёт множество мощности 100 000; статический тест доказывает отсутствие nonce как входного параметра во всём модуле.
- [ ] Клиент отказывает при `kdfParams` ниже порога и при неизвестном `algoVersion`; подмена любого параметра KDF ломает аутентификацию блоба (AAD), а не приводит к тихому понижению стойкости.
- [ ] Архитектурный тест: чанк `units/vault/lib/crypto` не импортирует ничего, кроме `libsodium-wrappers-sumo`; сетевых вызовов в нём нет; у чанка отдельная строка в `size-limit` со своим порогом (исключение из бюджета ленивого чанка узаконено в [`stack.md`](../../docs/architecture/stack.md)).
- [ ] Тест «ключей нет в persist»: `localStorage`, `sessionStorage`, IndexedDB, cookie, `history.state`, zustand-persist и TanStack Query cache после полного цикла работы не содержат ключевого материала (митигация `T-VAULT-03`).
- [ ] Тест «дамп БД + исходный код не дают открытый текст»: из содержимого `UserKeyPair` без пароля пользователя ничего не восстанавливается.
- [ ] Авто-lock срабатывает по всем трём триггерам; lock распространяется на все вкладки; через `BroadcastChannel` не проходит ни байта ключевого материала.
- [ ] Смена пароля перешифровывает ровно один блоб: тест сверяет, что `VaultKey`, `itemKeyWrapped`, `dataEnc`, `recoveryBlobEnc` побайтно не изменились.
- [ ] Агент `e2ee-crypto-reviewer` существует, включён в commit-гейт и даёт вердикт PASS на весь дифф эпика.
- [ ] Телеметрия отключена целиком на маршрутах `/vault/**` и `/l/**`; ни одно поле формы не уходит в Sentry/RUM/аналитику.

## Модель данных

- Затрагиваемые сущности: `UserKeyPair` [T], `User` [T] (расширение), `Vault` [T] (создаётся личное хранилище при онбординге), `VaultMembership` [T] (единственная запись на владельца), `Session` [T] (отзыв при смене пароля), `AuditLog` [T].
- Новые поля/таблицы и **обязательные правки `data-model.md` до старта** (перечислены в разделе «План реализации» [`e2ee-design.md`](../../docs/security/e2ee-design.md)):
  - `User.authVerifierSalt?` (saltB, 16 B) и `User.authVerifierHash?` — **закрыто (2026-07-26): описаны в `data-model.md`**, группа 1 (`User`, плюс пояснение «поля E2EE-подсистемы, а не обычной аутентификации»). Правка модели не требуется.
  - **Закрыто (2026-07-26): колонки под депонирование MUK в `UserKeyPair` нет.** Прежний `orgEscrowBlobEnc` удалён из [`data-model.md`](../../docs/architecture/data-model.md) (группа 7). Запрет постоянный, а не «пока не используем»: депонирование работает на уровне ключа хранилища (`Vault`, строка `VaultMembership` с `subjectKind = ESCROW`), **депонирование MUK запрещено** инвариантом «админ не читает личные хранилища». Поле нельзя вернуть ни под каким предлогом — пустой слот в схеме и есть соблазн реализовать escrow личных ключей и разрушить главное обещание продукта.
  - `VaultItem.nonce` и `VaultItemVersion.nonce` — **избыточны и подлежат удалению**: nonce живёт внутри самодостаточного блоба. Оставленные колонки неизбежно рассинхронизируются.
  - `UserKeyPair.recoveryAckAt` — **отсутствует**, требуется для режима «Recovery Kit не подтверждён → только чтение».
- Инвариант, обеспечиваемый здесь и проверяемый CHECK-ограничением: у `Vault.kind = PERSONAL` не может существовать membership с `subjectKind = ESCROW` (поле `subjectKind` вводится в [EPIC-035](../epic-035-vault-sharing/epic.md), ограничение объявляется вместе с ним).
- Главный инвариант группы 7: **ни одного поля с открытым пользовательским значением**. Проверка на plaintext-колонки входит в чек-лист новой таблицы (`T-VAULT-02`).

## Права

- Новые ключи (из каталога [`permission-model.md` §3.9](../../docs/security/permission-model.md)): `vault:create` (создание личного хранилища), `vault:read`.
- **Важно и должно быть записано в каталоге явно:** операции над **собственной** ключевой парой — регистрация ключей, unlock, смена мастер-пароля, восстановление по Recovery Kit — capability **не требуют**: субъект и объект совпадают, авторизация выражается сессией. Отсутствие ключа здесь — не пробел, а решение; но его стоит зафиксировать в §3.9, иначе при ревизии прав M9 кто-нибудь «добавит недостающее право» и сломает онбординг.
- **Закрыто (2026-07-26):** `organization:manage_signing_key` **уже в каталоге** ([`permission-model.md`](../../docs/security/permission-model.md) §3: ресурс `organization`, ACL `MANAGER`, **опасное**, домен `organization`) — генерация и ротация Ed25519-ключа организации, которым подписываются записи публичных ключей участников, находится внутри модели прав.
- Требуемые ACL-уровни: `vault:read` — `VIEWER` (для личного хранилища выполняется автоматически через владение).
- Опасное: `vault_item:decrypt` (§3.9) — вводится в [EPIC-034](../epic-034-vault-items/epic.md), но семантика «capability — необходимое, но не достаточное условие» устанавливается здесь: сервер не имеет ключей и не может выдать доступ «по праву».

## Зависимости / риски

- Зависит от: **внешнего крипто-ревью и ADR-0009** (жёсткий гейт), [EPIC-006](../epic-006-auth-core/epic.md) (сессии, вход, сброс пароля входа), [EPIC-005](../epic-005-multi-tenancy-rls/epic.md), [EPIC-011](../epic-011-rbac-permissions/epic.md), [EPIC-016](../epic-016-audit-log/epic.md), [EPIC-004](../epic-004-client-shell-fsd/epic.md) (маршрут `/vault/unlock` и гарды).
- Блокирует: [EPIC-034](../epic-034-vault-items/epic.md), [EPIC-035](../epic-035-vault-sharing/epic.md), [EPIC-036](../epic-036-secure-links/epic.md). **За пределы M7 не выходит** — ни один эпик других майлстоунов не ждёт крипто-фундамент.
- Риски:
  - **R-03** (ошибка в криптографической реализации) — центральный риск; митигации: внешнее ревью до кода, KAT-векторы, property- и негативные тесты, изоляция модуля, обязательный `e2ee-crypto-reviewer`.
  - **R-02** (потеря данных при забытом мастер-пароле) — обязательный Recovery Kit с подтверждением, явные предупреждения, разделение понятий «пароль входа» и «мастер-пароль хранилища» в интерфейсе.
  - **`T-VAULT-03`** (ключевой материал утекает из памяти вкладки) — только `Uint8Array`, module-private closure, запрет persist, отключение телеметрии на vault-маршрутах, `memzero` в `finally`.
  - **`T-VAULT-04`** (nonce/IV reuse) — только `randombytes_buf(24)`, тест уникальности, статический запрет внешнего nonce.
  - **`T-VAULT-07`** (downgrade параметров KDF) — жёсткие пороги + параметры в AAD (fail-closed).
  - **`T-VAULT-10`** (порча ключевых блобов миграцией) — блобы не трогаются миграциями; любое изменение колонок группы 7 требует `db-reviewer` + `e2ee-crypto-reviewer`.
  - **Остаточный риск, не устраняемый:** злонамеренный сервер отдаёт модифицированный JS. Уменьшается воспроизводимыми сборками, SRI, отсутствием CDN, жёстким CSP и AGPL; полностью закрывается только desktop-клиентом (backlog). Формулировка обязана присутствовать в пользовательской документации — мы не делаем вид, что решили эту проблему.
