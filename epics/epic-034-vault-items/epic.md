# EPIC-034 — Хранилища и элементы

## Зачем (ценность)

Разработчик перестаёт просить пароль от тестового стенда в чате — а вместе с этим перестаёт
навсегда оставлять его в истории переписки. Секреты живут рядом с проектом, а не в отдельном
менеджере паролей с отдельной моделью доступа и отдельной подпиской.

Эпик превращает крипто-фундамент в работающее хранилище: личное и общее, папки, теги, история
версий, поиск. Ключевое ограничение, определяющее каждое решение: **сервер не должен узнать
ничего** — ни имени элемента, ни имени папки, ни имени тега. Поэтому поиск строится на blind-индексе
(точное совпадение вместо подстроки), а не на индексации plaintext «для удобства».

## Scope

### В скоупе

- **Хранилища `Vault`** трёх видов: `PERSONAL` (создаётся при инициализации ключей, единственный участник — владелец), `SHARED` (командное), `PROJECT` (привязано к проекту). Дерево хранилищ, создание, переименование, удаление.
- **Элементы `VaultItem`** типов `PASSWORD`, `NOTE`, `SSH_KEY`, `API_KEY`, `CARD`, `FILE` (канон перечня, см. ниже; `LOGIN` отменён) — с **per-item ключом**, генерируемым заново **на каждую версию** (следствие: участник с отозванным доступом не прочитает версии, созданные после отзыва).
- Шифрование по [`e2ee-design.md`](../../docs/security/e2ee-design.md) §5.3/5.4: `dataEnc` и `nameEnc` под `ItemKey`, `itemKeyWrapped` под `VaultKey`, обязательный AAD с меткой и полным контекстом, padding `sodium.pad` до кратного 256 байт.
- **Папки и теги с шифрованными именами** (`VaultFolder.nameEnc`, `VaultItemTag.tagNameEnc`) — сервер видит форму дерева, но не подписи.
- **История версий** `VaultItemVersion` со своим `itemKeyWrapped` и `dataEnc` на каждую версию; просмотр и восстановление предыдущей версии.
- **Blind index** для точного поиска: `BlindIndexKey = HKDF-SHA256(VaultKey, salt=vaultId, info="badcrm/v1/blind-index/"||keyVersion)` как **неэкспортируемый** `CryptoKey`; `blindIndexName`, `blindIndexUrl`, `blindIndexTag` — HMAC-SHA-256, усечённый до 16 B. Нормализация (`normalizeName`, `normalizeTag`, `normalizeUrl`) — часть спецификации, реализуется буква в букву, включая `toLowerCase()` вместо `toLocaleLowerCase()`.
- **Двухпутевой поиск в UI**: параллельно (а) blind-индексы на сервер — находит элемент в закрытом сейчас хранилище, (б) фильтрация по подстроке в уже расшифрованном списке текущего хранилища. Поисковая строка **не пишется в URL и не уходит на сервер в открытом виде**.
- **Никаких оптимистичных обновлений** во всём разделе `/vault/**`: создание, изменение, удаление, восстановление версии — только пессимистично. Оптимизм здесь означал бы «показали сохранённым то, что не сохранилось», а секрет, которого нет в базе, — это потерянный доступ.
- **Копирование в буфер с авто-очисткой** через 30 с с проверкой, что в буфере всё ещё наше значение (чужое копирование не затираем), стабильный `id` тоста с обратным отсчётом, честная оговорка про закрытие вкладки; показ значения с автоскрытием через 20 с; генератор паролей.
- **`VaultAccessLog`** — append-only журнал обращений (`VIEW`, `DECRYPT`, `COPY`, `EXPORT`) с `ipHash` и `userAgent`; `dataEnc` не приходит в списке, только по открытию карточки.
- Зашифрованные вложения: `File.isEncrypted = true`, `scanStatus = SKIPPED`, ключ файла — внутри `dataEnc` элемента.

### Вне скоупа

- Шаринг, `VaultMembership` с подписью выдачи, ротация ключа хранилища, escrow, офбординг — [EPIC-035](../epic-035-vault-sharing/epic.md).
- Защищённые ссылки — [EPIC-036](../epic-036-secure-links/epic.md).
- Импорт из 1Password / Bitwarden / KeePass — вне 1.0 (обсуждается после релиза; формат экспорта заложен, импорт — нет).
- Автозаполнение форм и браузерное расширение — вне продукта.

## Acceptance (эпик выполнен, когда)

- [ ] Личное хранилище полностью функционально: создание, редактирование, удаление, папки, теги, история версий, генератор паролей, копирование с очисткой буфера.
- [ ] **Автотест на список колонок группы 7**: ни одно поле таблиц vault не содержит открытого пользовательского значения; добавление такой колонки ломает сборку (митигация `T-VAULT-02` — угроза №2 в топ-15 модели угроз).
- [ ] Дамп БД плюс исходный код не позволяют получить ни одного открытого значения — тест выполняется на реальном дампе после наполнения хранилища.
- [ ] `ItemKey` генерируется заново на каждую версию: тест сверяет, что `itemKeyWrapped` версий N и N+1 различны и что старый `ItemKey` не расшифровывает новую версию.
- [ ] Поиск по blind-индексу находит элемент по точному имени, точному домену URL и точному тегу; поисковый запрос **не появляется** ни в URL, ни в теле запроса в открытом виде, ни в серверных логах.
- [ ] Нормализация даёт одинаковый индекс на разных устройствах и в разных локалях (тест с турецкой локалью — `toLowerCase()` против `toLocaleLowerCase()`).
- [ ] Vault **не попадает в Meilisearch**: архитектурный тест доказывает отсутствие обработчика outbox-события индексации в контексте `vault`; глобальный поиск `Cmd+K` не возвращает элементы хранилища.
- [ ] Vault **не попадает в эмбеддинги**: для vault-сущностей не создаются `Embedding`; `VAULT_ITEM` отсутствует в allow-list типов RAG-ретривера (проверяется здесь, доводится в [EPIC-039](../epic-039-ai-assistant/epic.md)).
- [ ] Ни одна мутация раздела `/vault/**` не выполняется оптимистично — проверяется линт-правилом/архитектурным тестом на отсутствие `onMutate` в `units/vault`.
- [ ] Буфер очищается через 30 с; если пользователь скопировал что-то другое, чужое содержимое не затирается.
- [ ] `dataEnc` не приходит в списочном ответе; открытие карточки порождает запись `DECRYPT` в `VaultAccessLog`; в журнале нет ни содержимого, ни имён, ни blind-индексов запроса.
- [ ] Расшифровка не удалась у одного элемента — остальные продолжают работать, показывается inline-диагностика «ключ не подходит», а не пустой экран.
- [ ] Кросс-тенантный негативный тест на все девять таблиц группы 7; RLS `ENABLE` + `FORCE` с `USING` и `WITH CHECK`.

## Модель данных

- Затрагиваемые сущности: `Vault` [T], `VaultFolder` [T], `VaultItem` [T], `VaultItemVersion` [T], `VaultItemTag` [T], `VaultAccessLog` [T], `VaultMembership` [T] (только запись владельца), `File` [T] (зашифрованные вложения), `Project` [T] (для `kind = PROJECT`).
- Новые поля/таблицы и расхождения, требующие правки:
  - **Закрыто (2026-07-26): канон перечня типов элемента — `PASSWORD | NOTE | SSH_KEY | API_KEY | CARD | FILE`.** Прежний набор `LOGIN|NOTE|CARD|SSH_KEY|API_KEY|CERTIFICATE` из `data-model.md` отменён; расхождение сведено **до первой миграции** осознанно, потому что `itemType` — PostgreSQL enum, входящий в **AAD блоба `item-data`**: переименование значения после релиза не «переименование колонки», а невозможность расшифровать все существующие элементы этого типа. Обоснование выбора: `PASSWORD` вместо `LOGIN` — элемент хранит секрет, а не учётную запись; `FILE` вместо `CERTIFICATE` — сертификат это частный случай файла, а файлов в vault хочется больше одного вида. Приведены в соответствие [`data-model.md`](../../docs/architecture/data-model.md), [`e2ee-design.md`](../../docs/security/e2ee-design.md) и [`glossary.md`](../../docs/product/glossary.md).
  - `VaultItem.nonce`, `VaultItemVersion.nonce` — **подлежат удалению** (nonce внутри блоба, требование [`e2ee-design.md`](../../docs/security/e2ee-design.md)).
  - `VaultItem.blindIndexTag` — в `data-model.md` blind-индекс тега объявлен на `VaultItemTag`; согласовано, отдельного поля на `VaultItem` не требуется.
  - `Vault.vaultKeyId` (16 B, `HKDF(VaultKey, info="badcrm/v1/vault-key-id")`) — **отсутствует**, требуется уже здесь: без него невозможно обнаружить «расщепление ключа», а вводить его позже — значит пересчитывать для всех существующих хранилищ.
  - `VaultItemVersion.version` и `VaultItem.version` — в модели `version` есть у версии; поле «текущая версия» на самом элементе в таблице полей не отражено, хотя AAD (`item-data`) его требует. Требуется явно зафиксировать.
- Инвариант: `Vault.kind = PERSONAL` ⇒ ровно одна `VaultMembership` (владелец); `kind = PROJECT` ⇒ `projectId IS NOT NULL`; `kind = PERSONAL` ⇒ `ownerId IS NOT NULL`. CHECK-ограничения объявляются здесь.

## Права

- Новые ключи (из каталога [`permission-model.md` §3.9](../../docs/security/permission-model.md)): `vault:read`, `vault:create`, `vault:update`, `vault:delete`, `vault:view_access_log`, `vault_item:read`, `vault_item:create`, `vault_item:update`, `vault_item:delete`, `vault_item:decrypt`, `vault_item:export`, `vault_item:view_history`.
- **Закрыто (2026-07-26):** канон — каталожное `vault:view_access_log` ([`permission-model.md`](../../docs/security/permission-model.md) §3.9). Прежнее написание `vault.audit.read` в [`e2ee-design.md`](../../docs/security/e2ee-design.md) отменено, документ приведён в соответствие.
- Требуемые ACL-уровни: `vault:read`, `vault:view_members`, `vault_item:read`, `vault_item:decrypt` — `VIEWER`; `vault_item:create/update/delete`, `vault_item:view_history` — `EDITOR`; `vault:update`, `vault:delete`, `vault:view_access_log`, `vault_item:export` — `MANAGER`. Источник ACL — `VaultMembership.accessLevel`.
- Опасные: `vault:delete`, `vault_item:decrypt`, `vault_item:export`.
- Нормативная формулировка, обязательная к пониманию: **ACL управляет тем, кто может получить обёрнутый ключ, а не тем, кто может расшифровать.** Администратор с `vault:manage` вправе удалить хранилище, но не может прочитать его содержимое — `vault:manage` не является и не может являться источником ключевого материала.

## Зависимости / риски

- Зависит от: [EPIC-033](../epic-033-e2ee-crypto-foundation/epic.md) (крипто-модуль, `UserKeyPair`, unlock), [EPIC-015](../epic-015-file-storage/epic.md) (зашифрованные вложения), [EPIC-024](../epic-024-search-meilisearch/epic.md) (доказательство исключения vault из индекса), [EPIC-014](../epic-014-project-core/epic.md) (`kind = PROJECT`), [EPIC-011](../epic-011-rbac-permissions/epic.md), [EPIC-016](../epic-016-audit-log/epic.md).
- Блокирует: [EPIC-035](../epic-035-vault-sharing/epic.md), [EPIC-036](../epic-036-secure-links/epic.md). За пределы M7 не выходит.
- Риски:
  - **`T-VAULT-02`** (plaintext-поле в vault-таблице) — угроза №2 топ-15: одна фича «просто добавим имя для поиска» разрушает главное обещание продукта и необратима для уже сохранённых данных. Митигация — автотест на список колонок, чек-лист новой таблицы, обязательный `e2ee-crypto-reviewer`.
  - **`T-VAULT-06`** (blind index как оракул равенства) — принятый остаточный риск `RR-03`: индексируются только имя, домен URL и теги; пароль, логин, заметка, TOTP-секрет и приватный ключ не индексируются никогда.
  - **`T-VAULT-04`** (nonce reuse при перешифровке версий) — новый `ItemKey` на каждую версию делает повтор пары «ключ+nonce» невозможным.
  - **`T-VAULT-08`** (расшифровка без следа) — честное ограничение: сервер фиксирует выдачу `dataEnc`, но не знает, была ли расшифровка успешной, и не может проверить `COPY`. Аудит — инструмент расследования, а не барьер.
  - **`T-VAULT-11`** (эксфильтрация легитимным участником) — экспорт под отдельным опасным правом с записью в аудит; предотвратить невозможно, можно только зафиксировать.
  - **R-03** — любое касание крипты в этом эпике проходит `e2ee-crypto-reviewer`.
