# EPIC-035 — Шаринг хранилищ и отзыв доступа

## Зачем (ценность)

Общее хранилище проекта — то, ради чего секреты вообще переезжают внутрь CRM: доступ выдаётся и
отзывается **вместе с участием в проекте**, а не в шестом по счёту сервисе, о котором вспоминают
через месяц после увольнения. Это же закрывает боль персоны P5: офбординг должен быть доказуемо
полным.

Эпик решает три неочевидные задачи. Первая: `crypto_box_seal` анонимен — он даёт конфиденциальность,
но не аутентификацию отправителя, поэтому сервер, зная публичный ключ получателя, может подсунуть
**свой** `VaultKey` и читать всё, что получатель зашифрует дальше. Ответ — **Ed25519-подпись
выдачи**. Вторая: отзыв доступа в UI без ротации ключа — ложная гарантия, на которую опирается весь
офбординг (`T-VAULT-05`). Ответ — отзыв **есть** ротация. Третья, самая важная и не техническая:
ротация не делает секрет неизвестным человеку, который его видел. Продукт обязан говорить это прямым
текстом и подталкивать к смене самих секретов, а не создавать иллюзию.

## Scope

### В скоупе

- **Шаринг с пользователем**: получение записи публичных ключей получателя, **проверка подписи org signing key** над этой записью, `wrappedVaultKey = crypto_box_seal(VaultKey, recipient.publicKeyX25519)`.
- **Ed25519-подпись выдачи**: `grantSignature = sign((vaultId, granteeId, keyVersion, sha256(wrapped), organizationId), ownerSeed)` + `grantedByKeyId`. Membership без валидной подписи **отбрасывается клиентом** и не даёт доступ — это защита от подмены ключа сервером.
- **Fingerprint получателя в UI при первом шаринге**: SHA-256 публичного ключа группами по 4, обязательное подтверждение «сверьте отпечаток лично» (защита от MITM, остаточный риск `RR-01` фиксируется в интерфейсе, а не замалчивается).
- **Уведомление всем, кто делился с человеком, при смене его публичного ключа** — делает подмену обнаруживаемой.
- **`vaultKeyId`** (`HKDF(VaultKey, salt=vaultId, info="badcrm/v1/vault-key-id")[0..16]`, хранится открыто на `Vault`) — участник сверяет, что получил тот же ключ, что и остальные; расхождение = немедленная ошибка и инцидент («расщепление ключа»).
- **Шаринг с командой и с проектом**: разворачивается в N персональных membership (у `Team` нет ключевой пары и не будет в 1.0). Следствие, обязательное в UI: **добавление человека в команду не даёт ему доступ автоматически** — сервер ставит `pendingGrants > 0` и показывает баннер владельцам, кто-то с открытым хранилищем выполняет довыдачу.
- **Отзыв = ротация**: удаление membership → `keyVersion++`, новый `VaultKey`, перезаворачивание для всех оставшихся участников, **перешифровка всех `itemKeyWrapped`** и **пересчёт всех blind-индексов** (они выводятся из `VaultKey` — забыть это значит сломать поиск после первой же ротации). Применение — **одной транзакцией с оптимистической проверкой `keyVersion`**; параллельная ротация из другой вкладки получает 409 и перезапускается.
- **Честный диалог отзыва**: `ConfirmDialog` с текстом «Отзыв доступа не делает секреты неизвестными для {имя}. Все элементы этого хранилища следует считать скомпрометированными и заменить», ввод имени пользователя, чекбокс «Понимаю, запланировать ротацию», после отзыва — постоянный баннер «Требуется ротация: N элементов» и **чек-лист элементов** с отметками «сменён».
- **Ротация уровня 2** (полная перешифровка тел элементов) — отдельное тяжёлое действие в `DangerZone`, рекомендуемое при конфликтном увольнении.
- **Org escrow**: `OrgRecoveryKey`, Shamir 2-of-3 над `EscrowUnwrapKey`, `commitment = SHA-256(EscrowUnwrapKey)`, `EscrowRequest` с двумя явными подтверждениями хранителей, уведомления всем хранителям и владельцу, **обязательная ротация `OrgRecoveryKey` после использования**. Escrow — **opt-in и только для `SHARED` и `PROJECT`**.
- **Офбординг сотрудника**: снятие всех его membership одной операцией, пометка каждого затронутого хранилища `rotationRequired`, уведомление владельцам; личное хранилище **не открывается никем** и удерживается `retainedUntil` + 90 дней, затем физическое удаление шифротекста.
- Отчёт «элементы личных хранилищ, помеченные владельцем как рабочие» — сервер видит только счётчик, метка зашифрована.

### Вне скоупа

- Ключевая пара на команду вместо N персональных membership — открытый вопрос `e2ee-design.md`, вне 1.0.
- Верифицируемое разделение секрета (Feldman VSS) для атрибуции плохого шарда — открытый вопрос.
- Подписанный монотонный манифест хранилища против rollback-атаки — открытый вопрос.
- Механизм делегирования массовой ротации при офбординге человека из 40 хранилищ — открытый вопрос (риск превращения в escrow чёрным ходом).

## Acceptance (эпик выполнен, когда)

- [ ] Membership с невалидной или отсутствующей `grantSignature` **не даёт доступ**: клиент отбрасывает её и пишет инцидент; тест подставляет корректно сформированный `wrappedVaultKey` без подписи и получает отказ (митигация `T-VAULT-01`).
- [ ] Запись публичных ключей получателя без валидной подписи org signing key даёт жёсткий отказ шаринга и запись в аудит.
- [ ] При первом шаринге с человеком UI показывает fingerprint и требует подтверждения; повторный шаринг с тем же ключом подтверждения не требует; смена его публичного ключа возвращает требование и рассылает уведомления.
- [ ] **Отзыв доступа приводит к перевыпуску ключа, а не к скрытию элемента в UI** — тест `revoke-rotates-vault-key`: после отзыва `Vault.keyVersion` увеличен, все `itemKeyWrapped` перезавёрнуты, старый `wrappedVaultKey` бесполезен.
- [ ] Отозванный участник **не может прочитать версии, созданные после отзыва**, даже сохранив старые ключи (следствие «новый `ItemKey` на каждую версию»).
- [ ] Ротация применяется атомарно: полу-повёрнутого хранилища не существует; конкурентная ротация даёт 409 и корректный перезапуск.
- [ ] Ротация хранилища с 10 000 элементов проходит за приемлемое время одним запросом; тела элементов по сети не гоняются (проверяется объёмом трафика в тесте).
- [ ] **Blind-индексы пересчитаны после ротации** — отдельный обязательный тест: поиск по имени и по домену URL работает так же, как до ротации.
- [ ] `vaultKeyId` совпадает у всех участников; искусственно «расщеплённый» ключ обнаруживается клиентом и порождает инцидент.
- [ ] Тест `admin-cannot-read-personal-vault`: администратор с любым набором прав и работающий escrow не дают доступа к `Vault.kind = PERSONAL`; escrow-membership для `PERSONAL` невозможно создать ни через use-case, ни прямым SQL (CHECK-ограничение) — митигация `T-VAULT-09`.
- [ ] Escrow-восстановление общего хранилища работает end-to-end: два хранителя подтверждают, `EscrowUnwrapKey` собирается, `commitment` сходится, `OrgRecoveryKey` после процедуры ротируется, всё событие целиком видно в `AuditLog` и `VaultAccessLog`.
- [ ] Офбординг одной операцией снимает все membership, помечает хранилища `rotationRequired`, уведомляет владельцев; ручной прогон офбординга (сессии, WS, secure links, presigned, vault-ключи, экспорт) выполнен по чек-листу [`threat-model.md`](../../docs/security/threat-model.md).
- [ ] Диалог отзыва содержит требуемый текст дословно и не может быть подтверждён без ввода имени; баннер «Требуется ротация: N» держится до закрытия чек-листа.

## Модель данных

- Затрагиваемые сущности: `VaultMembership` [T], `Vault` [T], `VaultItem` [T], `VaultItemVersion` [T], `VaultItemTag` [T], `OrgRecoveryKey` [T], `VaultAccessLog` [T], `UserKeyPair` [T], `Team` [T], `TeamMember` [T], `Project` [T], `User` [T], `EmployeeProfile` [T], `AuditLog` [T].
- Новые поля/таблицы (требуются, **в `data-model.md` отсутствуют**):
  - `VaultMembership.grantSignature Bytes` (Ed25519, 64 B) и `grantedByKeyId` — в таблице полей группы 7 они **уже перечислены**, но отсутствуют в ER-диаграмме того же раздела; расхождение требует правки диаграммы.
  - `VaultMembership.subjectKind USER | ESCROW` — **отсутствует**; без него невозможно выразить CHECK «`PERSONAL` не имеет escrow-membership», то есть техническую реализацию главного обещания продукта.
  - `Vault.vaultKeyId Bytes`, `Vault.rotationRequired Bool`, `Vault.retainedUntil DateTime?` — **закрыто (2026-07-26): уже в `data-model.md`**, группа 7 (`Vault`). Правка модели не требуется.
  - `Vault.pendingGrants Int` — **действительно отсутствует**; нужен для баннера «есть невыданные доступы». Требуется добавить до первой миграции либо явно заменить вычислением `COUNT(*)` по невыданным `VaultMembership` (тогда поле не вводить).
  - `EscrowRequest` [T] (`vaultId`, `requestedById`, `reason`, `status PENDING|APPROVED|REJECTED|EXPIRED`, `threshold`, `approvals Json`, `completedAt?`) — **таблицы нет вовсе**, хотя процедура 5.12 [`e2ee-design.md`](../../docs/security/e2ee-design.md) её требует.
  - `OrgRecoveryKey.commitment Bytes` (SHA-256 `EscrowUnwrapKey`) и `encryptedOrgSk` — в модели есть `encryptedPrivateKeyShares Json` и `threshold`, но `commitment` и отдельный блоб приватного ключа организации не выделены.
  - **Закрыто (2026-07-26): депонирование MUK запрещено.** Колонка `UserKeyPair.orgEscrowBlobEnc` удалена из [`data-model.md`](../../docs/architecture/data-model.md) (группа 7) и **не заводится вновь**: депонируется только `VaultKey` — строкой `VaultMembership` с `subjectKind = ESCROW`, запрещённой для `kind = PERSONAL`. Любое поле в `UserKeyPair`, позволяющее восстановить MUK силами организации, нарушает инвариант «админ не читает личные хранилища» и отклоняется агентом `e2ee-crypto-reviewer` (см. [EPIC-033](../epic-033-e2ee-crypto-foundation/epic.md)).
- **Зарегистрированные открытые вопросы M7** (не пробелы документации, а нерешённые проектные развилки — закрываются на kickoff M7 до первой миграции): `Vault.pendingGrants` (поле-счётчик против вычисления `COUNT(*)`) и таблица `EscrowRequest` (форма хранения подтверждений хранителей). Оба остаются в списке выше намеренно.
- Инварианты, обеспечиваемые здесь: `kind = 'PERSONAL'` ⇒ отсутствие membership с `subjectKind = ESCROW` (CHECK + доменный use-case + тест); `VaultMembership.keyVersion` всегда равен `Vault.keyVersion` после успешной ротации.

## Права

- Новые ключи (из каталога [`permission-model.md` §3.9](../../docs/security/permission-model.md)): `vault:share`, `vault:revoke_access`, `vault:rotate_keys`, `vault:view_members`, `vault:manage_org_escrow`, `vault:use_org_escrow`, `vault:update`, `vault:delete`.
- Из смежных доменов: `user:suspend`, `employee:manage_employment` (офбординг), `team:manage_members` (следствие «добавление в команду не даёт доступ»), `audit:read`.
- **Закрыто (2026-07-26): введён отдельный ключ.** `vault:rotate_payload` **уже в каталоге** ([`permission-model.md`](../../docs/security/permission-model.md) §3: ресурс `vault`, ACL `MANAGER`, **не опасное**, домен `vault`) — «ротация уровня 2», полная перешифровка тел элементов при неизменном составе участников. Отделён от `vault:rotate_keys` по стоимости операции; опасным не помечен, потому что состав доступа не меняет.
- Требуемые ACL-уровни: `vault:view_members` — `VIEWER`; `vault:share`, `vault:revoke_access`, `vault:rotate_keys`, `vault:update`, `vault:delete` — `MANAGER` (источник — `VaultMembership.accessLevel`). `vault:manage_org_escrow` и `vault:use_org_escrow` — организационные (ACL `—`).
- Опасные: `vault:share`, `vault:revoke_access`, `vault:rotate_keys`, `vault:delete`, `vault:manage_org_escrow`, `vault:use_org_escrow`.
- Нормативно: удаление `VaultMembership` — **административный** отзыв. Криптографический отзыв — только ротация. Право `vault:manage` не является источником ключевого материала ни при каких условиях.

## Зависимости / риски

- Зависит от: [EPIC-034](../epic-034-vault-items/epic.md) (элементы, `itemKeyWrapped`, blind-индексы), [EPIC-033](../epic-033-e2ee-crypto-foundation/epic.md) (sealed box, Ed25519, HKDF), [EPIC-014](../epic-014-project-core/epic.md) (проектные хранилища), [EPIC-012](../epic-012-employee-management/epic.md) (офбординг одной операцией), [EPIC-016](../epic-016-audit-log/epic.md), [EPIC-028](../epic-028-notifications/epic.md) (уведомления о выдаче, смене ключа, escrow).
- Блокирует: обязательных зависимостей нет — за пределы M7 эпик не выходит. [EPIC-036](../epic-036-secure-links/epic.md) зависит от [EPIC-033](../epic-033-e2ee-crypto-foundation/epic.md) и [EPIC-034](../epic-034-vault-items/epic.md), но не от шаринга.
- Риски:
  - **`T-VAULT-01`** (подмена публичного ключа, MITM) — пять митигаций: подпись записи ключей org signing key, fingerprint при первом шаринге, уведомление при смене ключа, `grantSignature`, `vaultKeyId`. Остаточный риск `RR-01`: org signing key принимается по TOFU при первом входе — атака остаётся возможной, но становится **обнаруживаемой**.
  - **`T-VAULT-05`** (отзыв без ротации) — угроза №5 топ-15; закрывается тем, что отзыв **есть** ротация, а не сопровождается ею.
  - **`T-VAULT-09`** (тайное использование escrow для чтения личного хранилища) — CHECK-инвариант + тест; escrow принципиально не депонирует MUK.
  - **`RR-04`** (знание секрета после отзыва) — криптография бессильна по определению; митигация организационная: честный текст, чек-лист смены секретов, баннер, ротация уровня 2.
  - **Момент централизации в escrow** — в браузере инициатора `EscrowUnwrapKey` собирается целиком; скомпрометированный браузер в этот момент компрометирует депонирование. Митигации: редкость процедуры, два подтверждения, уведомления, полный аудит, обязательная ротация `OrgRecoveryKey` после.
  - **Злонамеренный хранитель** отдаёт корректно выглядящий, но неверный шард: `commitment` ловит результат, но не атрибутирует виновного (VSS — открытый вопрос).
  - **R-02** — общие хранилища не теряются при потере пароля участником: достаточно, чтобы любой другой участник выдал доступ на новую ключевую пару.
