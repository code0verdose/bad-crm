# EPIC-036 — Защищённые ссылки

## Зачем (ценность)

Секрет, отправленный сообщением в чат, остаётся в истории навсегда — у отправителя, у получателя, в
бэкапе мессенджера и в индексе поиска по переписке. Одноразовая ссылка решает ровно эту задачу:
содержимое живёт один просмотр и исчезает, а сервер, у которого лежит шифротекст, ключа не имеет
вовсе — он находится **во фрагменте URL**, который браузер не отправляет по сети.

Второй режим — адресная ссылка для выбранных пользователей — закрывает внутренний обмен: ссылку
можно спокойно переслать в общий канал, потому что без сессии и без записи в `SecureLinkGrant` она
бесполезна. Пункт 8 ТЗ закрывается целиком, и делается это как надстройка над крипто-фундаментом, а
не как отдельная подсистема.

## Scope

### В скоупе

- **Режим `ONE_TIME` (privnote)**: `linkKey` и `token` генерируются на клиенте, `payloadEnc = AEAD(pad(payload, 256), linkKey, AAD=link-payload)`; ссылка вида `/l/<token>#v1.<base64url(key)>`; в БД — только `SHA-256(token)`, ключа нет нигде.
- **Атомарный burn** единственно допустимой формой: один `UPDATE … SET burned_at = now(), view_count = view_count + 1 WHERE token_hash = $1 AND burned_at IS NULL AND (expires_at IS NULL OR expires_at > now()) RETURNING …`; журнал и обнуление `payload_enc` — вторым оператором **той же транзакции**. Burn-before-deliver: содержимое теряется при обрыве сети, и пользователь предупреждён об этом текстом на странице.
- **Двухшаговое подтверждение «показать содержимое»** — обязательная митигация против превью-ботов: `GET /l/:token` **не сжигает и не отдаёт содержимое**, а возвращает нейтральную страницу с кнопкой; сжигает только `POST /links/:token/burn` с заголовком `X-Requested-With` и одноразовым CSRF-nonce, выданным `GET`-страницей. Заголовки страницы: `X-Robots-Tag: noindex, nofollow`, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`; **никаких OpenGraph/Twitter-card метатегов** — превью пустое намеренно.
- **Режим `RESTRICTED`**: `SecureLinkGrant.sealedKey = crypto_box_seal(linkKey, pk_получателя)` на каждого выбранного пользователя; ключа в URL нет; **обязательная аутентификация** и разблокированное хранилище у получателя (нужен его приватный X25519); получатель не из списка получает **404**, а не 403 — существование ссылки не подтверждается.
- Внешний получатель без аккаунта: единственный допустимый путь — обёртка `linkKey` ключом из парольной фразы (`Argon2id(passphrase, saltC)`), фраза генерируется системой и передаётся **по другому каналу**; интерфейс говорит прямым текстом, что ссылка и фраза в одном мессенджере = отсутствие защиты.
- **Аудит просмотров**: `SecureLinkView` пишет и успешные, и неуспешные попытки с `failureReason`; владелец видит таблицу «кто открыл и когда» на карточке ссылки.
- **Анонимный путь через `SECURITY DEFINER`-функцию** `secure_link_resolve` — единственная точка системы, работающая без tenant-контекста: принимает только `tokenHash`, выставляет контекст по найденной ссылке, имеет зафиксированный `search_path` и не умеет ничего другого.
- **Обрезка токена в логах reverse-proxy**: маскирующий middleware приложения **и поставляемый конфиг прокси** (nginx/Caddy) в составе self-host-поставки, потому что иначе весь смысл теряется на уровне веб-сервера (`T-LINK-02`).
- Rate limit резолвера по IP и по префиксу токена, журналирование неуспешных попыток, одинаковый ответ 404 для «нет такой» и «не ваша».
- Ограничения `expiresAt`, `maxViews`, `allowedIpCidrs`, `requiresAuth` — серверные и **явно не криптографические**; в пользовательской документации это разделено.
- Ужесточённая CSP на маршрутах `/l/**` (как и на `/vault/**`), `Trusted Types`, запрет `innerHTML`.
- Джоб зачистки истёкших ссылок по `idx_secure_links_expiry`.

### Вне скоупа

- Хранилища и элементы — [EPIC-034](../epic-034-vault-items/epic.md); ссылка на элемент vault использует уже готовый крипто-модуль.
- Публичные клиентские порталы и любой другой постоянный внешний доступ — **Won't** 1.0.
- Пересылка ссылки по email из продукта (обязательный SMTP отсутствует по NFR-9): ссылка копируется пользователем.

## Acceptance (эпик выполнен, когда)

- [ ] Тест конкурентности: **50 параллельных `burn` одной ссылки дают ровно один успех**, остальные — 410 Gone; проверка и изменение выполнены одним оператором (митигация `T-LINK-03`).
- [ ] Превью-бот не сжигает записку: последовательность `GET /l/:token` (в том числе `HEAD` и повторные `GET`) не меняет `burned_at`; сжигает только `POST` с валидным CSRF-nonce.
- [ ] Ключ не появляется **ни в одном серверном логе**: тест на маскирование прогоняет полный сценарий и грепает access-логи приложения и поставляемого конфига прокси на паттерн токена и фрагмента (митигация `T-LINK-02`).
- [ ] Сервер не может расшифровать `ONE_TIME`-ссылку: дамп БД + исходный код не дают открытый текст (ключ существует только в строке URL у отправителя и получателя).
- [ ] После успешного показа фрагмент убирается из адресной строки (`history.replaceState`), содержимое в `payload_enc` обнулено в той же транзакции.
- [ ] `RESTRICTED`-ссылка: получатель не из списка получает 404; получатель из списка без разблокированного хранилища ведётся на `/vault/unlock` с `redirect` обратно; после разблокировки `sealedKey` распечатывается его X25519.
- [ ] Перебор токенов ограничен: нагрузочный тест `secure-link-bruteforce` показывает работающий rate limit по IP и по префиксу, неуспешные попытки журналируются (митигация `T-LINK-01`).
- [ ] `SECURITY DEFINER`-функция проходит структурный тест: зафиксированный `search_path`, проверка `expires_at` и `burned_at` внутри функции, возврат строго необходимого набора колонок, невозможность расширить область доступа вложенными запросами (митигации `T-LINK-04`, `T-LINK-06`).
- [ ] Запись `SecureLinkView` и выдача содержимого выполняются в одной транзакции — просмотр без следа невозможен (митигация `T-LINK-08`).
- [ ] `RESTRICTED`-ссылка на ресурс перестаёт работать, когда её создатель теряет доступ к ресурсу или деактивирован (митигация `T-LINK-05`); проверяется в ручном прогоне офбординга.
- [ ] Квота на число активных ссылок на пользователя работает; массовое создание не раздувает БД (митигация `T-LINK-07`).
- [ ] CSP на `/l/**` не содержит `unsafe-inline`; нарушение CSP на этом маршруте порождает алерт как инцидент.
- [ ] Кросс-тенантный негативный тест на `SecureLink`, `SecureLinkGrant`, `SecureLinkView`; RLS-путь №2 (`data-model.md`) реализован ровно как описано.

## Модель данных

- Затрагиваемые сущности: `SecureLink` [T], `SecureLinkGrant` [T], `SecureLinkView` [T], `UserKeyPair` [T] (публичные ключи получателей), `VaultItem` [T] (источник содержимого при отправке секрета из хранилища), `AuditLog` [T].
- Новые поля/таблицы и правки:
  - **Закрыто (2026-07-26): колонки `SecureLink.payloadNonce` нет.** Канон един для всей модели — nonce живёт внутри самодостаточного блоба `algoVersion || nonce || ciphertext || tag`, отдельных колонок `nonce`/`payloadNonce` нет ни у `VaultItem`, ни у `VaultItemVersion`, ни у `SecureLink`. Приведены в соответствие [`data-model.md`](../../docs/architecture/data-model.md) (группа 8), SQL атомарного burn в [`e2ee-design.md`](../../docs/security/e2ee-design.md) и функция `secure_link_resolve` в [`rls-design.md`](../../docs/security/rls-design.md) — все три больше не упоминают `payload_nonce`. Практическое следствие для реализации burn: стирается **одно** поле (`payload_enc = NULL`), поэтому не существует промежуточного состояния «тело стёрли, nonce остался», в котором строка выглядит частично живой.
  - `SecureLink.passphraseSaltC` — **отсутствует**; требуется для сценария «внешний получатель без аккаунта» (`Argon2id(passphrase, saltC)`).
  - `SecureLinkGrant` — уникальный индекс объявлен как `(link_id, grantee_email)`; для выдач по `granteeUserId` уникальности **нет**, то есть одному пользователю можно создать N дублирующих выдач. Требуется частичный уникальный индекс `(link_id, grantee_user_id) WHERE grantee_user_id IS NOT NULL`.
  - `SecureLink.csrfNonceHash` (или эквивалентное хранение одноразового nonce `GET`-страницы) — **отсутствует**; без него двухшаговое подтверждение не проверяемо на сервере.
- **Особый путь RLS №2** (`data-model.md` → Мульти-тенантность и RLS): анонимный резолвер — единственная привилегированная поверхность без аутентификации во всей системе.
- `CHECK (max_views IS NULL OR view_count <= max_views)` — страховка второго уровня поверх атомарного инкремента.

## Права

- Новые ключи (из каталога [`permission-model.md` §3.10](../../docs/security/permission-model.md)): `secure_link:read`, `secure_link:read_any`, `secure_link:create`, `secure_link:attach_resource`, `secure_link:revoke`, `secure_link:view_access_log`, `secure_link:manage_policy`.
- Из смежных доменов: `vault_item:decrypt` (отправка секрета из хранилища ссылкой), `vault_item:export` (по смыслу одноразовая ссылка — форма выноса секрета наружу; связь должна быть зафиксирована при ревизии прав M9).
- **Требуется зафиксировать в каталоге:** анонимный путь `GET /l/:token` и `POST /links/:token/burn` **не проверяет capability вовсе** — это единственный такой случай в продукте. Отсутствие ключа здесь — решение, а не пробел; оно должно быть записано в §3.10 явно, иначе ревизия M9 воспримет анонимный маршрут как дефект или, что хуже, «починит» его.
- Требуемые ACL-уровни: `secure_link:attach_resource` — `VIEWER` на прикрепляемый ресурс (нельзя поделиться тем, что сам не видишь). Остальные ключи организационные (ACL `—`); принадлежность ссылки проверяется по `createdById`.
- Опасные: `secure_link:read_any`, `secure_link:attach_resource`, `secure_link:manage_policy`.

## Зависимости / риски

- Зависит от: [EPIC-033](../epic-033-e2ee-crypto-foundation/epic.md) (AEAD с AAD, sealed box, CSPRNG, формат блоба), [EPIC-034](../epic-034-vault-items/epic.md) (отправка элемента хранилища ссылкой), [EPIC-005](../epic-005-multi-tenancy-rls/epic.md) (особый путь RLS), [EPIC-009](../epic-009-observability/epic.md) (маскирование в логах), [EPIC-017](../epic-017-self-host-alpha/epic.md) (поставляемый конфиг reverse-proxy).
- Блокирует: ничего — завершающий эпик M7, за пределы майлстоуна не выходит.
- Риски:
  - **`T-LINK-04`** (ошибка в `SECURITY DEFINER`-резолвере) — угроза №8 топ-15: единственная анонимная привилегированная поверхность, ошибка = обход RLS без аутентификации. Структурный тест + внешний аудит SQL-поверхностей в [EPIC-045](../epic-045-security-hardening/epic.md).
  - **`T-LINK-03`** (гонка на одноразовой ссылке) — закрывается предикатом на изменяемой колонке в одном операторе; `SELECT` + `UPDATE` запрещены.
  - **`T-LINK-02`** (токен и ключ в логах) — маскирование в приложении **и** в поставляемом конфиге прокси; без второго первое бессмысленно.
  - **`T-LINK-01`** (перебор токенов) — 256 бит энтропии + rate limit; основной остаточный риск — утечка самой ссылки через мессенджер или историю браузера.
  - **`T-LINK-05`** (ссылка переживает отзыв прав) — проверка прав создателя на момент разрешения ссылки, а не на момент создания.
  - **Превью-боты** — бот, эмулирующий клик, теоретически возможен; для него ссылка бесполезна (ключ во фрагменте), но записка сгорит. Пользователь предупреждён — это честная граница, а не решённая проблема.
  - **Физическое стирание** — `UPDATE … SET payload_enc = NULL` создаёт новую версию строки; старая живёт в heap до `VACUUM`, в WAL и в снятых бэкапах. Криптографически неважно (ключа нет нигде), но заявлять «стёрто немедленно и физически» мы не имеем права.
