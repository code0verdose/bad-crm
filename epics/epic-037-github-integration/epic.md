# EPIC-037 — Интеграция с GitHub Actions

## Зачем (ценность)

Тимлид смотрит статусы сборок в GitHub отдельной вкладкой, а связь «эта задача сломала прод» держит
в голове. Эпик закрывает пункт 15 ТЗ: статус пайплайна и деплоя виден в карточке задачи и на
дашборде, коммиты привязаны к задачам, длительность билда и его автор — данные, а не история
переписки.

Это единственная внешняя интеграция кода в продукте, поэтому она проектируется как **строго
опциональная**: отключённая или недоступная GitHub API не должна ломать ни дашборды, ни задачи
(NFR-9). И как всякий приём внешних данных — она проектируется недоверчиво: вебхук доставляется
«как минимум один раз», подпись обязана проверяться, содержимое коммита — это чужой текст, который
попадёт и в UI, и потенциально в контекст AI.

## Scope

### В скоупе

- **Подключение через GitHub App** (предпочтительно — тонкие права, установка на организацию, ротация токена) с возможностью OAuth-режима для инсталляций, которым App недоступен. Решение фиксируется ADR.
- **`RepoLink`** — привязка репозитория к проекту (`uq_repo_links_org_provider_repo`), включение/выключение синхронизации, выбор дефолтной ветки.
- **Приём вебхуков с обязательной проверкой подписи** и идемпотентностью: повторная доставка — норма, а не сбой, поэтому `ON CONFLICT DO UPDATE` по `(repo_link_id, provider_run_id)` вместо второй строки в истории. То же для `WorkflowJob` и `Deployment`.
- **Синхронизация `WorkflowRun` / `WorkflowJob` / `Deployment`**: статус, `conclusion`, автор (`actorLogin`), ветка, `headSha`, длительность (`durationMs`), окружение и состояние выкатки.
- **`CommitRef`** — связь коммитов с задачами по номеру задачи в сообщении, имени ветки или заголовке PR; `linkSource MESSAGE|BRANCH|PR_TITLE|MANUAL` фиксирует происхождение связи, чтобы автоматическую догадку можно было исправить, не потеряв остальное; `authorUserId` нуллабелен — коммиттер может не иметь аккаунта в CRM.
- **Лента пайплайнов** на дашборде (карточка «статус CI-ранов», в том числе срез «красные сборки» через `idx_workflow_runs_failed`) и в карточке проекта и задачи.
- **Шифрование секретов интеграции**: `tokenEnc`, `webhookSecretEnc` — симметричное шифрование ключом приложения из окружения (не E2EE: серверу нужен доступ, чтобы ходить в API), `algoVersion` и перешифровка фоновым джобом при ротации ключа. Открытых токенов в модели нет, в логи они не попадают.
- **Работа с rate limits GitHub API**: учёт остатка, экспоненциальный backoff, очередь запросов, деградация до «данные устарели» вместо каскада ошибок.
- **Backfill истории** при первом подключении репозитория (ограниченная глубина, фоновым джобом, с прогрессом в UI).
- Экран `/admin/integrations/$integrationId` с вкладками `connection | repos | events | logs`, просмотр доставок вебхуков и их повтор.
- TTL на `rawPayload` — иначе эта таблица растёт быстрее всей остальной БД.

### Вне скоупа

- **Двусторонняя синхронизация issue / PR — явный Won't 1.0**: мы не создаём и не обновляем задачи в GitHub и не импортируем issues. Продукт заменяет Jira, а не зеркалит GitHub.
- GitLab, Gitea, Bitbucket — Backlog (открытый вопрос №9 `data-model.md`: обобщение до `VcsProvider` делается только когда появится вторая интеграция, а не «заранее»).
- Запуск и отмена workflow из интерфейса реализуются как тонкая прокси-операция (`ci:rerun`, `ci:cancel`, `deployment:trigger`) без собственной логики оркестрации.
- Анализ кода, метрики покрытия, code review как сущность — вне 1.0.

## Acceptance (эпик выполнен, когда)

- [ ] Вебхук с неверной или отсутствующей подписью отклоняется до любой обработки; факт отклонения журналируется; тест подделывает подпись и получает 401.
- [ ] Повторная доставка одного и того же события не создаёт вторую строку: тест отправляет один payload трижды и получает одну запись с актуальным статусом.
- [ ] Отключение интеграции или недоступность GitHub API **не ломает** дашборды, карточки задач и проектов — соответствующие секции показывают корректное пустое состояние (NFR-9, критерий выхода M8).
- [ ] `tokenEnc` и `webhookSecretEnc` хранятся только зашифрованными; ни один эндпоинт не возвращает их, ни в каком виде; `log-redaction-corpus` не находит токен в логах.
- [ ] Привязка коммита к задаче работает по всем трём источникам (`MESSAGE`, `BRANCH`, `PR_TITLE`); ручная привязка (`MANUAL`) переживает повторную синхронизацию и не перезаписывается автоматической догадкой.
- [ ] Статусы пайплайнов видны в карточке задачи, в карточке проекта и на дашборде; клик ведёт в детали прогона с джобами и длительностями.
- [ ] Исчерпание rate limit GitHub не приводит к каскаду ошибок: запросы уходят в очередь с backoff, интерфейс показывает «данные могут быть неактуальны», фон восстанавливается сам.
- [ ] Backfill не блокирует приложение: выполняется фоновым джобом с видимым прогрессом и корректно возобновляется после рестарта.
- [ ] Имя ветки, сообщение коммита и логин автора рендерятся как текст: `xss-payload-corpus` по этим полям не находит исполнения скрипта (митигация `T-GH-04`).
- [ ] Исходящие запросы к GitHub проходят `ssrf-blocklist` (адрес API не берётся из пользовательского ввода) — митигация `T-GH-05`.
- [ ] Кросс-тенантный негативный тест на все шесть таблиц группы 11; вебхук, пришедший на установку чужой организации, не может записать данные в текущую.
- [ ] `rawPayload` подчиняется TTL; джоб очистки работает и покрыт тестом.

## Модель данных

- Затрагиваемые сущности: `GithubInstallation` [T], `RepoLink` [T], `WorkflowRun` [T], `WorkflowJob` [T], `Deployment` [T], `CommitRef` [T], `Project` [T], `Task` [T], `OutboxEvent` [T], `AuditLog` [T].
- Новые поля/таблицы:
  - `GithubInstallation.tokenTail` — **отсутствует**. По аналогии с `AIProvider.apiKeyTail` (§12 `data-model.md`) нужен способ отличить «тот самый токен» в UI без расшифровки; сейчас модель предполагает шифротекст без опознавательного хвоста.
  - `GithubInstallation.algoVersion` — **отсутствует** в перечне полей, хотя раздел про ротацию ключа приложения явно на него ссылается («перешифровка колонок фоновым джобом с `algoVersion`»).
  - `WebhookDelivery` [T] — **таблицы нет**, при этом каталог прав содержит `webhook:view_deliveries` и `webhook:replay`, а UX-документ — вкладку `events` с журналом доставок. Требуется либо добавить сущность (`installationId`, `deliveryId`, `event`, `signatureValid`, `receivedAt`, `status`, `payload` c TTL), либо убрать оба права и вкладку.
  - `RepoLink.backfillState` / `backfillCursor` — **отсутствуют**; без них возобновляемый backfill не выразим.
- Модель завязана на GitHub App: обобщение до `VcsProvider` **сознательно не делается заранее** (открытый вопрос №9).
- Обновления `WorkflowRun` порождают события в outbox для карточек дашборда; контекст `analytics` не читает таблицы `integration` напрямую.

## Права

- Новые ключи (из каталога [`permission-model.md` §3.14](../../docs/security/permission-model.md)): `integration:read`, `integration:connect`, `integration:disconnect`, `integration:manage_secrets`, `repo_link:read`, `repo_link:create`, `repo_link:delete`, `ci:read`, `ci:rerun`, `ci:cancel`, `deployment:read`, `deployment:trigger`, `webhook:view_deliveries`, `webhook:replay`.
- Требуемые ACL-уровни: `repo_link:read`, `ci:read`, `deployment:read` — `VIEWER` на проект; `repo_link:create`, `repo_link:delete` — `MANAGER`; `ci:rerun`, `ci:cancel`, `deployment:trigger` — `EDITOR`. Ключи `integration:*` и `webhook:*` организационные (ACL `—`).
- Опасные: `integration:connect`, `integration:disconnect`, `integration:manage_secrets`, `ci:rerun`, `deployment:trigger`, `webhook:replay`.
- Отдельно: статус пайплайна виден только тому, кто видит проект. Приватный проект не раскрывает имена веток и логины авторов через ленту CI — проверяется `permission-matrix` snapshot как вторичный путь.

## Зависимости / риски

- Зависит от: [EPIC-014](../epic-014-project-core/epic.md) (проект как точка привязки), [EPIC-019](../epic-019-tasks-core/epic.md) (задача и её номер для `CommitRef`), [EPIC-031](../epic-031-dashboards/epic.md) (дашборд, куда встраивается лента пайплайнов), [EPIC-016](../epic-016-audit-log/epic.md), [EPIC-009](../epic-009-observability/epic.md) (маскирование секретов, метрики очереди).
- Блокирует: [EPIC-043](../epic-043-sprints-and-delivery/epic.md) (сводка поставки использует статусы пайплайнов и деплоев).
- **Расширяет, но не блокирует:** [EPIC-032](../epic-032-employee-drilldown/epic.md) — вкладка `activity` и секция качества наполняются данными `CommitRef` / `WorkflowRun` после закрытия этого эпика; контракт экрана при этом не меняется.
- Риски:
  - **`T-GH-04`** (инъекция через содержимое GitHub) — имя ветки, сообщение коммита и логин автора приходят от внешнего источника и попадают и в UI, и потенциально в контекст ассистента; санитизация на границе + `xss-payload-corpus`.
  - **`T-GH-02`** (компрометация токена установки) — шифрование, отсутствие в ответах API и логах, ротация ключа приложения.
  - **`T-GH-05`** (SSRF через исходящие вызовы) — `ssrf-blocklist`, адрес API не конфигурируется пользовательским вводом.
  - **Зависимость от внешнего API** — отдельный риск устойчивости: недоступность GitHub не должна деградировать основные сценарии; критерий выхода M8 требует это доказать.
  - **R-05** (рассинхрон проекции) — данные CI по своей природе догоняющие; интерфейс обязан показывать время последней синхронизации, а не делать вид, что данные всегда свежие.
  - Организационный: соблазн «раз уж есть интеграция, давайте синхронизировать issues» — прямой путь к нарушению **R-08**; двусторонняя синхронизация зафиксирована как Won't.
