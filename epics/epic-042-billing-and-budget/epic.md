# EPIC-042 — Счета и бюджет

## Зачем (ценность)

Здесь замыкается главная связь продукта: **созвон → решение → задача → часы → инвойс**. Ни в одном
из шести заменяемых инструментов этой связи не существует; в Bad CRM она существует как данные.
Руководитель проекта отвечает заказчику на вопрос «почему бюджет вырос» цифрами, которые
прослеживаются до конкретных подтверждённых записей времени, а не сводит таблицы вручную.

Ключевое требование — **воспроизводимость**: пересчёт инвойса через месяц обязан дать тот же
результат. Это возможно только потому, что [EPIC-030](../epic-030-timesheets-and-approval/epic.md)
сделал подтверждённое время неизменяемым и зафиксировал снапшоты ставок. Счёт строится из
подтверждённых часов и ставок, действовавших на дату работ, — не из текущих.

## Scope

### В скоупе

- **`Invoice` / `InvoiceLine` из подтверждённого времени**: сборка строк по проекту, активности и периоду; `sourceTimeEntryIds Uuid[]` — денормализованный снимок состава строки, `TimeEntry.invoiceLineId` — авторитетная сторона связи (защита от двойного выставления одних и тех же часов).
- **Ставки берутся из снапшотов** (`billRateSnapshotMicros`), а не джойном по дате: изменение ставки задним числом не переписывает выставленный счёт.
- **Нумерация счетов** — уникальный номер в организации (`uq_invoices_org_number`) с настраиваемым шаблоном; выдача номера при выставлении, а не при создании черновика.
- **Статусы** `DRAFT | SENT | PARTIAL | PAID | OVERDUE | VOID`. `OVERDUE` вычисляем, но **материализуется джобом** — чтобы список «просроченные» был индексным запросом и чтобы момент перехода фиксировался в аудите и уведомлениях. `VOID` вместо удаления: выставленный документ не удаляется никогда.
- **`Payment`** — платежи с суммой, валютой, датой, методом `BANK | CARD | CRYPTO | CASH | OTHER`, референсом; частичная оплата переводит счёт в `PARTIAL`, полная — в `PAID`.
- **`Budget`** двух видов — `HOURS` и `MONEY`, на проект и опционально на контракт: `amountMicros` / `hoursLimit`, период, `alertThresholdPct`, `consumedMicros`, `consumedMinutes`.
- **План/факт burn в часах и деньгах**: график сгорания против плана, прогноз даты исчерпания по текущему темпу, остаток по майлстоуну и по контракту (`capAmountMicros`).
- **Маржа**: выручка по `billRateSnapshot` минус себестоимость по `costRateSnapshot`; видна только с отдельным опасным правом.
- **Алерты по порогам** (`alertThresholdPct`, `lastAlertAt`): уведомление при достижении порога бюджета и при приближении к потолку контракта; превышение `capAmountMicros` **блокирует выставление**.
- **Пересчёт строки счёта при сторно**: сторно уже выставленного времени пополняет `sourceTimeEntryIds` id сторно-записи, сумма пересчитывается как сумма со знаком — корректировка **видна в счёте**, а не прячется удалением ссылки.
- **Экспорт инвойса в PDF** (`pdfFileId`), локализованный шаблон EN/RU, реквизиты организации и клиента.
- Карточки дашборда: неоплаченные счета, burn проекта, маржа (по правам) — реестр из [EPIC-031](../epic-031-dashboards/epic.md).

### Вне скоупа

- **Реальный платёжный процессинг** — вне скоупа: продукт **не проводит платежи**, `Payment` — это запись факта, внесённая человеком. Интеграции с платёжными провайдерами не входят в 1.0.
- Биллинг самого продукта как SaaS — **вне продукта** (`prd.md`).
- Бухгалтерский учёт, налоговая отчётность, интеграция с 1С/QuickBooks — вне 1.0.
- Автоматическая отправка счёта заказчику по email (обязательного SMTP нет по NFR-9): счёт выгружается и отправляется человеком; `sentAt` фиксирует факт.
- Рекуррентное выставление по ретейнеру по расписанию — вне 1.0 (прав на рассылку по расписанию в каталоге сознательно нет).

## Acceptance (эпик выполнен, когда)

- [ ] **Инвойс воспроизводимо считается из подтверждённых записей времени и ставок, действовавших на дату работ; повторный пересчёт даёт тот же результат** (критерий выхода M9).
- [ ] Одни и те же часы невозможно выставить дважды: `TimeEntry.invoiceLineId` заполнен, повторная сборка их не берёт; тест на конкурентную сборку двух счетов по одному периоду.
- [ ] Изменение `BillRate` / `CostRate` / `ContractRate` **после** выставления не меняет ни одну сумму существующего счёта.
- [ ] Сторно уже выставленного времени пересчитывает сумму строки со знаком, id сторно попадает в `sourceTimeEntryIds`, связь счёта с полным набором фактов сохраняется; сумма часов по строкам сходится с суммой в счёте (триггер эскалации **R-16** не срабатывает).
- [ ] Номер счёта уникален в организации и не выдаётся черновику; конкурентное выставление двух счетов не порождает дубль номера.
- [ ] `VOID` не удаляет документ и не рвёт ссылки на записи времени; удаление счёта из UI невозможно.
- [ ] `OVERDUE` материализуется джобом, момент перехода виден в аудите, уведомление отправляется один раз.
- [ ] Частичная оплата корректно переводит статус в `PARTIAL`, сумма `paidMicros` сходится с суммой платежей; переплата отклоняется или явно помечается (правило фиксируется).
- [ ] Burn в часах и деньгах строится из подтверждённых записей и совпадает с суммой по факту; расхождение преагрегата с фактом ловится ночной сверкой.
- [ ] Превышение `capAmountMicros` контракта блокирует выставление с внятным сообщением и поднимает алерт.
- [ ] Маржа и себестоимость не появляются в ответах API без `report:view_margin` / `time:view_cost`; проверяется контрактным тестом сериализаторов (митигация `T-TIME-02`).
- [ ] PDF генерируется на сервере, содержит корректные суммы и реквизиты, доступен по presigned-ссылке с TTL ≤ 15 минут и записью в аудит.
- [ ] Кросс-тенантный негативный тест на `Invoice`, `InvoiceLine`, `Payment`, `Budget`.

## Модель данных

- Затрагиваемые сущности: `Invoice` [T], `InvoiceLine` [T], `Payment` [T], `Budget` [T], `Contract` [T], `ContractRate` [T], `Client` [T], `Project` [T], `TimeEntry` [T], `Milestone` [T], `File` [T] (PDF), `AuditLog` [T].
- Новые поля/таблицы и пробелы:
  - **`FxRate` отсутствует** (открытый вопрос №10 `data-model.md`). `Invoice.fxRateMicros` фиксирует курс на счёте, но источника курсов и их истории нет — отчёт «выручка в валюте организации» по счетам в разных валютах не построить. Требуется либо ввести `FxRate` [T], либо явно ограничить 1.0 одной валютой отчётности.
  - **Плана burn по периодам нет.** `Budget` содержит только `consumedMicros` / `consumedMinutes` (факт) и общий лимит; «план» как кривая по времени отсутствует, поэтому график «план против факта» строить не из чего. Требуется `BudgetPlanPoint` [T] (`budgetId`, `periodStart`, `plannedMicros`, `plannedMinutes`) либо явное сведение плана к линейной интерполяции лимита (проще, но это надо зафиксировать, а не подразумевать).
  - **Нумерации счетов негде храниться**: `Invoice.number` уникален, но счётчика или шаблона нумерации на организацию в модели нет. Требуется `Organization.invoiceNumberTemplate` + последовательность, иначе номер генерируется в коде и ломается при конкурентном выставлении.
  - `Payment` — нет CHECK на неотрицательность суммы и на превышение `paidMicros` над `totalMicros`; правило переплаты не зафиксировано.
  - `Budget.consumedMicros` / `consumedMinutes` обновляются **через outbox**, а не прямой записью — как и `TimeRollupDaily`; это должно быть выражено явно.
- `sourceTimeEntryIds Uuid[]` — осознанный компромисс вместо join-таблицы: GIN-индекс закрывает поиск, целостность массива проверяется тем же ночным джобом, что и полиморфные связи. Если состав строк начнёт требовать атрибутов (скидка на конкретную запись) — превращается в полноценную join-таблицу.
- Права на уровне колонок для финансовых полей — открытый вопрос №7, решается в [EPIC-045](../epic-045-security-hardening/epic.md).

## Права

- Новые ключи (из каталога [`permission-model.md` §3.16](../../docs/security/permission-model.md)): `invoice:read`, `invoice:create`, `invoice:update`, `invoice:issue` (**опасное**), `invoice:send` (**опасное**), `invoice:void` (**опасное**), `invoice:export` (**опасное**), `payment:read`, `payment:record`, `payment:delete` (**опасное**).
- Из §3.4 и §3.13: `project:view_budget`, `project:manage_budget`, `project:view_financials` (**опасное**), `report:view_margin` (**опасное**), `report:view_cost` (**опасное**), `report:export` (**опасное**).
- Из §3.11 и §3.16: `time:view_bill_rate`, `time:view_cost` (**опасное**), `contract:view_rates` (**опасное**), `delivery:access` (шлюз в раздел).
- Требуемые ACL-уровни: `project:view_budget` — `VIEWER`, `project:manage_budget` — `MANAGER`, `project:view_financials` — `VIEWER` (но право опасное — виден сам факт финансовых данных проекта). Ключи `invoice:*` и `payment:*` организационные (ACL `—`) под шлюзом `delivery:access`.
- Опасные — все операции, изменяющие финансовый документ или раскрывающие себестоимость и маржу. Каждая требует подтверждения в UI и записи в `AuditLog` с повышенной `severity`.
- Отдельно: `invoice:issue` и `invoice:void` — необратимые по смыслу действия над документом; в интерфейсе оформляются как разрушающие с явным подтверждением.

## Зависимости / риски

- Зависит от: [EPIC-041](../epic-041-client-and-contract/epic.md) (клиент, контракт, ставки контракта, потолок), [EPIC-030](../epic-030-timesheets-and-approval/epic.md) (подтверждённое время и снапшоты ставок — **единственный** допустимый источник), [EPIC-029](../epic-029-time-tracking-core/epic.md), [EPIC-031](../epic-031-dashboards/epic.md) (карточки burn и неоплаченных счетов), [EPIC-015](../epic-015-file-storage/epic.md) (PDF), [EPIC-016](../epic-016-audit-log/epic.md), [EPIC-028](../epic-028-notifications/epic.md) (алерты порогов).
- Блокирует: [EPIC-043](../epic-043-sprints-and-delivery/epic.md) (приёмка майлстоуна fixed-price связывается с инвойсом через `Milestone.invoiceId`).
- Риски:
  - **R-16** (время как источник денег) — эпик является потребителем риска: любая ошибка в M6 проявляется здесь как неверный счёт. Триггеры эскалации: расхождение суммы часов по строкам с суммой в инвойсе; сторно без `reversesId`.
  - **`T-TIME-02`** (утечка себестоимости) — маржа и `CostRate` за отдельными опасными правами; сериализаторы под контрактным тестом.
  - **`T-ANLT-02`** (дифференциальная утечка) — отчёт по марже на проекте из одного человека раскрывает его ставку.
  - **Мультивалютность** — при счетах в разных валютах без `FxRate` отчёт по организации либо неверен, либо невозможен; решить до реализации отчётов.
  - **Юридический риск** — PDF счёта воспринимается как документ; ошибка в реквизитах или суммах имеет последствия за пределами продукта. Отсюда требование воспроизводимости и запрет удаления выставленных документов.
  - **R-08** — соблазн добавить платёжный процессинг «раз уж есть счета»; зафиксировано вне скоупа.
