# EPIC-046 — Self-host релиз 1.0

## Зачем (ценность)

Продукт, который нельзя безопасно обновить, мёртв: владелец инсталляции однажды побоится накатить
новую версию и останется на старой навсегда. Поэтому среди контрметрик PRD стоит доля инсталляций,
обновившихся на текущий minor за 60 дней, — она измеряет не популярность, а доверие к процессу
апгрейда.

Эпик превращает работающий код в **релиз**: версионированные образы, документированный путь
обновления с бэкапом и точкой отката, проверенное восстановление, runbook'и и соблюдение AGPL-3.0.
Отдельно — то, что обычно обнаруживают в момент аварии: **бэкап, снятый под ролью приложения,
неполон**, потому что `FORCE RLS` действует и на дамп. Проверять это надо до релиза, а не после.

## Scope

### В скоупе

- **Версионирование и публикация образов**: семантические версии, теги вида `1.0.0` / `1.0` / `stable` (**без `latest` как рекомендуемого** — self-host-владелец обязан ставить конкретный тег, это требование E2EE-модели), multi-arch, подпись образов, публикация SHA-256 бандла в GitHub Release.
- **Путь обновления между версиями**: миграции только по схеме **expand → migrate → contract**, разрушающие операции никогда в одном релизе с добавлением, **backup-first** — автоматический бэкап перед миграцией на self-host, документированная точка отката на каждый релиз, проверка миграций на снимке реальных объёмов данных.
- **Runbook'и** `docs/runbooks/`: `install.md`, `upgrade.md`, `backup-restore.md`, `incident.md` — с точными командами, ожидаемым выводом и критериями успеха каждого шага.
- **Восстановление из бэкапа со сверкой числа строк** по каждой таблице. Критично: **бэкап снимается под ролью с `BYPASSRLS`** (или под владельцем таблиц) — иначе `FORCE RLS` даёт **частичный дамп**, который выглядит успешным и обнаруживается только при восстановлении. Отдельная проверка «число строк в дампе = число строк в источнике» является обязательным шагом процедуры, а не рекомендацией.
- **Предупреждение о E2EE в бэкапе** — обязательный текст в runbook и в UI админки: бэкап содержит хранилище секретов в зашифрованном виде и **бесполезен без мастер-паролей пользователей**; восстановление из бэкапа не восстанавливает доступ к vault.
- **Smoke-тест чистой установки и апгрейда в CI**: «чистая машина → рабочая система» и «предыдущий минор → текущий» на каждый релиз; замер медианы времени холодного старта.
- **AGPL-compliance**: уведомление об исходниках **в самом интерфейсе** (ссылка на репозиторий и на точную версию/коммит запущенной сборки — требование AGPL-3.0 для сетевого взаимодействия), файл лицензии, список зависимостей с лицензиями, инструкция получения исходников модифицированной версии.
- **`CHANGELOG.md`** по Keep a Changelog + Conventional Commits, страница релиза с известными ограничениями, миграционными заметками и списком закрытых `T-*`/`RR-*`.
- **Экспорт данных организации** в машиночитаемом виде (задачи, документы, заметки, файлы, время) — обязательная функция NFR-12, а не «по запросу в поддержку».
- Проверка **RPO ≤ 24 ч** и **RTO ≤ 2 ч** реальным прогоном восстановления; профиль с WAL-архивированием документируется как рекомендуемый (инструкция и скрипт, не управляемый сервис).
- Preflight-проверка окружения при старте: отказ на дефолтных секретах, под ролью-владельцем БД, при публичном бакете, при `http://` в проде.
- Финальная сверка **таблицы трассируемости ТЗ → эпики**: ни одной непокрытой строки.

### Вне скоупа

- Kubernetes-чарты, Helm, оператор — вне 1.0: целевая конфигурация — один инстанс приложения и `docker compose` (NFR-4).
- Управляемый облачный хостинг продукта — продукт self-hosted по определению.
- Автоматическое обновление инсталляций (auto-update) — владелец решает сам, когда обновляться; принудительное обновление противоречит модели доверия.
- Миграция данных из внешних систем (Jira, Notion) — Backlog; в 1.0 есть импорт `.md` для базы знаний.

## Acceptance (эпик выполнен, когда)

- [ ] **Установка на чистом хосте < 10 минут** по протоколу проверки (медиана); e2e-сценарий «чистая машина → рабочая система» зелёный в CI.
- [ ] **Обновление с предыдущего минора проходит автоматически**, с бэкапом и документированной точкой отката; smoke-тест апгрейда в CI зелёный; успешность миграций без ручного вмешательства ≥ 99 %.
- [ ] **RPO ≤ 24 часа и RTO ≤ 2 часа подтверждены прогоном восстановления** на копии данных; результат зафиксирован.
- [ ] Восстановление из бэкапа выполняется **со сверкой числа строк по каждой таблице**; тест доказывает, что дамп, снятый под ролью приложения, неполон, а под ролью с `BYPASSRLS` — полон (защита от тихого частичного бэкапа под `FORCE RLS`).
- [ ] Runbook'и `install`, `upgrade`, `backup-restore`, `incident` существуют, содержат точные команды и проверены прогоном человеком, не участвовавшим в их написании.
- [ ] Ни одна миграция релиза не содержит разрушающей операции в одном релизе с добавлением; `db-reviewer` подтверждает двухфазный план для каждой (**R-10**).
- [ ] Откат на предыдущую версию выполнен на копии данных и задокументирован — точка отката не теоретическая.
- [ ] Интерфейс содержит уведомление об исходниках с точной версией и ссылкой на репозиторий (AGPL-3.0); `license-check` по всему дереву зависимостей зелёный, лицензий вне allow-list нет (**R-13**).
- [ ] `CHANGELOG.md` и страница релиза опубликованы; миграционные заметки описывают все изменения, требующие внимания владельца инсталляции.
- [ ] **Экспорт данных организации** выгружает задачи, документы, заметки, файлы и время в машиночитаемом виде; выгрузка проверена восстановлением содержимого во внешних инструментах.
- [ ] Preflight отказывает на небезопасной конфигурации с внятной диагностикой конкретной переменной, а не работает «наполовину».
- [ ] Предупреждение о бесполезности бэкапа vault без мастер-паролей присутствует и в runbook, и в UI админки.
- [ ] Таблица трассируемости ТЗ → эпики в [`prd.md`](../../docs/product/prd.md) не содержит непокрытых строк; все 18 доменов закрыты.
- [ ] Профиль `minimal` (без Meilisearch, деградированный поиск по БД) работает и документирован — путь быстрого старта для митигации **R-14**.

## Модель данных

- Затрагиваемые сущности: **новых доменных сущностей эпик не вводит**. Затрагиваются все `[T]`-таблицы — как объект бэкапа, восстановления, сверки и экспорта.
- Новые поля/таблицы:
  - `SchemaMigrationLog` или эквивалент — **не описан** в [`data-model.md`](../../docs/architecture/data-model.md). Prisma ведёт собственную таблицу миграций, но точка отката релиза (какая версия схемы соответствует какому образу и какой бэкап снят перед ней) нигде не фиксируется. Требуется решение: полагаться на историю Prisma + внешний журнал в `~/.claude/devops-history`-стиле или ввести таблицу релизов инсталляции.
  - `Organization.exportRequestedAt` / сущность `DataExport` — **отсутствует**; экспорт организации по NFR-12 — длительная фоновая операция с артефактом в S3, ей нужно состояние и срок жизни ссылки.
- Роли БД (`app_user`, `app_migrator`, роль для бэкапа) — вводятся в [EPIC-005](../epic-005-multi-tenancy-rls/epic.md); здесь фиксируется, что **роль для снятия бэкапа отличается** от роли приложения и обладает `BYPASSRLS`, а роль приложения не обладает ею никогда.
- Каскадное удаление организации (NFR-12) затрагивает объекты в S3 и документы в индексе поиска — процедура и отложенный период проверяются здесь.

## Права

- Новые ключи (из каталога [`permission-model.md` §3.18 и §3.1](../../docs/security/permission-model.md)): `settings:manage_backup` (**опасное**), `settings:run_backup`, `settings:restore_backup` (**опасное**), `settings:view_system_health`, `settings:manage_storage_backend` (**опасное**), `organization:export_data` (**опасное**), `organization:delete` (**опасное**), `job:read`, `job:retry` (**опасное**), `search:reindex` (**опасное**).
- Требуемые ACL-уровни: все ключи организационные (ACL `—`); `organization:export_data`, `organization:delete`, `organization:transfer_ownership` — `MANAGER` по каталогу.
- Опасные: почти весь набор — операции этого эпика необратимы или влияют на всю инсталляцию. Каждая требует подтверждения в UI и записи в `AuditLog` с повышенной `severity`.
- Отдельно фиксируется: **восстановление из бэкапа выполняется вне приложения** (командой на хосте) — право `settings:restore_backup` покрывает инициацию из UI, если она реализована; операции уровня хоста моделью прав не покрываются и описываются в runbook.

## Зависимости / риски

- Зависит от: [EPIC-045](../epic-045-security-hardening/epic.md) (релиз не выпускается без зелёного внешнего аудита), [EPIC-017](../epic-017-self-host-alpha/epic.md) (образы, `.env.example`, preflight — здесь доводятся до релизного качества), [EPIC-002](../epic-002-ci-and-commit-gate/epic.md) (CI, license-check), [EPIC-005](../epic-005-multi-tenancy-rls/epic.md) (роли БД и `FORCE RLS`), [EPIC-031](../epic-031-dashboards/epic.md) и остальные домены — как объект финальной трассируемости.
- Блокирует: ничего — финальный эпик проекта.
- Риски:
  - **R-10** (опасные миграции на self-host-инсталляциях) — центральный риск эпика: пользователь обновляется, миграция блокирует таблицу или теряет данные, откат невозможен. Митигации: expand → migrate → contract, запрет разрушающих операций в одном релизе с добавлением, автоматический бэкап перед миграцией, проверка на реальных объёмах, `CREATE INDEX CONCURRENTLY`, `lock_timeout`.
  - **R-14** (сложность самохостинга) — шесть сервисов в compose; митигации: разумные дефолты, генерация секретов, профиль `minimal`, мастер первичной настройки, preflight с внятной диагностикой, целевая метрика < 10 минут как контрактное требование.
  - **Тихий частичный бэкап под `FORCE RLS`** — риск без ID в модели угроз, обнаруживаемый только при восстановлении. Митигация: сверка числа строк как обязательный шаг и отдельная роль для дампа.
  - **R-13** (AGPL-совместимость) — финальная проверка дерева зависимостей; уведомление об исходниках в UI является требованием лицензии, а не вежливостью.
  - **R-02** — восстановление из бэкапа не восстанавливает доступ к vault; если все пользователи забыли мастер-пароли и не имеют Recovery Kit, данные утрачены навсегда, и никакой бэкап это не исправит. Обязано быть сказано прямым текстом.
  - **Частичное восстановление одного хранилища «на вчера»** ломает `keyVersion`-консистентность, если между этими моментами была ротация; процедура описывается в runbook отдельно и требует ротации после.
  - **R-08** — соблазн «добавить ещё одну фичу в 1.0»; релизный эпик закрывается по критерию выхода, а не по остаточному желанию.
